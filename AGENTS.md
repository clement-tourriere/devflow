# devflow for agents and automation

devflow gives each task its own Git worktree, copy-on-write payloads, a database branch and a generated env file. This guide is the automation contract. Humans start with the [README](README.md).

## Output contract

| Flag | Effect |
| --- | --- |
| `--json` | Print exactly one JSON document on stdout. Progress and hook output go to stderr; warnings are added to the document's `warnings` array. Never prompts. |
| `--non-interactive` (or `DEVFLOW_NON_INTERACTIVE=1`; also `0`, `true`, `false`, `yes`, `no`, `on`, `off`) | Never prompt. Untrusted hooks are skipped instead of asked about. |
| `-C DIR` | Run as if devflow was started in `DIR`. |

Every document has `"version"` (currently `1`) and `"command"`. With `--json` anywhere in the arguments before a `--`, every failure prints `{"version": 1, "command": …, "error": "…"}` and exits 1: a missing argument, a bad `-C` directory, a configuration problem and a refused operation alike. `command` is the subcommand that was asked for (`devflow` when none could be identified). When devflow knows the next step, the document also has `"hint"` (for example `run `devflow init` …` when there is no `devflow.toml`, or `devflow remove NAME --force` when only `--force` can override a protection). `--help` and `--version` still print their text.

### Errors and remedies

When devflow knows how to get past a failure, the error document also has `"remedies"`: an array, most useful first, of things that can be done about it. A remedy is data, not a sentence to parse:

```json
{"version": 1, "command": "list",
 "error": "no devflow.toml in /work/shop",
 "hint": "run `devflow init` in /work/shop (`devflow init --plan` shows the proposed setup first)",
 "remedies": [{"kind": "init", "root": "/work/shop", "label": "Set up devflow…", "command": "devflow init", "destructive": false}]}
```

`kind` is one of `retry`, `forget_project` (`root`), `locate_project` (`id`, `root`), `migrate_config` (`root`), `init` (`root`), `open_file` (`path`), `reveal` (`path`), `open_guide` (`url`), `setup` (`workspace`), `trust` (`workspace`), `start_database` (`root`), `start_service` (`root`, `key`, `branch`, `workspace`), `measure_services` (`root`, `key`), `reconcile_service` (`root`, `key`), `forget_service` (`root`, `key`), `drop_service_branch` (`root`, `key`, `branch`; an orphan no workspace owns), `drop_lost_branch` (`root`, `key`, `branch`; a branch a workspace owns whose volume is gone), `reconcile_databases` (`root`), `drop_orphan_databases` (`root`), `install_git_hook` (`root`), `chain_git_hook` (`root`; `destructive`: it appends a line to a hook somebody else wrote), `install_pitchfork`, `prune_worktrees` (`root`), `remove_workspace` (`root`, `name`), `switch_to` (`root`, `name`) and `add_env_preset` (`root`, `preset`); new kinds appear over time, so ignore the ones you do not know. A remedy always names its target (the workspace's path, the project's root, the service key); it never means "the current directory's" or "the selection". `label` is the button text the desktop app shows. `command` is the equivalent CLI line when there is one (`devflow setup`, `devflow db up`, `devflow service KEY reconcile`, … run in the workspace or project the remedy names; `start_service` has a `command` only when `workspace` (the one checkout whose receipt binds that branch) is known: `devflow -C WORKSPACE service KEY up`; `prune_worktrees` is `devflow prune`, which is `destructive` and asks first).

The remedies of a refused `up` or `down` name the workspace the command resolved (`devflow --json up feature` from the main checkout names `feature`'s directory), never the directory it was started in.

Messages say what is wrong in plain words and never carry a command line: the fix travels as a remedy. This holds for the errors above, for `doctor` checks, for the `reason` of a phase a configuration change reopened, and for `warnings`. A setup outcome (`setup`, `switch`, `create`) has `remedies` too when the workspace is not ready (`trust` first when the hooks or `[env]` wait for approval, then `setup`). An older receipt on disk may still hold a reason written with a command in it.

`devflow --json list --all` gives each registered project a `problem` (`kind`, `message`, `root`, `remedies`) instead of `workspaces` when it cannot be opened: `folder_missing`, `not_git_checkout`, `not_initialized`, `pre_release_config`, `legacy_config`, `invalid_config`, `wrong_project` or `unreadable`.

```sh
devflow --json list --all                                  # which projects have a problem
devflow --json project forget PATH_OR_ID                   # remove an entry; nothing on disk changes
devflow --json project forget --missing                    # every entry whose folder is gone
devflow --json project relocate PATH_OR_ID NEW_PATH        # the folder moved (it must be that project)
devflow --json config migrate --dry-run                    # show how an earlier build's [postgres] becomes [services.db]
devflow --json config migrate                              # write it (never prompts under --json)
```

`config migrate` rewrites only the top-level `[postgres]` table of `devflow.toml` (or `.devflow.toml`) and `devflow.local.toml` into `[services.db]` with `engine = "postgres"`, keeping comments and the table's place. The server, its branches and the workspaces' receipts are identified by the project id, not by the service key, so they keep working. It refuses (nothing is written) when a file has both `[postgres]` and a PostgreSQL service, when `services.db` is something else, and for 0.x configuration, which is never rewritten. The document has `migrated`, `dry_run`, `service_key`, `files` (`file`, `path`, `added`, `removed`, `diff`) and `notes`.

| Exit code | Meaning |
| --- | --- |
| 0 | Done; for `switch` and `setup`, the workspace is `ready` |
| 1 | Error: usage, configuration, an unreachable server, a failed protection check. The message is in `error`. This includes a phase that fails after the worktree was created (for example an unreachable server during `switch -c`): the worktree is kept and named in the message; re-run `switch -c NAME` or `devflow setup` there. `doctor` also exits 1 when a check fails, but prints its normal document with `"ok": false` and no `error`. |
| 2 | The workspace is not ready. The worktree exists, but `status` is `needs_attention` (a required phase was skipped or failed) or `in_progress` (another process holds the receipt lock, or a crash left a phase started). The reason is in the document and in the receipt. When `switch` or `setup` finds the lock held, the document has `"status": "in_progress"` and a `detail` message instead of an `error`; wait and run the command again. |

`switch` and `setup` documents carry `project`, `created`, `skipped`, `status` (`ready`, `needs_attention` or `in_progress`), `path`, `workspace` (`name`, `branch`, `path`, …), the `receipt` (phases `materialize`, `payload`, `services`, `env` and `hooks`, each with its state and detail, and the bindings of the project's services under `receipt.services.<key>`), `payload`, `hooks` and `warnings`. With `[pitchfork] autostart = true` the document also has `processes` once the workspace is `ready`: `{report}` (what `devflow up` would print, see Processes) or `{skipped, refusal}` when the daemons were not started and why. It never changes `status` or the exit code. `switch` into an existing workspace reports the switch hooks it ran in `hooks`. `switch -c` also runs the project's `switch` hooks once the new workspace is `ready` (the same as every later `switch` into it) and reports them as `switch_hooks`; a failing or skipped switch hook is a warning. `setup --if-new` on a `ready` workspace returns only `{project, skipped: true, workspace, path}`, with no `status` or `receipt`. Passwords are replaced by `***` in every document and message except where handing out the credential is the command's purpose: `devflow db url`, `devflow db branch create` (also when `--instance-id` rotates an existing branch's password), `devflow service [NAME] url` and `devflow env list --show-values` (the real recipe templates and resolved values). Without `--json`, `db url` and `service url` print the URL alone. The same secrets are in files written 0600 (`.devflow/env`, receipts, `admin.json`, the managed `compose.yaml`), and the desktop app reveals a connection only on request. `db psql`, `shell-init`, `completions` and `gui` do not accept `--json`.

## Set up a project

Do not write `devflow.toml`, `pitchfork.toml` or `mise.toml` from guesses: ask devflow to propose them, read the proposal, and apply the items you agree with. `init` is two steps with a document between them, and neither step installs a tool, approves a hook or runs a command.

```sh
devflow --json init --plan > plan.json     # writes nothing
jq '.items[] | {id, confidence, title, risks, conflicts, depends_on}' plan.json
devflow --json init --apply plan.json --accept hook:setup:compose-up --reject daemon:worker
```

`init --plan` takes `--name NAME` and `--postgres managed|external|none`, which change the proposal. Without `--plan`, `--apply` or `--yes`, `init` needs a terminal and fails under `--json`, `--non-interactive` and in a pipe.

The plan is the whole stdout document: the envelope (`version`, `command`) plus `proposal_version`, `schema_version`, `input_hashes` (the SHA-256 of every configuration file the plan read or could write, `null` when absent, and of the detection facts under `detection`), `items`, `already_configured` (ids the files already have) and `warnings`. Each item has:

| Field | Meaning |
| --- | --- |
| `id` | Stable and deterministic: `project:init`, `copy:node_modules`, `service:db`, `service:cache`, `service:mysql`, `hook:setup:install`, `hook:setup:codegen`, `hook:setup:migrate`, `hook:setup:compose-up`, `env:preset:prisma`, `daemon:web`, `pitchfork:autostart`, `mise:env-file`, … |
| `kind` | `project`, `copy`, `service`, `hook`, `env`, `daemon` or `mise` |
| `title`, `value` | One sentence, and the proposed content as structured data (never a secret; `.env` values are never read) |
| `confidence` | `high` (applied by default), `medium` (likely, depends on something detection cannot see: compose hooks, extra daemons, a new `mise.toml`) or `low` |
| `evidence`, `risks` | Files and keys that support it (`compose.yaml:services.db.image`); what can go wrong (an older compose Postgres major, init scripts, `container_name`, fixed ports, named volumes, a copied `.env` that keeps the original `DATABASE_URL`) |
| `depends_on`, `conflicts` | Ids that must be applied with it; ids it excludes, or descriptions of existing configuration in the way |
| `patch` | `{file, ops}`: the additive edit (`table`, `set`, `append`). No `ops` means there is nothing devflow can write: a Procfile process to copy by hand, or a conflict |

A `conflicts` entry that is not an item id describes existing configuration in the way (a `mise.toml` with another `_.file`, an `[env]` recipe that already sets `DIRECT_URL`, a hook named `migrate` that runs something else). Such an item has no `ops`, is never applied by default and is refused if you `--accept` it: resolve it in the file, then plan again. Nothing is ever overwritten. `mise:env-file` is judged on mise's layered configuration (`.tool-versions`, `.config/mise/conf.d`, the base files, `mise.<env>.toml`, `mise.local.toml`, `.mise.local.toml`, … in mise's precedence order, every `_.file`/`_.source` entry in order, repeats included): it is blocked, naming the file (`mise.local.toml ([env] _.file)`, never a path or a value), when an entry comes after `.devflow/env`, whether in the same list, in a file mise reads later, or in any file above the one the wiring would go to. A `mise.<env>.toml` applies only when its `MISE_ENV` is selected, which a scan cannot tell; it is a warning. A hook or daemon depends on `mise:env-file` only when it runs repository code through mise without `devflow exec` having the last word: a mise task (`mise run migrate`, `mise watch`) or a bare `mise exec -- CMD`, since mise applies its own `[env]` over whatever devflow set (installs and code generation count as well as migrations, since `postinstall` scripts can reach the database). Wrapped commands do not depend on it and need no wiring change: `mise exec -- devflow exec -- CMD` in a hook and `run = "devflow exec -- CMD"` (with `mise = true`) in a daemon get `.devflow/env` from `devflow exec`, which sets it after mise has run. This is an early warning: `devflow setup` asks mise what it really resolves (see "Start a task", item 7).

`--apply` takes the plan's `high` items that can be applied, plus every `--accept ID`, minus every `--reject ID`. A default item whose dependency is not selected is left out and listed in `dropped` with the reason; an explicit `--accept` whose dependency is missing is an error that names it. `--no-defaults` applies only what `--accept` names. Dependencies and conflicts are validated before the first write, then the current hashes are compared with `input_hashes`: if any file changed since the plan (or the repository's detected facts did), nothing is written and the error lists what changed, so plan again. A save that lands between that check and the write is not overwritten either: each file is replaced by exchanging a staged copy with it and comparing what was displaced with what the plan read. A mismatch is put back and the apply stops with "edited since the plan was made"; if it cannot be put back, or the file changed twice, the displaced content is kept next to the file as `NAME.devflow-conflict-<timestamp>` and the error names both paths.

**Container services.** A compose service with a `valkey/valkey`, `redis` (or `docker.io/library/…`, Bitnami's, or a `valkey`/`redis` tag) or `mysql:8.4*` image becomes `service:<key>` (the key is the compose name; `service:mysql` for MySQL), whose `value` is `{key, engine, image, env, compose_service}` (`preview: true` for MySQL) and whose patch writes `[services.<key>]`. The compose image is kept when devflow's profile can run it (Redis 7+, Valkey 7.2+, the official MySQL 8.4 image); otherwise the item sets devflow's default image and the first `risks` entry says why. Valkey and Redis are `high` (applied by default; `medium` for an image from a repository devflow does not know); **MySQL is a preview, `medium`, never applied unless you `--accept service:mysql`**. `env` is what the application reads (`REDIS_URL`, `VALKEY_URL`, `CACHE_URL`; MySQL `DATABASE_URL`, or `MYSQL_URL` beside a PostgreSQL service) and a second cache gets `<KEY>_URL`; it is written to the file only when it is not the default. `risks` name what devflow knows: AOF and other persistence settings do not carry over, compose volumes are not carried over, init scripts do not run, MySQL is InnoDB only and at most one, and a cloned `.env` that defines the variable keeps the original value. The compose container can stay for other uses, but the application must use the URL devflow exports. **Branch or compose is decided at selection.** The compose hook items (`hook:setup:compose-up`, `hook:switch:compose-up`, `hook:teardown:compose-down`) list what devflow never branches; their `value.compose.members` also lists every compose service devflow proposes to branch, with `branched_by` (the `service:<key>` item). `apply` and `preview` render the hooks from the final accepted ids (`Proposal::resolved`): a service whose item is not accepted (unticked, `--reject service:cache`, MySQL without `--accept service:mysql`) is started by the hooks you accepted, in compose order; an accepted hook with nothing left to start is not written and appears neither in `applied` nor in `manual`. A project whose only datastore is a proposed cache or MySQL lists the three hooks as `medium` alternatives to the service. The plan itself and its digest do not change, so a saved `plan.json` stays valid for any choice. Nothing is proposed (and no item duplicates) when the configuration already has that service. What is not proposed is in `warnings`, in two kinds: `not proposed automatically` (modules in the image, an unpinned MySQL tag, a second MySQL service, a compose profile: configure it by hand, see the README sections it names) and `unsupported` (MySQL other than 8.4, Percona, a Redis cluster); both stay in the `hook:setup:compose-up` hook when compose can start them.

The apply document has `project`, `config`, `postgres`, `services` (`[{key, engine}]` of the configuration now), `accepted`, `dropped`, `applied` (items now in the files), `manual` (accepted items that ask for work by hand), `files` (`{file, status: created|modified|already_applied, before, after}`), `resumed`, `already_applied`, `journal` and `next_steps`. The journal (`.git/devflow/init-apply.json`, 0600) records each file's intended hashes: if a run is interrupted, repeat the same command with the same `--accept`/`--reject` and it continues; once finished, repeating it changes nothing.

Then a person reviews and commits the files and runs `devflow trust` (hooks, `[env]` and pitchfork daemons stay unapproved until then), and `devflow switch -c NAME` creates a workspace.

### LLM setup recipe

The whole path, from an unconfigured repository to a workspace that runs its own hooks, using only commands that print one JSON document and never prompt. Each step names the next.

```sh
# 1. Read the proposal. Writes nothing.
devflow --json init --plan > plan.json
jq '.items[] | {id, confidence, title, risks, conflicts}' plan.json
# 2. Apply the items you agree with (high-confidence ones are applied by default).
devflow --json init --apply plan.json --accept hook:setup:compose-up --reject daemon:worker
# 3. Adjust hooks and [env] with typed edits instead of editing TOML. Read what init
#    already set first, and edit only what is missing.
devflow --json hooks list
devflow --json env list
devflow --json hooks add setup 'bunx prisma migrate deploy' --name migrate --timeout 5m --after install
#    A variable has one owner. Pick ONE of these for DIRECT_URL; core refuses both,
#    because the prisma preset sets DIRECT_URL itself:
devflow --json env preset add prisma                  # typed: the preset owns DIRECT_URL
# devflow --json env set DIRECT_URL '${DATABASE_URL}' # or a recipe of your own, without the preset
# 4. A person reviews and approves what now runs; you do not.
devflow --json trust            # shows everything one approval covers; approves nothing
#    (a person runs: devflow trust)
# 5. Create the workspace.
devflow --json --non-interactive switch -c agent/TASK
# 6. Commands that need the workspace's database go through `devflow exec`: it applies
#    .devflow/env last (over mise, a profile, anything), from any subdirectory, and
#    refuses to start the command without it.
(cd "$path" && devflow exec -- bun test)
```

Never write `devflow.toml` by hand when `init` or `hooks`/`env` can do it: those edits keep comments and order, are validated before they are written, and refuse to overwrite a file that changed meanwhile. Never approve for the person: `trust` is the one step that is not yours.

#### `devflow hooks` and `devflow env`

Both print one document with `--json` and exit 1 with `{"error", "hint"?}` when an edit is refused; a refused edit writes nothing.

| Command | Effect |
| --- | --- |
| `devflow --json hooks list` | `phases.{setup,switch,teardown}`: `source` (`project` or `local`), `hooks[]` of `{position (from 1), name, run, timeout, effective_timeout}` and `shadowed[]` (committed hooks a local list hides); `timeout`, `files.{project,local}` with `name`, `exists` and `sha256`, and `trust` |
| `devflow hooks add PHASE COMMAND [--name N] [--timeout T] [--before REF \| --after REF] [--local]` | Adds a command (`PHASE` is `setup`, `switch` or `teardown`). A plain command is written as a string, one with a name or timeout as a table. `REF` is a hook name or a position from 1 |
| `devflow hooks update PHASE REF [--run C] [--name N \| --clear-name] [--timeout T \| --clear-timeout] [--local]` | Changes what is given and keeps the rest |
| `devflow hooks remove PHASE REF [--local]`, `devflow hooks move PHASE REF POSITION [--local]` | `POSITION` is a number from 1, `first` or `last` |
| `devflow --json env list [--workspace NAME] [--show-values]` | `recipes[]` of `{key, template, masked, source}`, `presets[]` with their variables and description, `available_presets`, `references` (the `${NAME}` you may use), `preview` (what the recipes resolve to in a workspace, as `variables[]` of `{key, origin, value, masked}`; `null` before the workspace is set up), `revealed`, `trust` and `warnings` (valid configuration that is probably not what was meant: `[env] preset = "prisma"`, or `presets_`, `Presets` and other near misses of `presets`, is a variable named `preset`, and the warning says `did you mean `presets = ["prisma"]`?`; `devflow --json doctor` has the same warning as an `env-presets` check). A credential is shown as `***` (`masked: true`): a recipe whose name says it holds one (`PASSWORD`, `PASS`, `SECRET`, `TOKEN`, `KEY`, `CREDENTIAL`, `DSN`, in any spelling) and has literal text, and any text with a password in a URL or a `password=` assignment. A template made only of `${NAME}` references is shown as written. **`--show-values` prints the real templates and resolved values, secrets included** (`revealed: true`, `masked: false`): use it only when you must read one, and never log or paste its output |
| `devflow env set KEY VALUE [--local]`, `devflow env unset KEY [--local]` | A recipe: `VALUE` may reference `${DATABASE_URL}`, `${PGHOST}`, `${DEVFLOW_WORKSPACE}` and the other generated variables, once. The response lists `recipes[]` as `{key, source}` only: an edit never echoes a value (read it with `env list`) |
| `devflow env preset add\|remove NAME [--local]` | `prisma`, `laravel`, `spring`, `sqlalchemy`, `db_parts` |

Every edit command takes `--if-unchanged SHA256` (the `files.*.sha256` of a `list` you read, or `none` for a file that does not exist yet): the edit is refused when the file is different now, so an agent never overwrites a person's edit. Without it, the file is compared with what the command itself just read.

Every edit document has `file`, `path`, `target` (`project` or `local`), `changed` (an edit whose effect is already there changes nothing), the resulting list, `notes` and `trust`:

- `--local` writes `devflow.local.toml` (not committed, merged on top). A list there replaces the committed list whole, so the first local edit of a phase copies the committed hooks (or presets) into it first and says so in `notes`. Removing the last entry of a local list leaves an empty list (`setup = []`, `presets = []`) rather than dropping the key, since a local file without the key inherits the committed list again; `env unset --local` of a recipe the committed file also sets brings the committed value back, and says so. Editing the committed file while a local list overrides it is allowed and reported, because it changes nothing on this machine. A credential in a recipe or a command is refused in the committed file and accepted with `--local`.
- `trust.needs_review` is `true` when the edit changed what an approval covers (hooks, `[env]`) and the project is not trusted now; `trust.review` is then `devflow trust`. Until a person approves it, the new hooks and recipes are skipped and a workspace set up meanwhile is `needs_attention`. An edit that returns to the approved content leaves the project `trusted`.
- Errors name the key (`hooks.setup[1]`, `env.DIRECT_URL`) and never repeat the command, name or value they complain about.

## Start a task

```sh
devflow --json --non-interactive switch -c agent/TASK > switch.json
status=$?                                   # 0 ready, 2 needs_attention, 1 error
path=$(jq -r '.workspace.path' switch.json)       # same value as .path
jq -r '.status' switch.json                       # ready | needs_attention | in_progress
```

1. Read `workspace.path` from the output and run every later command with that directory as the working directory. The worktree is outside the main checkout, under `worktree.dir` from `devflow.toml` (by default `../<repo>.worktrees/`), in a directory named after the sanitized workspace (`agent/a` becomes `agent-a`); `workspace.path` is authoritative, so do not build the path yourself.
2. The environment is in `<path>/.devflow/env`: `DATABASE_URL`, the `PG*` variables, `DEVFLOW_*` identifiers, `COMPOSE_PROJECT_NAME` (`df-<project8>-<instance8>`, unique to the workspace) and the project's `[env]` recipes and presets (for example `DIRECT_URL`, `DB_*`, `SPRING_DATASOURCE_*`, `SQLALCHEMY_DATABASE_URI`). `DATABASE_URL` and `PG*` are absent when the project has no postgres service (`[services.<key>]` with `engine = "postgres"`) or the workspace was created with `--no-db`, and so are the presets and the recipes that reference them (a warning says which). When the service sets `extra_databases = ["test", "shadow"]`, the file also has `TEST_DATABASE_URL` and `SHADOW_DATABASE_URL` (generally `<NAME>_DATABASE_URL`): separate, empty databases for tests and migration shadow schemas, reached with the same login and password as `DATABASE_URL`. Point test runners and `prisma migrate dev` at them instead of trying to create a database (branch logins cannot). A reset empties them again; they are never cloned from another workspace or snapshot. A `valkey` or `redis` service (`[services.cache]`) adds one more variable, `REDIS_URL` by default or the service's `env`: `redis://:<password>@127.0.0.1:<port>/0` for the workspace's own cache branch, cloned from the data source, with a port and a password of its own. It is a secret like `DATABASE_URL`. Point test runners and queues at it; do not share one `REDIS_URL` between workspaces. A `mysql` service (`[services.sql]`, **preview**) adds its URL, `mysql://app:<password>@127.0.0.1:<port>/<database>`, as `DATABASE_URL` (the service's `env` if set, or `MYSQL_URL` when the project also has a postgres service, which owns `DATABASE_URL`; a collision is a configuration error naming both services) and the typed fields `MYSQL_HOST`, `MYSQL_PORT`, `MYSQL_USER`, `MYSQL_PASSWORD` and `MYSQL_DATABASE`, which `[env]` recipes may read (`${MYSQL_HOST}`) and cannot set. A project has at most one `mysql` service for now. The account is `app`, the database is the service's `database` (default: the project name as an identifier), the password is the branch's own and a secret. Creating a MySQL branch from a running source stops that source for a few seconds (below), so a `switch -c` that clones a MySQL source briefly interrupts the source workspace's connections: a client must reconnect. The container starts on `setup` and `switch`; if `switch` warns that it could not start (the port is taken), free the port and run `devflow --json service up`. The `[env]` variables appear only once the scope is trusted (see below); until then the env phase is a required skip. Run commands that need it through `devflow exec -- CMD` (item 7), which applies it last, or load it yourself in a plain shell (`set -a; . .devflow/env; set +a`). The directory ignores itself; never commit it.
3. Choose where code and data come from with `--from WS` (code; needs `-c`) and `--data-from WS|snapshot:NAME[@vN]|branch:ID|empty` (data). Both are fixed once chosen. A branch `ID` anywhere (`--data-from branch:ID`, `db branch delete ID`, `service NAME drop ID`) is a UUID or a unique prefix of at least 8 hex characters, with or without dashes: the short ids the listings show work; an unknown or ambiguous prefix is an error naming the candidates. `--data-from` defaults to the code source's database, or `empty` for the default workspace. If a local branch NAME already exists, `switch -c` checks it out and `--from` only sets the payload and data source.
4. `--no-db` and `--no-hooks` skip those phases, and the skip is recorded permanently: a later `devflow setup` leaves them skipped and the workspace stays `ready`. Only `setup --new-instance` runs the services, env and hooks phases again.
5. If the exit code is 2, read the reason from the document, fix it (usually trust, see below, or the mise checks, see item 8) and run `devflow --json --non-interactive setup` inside the worktree. It resumes at the first incomplete phase.
6. A workspace stays `ready` only while the configuration it was set up under is current. When `devflow.toml` (with `devflow.local.toml`) adds a service or changes a service's section, every earlier workspace reports `needs_attention` with the `services` (for that service), `env` and `hooks` phases reopened, until `devflow setup` or the next `devflow switch` there completes them; `setup --if-new` does not skip such a workspace. The bindings and the configuration generation they were applied under are in `receipt.services.<key>` (`applied`). `--no-db` and `--no-hooks` skips are kept. A receipt written by an earlier 1.0 build is migrated in place by the next `setup`; a database binding the configuration cannot place is kept as `receipt.unmapped` and reported in `warnings` and by `doctor`, never exported.
7. **Commands that need the workspace's database go through `devflow exec`.** `devflow exec [--workspace NAME] -- CMD [ARGS…]` finds the workspace containing the current directory (any subdirectory; the nearest directory with a `.git` is the worktree root) or the named one, reads its `.devflow/env`, sets each variable over the inherited environment (overriding whatever mise, a profile or the shell set) and replaces itself with `CMD`: signals, standard streams and the exit status pass through (a program that cannot start exits 127 when it is not found and 126 otherwise, like `env(1)`, with a message that never holds an argument). It never starts `CMD` against an unknown database: outside a workspace, in a checkout without `.devflow/env`, or with a symlinked `.devflow` or `.devflow/env` it exits 1 with a message that holds no value (`--json` is refused). It prints nothing of its own. Use it for tests, migrations, a REPL, anything that connects: `cd "$path" && devflow exec -- bun test`; inside mise, `mise exec -- devflow exec -- bun test`, so mise sets its environment first and devflow's values win. Loading the file by hand (`set -a; . .devflow/env; set +a`) works in a plain shell and loses to anything that runs after it, mise included.
8. **mise checks, for hooks written by hand.** A command that goes through mise (`mise exec`, `mise run`, a shim) has mise's `[env]` applied over the variables devflow gives it: a later `_.file`, `mise.local.toml`, a plain `[env]` key or `DATABASE_URL = false`, a `mise.toml` in a subdirectory, an environment-specific file selected by `MISE_ENV`, a task's own `env`, `conf.d` or the global configuration can hand a hook the main checkout's database. Hooks that `devflow init` generates avoid it by construction (`mise exec -- devflow exec -- CMD`). Before the first setup hook the `hooks` phase reads the hooks' commands (a hook "runs mise" when `mise` is a command word of its string, also inside `sh -c '…'` and after `devflow exec --`; a command hidden behind `xargs` or a variable, or one that reaches mise through a shim, is not seen): a hook that runs `devflow exec` inside mise needs no check of the variables; for any other hook that runs mise devflow runs `mise exec -- sh -c …` in the worktree with exactly the environment the hook gets (the workspace's variables injected, `MISE_ENV` included; killed after 20 seconds; no tool is installed) and compares each variable of `.devflow/env` with what the process sees. Only variable names are ever shown, never values. If a variable is overridden or removed the phase is a required skip (`status` `needs_attention`, exit 2) and **no hook runs**; `receipt.phases.hooks.detail` reads "setup hook #2 would not get the workspace's variables as devflow sets them: mise resolves DATABASE_URL from another source than .devflow/env; …" and suggests `devflow exec`. The same happens when mise does not trust the configuration (asked with `mise env` for every hook that runs mise, because `mise exec` would trust it itself without a terminal; the detail gives `mise trust PATH`; devflow never trusts anything itself, and `devflow doctor` prints the choices), when the check cannot be made, and when mise is not installed while a setup hook runs it. A hook the check cannot stand for (a `cd` ahead of mise, `mise run`/`mise r`/`mise tasks run`, `mise -C`/`-E`, a `MISE_*` assigned in the command) is not blocked: `warnings` names it (`the setup hook 'NAME'` or `setup hook #N`, never its command) and recommends `devflow exec`. Only the `setup` hooks are checked, once, when the `hooks` phase runs; `switch` and `teardown` hooks are not. Fix mise's configuration, route the command through `devflow exec`, and run `devflow setup`, or run the hooks anyway with `devflow setup --skip-mise-check` (also on `switch`): `receipt.mise_check_skipped_at` records when, `devflow list` shows `ready (mise check skipped)` and the setup summary says so. `devflow --json doctor` runs the same check for the current workspace as `mise-env` (a failure when a hook that would be refused is overridden, naming the variables; the setup hooks not routed through `devflow exec` are listed) and `mise-wiring` (what shells and editors get through mise: a warning that "shells in the worktree won't see the branch's variables through mise; commands devflow runs are unaffected"). `devflow_core::env_file::check_mise_delivery` (`mise env --json`) remains for a caller that starts daemons with `mise = true`.

Work inside the worktree as usual: commit with Git, run tests, start daemons with pitchfork. Do not edit `.devflow/` or the receipt in the worktree's Git directory.

## Finish a task

`devflow prune [NAME…] [--yes]` forgets the Git registration of worktrees whose directory is gone, as far as core allows. Without `--yes` (and always with `--json`) it only lists them: `{project, candidates[], confirmed, pruned[], refused[], changed[]}`, each candidate `{name, id, path, why, has_receipt, data[], refusal?, remedies?}`. A registration whose receipt still records data (service bindings, a branch being created, daemons devflow started), whose receipt cannot be read, that another devflow operation holds, or whose directory's folder is missing too (an unplugged drive) is kept with a `refusal` (`owns_data`, `receipt_unreadable`, `busy`, `parent_missing`); `owns_data` carries the `remove_workspace` remedy, the normal removal that drops the data. Each confirmed registration is looked at again under its locks; branches are never deleted. Exit 1 when something named was refused.

Remove from the **main checkout**, not from inside the worktree: devflow refuses to remove the default workspace and the workspace that contains the caller's directory, and `--force` does not override either.

```sh
cd "$MAIN_CHECKOUT"
devflow --json --non-interactive remove agent/TASK --force
```

`--force` accepts a dirty or locked worktree and a failing `teardown` hook, and it skips untrusted `teardown` hooks with a warning, so a cleanup script that passes `--force` does not run them. Without it, a protection (dirty, locked, untrusted teardown hooks) stops the removal before anything changes; a failing `teardown` hook can only be detected after it ran, and it then stops the removal before the database branch or the worktree is touched. `--keep-data` leaves the database branch and the Valkey/Redis/MySQL branches in place (they show as orphans in `service list --orphans`); without it their containers and volumes are removed by recorded identity; `--delete-branch` also deletes the Git branch, and without `--force` it requires that branch to be merged into the default workspace's HEAD. Merge or push what you want to keep first.

## Trust in automation

`[hooks]` commands are arbitrary shell, and `[env]` and pitchfork's `pitchfork.toml` decide what runs in the worktree's processes, so devflow acts only on content a person has approved. Approval is the SHA-256 of a versioned **scope** (version 2): every hook command with its name and effective timeout, the `[env]` presets and recipe templates (never generated values or passwords), and the project directory's pitchfork configuration (`pitchfork.toml`, `.config/pitchfork.toml` and their `.local.toml` overlays, every daemon field). It is stored per project checkout (project id and main-checkout path), and the digest is compared with the scope of the workspace the command acts on (the pitchfork files of that worktree; `devflow --json trust` inside a worktree reports its directory as `path`); a change to any part needs approval again, and an approval made by version 1 (hooks only) authorizes nothing (`trust.format_changed`). It does not cover scripts the commands invoke. A project with no hook, no `[env]` and no pitchfork configuration has nothing to approve.

| Situation | What happens |
| --- | --- |
| Scope trusted | `setup` commands run in order in the worktree with the env applied, and the `[env]` recipes and presets are written to `.devflow/env` |
| Setup hooks or `[env]` untrusted, and no prompt is possible (`--non-interactive`, `--json`, or stdin or stderr is not a terminal) | Hooks are skipped and `.devflow/env` holds only what devflow generates; the workspace is `needs_attention` and the worktree is kept |
| `switch` hooks untrusted, workspace `ready` | Not run; a warning is added and the switch succeeds |
| `teardown` hooks untrusted | `remove` is refused; `--force` skips them with a warning |
| `DEVFLOW_TRUST_HOOKS=1` | Trusts the whole scope (hooks, `[env]`, pitchfork processes) for that one run. Use it in CI, or for repositories whose configuration you have read. Do not set it for code you did not review. |

The usual setup is a one-time `devflow trust` by a person, which then covers every agent task in that project until the scope changes. `devflow --json trust` shows everything one approval covers and the trust state without approving anything. `scope` has `version` (2), `hooks` (`setup`, `switch` and `teardown` lists of `{name, run, timeout}`, and the default `timeout`), `env` (`presets` and `vars`: the templates; a variable whose name says it holds a credential, such as `DB_PASS`, `SESSION_KEY` or `MY_CREDENTIAL`, shows `***` when its template has literal text, exactly as in `env list`, and a template of `${NAME}` references only is shown as written; the same holds for the `env` tables of pitchfork files and for the text review; the `digest` is the real scope's), `processes` (`layers`: one per pitchfork file with content, lowest precedence first, each with its `daemons` and `shared` content, or a `problem` and `sha256` for a file that could not be read; and `autonomous`: every `{file, daemon, trigger}` where pitchfork starts a daemon on its own with `cron`, `watch`, `boot_start` or `auto`) and the `digest`. `trust.state` is `nothing_to_approve`, `trusted` or `untrusted` (with `previously_trusted` and `format_changed`). `devflow trust -y` (`--yes`) approves exactly that scope without asking and prints it, so run it only after reading it, autonomous triggers included. `devflow trust --revoke` withdraws approval. An approval handed to a single operation (the terminal's "Run once" or "Trust and run", the GUI's dialog) is bound to the digest that was shown: core compares it with the scope of the workspace the operation acts on after the payload exists and before any hook, recipe or process runs, and refuses the run (`needs_attention`, "differs from what you reviewed") if that workspace holds something else, for example an existing branch with other hooks. `doctor` judges the worktree it runs in and says which directory.

## Processes

devflow does not supervise anything: pitchfork does, and mise delivers the environment. devflow decides whether it may *ask* pitchfork to start or stop a workspace's daemons, and reports what pitchfork says afterwards.

```sh
devflow --json pitchfork status        # installed? version, missing features, supervisor, proxy, conflicts, install plan
devflow --json up [WS] [--daemon NAME]… [--timeout SECONDS]     # pitchfork start -q NAMESPACE/NAME…, then list --json
devflow --json ps [WS | --all]         # daemons of the workspace(s): state, pid, ports, url
devflow --json down [WS] [--force]     # pitchfork stop NAMESPACE/NAME… (the workspace's running daemons)
```

devflow never uses `--local`, `--all` or `--global` with pitchfork: `--local` selects the daemons of every configuration from the working directory up to the root, so a worktree inside another project would start and stop that project's daemons too. It starts and stops exactly the fully qualified ids `<namespace>/<name>` of the workspace's own daemons.

- **Namespace.** For a project with a `pitchfork.toml`, the env phase writes a machine-local `pitchfork.local.toml` in each worktree: a marker comment, `namespace = "df-<project8>-<instance8>"` (the receipt's `COMPOSE_PROJECT_NAME`) and `worktree_label`, nothing else, and adds it once to the repository's `info/exclude`. A file that is not exactly that is never touched. If a committed pitchfork file declares its own `namespace`, pitchfork would refuse the siblings that disagree, so devflow writes nothing and says so in `warnings` and `doctor` (`pitchfork-namespace`), and such a workspace is refused for `up` and `down` (`foreign_namespace`, below). Daemons of a workspace are the ones of its assigned namespace in `pitchfork list --json`; proxy URLs come from `pitchfork proxy status --json`, matched by the worktree directory.
- **Environment.** `.devflow/env` reaches daemons through `devflow exec`: `run = "devflow exec -- CMD"` on each daemon, with `mise = true` for the toolchain (devflow exec runs inside mise and applies the file after it), which is what `devflow init` proposes whenever the project has a managed service (PostgreSQL, Valkey, Redis or MySQL, configured or proposed) or `[env]` content, and the same condition proposes `mise:env-file`; a project with neither keeps its daemon commands as they are. Only a `run` that is wholly one simple `devflow exec -- CMD` counts (optionally behind `NAME=value` and `exec`, redirections allowed): `devflow exec -- true; npm run dev` starts the app outside the wrapper, and `devflow exec -- mise exec -- npm run dev` hands it mise's values, applied after devflow's, so neither is treated as delivered, and a daemon with `mise = true` is checked like any other that relies on mise. The test after `devflow exec --` is conservative: any occurrence of `mise` as a word counts, in a string for `sh -c`/`bash -c`/`zsh -c`/`eval` (`devflow exec -- sh -c 'env -u X mise exec -- bun run dev'`), behind a wrapper with options (`env -u X`, `sudo -E`, `timeout 5`, `nice -n`, `nohup`, `xargs`, `command`, `exec`, `time`) or in a path ending in `/mise`; a command word that is a shell expansion (`devflow exec -- $TOOL run`) is not followed; anything the scanner does not understand is not wrapped. The hook gate applies the same rule to `through_devflow_exec`, so a `mise exec -- devflow exec -- sh -c '… mise …'` is an unprotected use, and so is a `mise` in the same string that the scanner did not classify next to a protected use (`mise exec -- devflow exec -- true; echo "mise exec -- bun run migrate" | sh`: every occurrence of `mise` as a word must be a protected use, or the command is unprotected), and a hook that runs `devflow exec -- sh -c 'env -u X mise …'` is checked like any other that runs mise. A daemon can still get it from mise alone (`mise = true` and `[env] _.file = ".devflow/env"` in `mise.toml`), which loses to anything mise applies later. devflow never writes environment or credentials into a pitchfork file (pitchfork keeps daemon environments in its state file). `doctor` (`pitchfork-env`) warns about daemons without the mise wiring.
- **Namespace ownership.** A workspace acts only through the namespace devflow assigned to it, the receipt's `df-<project8>-<instance8>`, never through whatever its pitchfork files declare. Before a daemon is attributed to a workspace (`ps`), started or stopped, the namespace the files give must equal it, or the command is refused with `foreign_namespace` ("the pitchfork namespace does not belong to this workspace"). `--force` does not override it. A start first rewrites devflow's own `pitchfork.local.toml` when it is missing or stale (that is how a file edited to name another workspace's namespace is repaired); a hand-written file or a committed `namespace` is never touched, so those workspaces stay refused. `ps` shows no daemon for a workspace whose files name another namespace. The digest leaves out only the `namespace` and `worktree_label` equal to the values devflow generated for that workspace; any other value of either key, in any file, is part of the scope, so pointing a file at another namespace also drops the approval.
- **Start** is refused, with a typed reason, unless pitchfork runs with every feature devflow calls (`--version` exits 0, `list --json` and `proxy status --json` exist, and the version is 2.0.0 or later, which is when `start` and `stop` take `namespace/name` ids; `pitchfork status` names what is missing), the workspace is `ready`, the namespace is the assigned one, that worktree's own scope (hooks, `[env]` and pitchfork files) is approved, and no daemon about to start also starts on its own (`cron`, `watch`, `boot_start`, `auto`). What a started daemon `depends` on must be a daemon of the workspace's own files (a plain name, or its own namespace): pitchfork starts dependencies by itself, so one that points anywhere else is refused with `external_dependency`. Only a daemon's highest-priority definition counts (pitchfork replaces a daemon defined in several files whole), and `ps` judges each daemon on its own closure: starting everything is refused, but a daemon that depends on nothing outside the workspace stays `startable` and `up --daemon NAME` starts it. Plain daemons can still be started by name (`--daemon NAME`) once approved. A start that is already satisfied is not repeated. pitchfork is run with a timeout (default 60 s); afterwards the real state is read back, so a timeout or a failure is reported with the state at that moment and exits 1.
- **The last look.** The slow parts of a start (the mise check, asking pitchfork what runs) come first. Immediately before `pitchfork start`, `stop` or a removal's stop, devflow reads the files again, `devflow.toml` included (the project in hand is a snapshot: readiness against the configuration's generations, the scope and the approval are judged on the configuration as it is then), and checks readiness, namespace, approval and (for a start) that the content is the one it first checked; any change refuses the operation (`not_ready`, `not_approved`, `foreign_namespace`, …), and a `devflow.toml` that cannot be read then is `unreadable` (a stop answers it with `--force`). The instant between that look and pitchfork reading its own files remains (see SECURITY.md).
- **Stop** runs only while the worktree's scope still matches the approval, because pitchfork runs lifecycle hooks (`on_stop`, …) from the current file. Otherwise it is refused; `--force` stops anyway and the report carries a warning. A state devflow cannot read (the listing fails, its output is over the 4 MiB devflow keeps, or pitchfork lacks a feature) is never read as "nothing runs": it is refused with `state_unknown`, and `--force` asks pitchfork to stop the daemons the workspace declares without being able to tell which ran. So is a listing that cannot show the workspace's daemons stopped: for a stop or a removal only `stopped`, `errored`, `failed` and `available` count as not running (`running`, `waiting` and `stopping` as running; a status counts by its leading word, so `running (ready)` is running and `failed: exit 3` is failed, and one classifier, `pitchfork::DaemonStatus`, is shared by the listing, `ps`, the reports and the app's counts and pills), a daemon of the workspace in any other state (`unknown`, one a later pitchfork adds), a malformed required field (an `id` that is not `namespace/name` or that contradicts the `namespace` field, a status that is missing or not text, a pid that is not a number) and an entry that cannot be read at all are `state_unknown` (forceable), and a stop whose listing afterwards shows one of them is not ok. **A supervisor that is down is not "nothing runs"** (pitchfork's daemons survive their supervisor: SIGKILL of the supervisor leaves them running, and a restarted one takes them back): devflow records in the receipt, before it asks pitchfork to start daemons (`up`, autostart, the app's start, `restart`), `processes: {started_at, ids}` (the qualified ids), and clears it after a stop whose result it read back with the supervisor up and nothing of the namespace active. With the supervisor down and a recorded start, `down` and `remove` are refused with `state_unknown` (the message says the supervisor is down and the daemons devflow started may still run; the hint is `pitchfork supervisor start`, then `devflow down`, or `--force`); `down --force` cannot stop anything and returns a report that is not ok, and a forced removal goes on with a warning and stops nothing. With the supervisor down and no recorded start, `down` and `remove` proceed with the warning "pitchfork's supervisor is down; devflow started no daemons here, but processes started outside devflow can't be checked". The result of a start or stop is verified against the namespace it acted in (the receipt's, captured when it decided to act) in the raw `list --json`, not through the workspace's files as they are afterwards: a daemon of that namespace that still runs makes a stop not ok, and an attribution that changed while the operation ran (the files now name another namespace) is a not-ok report with `state_error`. `restart` returns the stop's report, and starts nothing, unless the stop left none of the workspace's daemons active and its state could be read. **One operation at a time.** `up`, `down`, `restart`, `remove` and `setup --new-instance` each hold the workspace's process lock (`devflow/process.lock` in its Git directory, always taken before the receipt lock) from the record of intent through the effect to the read-back, so a stop cannot read "nothing runs" between a start's record and its effect and erase the record; a second operation waits two seconds and then fails with `Busy` ("another devflow operation is starting, stopping or replacing the daemons of '…'"; exit 1, or `in_progress` from `setup`). `remove` stops the workspace's running daemons first (before teardown) and lists them in `stopped_daemons`; it needs a stop whose result it saw (pitchfork succeeded, the state could be read and verified back, nothing of the workspace is active) and otherwise it is a forceable protection (`--force` goes on with a warning); with a namespace it cannot attribute, or a pitchfork that is on `PATH` but cannot be asked (it does not run, as a mise shim without a version, or lacks a feature: `state_unknown`), a forced removal leaves the daemons running and says so. A workspace with no pitchfork file and one devflow never set up proceed without asking, and so does a machine with no pitchfork on `PATH` at all, with a warning in the removal result ("pitchfork isn't on PATH, so devflow couldn't check this workspace's daemons") when the workspace has devflow's namespace file or a recorded start.
- **Approval** is asked at a terminal as for hooks (`up` shows the worktree's scope); `--json` and `--non-interactive` never ask, run `devflow trust` first.
- **Install and proxy are offers.** `pitchfork install` runs `mise use -g pitchfork@latest` only with `--yes` or after a terminal confirmation (the JSON form without `--yes` returns `needs_confirmation: true` and runs nothing), and prints brew and cargo instructions when mise is missing. `pitchfork proxy` and `doctor` print the proxy commands (`pitchfork settings set proxy.enable true --global`, a supervisor restart, `pitchfork proxy setup`, which uses sudo); devflow never runs them.
- **Documents.** `up` and `down`: `{project, ok, workspace, path, namespace, action, ran, timed_out, error, daemons[], state_error, warnings}` (`state_error` is also how a result that could not be verified is said, for example an attribution that changed during the operation; `daemons[]` then includes the raw daemons of the namespace devflow acted in). `ps`: `{project, workspaces[]}` of `{workspace, path, namespace, installed, version, configured, supervisor_up, daemons[], observation, proxy, error, can_start, can_stop, autostart, autostart_blocked}`, where `observation` is `{complete, reasons[]}`: `complete: false` says `daemons[]` (its `not started` fallbacks and "nothing runs") was not observed, because pitchfork could not be used or its listing failed, an entry could not be read or a daemon is in a state devflow does not know (the judgement a stop makes), the files could not be read or name another namespace, the workspace's receipt cannot be read (no namespace is assigned, so every listed daemon would be filtered out), devflow's `pitchfork.local.toml` is missing while the receipt records a start or pitchfork lists daemons under the assigned namespace (the same filtering; a start writes the file again), or the supervisor is down while the receipt records a start devflow has not seen stop (pitchfork's daemons survive a supervisor that crashed); a stop in that state is the forceable `state_unknown`; and `can_start` and `can_stop` are `{allowed, reason, refusal{kind, …}}` (`kind`: `not_installed` (also a pitchfork that runs but lacks a feature: its `detail` names it), `nothing_configured`, `unreadable`, `not_ready`, `foreign_namespace` (`expected`, `found`, `file`), `not_approved`, `autonomous_triggers`, `unknown_daemon`, `external_dependency` (`daemon`, `dependency`), `state_unknown` (`detail`, and a `hint` when the generic advice would mislead, as for a supervisor that is down; the only one besides `not_approved` that `--force` answers), and at start time `mise_delivery`: daemons that pitchfork runs through mise (`mise = true` on the daemon, else `[settings.general] mise = true` resolved over every pitchfork file in pitchfork's own order, `pitchfork.local.toml` first and the daemon's own value winning) start only when `mise env` resolves every variable of `.devflow/env` as devflow wrote it, the check `doctor` shows as `mise-env`) and a daemon is `{name, id, state, pid, ports, url, error, triggers, configured, startable}`. A refused `up` or `down` is the usual error document with `hint`.

## Worktrees created by other tools

Install the Git hook once per repository: `devflow hook install`. It adds a `post-checkout` hook (respecting `core.hooksPath`) that runs `devflow setup --if-new` when a new branch is checked out into an empty worktree. That covers `git worktree add` and tools such as T3 Code and Claude Code that use the git CLI. Git does not copy `.git/hooks` on clone, so a fresh clone gets the hook only through `core.hooksPath` or a template directory.

- It does nothing when the worktree's receipt is `ready`, and resumes any other receipt.
- It does nothing unless `devflow` is on the `PATH` of the process that runs Git, which matters for GUI tools started outside your shell.
- `hook install` refuses to overwrite a `post-checkout` hook devflow did not write. The error is plain words with remedies (`chain_git_hook`, `open_file`), and its `hint` is the one-line snippet to add by hand. `hook install --chain` adds that line to the hook for you: it appends to the file (mode and owner stay), does nothing twice, and refuses a symbolic link, a hook that is not executable or not a POSIX shell script, and one with a top-level `exec` or `exit` where an added line would never run. It prints `{"chained": true, "added": BOOL, "path": …}`; a hook devflow wrote is never edited and `hook uninstall` never removes one it did not write.
- It always exits 0 so Git does not report the worktree as failed, and it stays silent when another devflow process is already setting the worktree up. Check `devflow --json list` for `needs_attention`, or read the setup logs under the worktree's Git directory (`devflow/logs/`).
- `git worktree add --orphan`, `--no-checkout` and libgit2-based tools skip the hook. Run `devflow setup` in those worktrees.
- Adopted worktrees take the default workspace as code and data source.
- `DEVFLOW_SETUP_ACTIVE=1` prevents re-entry from inside hooks.

## Sandboxes and forks

For VM sandboxes and forks, keep the admin credentials on the trusted side and give the sandbox only a branch URL: `devflow setup --database-url URL` attaches it, and `devflow setup --new-instance` (or an orchestrator-set `DEVFLOW_INSTANCE_ID`, honoured only by an explicit `devflow setup`) gives a forked worktree a fresh identity. The identity is the pitchfork namespace the workspace's daemons run under, so a new one is refused, before anything changes, while this machine's pitchfork lists a daemon of the old namespace as active (`daemons_running`: run `devflow down` first) and while devflow cannot show that none is (`state_unknown`: pitchfork cannot be asked, its listing cannot be read or has a state devflow does not know, or its supervisor is down while the receipt records a start devflow has not seen stop; `pitchfork supervisor start` then `devflow down` answers it). There is no `--force`: stopping daemons is `devflow down`'s job. **A copy from another machine is told from a second instance on this one by how the new identity is chosen:** with `DEVFLOW_INSTANCE_ID` naming another instance the orchestrator declares the receipt a copy, so its record of started daemons, and a pitchfork that cannot answer, describe another machine and do not block (a daemon this machine's own pitchfork lists as active in the old namespace still does); `--new-instance` alone declares nothing, so a copy made with it needs a supervisor that is up and shows nothing active, or `DEVFLOW_INSTANCE_ID`. Setup, the secrets a sandbox must not receive, and cleanup are in [docs/REMOTE.md](docs/REMOTE.md).

| Restore a workspace's data to its source (immediately: there is no confirmation prompt) | `devflow --json db reset [WS] [--to SRC]` |

| Run a command with the workspace's variables applied last (not JSON: it replaces itself with the command) | `devflow exec [--workspace NAME] -- CMD [ARGS…]` |
| Check Docker, the server, CoW capability (measured or declared), trust, pitchfork (install state, namespace, `.devflow/env` delivery, proxy), and (inside a workspace) what mise does to its variables (`mise-env`, with variable names and the hooks not routed through `devflow exec`; `mise-wiring` for shells; for an untrusted configuration the choices, as text). Each check is `{name, status, detail, hint?, remedies?}`: `hint` is plain words (no command line), `remedies` the actions that fix it, each with its CLI `command` (`devflow db up`, `devflow hook install`, `devflow setup` …). The human output prints each remedy's command after the hint. Before this change `hint` held the command itself; read `remedies[].command` now | `devflow --json doctor` |
| Start, stop and list a workspace's pitchfork daemons (see Processes) | `devflow --json up [WS]`, `down [WS]`, `ps [WS \| --all]` |

| Valkey/Redis/MySQL: the service, its engine and Docker daemon, the copy-on-write result (`cow`: `verified`, `copy` or `unknown`, from a cached probe), every branch with its container state, port, source, capture time, clone method and, for MySQL, `database` and `source_downtime_ms` (no passwords), and the last finished clone, snapshot or reset (`services[]` of `{key, engine, image, docker, cow, branches[], snapshots, unfinished, last_clone}`; `last_clone` is `{operation, target, finished_at, method, source_downtime_ms}`, where `source_downtime_ms` is how long a MySQL source was stopped for the copy and `null` when no source was stopped: Valkey and Redis keep serving, and a clone from a snapshot has no source) | `devflow --json service [NAME] status` |

When the PostgreSQL server is unreachable, `list`, `path`, `db url`, `switch` to a ready workspace and `remove --keep-data` do not need it and still work; operations that provision or drop data fail with an error.

## Environment variables

| Variable | Use |
| --- | --- |
| `DEVFLOW_TRUST_HOOKS=1` (or `true`) | Trust the `[hooks]` section for this run |
| `DEVFLOW_NON_INTERACTIVE=1` | Same as `--non-interactive` |
| `DEVFLOW_INSTANCE_ID` | Orchestrator override: the instance identity a forked worktree takes. Must be a UUID (anything else is ignored) and is refused if another worktree of the project already records it. Honoured only by an explicit `devflow setup` |
| `DEVFLOW_PG_ADMIN_URL` | Admin URL for external mode (trusted machines only) |
| `DEVFLOW_CONFIG_DIR`, `DEVFLOW_DATA_DIR` | Redirect the registry, trust and managed-server directories (useful for isolated tests) |
| `DEVFLOW_SETUP_ACTIVE` | Set to `1` by devflow inside hook commands; the `post-checkout` hook does nothing when it is `1`, so Git commands in a hook cannot start another setup |

Hook commands run with `sh -c` in the worktree with stdin closed. Each entry of `setup`, `switch` and `teardown` is a string or a table `{ name = "migrate", run = "…", timeout = "5m" }` (`name` and `timeout` optional; `timeout` overrides `[hooks] timeout`); a name is shown in output and logs as `[migrate] $ …`, and hook runs in the JSON documents carry it as `name`. Hooks also receive the `[env]` recipes and presets, and `DEVFLOW_PROJECT`, `DEVFLOW_PROJECT_ROOT`, `DEVFLOW_WORKSPACE`, `DEVFLOW_WORKSPACE_PATH`, `DEVFLOW_SOURCE_PATH` (absent for the default workspace), `DEVFLOW_WORKSPACE_ID` (the workspace's instance id; informational, also in `.devflow/env`), `COMPOSE_PROJECT_NAME` and `DEVFLOW_PHASE` (`setup`, `switch` or `teardown`). Git's hook context (`GIT_DIR`, `GIT_WORK_TREE`, …) is removed, and when the workspace has a database so are inherited libpq variables such as `PGHOST`, so `psql` in a hook reaches the workspace's own database. Hooks run at least once, so write them to be idempotent. There is no command templating (`[env]` values reference generated variables as `${NAME}`, and nothing else).

[`examples/agent-task.sh`](examples/agent-task.sh) implements this flow: it stays the parent of the command, so the workspace is removed after a success and after a failure (`KEEP=1` keeps it), the command's exit status is the script's, and INT and TERM are forwarded to the command's whole process group. The workspace is removed only once that group has exited: processes the command left behind (a dev server, a test runner's workers) are stopped when it ends, TERM first and KILL after `AGENT_TASK_GRACE` seconds (default 10), with a message on stderr; a process that started its own session is not stopped. A command that ignores INT or TERM is not waited for forever: the grace starts at the first signal, and when it is over with the command still running the group is killed and the command's real exit status is the script's. `AGENT_TASK_GRACE` is a whole number of seconds from 0 to 3600 (anything else is refused before the workspace is created). If the group is still there after KILL, the workspace is kept, stderr names it and the remaining PIDs, and the exit status is 70.
