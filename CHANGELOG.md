## Unreleased

devflow 1.0 is a breaking simplification. It keeps Git worktrees, copy-on-write payloads, PostgreSQL branches and trusted setup hooks, adds a GPUI desktop app, and delegates processes and the proxy to pitchfork and toolchains and dependencies to mise. There is no in-place upgrade: read [docs/MIGRATING.md](docs/MIGRATING.md). The design is in [docs/plans/2026-10-10-devflow-1.0.md](docs/plans/2026-10-10-devflow-1.0.md).

### Added

- **Postgres branches** — One PostgreSQL 18 server per project (managed container or external). Each workspace database is cloned with `CREATE DATABASE … TEMPLATE … STRATEGY FILE_COPY` and `file_copy_method = clone`, so on btrfs, XFS (reflink), ZFS 2.2+ and OrbStack volumes it shares blocks with its source. CoW is measured and reported as `verified`, `copy` or `unknown`; `require_cow` refuses branches otherwise.
- **Snapshots** — Versioned, immutable `db snapshot` seeds selectable with `--data-from snapshot:NAME[@vN]`; `db reset`, `db reconcile` and explicit `db branch` management.
- **Role isolation** — Branch logins connect to their own database only, behind a per-project owner role and a metadata database; a non-superuser `CREATEDB CREATEROLE` provisioner is enough.
- **Receipts and resumable setup** — Each worktree records its phases (materialize, payload, services, env, hooks) and one binding per service (`receipt.services.<key>`). `devflow switch` and `devflow setup` resume at the first incomplete phase; status is `ready`, `needs_attention` or `in_progress`, and exit code 2 means the workspace is not `ready`.
- **Services schema** — `[services.<key>]` tables selected by `engine` (`postgres` first; at most one, and `devflow db …` addresses it whatever its key). Keys match `^[a-z][a-z0-9_-]{0,30}$`; unknown engines and fields are errors; 0.x files are recognised by shape and files mixing 1.0 and 0.x keys are refused with the conflicting keys named.
- **Configuration generations** — Each service section and the environment have a stable SHA-256 generation (passwords in `admin_url` are masked). Receipts record the generation each binding and `.devflow/env` were applied under: adding or changing a service reopens `services`, `env` and `hooks` (`needs_attention` until `devflow setup` or the next `switch`), keeping `--no-db` and `--no-hooks` skips and never deleting a removed service's data. `setup --if-new` and `switch` check generations before treating a workspace as ready.
- **Stable endpoints** — A managed server's host port is allocated once from the project and service identity (20000–39999), recorded in `admin.json` and published fixed; a recorded port that becomes unavailable is an error naming the port and the cause, never moved. On OrbStack the server also gets the name `<service>.<project>-<id8>.devflow.orb.local`, reported as `container_endpoint` by `devflow db status`; `DATABASE_URL` stays on `127.0.0.1`.
- **Trusted hooks** — `[hooks]` `setup`, `switch` and `teardown` shell commands, each a string or a table `{ name, run, timeout }` (a name appears in output and logs; a timeout overrides `[hooks] timeout`), gated by `devflow trust` or `DEVFLOW_TRUST_HOOKS=1`.
- **Trust scope v2** — One approval covers a versioned scope: the hooks (names and timeouts included), the `[env]` recipes and presets as templates (never generated values or passwords) and the project's pitchfork configuration (`pitchfork.toml`, `.config/pitchfork.toml` and their `.local.toml` overlays, every daemon field). `devflow trust` and the GUI dialog show all of it and flag the daemons pitchfork starts without devflow (`cron`, `watch`, `boot_start`, `auto`). Approvals carry the scope version: a version 1 approval authorizes nothing (`format_changed`), and "nothing to approve" now means the whole scope is empty. The approval is kept per project and main checkout, but its digest is compared with the scope of the workspace a command acts on (that worktree's own pitchfork files): setup, switch and teardown hooks and `[env]` recipes in a linked worktree wait for `devflow trust` run inside it, and `devflow --json trust` gives the `path` it judged. pitchfork files are hashed whole, whatever their size up to 256 MiB, and every component of their path is checked for links.
- **`[env]` recipes and presets** — Extra variables for `.devflow/env` and hooks: recipes with `${NAME}` references to devflow-generated variables (one pass, no defaults, no nesting) and `presets = ["prisma", "laravel", "spring", "sqlalchemy", "db_parts"]` rendering typed fields from the database's connection parameters. Invalid names, reserved or generated names, bad references and conflicts are configuration errors naming the key. Values built from the password are secret (0600 file, never shown, masked whole in hook output and logs) and are applied only for an approved scope.
- **`COMPOSE_PROJECT_NAME`** — Every workspace exports `df-<project8>-<instance8>` so Docker Compose projects never collide across workspaces.
- **Test and shadow databases** — `[services.<key>] extra_databases = ["test", "shadow"]` (names `^[a-z][a-z0-9_]{0,20}$`, unique, not `main`, `postgres`, `devflow` or `template*`) gives every branch recorded, empty **scratch databases**, exported as `<NAME>_DATABASE_URL` (`TEST_DATABASE_URL`, `SHADOW_DATABASE_URL`) with the branch's own login and password, masked like `DATABASE_URL`. Branch logins keep `NOCREATEDB`: the databases are created by the same closed-creation protocol as a branch's own, owned by the admin and open to that login only, with generated names (`df_<project8>_<branch12>_<n>`). They are empty in every clone, absent from snapshots, emptied again by `db reset` (recorded steps, finished by `db reconcile` after an interruption), covered by credential rotation, and dropped with their branch (kept with `--keep-data`). A name added to the configuration is provisioned for existing workspaces by the next `setup` or `switch`; a name removed leaves a recorded orphan that `db reconcile` and `doctor` report and `db reconcile --drop-orphans` drops. `db branch list` (an `EXTRAS` column) and the receipt bindings show names and databases, never a second copy of the password; `db branch create` and `--json db url` (which hand out credentials anyway) also give each scratch database's URL. A reset journals which scratch databases it empties, and finishing an interrupted one empties exactly those whatever `extra_databases` says by then. The metadata schema is version 3 (one new table, a counter column and that journal column): an older devflow refuses it.
- **Valkey and Redis branches** — `[services.<key>] engine = "valkey" | "redis"` (`image`, default `valkey/valkey:8-alpine` / `redis:8-alpine`; `env`, default `REDIS_URL`, and two services exporting one variable are a configuration error naming both; `require_cow`) gives every workspace a container of its own, managed only, on a fixed `127.0.0.1` port allocated once from `hash(project, service, branch)` (journaled before Docker publishes it, decided by the bind, kept: a retained port that became unavailable is reported, never moved), with its own generated `--requirepass`, exported as `redis://:<password>@127.0.0.1:<port>/0` (a secret, masked like `DATABASE_URL`). devflow runs the servers with AOF off and RDB on; a clone has the source write a complete `dump.rdb` (`BGSAVE`, completion proven by `INFO persistence`: no save running, `rdb_last_bgsave_status:ok`, `rdb_saves` advanced, `run_id` unchanged; the source is never paused) and reflinks it into a new volume inside the Docker VM with GNU `cp -a --reflink=always` (never `--reflink=auto`) in a helper container whose identity is recorded before it starts and which is killed and confirmed gone at its deadline. Without reflink, `require_cow` aborts the clone and otherwise a full copy is made, reported as `copy` (the decision is journaled before the source is quiesced). The capture time is the `BGSAVE` fork. The clone's own new password is the whole identity fix-up and applies before the server listens, then `AUTH` + `PING` must pass. The image digest is pinned per branch and snapshot, and a clone boots its source's.
- **MySQL branches (preview)** — `[services.<key>] engine = "mysql"` (`image`, default `mysql:8.4`, the only profile; `database`, default the project name as an identifier; `env`; `require_cow`) gives every workspace a MySQL 8.4 server of its own on a fixed `127.0.0.1` port, cloned copy-on-write from its source. The URL `mysql://app:<password>@127.0.0.1:<port>/<database>` is `DATABASE_URL` (`MYSQL_URL` beside a postgres service; a collision is a configuration error naming both services) and `MYSQL_HOST`, `MYSQL_PORT`, `MYSQL_USER`, `MYSQL_PASSWORD` and `MYSQL_DATABASE` are exported next to it (recipes may read them, not set them); one mysql service per project for now. devflow generates a `my.cnf` (standalone InnoDB, no binary log, no replication, `performance_schema` off, a 64 MiB buffer pool, `innodb_fast_shutdown=0`) mounted read-only. A clone refuses a running source that has tables outside InnoDB (MEMORY tables lose their rows when the server stops; the profile also forbids creating them), then shuts the source down cleanly (`docker stop`, verified by exit code 0 and InnoDB's shutdown report in the log; a SIGKILL aborts the clone and the source starts again), reflinks the whole data directory inside the Docker VM, starts the source again and reports its downtime, (`innodb_fast_shutdown` is set to 0 and read back right before the stop, a very fast shutdown is refused, and a start that logs InnoDB crash recovery, the source's or the clone's, abandons the clone), then gives the clone its own identity before it listens anywhere: `auto.cnf` and the key pairs are dropped, a bootstrap container with no network and no grant tables sets new root and application passwords through its local socket, a source with accounts, role grants or proxy privileges devflow did not create is refused by name, every managed account is normalized (plugin, no TLS requirement, expiry or lock-out) with its secondary password discarded and the accounts are read back before the clone is accepted, and the final container is checked with an authenticated `SELECT 1` as the application account and the greeting on its published port. The coordinator journals each step (`Quiescing`, `Quiesced`, `Copying`, `Copied`, `Restoring`, `Starting`); recovery after a crash first settles a `docker stop` that is still on its way (the request is journaled before it is issued; it waits for the client, asks `docker inspect` what state the container is in, and verifies the restarted source again after a settle period), then starts a source left stopped, kills the helper and aborts the destination. Snapshots, staged resets, `--data-from`, drop by recorded identity and port retention work as for Valkey and Redis. `devflow service status` and `doctor` report the engine, the copy-on-write result and the source downtime of the last clone. Passwords reach MySQL on the standard input of `docker exec`, not on a command line or in a container environment (SECURITY.md).
- **Container catalog and journal** — `<data dir>/services/<project id>.json` (0600, versioned, locked, written atomically, bound to the Docker daemon id) is the authority: branches (owner instance, container id and name, volume, pinned image, port, source, capture time, clone method, state), snapshots and the operation journal. Labels only corroborate, and all of them must: a volume or container is removed (by a rollback, a reset's cleanup, a drop or a snapshot delete), written into or started on only when it carries the record's project, service and branch, snapshot or operation labels (the project label alone is not enough); one that does not is kept, the operation stops there undone and `reconcile` reports it, a container that merely has a devflow name is refused, and a snapshot of a pre-release build (no snapshot label) is not migrated: copying from it is refused with the command that deletes it, and `snapshot delete` can remove it. A clone, snapshot or reset is journaled first and run by an operation-scoped coordinator process (`devflow __clone`, hidden, its own process group) that holds the source's lock and is waited for with a handshake. Every later operation on a source or destination first reconciles unfinished entries under the same lock: it kills the recorded helpers (the copy helper and the one that reads a volume, both journaled before they exist), confirms they are gone, aborts the destination (never promoted) and finishes what was asked for (removals, a copy proven complete).
- **`devflow service`** — `devflow service [NAME] status|up|down|url|list|snapshot create|list|delete|reset|reconcile|drop|forget`, each with a JSON document (`status`, `list` and the rest redact passwords; `url` prints them). Snapshots are immutable volumes (`BGSAVE` + reflink, no container; `--data-from snapshot:NAME[@vN]` clones from them); `reset` stages a replacement volume from the recorded source, starts and checks it, then swaps it in under the journal, keeping the URL and removing the original once validated; `list --orphans` and `reconcile` report services removed from the configuration and branches whose workspace is gone, and `forget` removes a service's data explicitly. `switch` starts a workspace's containers (a port that became unavailable is a warning naming the port), `remove` drops the branches the instance created (kept with `--keep-data`), and a VM fork clones the branches it knew.
- **Per-daemon CoW probe** — `devflow doctor` and `devflow service status` report `verified`, `copy` or `unknown` for the Docker engine's volumes, measured by reflinking a 64 MiB file in a scratch volume and comparing the guest's free space, cached per daemon id. On OrbStack each container also gets `<branch8>.<key>.<project>-<project8>.devflow.orb.local` as its container endpoint.
- **Worktrees from other tools** — `devflow hook install` adds a `post-checkout` hook that runs `devflow setup --if-new` for `git worktree add`, T3 Code, Claude Code and fresh clones.
- **Remote data hosts** — External mode, `app_host`, `DOCKER_CONTEXT` for a managed server on a remote engine, `setup --database-url`, and `setup --new-instance` for VM forks. See [docs/REMOTE.md](docs/REMOTE.md).
- **`.devflow/env`** — Generated `DATABASE_URL`, `PG*`, `DEVFLOW_*` and `COMPOSE_PROJECT_NAME` variables, plus the project's `[env]`, loadable with mise `[env] _.file`.
- **Proposed setup (`devflow init`)** — `init` plans from a read-only scan (manifests, lockfiles, compose, `.env*` variable names, Procfiles, mise and pitchfork files, ignored directories; no project code runs and no `.env` value is read) and proposes items with stable ids (`copy:node_modules`, `service:db`, `hook:setup:install`, `hook:setup:migrate`, `env:preset:prisma`, `daemon:web`, `mise:env-file`, …), each with a confidence, evidence, risks, dependencies, conflicts and a structured patch: the PostgreSQL service, `worktree.copy` paths, `mise install` (never `mise trust`: a worktree mise does not trust is stopped before any hook runs, so a hook cannot trust it), idempotent dependency installs, code generation, migrations (an existing `db:migrate` script or mise task preferred), `docker compose` hooks for the services devflow cannot branch, `[env]` presets, pitchfork daemons with their ports and the `.devflow/env` wiring in `mise.toml` (for shells and editors). `--plan [--json]` writes nothing and prints the proposal; `--apply PLAN.json [--accept ID] [--reject ID] [--no-defaults]` applies a saved plan (its high-confidence items by default); `--yes` plans and applies them; `--name` and `--postgres managed|external|none` override the proposal. Existing files are preserved and edited additively with their formatting and comments (`toml_edit`); a key that exists with another value is a reported conflict and the item cannot be applied. Before the first write `--apply` validates dependencies and conflicts and compares the current SHA-256 of every input with the plan's (naming what changed); it records the intended before and after hashes in an apply journal (`.git/devflow/init-apply.json`, 0600), writes atomically keeping the permissions of the file it replaces, re-reads each file right before replacing it and refuses one edited since the plan (the replacement itself is an atomic exchange with a staged copy, with what it displaced compared with what the plan read, so a save in the last instant is put back, or kept as `NAME.devflow-conflict-<timestamp>` and named in the error, where the filesystem has an atomic exchange: APFS and Linux filesystems with `RENAME_EXCHANGE`; elsewhere a narrow window remains and only a hard-link backup of the displaced file is kept), resumes an interrupted apply of the same plan and selection (still checking every repository fact the apply itself does not change, and every mise configuration layer by content and as a set, so a `.config/mise/config.local.toml` that appears between the interruption and the retry is noticed; only the files the journaled apply writes are left out), and does nothing when repeated. Conflicts name the key or entry, never what the files hold there (a hook command may carry a password). Hooks that run repository commands through mise are built as `mise exec -- devflow exec -- CMD` (the `cd DIR &&` ahead of it stays, which is safe because devflow applies last) and daemons as `run = "devflow exec -- CMD"` with `mise = true` when the repository uses mise, so none of them depends on how mise is configured; only a mise task (`mise run NAME`), which `devflow exec` cannot wrap, still depends on `mise:env-file`. That item makes mise load `.devflow/env` for shells and editors in the worktree: it is judged on mise's layered configuration in mise's own precedence order (`.config/mise.toml` below `mise.toml`, `mise.local.toml` and `.mise.local.toml` above, `mise.<env>.toml` between, every entry kept, repeats included) and is blocked, naming the file, when a later entry or file would override `.devflow/env`, which only warns that "shells in the worktree won't see the branch's variables through mise; commands devflow runs are unaffected"; the compose teardown uses `down -v` only when no volume is shared (an explicit `name:` or `external` is, whatever `COMPOSE_PROJECT_NAME` says) and every compose and override file could be read (an override that is a symlink leaving the repository, a dangling one or a directory counts as an unread file). Writing configuration never installs, trusts or runs anything.
- **Processes with pitchfork** — `devflow up`, `down` and `ps` start, stop and list a workspace's pitchfork daemons (`--json` for all); `devflow pitchfork status|install|proxy` reports and offers installation. Detection runs `pitchfork --version` (a mise shim without a version exits 1: not installed) and checks the features devflow uses (`list --json`, `proxy status --json`, and `start`/`stop` by `namespace/name`, which exists from pitchfork 2.0), reporting the version and what is missing; operations and gates use that full detection, remembered for ten seconds, not the version alone. Each worktree gets a machine-local `pitchfork.local.toml` holding only `namespace = "df-<project8>-<instance8>"` and `worktree_label`, added once to the repository's `info/exclude`; a committed `namespace`, or a `pitchfork.local.toml` devflow did not write, is reported and left alone. Daemons receive `.devflow/env` through mise only, never through pitchfork files (`doctor` warns about daemons without `mise = true`). A start requires a `ready` workspace whose own scope matches the approval and no daemon that starts on its own (`cron`, `watch`, `boot_start`, `auto`); it runs `pitchfork start -q NAMESPACE/NAME…` for the workspace's own daemons with a timeout (default 60 s) and reads the real state back. A stop runs only while the scope still matches the approval; `remove` stops the workspace's daemons first and refuses when they cannot be stopped under the approval unless `--force`. `[pitchfork] autostart = true` (proposed by `init` with medium confidence, off by default) starts after `setup` and `switch`; the outcome is reported apart from readiness. Installing pitchfork asks first (`mise use -g pitchfork@latest`); the proxy commands are only printed, `proxy setup` needs sudo and devflow never runs it.
- **Process safety** — devflow starts and stops only the full `namespace/name` ids of the workspace's own daemons and never uses pitchfork's `--local` (which also selects the daemons of every parent directory's configuration); a `depends` that points outside the workspace's own files is refused (`external_dependency`). A workspace acts only through the namespace its receipt assigned (`df-<project8>-<instance8>`): a namespace in its files that is not that one refuses `up`, `down` and `remove` (`foreign_namespace`), `ps` attributes no daemon through it, and only the `namespace` and `worktree_label` devflow generated are left out of the trust digest, so an edit to either also drops the approval; `up` restores devflow's own stale file. Readiness, namespace and approval are read again immediately before every start, stop and removal's stop, and any change refuses it. A pitchfork state that cannot be read is never taken for "nothing runs" (`state_unknown`; `--force` goes on without knowing), and neither is a listing with a daemon of the workspace in a state devflow does not know (only `stopped`, `errored`, `failed` and `available` count as not running; a malformed id, status or pid, or an unreadable entry, is `state_unknown` too), and neither is a supervisor that is down: the receipt records the daemons devflow starts (`processes`, written before the start, cleared by a stop that was read back with the supervisor up), so with the supervisor down a removal or `down` over a recorded start is refused (`pitchfork supervisor start`, then `devflow down`, or `--force`), while one with no recorded start proceeds with a warning, a removal needs a stop whose result it saw, and `restart` returns the stop's report when the stop did not leave the daemons stopped. `ps` and gates use the full feature detection. The last look also reloads `devflow.toml` and judges readiness, scope and approval on it (the project a caller holds is a snapshot), a start or stop is verified against the namespace it acted in in the raw listing (an attribution that changed meanwhile is a not-ok report, so a removal cannot go on over a daemon that vanished from the view), and removal treats a pitchfork on `PATH` that does not run as `state_unknown` instead of "nothing running" (with no pitchfork on `PATH` at all it proceeds, and warns that it could not check the daemons when the workspace has devflow's namespace file or a recorded start). A daemon counts as wrapped by `devflow exec` only when its whole `run` is one simple `devflow exec -- CMD` that starts no mise (`devflow exec -- true; npm run dev` and `devflow exec -- mise exec -- npm run dev` are checked like any daemon that relies on mise), and any occurrence of `mise` as a word after `devflow exec --` counts as starting it: inside a string for `sh -c` or `eval` (`devflow exec -- sh -c 'env -u X mise exec -- bun run dev'`), behind a wrapper with options (`env -u X`, `sudo -E`, `timeout 5`, `nice -n`, `xargs`) or in a path ending in `/mise`, for daemons and for the hook gate alike (a command the scanner does not understand is neither wrapped nor protected), dependencies are judged on a daemon's highest-priority definition and per daemon (an independent daemon stays startable when another depends on something outside the workspace), and the subprocess runner behind pitchfork and Docker calls keeps at most 4 MiB of each output stream (pitchfork queries, `docker compose` lookups and `docker exec` treat more as an error), waits once and briefly for output after a command exits, and ends what a query left behind. The remaining instant between the last look and pitchfork reading its own files is documented in SECURITY.md.
- **Process control, release review** — A protected use of mise no longer vouches for the rest of a command: when a hook has a `mise exec -- devflow exec -- CMD` and one more occurrence of `mise` as a word than the scanner classified (`echo "mise exec -- bun run migrate" | sh`), the surplus is an unprotected use and the hook gate checks the variables. Start, stop, restart, removal and the replacement of an instance (`setup --new-instance`) now hold a per-workspace process lock (`devflow/process.lock` in the worktree's Git directory, taken before the receipt lock) from the record of intent through the effect to the read-back, so a stop can no longer erase the record of a start that is still being made (after a supervisor crash, removal would have believed devflow never started anything); a second operation waits two seconds and fails with `Busy`. `setup --new-instance` (and a `DEVFLOW_INSTANCE_ID` naming another instance) no longer loses control of running daemons: the identity is the pitchfork namespace, so it is refused, under that lock and before anything changes, while this machine's pitchfork lists a daemon of the old namespace as active (`daemons_running`: `devflow down` first) or devflow cannot show that none is (`state_unknown`: an unreadable listing, an unknown state, a supervisor that is down over a recorded start, a pitchfork that does not run over a recorded start). A copied VM keeps working: `DEVFLOW_INSTANCE_ID` declares the receipt a copy, so its record of started daemons, which describes another machine, does not block (daemons this machine's pitchfork shows as active still do); `--new-instance` alone declares nothing. One classifier, `pitchfork::DaemonStatus`, now reads pitchfork's status strings for the listing, `verifiable` judgements, `ProcessReport::ok()`, the observation and the desktop app's counts, tones and tooltips: a decorated state such as `running (ready)` or `failed: exit 3` means the word it starts with everywhere, where the report used exact strings and called a still-running `running (ready)` daemon stopped. A process observation no longer claims to be complete when it could not attribute daemons: a receipt that cannot be read, or devflow's namespace file deleted while the receipt records a start or pitchfork lists daemons under the assigned namespace, filtered every listed daemon out of the view yet reported `observation.complete = true`; both are now incomplete and say why.
- **Editing hooks and `[env]` from the command line** — `devflow hooks list|add|update|remove|move` and `devflow env list|set|unset|preset add|remove`, each with `--json`, change `devflow.toml` (or `devflow.local.toml` with `--local`) through typed, format-preserving edits (core `config_edit`): comments and order survive, a hook is a string when only `run` is set and a table otherwise, the merged result is validated before the write, and a file that changed since it was read is never overwritten, not even by a save that lands while the edit is being validated or in the instant before the swap (`--if-unchanged SHA256` for scripts and agents, hashes in `list --json`; the file is replaced through `replace_if_unchanged`, and a save that had to be moved aside is kept as `NAME.devflow-conflict-<timestamp>` and named in the error). A list in the local file replaces the committed one, so the first local edit copies it and says so, and removing its last entry leaves `[]` (an absent `presets` or `hooks.setup` would inherit the committed list again and switch it back on); a credential is refused in the committed file and accepted with `--local`; errors name the key path and never the value. After a change that alters what an approval covers the command prints that the configuration needs review and points to `devflow trust` (`trust.needs_review` in JSON); it never approves. `devflow env list` previews the recipes in a workspace with credentials masked by the variable's name as well as by pattern (a literal `APP_PASSWORD = "hunter2"` in `devflow.local.toml` is `***`, and `masked` in the JSON says so; core builds the views with `config_edit::masked_template` and `masked_value` before anything renders them), `--show-values` prints the real templates and resolved values on request, and an edit's response lists recipe keys only and never repeats a value. The agent guide has an LLM setup recipe (`init --plan`, `init --apply --accept`, `hooks add`, `trust`).
- **Receipts remember how long and how** — A phase records when its attempt began (so its duration is known) and the payload phase records how each `worktree.copy` path was written (`cloned`, `mixed`, `copied`), kept across retries. Both are optional fields: older receipts still read.
- **Setting up from the desktop app** — A project with no `devflow.toml` offers **Set up devflow…** (also in the command palette and the project's context menu): a six-step wizard (Detected, Proposal, Review, Apply, Approve, Done) over core's `detect`, `propose` and `apply`, driven by the keyboard too. The proposal groups items by heading with a checkbox at its default, a confidence, the reason and an expandable detail, and takes the PostgreSQL choice (managed, existing or none); Review shows the exact diff per file before anything is written; Apply reports each file and, when the repository changed since the plan, writes nothing and offers to plan again; Approve lists exactly what an approval covers; Done offers the first workspace. The new **Setup** tab (⌘4; Config and Logs move to ⌘5 and ⌘6) lists the three hook phases with what each is for, adds, edits, reorders and removes hooks (with suggestions detected in the project), edits `[env]` recipes with masked resolved values and the framework presets, switches between `devflow.toml` and `devflow.local.toml`, and shows when what the project runs needs approval, all through core's `config_edit` (comments kept, validated, refused on a concurrent edit). Selecting a workspace shows its detail pane: phase timeline with durations, errors and Retry setup, connections and scratch databases, and time and disk reported honestly.
- **`devflow exec`** — `devflow exec [--workspace NAME] -- CMD [ARGS…]` runs a command with the workspace's `.devflow/env` set on top of the inherited environment, so what mise, a profile or the shell set cannot win, and replaces itself with the command (Unix `exec`: signals, standard streams and the exit status pass through; a program that cannot start exits 127 or 126 like `env(1)`). It finds the workspace from any subdirectory (the nearest directory with a `.git` is the worktree root) or by name, never starts the command without the file (outside a workspace, in a checkout without `.devflow/env`, or with a symlinked `.devflow` or `.devflow/env` it exits 1), prints no value, and on the fast path reads two things: measured on macOS with a release build it costs about 5 ms over starting the program directly (`/usr/bin/true`: 1.9 ms; `devflow exec -- true`: 6.6 ms, 7.1 ms from six directories down; `devflow --version` alone: 5.3 ms, so devflow's own work is about 1.3 ms). Hooks written as `mise exec -- devflow exec -- CMD` and daemons as `run = "devflow exec -- CMD"` get the workspace's database whatever mise's configuration says, from a `cd`-ed subdirectory too. This is a new command, not the 0.x `devflow exec`.
- **mise checks for hooks** — mise applies its `[env]` over the variables devflow gives a command that goes through it, and a probe made at the root of the worktree cannot say what a command receives (a `cd app && mise exec`, a task's `env`, a generated `MISE_ENV`, configuration in `conf.d` or an environment-specific file, `[env] NAME = false` without the file loaded). Before the first setup hook the `hooks` phase now reads the hooks' commands: a hook that runs `devflow exec` inside mise needs no check of the variables; for any other hook that runs mise, whatever files exist, devflow runs `mise exec -- sh -c …` in the worktree with exactly the environment the hook gets (devflow's variables injected, `MISE_ENV` included; bounded, the process group killed on timeout; no tool installed, no `[deps]` prepared, no cached environment) and compares each variable with what the process sees: a different value is overridden, a missing one removed (`MiseDelivery::Removed`, new). Either, a failed check or mise missing for a hook that runs it leaves the phase a required skip (`needs_attention`, exit 2) with no hook run and the hook named by its name or index, never its command. A hook the check cannot stand for (a `cd` ahead of mise, `mise run`/`mise r`/`mise tasks run`, `mise -C`/`-E`, a `MISE_*` in the command) gets a warning recommending `devflow exec` and is not blocked. Whether mise trusts the configuration is asked with `mise env` for every hook that runs mise, `devflow exec` inside it or not: with mise 2026.10, `mise exec` and `mise run` trust a configuration themselves when they have no terminal. devflow never trusts anything (`mise trust PATH` is named). Only variable names are shown, never values. `--skip-mise-check` on `setup` and `switch` runs the hooks anyway, recorded in the receipt (`mise_check_skipped_at`) and shown by `devflow list` (`ready (mise check skipped)`). `devflow doctor` runs the same check for the current workspace (`mise-env`, with the variable names and the setup hooks not routed through `devflow exec`; the workspace's mise configuration is found by the detection layer's complete discovery, not a list of names), reports what shells get (`mise-wiring`), and for a configuration mise does not trust prints your choices as text (`mise trust PATH`, or `mise settings add trusted_config_paths DIR` with what that trusts) and runs neither. `devflow_core::env_file::{check_command_env, check_mise_trust, classify_hooks, command_runs_devflow_exec}` are public; `check_mise_delivery` (`mise env --json`) remains for callers that start daemons with `mise = true`.
- **Desktop app** — `devflow-gui`, built on GPUI and `gpui-kit`, with projects, workspaces, database branches and snapshots, pitchfork daemons, a config editor and setup logs.
- **Desktop app, container services** — The Data tab lists every service with its branches, snapshots and orphans. Its actions run against the project they were opened for (never the one selected later) and, for a reset or a snapshot, against the workspace instance the dialog showed (core refuses with "the workspace changed since you reviewed it" otherwise); a confirmation says when MySQL will stop the source workspace's server for the copy; names that look like credentials are masked on screen but still act on the right snapshot; and what could not be read (Docker, the catalog, pitchfork) is shown as unavailable or unknown, never as zero. Round 2: an unreadable workspace receipt makes branch ownership unknown, so nothing is offered or dropped as an orphan until it is repaired (`service list --orphans`, `reconcile` and `doctor` say so); a process start, stop or restart acts on the workspace it was shown for (core refuses with "the workspace changed since you reviewed it" when its instance is another one), from the buttons, the review dialog and the palette alike; a reset is held to the source it showed (a workspace set up again, or a snapshot name pointing elsewhere, is refused before any effect); a snapshot opened from a branch row must match that row's workspace; workspace names that look like credentials are masked in every text the app draws; and a pitchfork listing that failed is shown as unknown with its reason instead of "not started". Round 3: a name that looks like a credential is masked in every text but never in the request it names (a daemon called `password=hunter2` is started by that name, and so are snapshots and forgotten services); a process state nobody observed (a failed listing, entries that could not be read, a supervisor that crashed after devflow started daemons) is unknown with core's reasons in the overview, the Daemons tab and the detail, `devflow ps` and its JSON carry `observation`, and Stop stays available as a confirmed "Stop anyway" instead of being disabled; a branch whose owner could not be resolved says "owner unknown" rather than "no workspace"; and `devflow doctor` says why a workspace receipt could not be read.
- **`devflow doctor`** reports the CoW capability and whether it was measured or declared.
- **Shell integration** — `devflow shell-init` (a `cd`-ing `switch`), `devflow completions SHELL`, and `devflow gui` to open the desktop app.
- Examples for `devflow.toml`, external mode, mise, pitchfork and an agent task script.
- **Container services, review round 3** — Valkey and Redis: a branch- or helper-labelled namesake volume no longer passes as a pre-release snapshot (`snapshot delete` keeps it); a `docker create` of a journaled helper that is still on its way is settled before the name is looked up, and helpers that mount a volume are removed before it is; `reconcile` no longer reports a reset's old container and volume as unrecorded while its cleanup is pending. MySQL: operations recover what a dead coordinator left once they hold the locks (a queued clone no longer runs against a source that was left stopped); `docker inspect` and `docker logs` are bounded (60 s) and a recovery that cannot get an answer stays pending with its journal intact.
- **Container services, final review** — A stop whose return was never seen is no longer waited out by the clock: recovery fences the container by identity (journals the decision, stops it itself, removes it by its recorded id, recreates it from the managed profile on the same volume, name, port and endpoint, health-checks it), so a `docker stop` delivered late names a container that no longer exists; MySQL sources and a Valkey/Redis reset's rollback both use it, and recovery no longer waits minutes. Every attempt to create a helper is recorded by name in a list that outlives the operation, and reconcile, rollbacks and volume removals remove any that Docker finished creating after its client was ended (the removal of a volume sweeps again and retries while it is in use). Every `docker` call of the container services is bounded by one runner, and a recovery passes its remaining time to each; a timeout is a typed error that keeps the journal. `forget` marks the service first, planners refuse to journal into it, and it deletes the entry only after reading it again under the catalog lock and finding nothing it did not handle.
- **`devflow init` proposes Valkey, Redis and MySQL services** — A compose service with a `valkey/valkey`, `redis` (also `docker.io/library/…`, Bitnami's, or a `valkey`/`redis` tag) or `mysql:8.4*` image becomes the item `service:<key>` for a `[services.<key>]` table with the right engine, in `--plan`, `--apply` (whose document now lists the configured `services`) and the desktop wizard. The compose image is used when devflow's profile can run it and devflow's default otherwise, with the reason in `risks`. The URL variable is the one the `.env*` files or compose services use (`REDIS_URL`, `VALKEY_URL`, `CACHE_URL`, `DATABASE_URL`/`MYSQL_URL`), following the postgres collision rules. Valkey and Redis are applied by default; MySQL is a preview, offered unticked. The planner names the risks it knows (AOF and persistence settings, init scripts, volumes, a cloned `.env` that keeps the variable), proposes nothing twice when the configuration has the service, and says apart what is *not proposed automatically* (modules, an unpinned MySQL tag, a second MySQL service, a compose profile) from what is *unsupported* (MySQL other than 8.4, Percona, a Redis cluster), pointing to the README for the manual configuration. The compose hooks now start only the services devflow does not branch.
- **Container services, release review: helper fences** — Cleanup no longer treats elapsed time as proof that a helper create is over. An attempt whose outcome is unknown (no id came back, no container has its name) is retired by a tombstone created under its exact name (from the helper image already present, never started, no mounts, labelled `dev.devflow.tombstone`), so a create the daemon delivers later fails with a name conflict and cannot pin or recreate a volume that was removed. If the tombstone itself meets the real helper, the real one is removed by its labels and the tombstone retried. Tombstones stay until `forget`, which removes them last; `reconcile` reports a newly fenced attempt. `DEVFLOW_TEST_HELPER_RECHECK_SECS` is gone.
- **Container services, release review: ordinary stops** — `devflow service down` (CLI and GUI) no longer bypasses the stop journal. Its stop is recorded in the branch's catalog record with its request time before it is issued and cleared when the client returns success; a stop that timed out or whose caller died is fenced by the next `up` or start of the branch exactly as recovery fences an operation's stop (stop by us, remove by the recorded id, confirm, recreate on the same volume, name, port and labels), so a late `docker stop` can no longer take down the container a later `up` started. A `down` that finds an unconfirmed one removes the container instead of stopping it twice.
- **`setup` locks before it looks, release review round 2** — A setup that found the receipt replaced between its first look and its locks (another setup gave the workspace a new identity under a `DEVFLOW_INSTANCE_ID`) checked the old identity's daemons before it held the process lock, so an `up` that recorded its start intent meanwhile could launch a daemon after the look and before the lock, and the replacement then orphaned it. It now tries the process lock first (a try, never a wait, because the receipt lock is already held and the lock order is process then receipt), gives up with `Busy` when an operation on the daemons holds it, reads the receipt again under both locks and only then asks pitchfork.
- **Helper sweeps are serialised per attempt, release review round 2** — Two reconciles that read the same attempt of unknown outcome could race: one removed the late helper and resolved the attempt, the other then found the name free, made a tombstone for it, and its catalog write succeeded although the attempt was gone, leaving a tombstone no record named and no cleanup removed (`forget` could do the same behind its own removal of the tombstones). Each attempt's inspect, removal, fence and catalog transition now run under a lock of its own (`locks::acquire_attempt`), `forget`'s removal of a tombstone and a recovery's removal of a helper included; the attempt is read again under the lock and acted on only as it is. A tombstone whose attempt is no longer listed is removed instead of recorded, and while `forget` has marked a service no other sweep makes a tombstone.
- **`forget` is exclusive per service, release review round 3** — Two `forget` calls of a service that held only a fenced helper took no overlapping locks and both counted as the forgetter: one removed the tombstone and released the attempt's lock, the other made it again and recorded it, and the first then deleted the entry (the fence was compared by the attempt's name), leaving a container no record named. A lock file per service (`locks::acquire_forget`) now covers a `forget` from before its marker is set until the entry is deleted or the marker cleared; a second one waits up to 30 seconds and then reports the service busy. The entry goes only while the catalog still names the very tombstone container that was removed (`FencedAttempt`, by container id).
- **Resolved helper attempts' lock files are removed by `forget`, release review round 3** — One lock file per helper attempt stayed in the catalog's lock directory for good. They are still never unlinked on release (a waiter could keep the old inode and a newcomer would lock a new file for the same attempt), but `forget`, once the entry is deleted and while it is still exclusive, removes the files of the service's attempts that are no longer listed (`locks::prune_attempts`, under the catalog lock). Attempt lock files are now named `<service>.attempt.<stem>.lock`, which cannot be mistaken for another service's (the keys `a` and `a-b` shared the prefix `a-attempt-`).
- **A Setup-tab form keeps the file it was opened on, release review round 3** — An automatic reload (window activation, the document syncing) that finished while a hook form was open replaced the tab's data, file hash included, under the form, which still pointed at a position: after an external edit inserted a hook before hook 0, Save sent the new hash and overwrote the inserted hook without a conflict. Each form now keeps the hash of the file and the command of the hook it was opened on, and Save sends that hash, so a changed file is a conflict. An automatic reload that completes while a form is open and finds the files changed keeps the data and shows the "changed on disk" notice. After an explicit Reload the form follows its hook (same command, at its position or its only other one) and is closed with a message when the hook is gone.
- **Setup-tab suggestions resolve the Compose selection, release review round 3** — The suggested hooks came from the unresolved proposal, whose compose start names only the services devflow never offers to branch. For a project with Compose `mysql:8.4` plus Elasticsearch and no configured MySQL, adding the suggestion started `search` only, and MySQL was neither branched nor started. The suggestions are now taken from the proposal resolved for that selection (the hooks accepted, no service item), so the compose start also starts a service that was not accepted, and a hook with nothing left to start is not offered.
- **The agent runner enforces the grace while the command is still running, release review round 3** — `examples/agent-task.sh` started its grace deadline only after the command's process had exited, so a command that ignored TERM kept the script inside a blocking `wait` for as long as it liked (reproduced with `AGENT_TASK_GRACE=0`). The script now polls for the command instead, starts the grace at the first INT or TERM it forwards, kills the whole group (KILL) when the grace is over and the command is still running, and then collects the command's real exit status (137 for a command killed that way) before the cleanup. Tests: a command that ignores TERM, with a zero grace (ended at once) and with a two-second grace (not before it).
- **The agent runner no longer cleans up over live descendants, release review round 3** — `AGENT_TASK_GRACE=08` passed the digits-only check but failed Bash's octal arithmetic, so the script reached the cleanup with the group still alive and returned the command's status; and after KILL the script slept 100 ms and carried on whether or not the group was gone. The grace is now validated and normalised as a bounded base-10 number (`10#`, 0 to 3600) before anything is created, and a value that is not one is refused with exit 1 instead of silently becoming 10. After KILL the script confirms the group is gone (up to five seconds). If it is not, the workspace is kept, stderr names it and the remaining PIDs, and the exit status is 70, distinct from the command's own (the message carries that one). Tests: `AGENT_TASK_GRACE=08` over a descendant that takes a second to die, invalid and extreme values, and a group that survives KILL (simulated with a `kill` function exported to bash).

### Changed

- **`[postgres]` is `[services.db]`** — The table moved under `[services]` with `engine = "postgres"`; its keys are unchanged. The old spelling fails with the new one. Receipts are version 2 (`services.<key>` replaces `data`, the `database` phase is `services`); a version 1 receipt is migrated in place by the next `setup` or `switch`, with no provisioning effect and no field lost (the environment and the hooks after it are redone by the next `setup`, which writes `COMPOSE_PROJECT_NAME` and the recipes), and a binding the configuration cannot place is kept as `unmapped` and reported. See [docs/MIGRATING.md](docs/MIGRATING.md).
- **`devflow init` proposes instead of templating** — It no longer writes a fixed starting file and refuses a second run: running it again in an initialized repository proposes only what is still missing. Without a terminal it needs `--plan`, `--apply PLAN.json` or `--yes` (it fails under `--json` and `--non-interactive` rather than guessing), and `--postgres` takes `none`. The `--json` document of a write reports `accepted`, `dropped`, `applied`, `manual`, `files`, `journal` and `next_steps`; `--json init --plan` is the proposal itself.
- **Configuration is TOML only** — `devflow.toml` (or `.devflow.toml`) plus a git-ignored `devflow.local.toml`. 0.x files stop with an error that links the migration guide.
- **Data and code origins** — `--from` (code) and `--data-from` (workspace, `snapshot:NAME[@vN]`, `branch:ID` or `empty`) are independent and immutable once chosen.
- **Removal** — `devflow remove` checks every protection before any effect, runs `teardown`, drops only branches this instance created, and deletes the Git branch only with `--delete-branch`.
- **One-time approvals are bound to what was reviewed** — A "Run once" or "Trust and run" answer is an `Approval` carrying the digest and version of the scope that was shown, not a boolean. Setup, switch hooks and teardown compare it with the scope of the workspace they act on after the payload exists, so `switch -c` onto an existing branch that holds other hooks, `[env]` or pitchfork files runs none of them on the review of the source workspace (the interactive CLI shows the new workspace's own scope and asks again; the GUI reports it and offers Set up). `doctor` judges the worktree it runs in and prints the directory. The GUI's badge, review dialog and approval use the per-workspace functions for the selected or target workspace.
- **Output** — One versioned JSON document per command; passwords are redacted except in `db url` and `db branch create`. `devflow --json trust` reports `scope` as `{version, hooks, env, processes, digest}` and the state as `nothing_to_approve`, `trusted` or `untrusted` (with `format_changed`).
- **Environment generation** — The generation of `.devflow/env` covers `[env]` and moved to `env.v2`: existing workspaces reopen `env` and `hooks` once to pick up `COMPOSE_PROJECT_NAME`.
- **Errors never quote values** — Errors about `devflow.toml`, `devflow.local.toml`, receipts, `admin.json`, init plans and connection strings name the file, the key path (`hooks.setup[2].timeout`, `env.AUTH`) or the line and column, and the rule broken. They no longer repeat a recipe, a hook command or name, a timeout, a scratch database name, an engine or a connection-string keyword, or any piece of one. A bare table key is named; other keys are not.
- **Native, synchronous core** — `devflow-core` has a blocking API (nothing async is public) and no GPUI types.
- **Releases** — Binaries ship `devflow` only; the desktop app is built from source. CI builds the GUI on macOS and runs the Docker database tests on Linux.
- **JSON masking keeps the structure of user-chosen keys** — A service called `tokens` or `password_store` used to turn `receipt.services.<key>` into the string `***`. Masking now keeps the shape of a document: an object under a secret-looking name stays an object and its own fields are judged one by one, and the maps keyed by names the user chose (`services`, `service_sources`, `service_source_ids`, `extras`, `snapshot_versions`, `phases`, `input_hashes`) are not judged by key at all. Credential fields, secret scalars and credentials inside strings are masked as before.
- **`examples/agent-task.sh` cleans up** — It ended with `exec devflow exec -- CMD`, which replaced the shell that owned the EXIT trap: a finished command left the worktree, data branches and containers behind whatever `KEEP` said. The script now stays the parent, waits for the command, exits with its status and forwards INT and TERM to it; `tests/agent_task.rs` covers cleanup after success and failure, `KEEP=1`, and both signals.
- **The LLM setup recipe no longer sets `DIRECT_URL` twice** — `AGENTS.md` told an agent to set `DIRECT_URL` by hand and then add the `prisma` preset, which owns `DIRECT_URL`; core refuses that combination. The recipe now reads `devflow --json env list` first and shows the recipe and the preset as alternatives.
- **Contract statements corrected** — `AGENTS.md` said every mise hook and daemon depends on `mise:env-file`; only code run through mise without `devflow exec` having the last word (a mise task, a bare `mise exec -- CMD`) does, and wrapped commands (`mise exec -- devflow exec -- CMD`, `run = "devflow exec -- CMD"`) need no wiring change. The list of commands that print a credential is now complete in `AGENTS.md`, `CLAUDE.md`, `SECURITY.md` and `docs/REMOTE.md`: `db url`, `db branch create`, `service [NAME] url` and `env list --show-values`.
- **`pg_database_size(current_database())` works in a branch** — GUI tools (pgAdmin, DBeaver, Prisma Studio) call it and got "permission denied for database": the session acts as the shared owner role, which held no `CONNECT`. The owner now has `CONNECT` on each branch's own database and scratch databases, and branch logins are `SET`-only members of the owner (`INHERIT FALSE`), so the connection check, made for the login, still lets a login reach its own databases only. Branches made earlier are converged by the next operation on the project (`devflow db reconcile`, or any create, reset or drop): logins stop inheriting first, then the owner is granted `CONNECT`. A session that does `SET ROLE NONE` no longer has the owner's rights, and can read a sibling database's size (never connect to it).
- **Counts in the singular** — The hooks phase says `1 command` (not `1 commands`), and the same fix applies to `1 variable`, `1 of 1 entry copied`, `1 item` in measurements and prompts, `1 more line` in the proposal diff, and `1 second` or `1 minute` in timeout errors; core has `text::counted` for them.
- **Daemons of container-only projects get the workspace environment** — `devflow init` wrapped pitchfork daemons in `devflow exec` and proposed `mise:env-file` only for a project with PostgreSQL or compose hooks, so a Redis-only, MySQL-only or Valkey-only project with a Vite dev script got an unwrapped `npm run dev` and no variables. The condition is now any managed service (PostgreSQL, Valkey, Redis, MySQL; configured or proposed) or `[env]` content.
- **Declining a proposed service keeps its Compose start** — `init` left a compose service out of the compose hooks as soon as it proposed `service:<key>` for it, so a MySQL left unticked, a rejected cache or a declined Valkey was started by nothing. The choice is now made at selection: the hooks start every compose service whose service item is not accepted, `init --apply` (`--accept`/`--reject`), `init --yes` and the desktop wizard get the same result because `apply` and `preview` render the hooks from the accepted ids (`Proposal::resolved`). The plan, its digest and its input hashes are unchanged, so nothing is reported as a stale plan. A project whose only datastore is a proposed service now lists the compose hooks as `medium` alternatives.
- **The trust review masks credential-named variables** — `devflow --json trust` serialised the `[env]` recipes through the generic JSON masker, whose key classifier misses `DB_PASS`, `SESSION_KEY` and `CREDENTIAL`, so `env set --local DB_PASS literal` was `***` in `env list` and the literal in the review (the desktop review masked formatted text and lost the name). The scope's review (`Scope::sections`, `Scope::review_json`) now uses the `env list` masker for `[env]` and for pitchfork `env` tables, in the terminal, JSON and the app; the scope that is hashed and approved is untouched. The generic JSON masker also judges keys shaped like variable names (`DB_PASS`) with the variable classifier and leaves a `${NAME}`-only value of such a key alone; ordinary field names (`key`, `session_key`) are unchanged.
- **The agent runner waits for the command's whole process group** — `examples/agent-task.sh` forwarded INT and TERM to the command's pid and waited for that one process, so a dev server or test worker the command started could outlive it and keep using the worktree and database while the cleanup deleted them. Signals now go to the group (`kill -s SIG -- -$pgid`), and the group has exited before the cleanup: processes left behind by a normal exit are stopped (TERM, then KILL after `AGENT_TASK_GRACE` seconds, default 10, with a message). Tests: a sleeping descendant after exit, after INT and TERM, and one that ignores TERM.
- **`[env] preset = "prisma"` is warned about** — A key one edit away from `presets` (`preset`, `presets_`, `Presets`) whose value names a known preset is a valid recipe that sets a variable of that name, which is what an LLM or a person who forgot the list syntax gets silently. `devflow env list` (a `warning:` line, and `warnings` in `--json`) and `devflow doctor` (an `env-presets` warning) now say `did you mean `presets = ["prisma"]`?`. Nothing is refused or rewritten.
- **The Setup tab follows edits made outside the app** — After `devflow env preset add prisma` from a terminal the tab still showed Prisma unchecked until its own Reload button was pressed, and ⌘R did not reload it. The global refresh and activating the window now compare the two configuration files with what the tab shows and read them again when they differ; with a form open or a save running the tab keeps its content and shows the "changed on disk" notice with Reload.
- **Help names MySQL** — `devflow --help` describes `service` as serving Valkey, Redis and MySQL (preview); comments and docs that said Valkey/Redis for what MySQL shares now include it.
- **Short ids everywhere** — Every branch id argument (`service NAME drop ID`, `db branch delete ID`, `--data-from branch:ID`, `--to branch:ID`) accepts what the listings show: a unique prefix of at least 8 hex characters, with or without dashes, resolved by core against the catalog or the metadata database. An unknown or ambiguous prefix is an error that names the candidates by the shortest ids that tell them apart; the receipt still records the whole id.
- **Valkey/Redis clones do not rewrite an unchanged source's dump** — A clone first reads `INFO persistence`; when the source has no change since its last save, no save running, a good last save and a `dump.rdb`, it reflinks that file instead of asking for a `BGSAVE`, so repeated clones no longer cost a dataset of new blocks each (the benchmark measured about +115 MiB per clone for 128 MiB). The record and the JSON output say `capture_last_save` and the capture time is the server's `rdb_last_save_time`. Any other state keeps the `BGSAVE` path.

### Known limitations

- **Platforms** — The desktop app is covered by headless tests on macOS 15+; native visual checks are manual. The Linux GUI is untested and unsupported. PostgreSQL 18 or later is required.
- **No TLS** — devflow's own database connections do not use TLS. Remote data hosts need a private network or a tunnel.
- **Copy-on-write depends on the filesystem** — Clones share blocks only on reflink-capable storage. External servers report `unknown` unless the operator declares the capability; sources in other tablespaces report `unknown`.
- **Container services** — Valkey, Redis and MySQL 8.4 (a preview; others are later), managed only; MySQL is InnoDB only (MEMORY tables are not supported and a source that has tables outside InnoDB is refused) and its source is unavailable while it is cloned, one machine per Docker daemon; servers with AOF on or ACL files are refused; containers start on `setup`, `switch` and `devflow service up` and do not restart by themselves; the password is on the container's command line (see SECURITY.md); reflink needs Docker volumes on btrfs or XFS with reflink (OrbStack), otherwise clones are full copies and reported as such.
- **Busy sources** — On a local managed server, cloning from a live workspace terminates the source database's sessions (open transactions are aborted). External and remote servers default to refusing instead.
- **Cloning contract** — Privileges or RLS policies that name a branch login are rejected; use the project owner role. Replication machinery is not cloned. Some cleanup blockers (prepared transactions, replication slots) need operator action.
- **Connections** — Multi-host URLs, `service=`, `sslpassword`, `ssl=`/`requiressl=` aliases and replication connections are refused.
- **Hooks** — Hooks run at least once and must tolerate retries. Trust covers the configured commands, not the scripts they invoke.
- **mise checks** — The check of what a hook receives reads the hook's command: a command hidden behind `xargs` or a variable, or one that reaches mise through a shim, is not seen, and a hook the check cannot stand for (`cd` ahead of mise, a mise task, `mise -C`) is only warned about; `devflow exec` is the way to be sure. A hook that goes through `devflow exec` inside mise is not checked for the variables at all. The probe is a `mise exec`, so it needs a mise that has it; `--no-deps` and `--fresh-env` are used where the installed mise knows them.
- **Replacing files without an atomic exchange** — `init --apply` is airtight against a concurrent save only where the filesystem has an atomic exchange (APFS, Linux filesystems with `RENAME_EXCHANGE`); elsewhere a narrow window between the last check and the rename remains.
- **pitchfork scope** — The trust scope reads the project directory's pitchfork files only. pitchfork's user and system configuration and the files of parent directories are the user's, and running pitchfork directly acts on whatever a worktree's configuration says, outside devflow's approval.
- **Redaction** — Credentials devflow knows are masked exactly in hook output and logs; other credentials are masked by pattern on a best-effort basis. Unencoded spaces in URL passwords, `.pgpass` lines, multi-line values that are not known credentials and non-PostgreSQL credential formats are not covered (see SECURITY.md).
- **Manual cleanup** — A failed worktree creation leaves its paths for you to inspect; an interrupted metadata bootstrap can leave an unmarked `devflow_bootstrap_*` database that devflow reports but never drops. Copied workspaces (VM forks) need `devflow setup --new-instance` or `DEVFLOW_INSTANCE_ID`.
- **Scope** — Git only; processes and the proxy come from pitchfork; no embedded terminal or tray; migration from 0.x is manual.
