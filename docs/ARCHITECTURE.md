# Architecture

devflow 1.0 creates Git worktrees, clones their payloads copy-on-write, branches PostgreSQL databases and Valkey, Redis and MySQL containers, and runs trusted setup hooks. Everything else (processes, the HTTPS proxy, toolchains, dependency installation) belongs to pitchfork and mise.

This page is the map. The design, schema and rationale are in [docs/plans/2026-10-10-devflow-1.0.md](plans/2026-10-10-devflow-1.0.md), the authoritative spec. Coming from 0.x? See [MIGRATING.md](MIGRATING.md).

## Crates

```
Cargo.toml              workspace + `devflow` CLI package (bin `devflow`)
src/                    CLI: clap parsing, JSON output, shell integration, prompts
crates/devflow-core/    all behavior; blocking API, nothing async public, no GPUI types
crates/devflow-gui/     GPUI desktop app (bin `devflow-gui`), gpui-kit pinned to =0.7.1
```

Dependencies point one way: `devflow` and `devflow-gui` depend on `devflow-core`; core depends on neither. Frontends build typed requests, call core, and render the result. The CLI calls core directly. The GUI calls it from `cx.background_spawn` and applies a result only if its request key (project and generation) still matches the selected project.

The GUI is split into `state` (selected project, request keys), `jobs` (background calls, typed failure kinds, masking), `ops` (calls into core), `model` (view rows), `activity` (progress panel), `settings` (editor, terminal, theme in `gui.toml`) and `views/` (pages and dialogs). The setup views: `onboarding` (the six-step wizard and the approval panel; each step is a core call on the background executor, `detect`/`propose`/`apply`/`trust`), `hooks_editor` (the Setup tab; every save is `config_edit::apply` with the hash of the file it read), `workspace_detail` (the pane under the Workspaces table, from the receipt) and `widgets` (cards, banners and chips drawn from theme tokens only).

The developer-experience views sit on the same split. `redaction` masks every view model once, when a call's result enters the app (credentials in daemon errors, process refusals, service rows; `RefusalView` carries core's code, text and hint). `services` holds the container services' view models and the `ServiceBackend` trait over core's `Service` (a fake backs the headless tests), read from the cache unless the user asks to measure. `ops_services` and `ops_pitchfork` are the jobs behind the buttons: each calls one core function (`up`, `down`, `setup::service_snapshot`, `service_reset`, `reconcile`, `workspace::forget`, `pitchfork::run_install`) and reports through the activity log. Gates are core's: `views/processes` derives Start, Stop, Restart and **Review and start…** from `processes::Gate`, and one function serves the Daemons tab, the workspace detail and the palette. The views: `data` (service cards) with `service_view` and `service_dialogs`, `overview`, `pitchfork_panel` (install and proxy cards shared by the wizard and the Daemons tab), `doctor` and `palette` (entries built from the same state).

## Principles

- **Data lifetime is independent of code lifetime.** A database branch has its own identity; a worktree or VM attaches to it. Code origin (`--from`) and data origin (`--data-from`) are separate and immutable once chosen.
- **Never infer ownership from names.** Branches, snapshots and roles are recorded in a metadata database on the server. Worktrees carry a receipt with their instance id. Generated database and role names are never derived from user input.
- **Resumable, not transactional.** Every multi-step operation records intent before its external effect and can be re-run to completion.
- **Report what actually happened.** CoW is `verified`, `copy` or `unknown`; it is never assumed.
- **Synchronous core.** Blocking API, no async runtime, no UI types.
- **No connection data on a command line.** `devflow db psql` parses the workspace URL like libpq does (`conn`), drops every connection variable inherited from the caller, and sets the workspace's `PG*` variables, password included, in psql's own environment (or the docker client's, forwarded into the container by name). argv is readable by every local user; a process's environment only by the same user and root, the audience of a 0600 file, and no temporary file has to be cleaned up. devflow then replaces itself with psql, so psql handles Ctrl-C and signals itself.

## The pipeline

`switch -c`, `setup` and `switch` to an existing workspace run the same five phases. The receipt is written as soon as the worktree exists; every later phase is recorded before and after its effect, and a re-run resumes at the first incomplete phase.

1. **materialize**: create the Git branch (or reuse an existing local branch of that name) and the worktree; write the receipt with a fresh instance id.
2. **payload**: clone each `worktree.copy` path from the source worktree. Paths stay inside both worktrees; entries are staged under a temporary name and renamed; existing destinations are left alone.
3. **services**: for each configured service (PostgreSQL, Valkey, Redis, MySQL), create or reconcile the data branch from `--data-from` and record its binding under `services.<key>`, saving the receipt after each service. A container service's binding names a catalog branch (id, URL with its password, the OrbStack container endpoint, owned flag, applied generation, how the data was cloned); its resolved data source is pinned per service before the branch is journaled, as a label in `receipt.service_sources` and as the catalog identity (branch or snapshot id) in `receipt.service_source_ids`, which a retry clones without looking the label up again; a source it lacks fails that service. Its container is started (and health-checked) here and again by every `switch`. A service with no binding, or bound under another generation of its section, is (re)applied; for a branch the workspace owns, that includes provisioning the scratch databases (`extra_databases`) the configuration now names and updating the binding's `extras`.
4. **env**: write the worktree's `pitchfork.local.toml` when the project uses pitchfork (identity only, no approval needed), then write `.devflow/env`: the generated variables (`DATABASE_URL`, `PG*`, `<NAME>_DATABASE_URL` for each scratch database of the binding, `DEVFLOW_*`, `COMPOSE_PROJECT_NAME`) and, for an approved scope, the rendered `[env]` recipes and presets. Without approval only the generated ones are written and the phase is a required skip.
5. **hooks**: if the scope is trusted, run `setup` commands (named, each with its timeout); otherwise prompt (interactive) or skip and mark `needs_attention`.

Status is derived from the phases: `ready` when every phase is done or skipped on request (`--no-db`, `--no-hooks`), `needs_attention` (a required phase was skipped or failed) or `in_progress` (another process holds the receipt lock, or a crash left a phase started). `list`, `switch` to a ready workspace and `remove --keep-data` do not contact the PostgreSQL server, so they work while it is unreachable; `db status` reports it unreachable. `remove` checks all protections before any effect, runs `teardown`, drops the data branch if this instance created it, then removes the worktree.

**Configuration generations.** Every binding records the generation of its service section (the SHA-256 of its canonical serialization; credentials in `admin_url` are masked first), and the receipt records the generation of the environment `.devflow/env` was written under. When the current configuration adds a service, changes a service's section or changes what the environment exports, the workspace reads as `needs_attention`: `services` (for the services concerned), `env` and `hooks` are reopened as required skips, in memory for `list` and on disk by the next `setup` or `switch`. Skips someone asked for (`--no-db`, `--no-hooks`) are kept, and removing a service from the configuration never deletes its binding or its data. `setup --if-new` and `switch` compare generations before treating a workspace as ready.

**Receipt versions.** Version 2 keeps one binding per service under `services.<key>` and renames the `database` phase to `services`. A version 1 receipt is migrated in place, under the receipt lock, by the next flow that holds the lock and the configuration; readers migrate in memory. Nothing is provisioned: every field is kept, `data` moves to the project's sole PostgreSQL service, or to `unmapped` when there is none (reported by `setup` and `doctor`, never exported or guessed).

Worktrees created by other tools are adopted through a `post-checkout` hook that runs `devflow setup --if-new --from-git-hook`: it skips a worktree whose receipt is `ready`, resumes any other, never prompts, and always exits 0.

**Processes.** `up`, `down`, `ps`, `[pitchfork] autostart` and `remove` go through `processes`, never straight to pitchfork. A start needs a pitchfork that runs with every feature devflow calls, a `ready` receipt (and no setup holding the lock), the scope of that worktree approved (`trust::state_at`, or the `Approval` of exactly that scope that the caller reviewed) and no daemon among those about to start that also starts on its own (`cron`, `watch`, `boot_start`, `auto`); naming a plain daemon starts it and what it depends on, which must be daemons of the same workspace. The namespace in the worktree's files must be the one in its receipt, or nothing is attributed, started or stopped. A stop needs the same approval because pitchfork runs lifecycle hooks from the current file. Both name the full `namespace/name` ids (never `--local`) and run pitchfork in the worktree with a deadline, after a last look at the files right before the effect, then read `list --json` and `proxy status --json` back: the report says what pitchfork reports, not what was asked. Process state never feeds back into the receipt or the exit code of `setup` and `switch`. `remove` stops the namespace's running daemons before teardown, as part of its protections: it fails before any effect if they must run `on_stop` hooks from a configuration that no longer matches the approval, if their state cannot be read, or if the stop cannot be seen to work (pitchfork failed, or the state afterwards is unreadable or shows a daemon still active), unless forced; the files are read again right before the stop is carried out. devflow never writes an environment or a credential into a pitchfork file and never runs `pitchfork proxy setup`.

## Role model

One PostgreSQL server per project. Verified on PostgreSQL 18.6 with a non-superuser provisioner.

| Role | Attributes | Holds |
| --- | --- | --- |
| Admin (provisioner) | Superuser (managed) or `CREATEDB CREATEROLE` login (external) | Owns every devflow database and the metadata database. Never given to sandboxes. |
| Project owner `dfo_<project8>` | `NOLOGIN` | Owns every object in every branch and snapshot database of the project; `CREATE, TEMPORARY, CONNECT` on each branch and scratch database (not on snapshots) |
| Branch login `dfl_<id12>` | `LOGIN`, random password, member of the owner with `SET` but not `INHERIT`, default `role` set to the owner | `CONNECT` on its own databases only |

Because the objects of all branches share one owner, clones need no ownership translation, and the owner role is the supported identity for anything that must survive cloning (default privileges, RLS policies, grants). The login does not inherit the owner, so a session that does `SET ROLE NONE` has no right to create in the owner's schemas; login-owned objects only exist in branches made by an earlier build (where the login inherited), and cloning or snapshotting reassigns them to the owner. Privileges or policies that name the login are rejected rather than translated.

Sessions run as the owner, so functions that check `CONNECT` on the current database for the current user, such as `pg_database_size(current_database())` (pgAdmin, DBeaver and Prisma Studio call it), need the owner to hold it: it does, on the branch's own databases. Granting the shared owner `CONNECT` is safe only because no login inherits the owner: `CONNECT` is checked for the login at connection time, before `SET role`, so each login still reaches its own databases only. Each mutation (and `devflow db reconcile`) first makes every branch login of the project non-inheriting, then grants the owner `CONNECT` where a branch made by an earlier build lacks it. The one visible side effect: a session can read the size of a sibling's database, not connect to it.

**Scratch databases** (`[services.<pg>] extra_databases = ["test", "shadow"]`) keep this model: the login stays `NOCREATEDB`, so tools that want a test or shadow database are given one instead of creating it. Each branch has, per configured name, a recorded database in the `scratch_databases` table (own id, the branch's id, the configured label, the generated name `df_<project8>_<branch12>_<n>` with a per-branch counter that is never reused, a status and the branch generation it was last emptied for). It is created empty from `template0` by the same protocol as a branch's own database, owned by the admin, with the owner role holding `CREATE, TEMPORARY` and the branch's login alone holding `CONNECT`. Because the login is the branch's, credential rotation covers them. They are separate databases, so a clone or snapshot never contains them: a new branch, whatever its source, gets empty ones. A reset empties each again in its cleanup phase, after the new data is in place; the label is configuration, the identity is the row.

Every new database is created closed (`ALLOW_CONNECTIONS false`) and opened only after its ACLs are normalized. The `devflow` metadata database is closed the same way, so branch logins cannot reach it; managed mode also revokes `PUBLIC` `CONNECT` on `postgres` and `template1`. On an external server devflow changes only databases it created. Snapshots are not templates; only the admin can clone them.

## Recovery model

- Every branch operation holds a session-level advisory lock on the project id and records each step on the branch row before performing it. If the lock connection dies, the operation stops and leaves the row.
- The next mutation of the project, or `devflow db reconcile`, completes or rolls back rows in `creating` or `deleting` and resets with an `op`, by inspecting `pg_database` and `pg_roles`. A reset in `staging` drops its replacement; one in `cutover` whose rename did not commit reopens the original; one in `cleanup` drops the backup. Any other combination is left alone and reported.
- Scratch databases are journaled on their own rows (`creating` before the build, `deleting` before the drop) and follow their branch. A new branch is `ready` only with all the scratch databases configured when it was created, so an interrupted creation is rolled back whole. A reset empties them in its `cleanup` phase and records on each the branch generation it was emptied for, so a repeat after a crash empties only the ones not done (never what the user wrote after the reset). A `creating` row of a ready branch is built again when its name is still configured and dropped when it is not; a `deleting` row is dropped; a branch drop removes its rows (orphans included) before its own database and login. A name that leaves the configuration is an orphan: kept, not exported, untouched by resets, reported by `reconcile` and `doctor`, dropped only by `db reconcile --drop-orphans`. A name that joins it is provisioned for existing branches by the next `setup` or `switch` (`Server::ensure_scratch`).
- A crash between creating a branch and saving the receipt is repaired by instance id: the retry finds the branch and sets a new password, since the old one was never delivered. Roles that cannot be dropped are made `NOLOGIN` and recorded in `retired_roles`; `reconcile` retries them. Prepared transactions and replication slots that block `DROP DATABASE … WITH (FORCE)` are reported, not forced.
- Container services record every operation in the catalog's journal before its first effect (destination ids and names, the port candidates, the credentials, whether a full copy is allowed, the deadline) and every step before it is taken. A clone, snapshot or reset is run by one coordinator process that takes the source's and destination's locks itself and holds them to the end; the recorded sequences are clone `planned → quiescing → quiesced → copying → copied → starting → done`, snapshot the same without `starting`, and reset `… → copied → staging → cutover → cleanup → done`. If the coordinator dies, its flocks vanish while a copy helper may live on in the Docker VM, so the next operation on either resource, or `devflow service reconcile`, finds an unfinished entry with free locks and recovers it: before a copy is proven complete (`copied`), and for a reset before its cutover is committed (the catalog moves to the new pair in the same write that enters `cleanup`), it kills the recorded helper, confirms it is gone, removes what the entry created by recorded identity (labels must agree) and marks the destination `aborted`, never promoted, restarting the original container if a cutover had stopped it (a stop whose return was never seen is fenced: the container is stopped, removed by its recorded id and recreated on the same volume, name and port, so a late `docker stop` names a container that is gone), and sweeping the list of helper attempts that outlives every operation; from `copied` a clone is finished by starting it again, and removals (`drop`, snapshot delete, a reset's cleanup) are always finished. An entry with no coordinator yet is given two minutes before it counts as abandoned. A copy past its deadline is the same abort, done by the coordinator.
- Worktree setup is resumable from the receipt. Hooks run at least once: a crash after a command succeeds but before the receipt update reruns it, so hook commands must be idempotent.
- A VM fork copies the receipt. `devflow setup --new-instance` gives it a fresh identity and a new branch. Only the instance that created a branch may reset or drop it; `--database-url` attachments are detach-only. For container services the fork's new branches are cloned from the branches the copy knew (or `--data-from`).
