# Architecture

devflow 1.0 creates Git worktrees, clones their payloads copy-on-write, branches PostgreSQL databases and Valkey, Redis and MySQL containers, and runs trusted setup hooks. Everything else (processes, the HTTPS proxy, toolchains, dependency installation) belongs to pitchfork and mise.

This page is the map. The design, schema and rationale are in [docs/plans/2026-10-10-devflow-1.0.md](plans/2026-10-10-devflow-1.0.md), the authoritative spec. Coming from 0.x? See [MIGRATING.md](MIGRATING.md).

## Crates

```
Cargo.toml              workspace + `devflow` CLI package (bin `devflow`)
src/                    CLI: clap parsing, JSON output, shell integration, prompts
crates/devflow-core/    all behavior; blocking API, nothing async public, no GPUI types
crates/devflow-gui/     GPUI desktop app (bin `devflow-gui`), gpui-kit pinned to =0.7.1
```

Dependencies point one way: `devflow` and `devflow-gui` depend on `devflow-core`; core depends on neither. Frontends build typed requests, call core, and render the result. The CLI calls core directly. The GUI calls it from `cx.background_spawn` and applies a result only if its request key (project and generation) still matches the selected project.

The GUI is split into `state` (selected project, request keys), `jobs` (background calls, typed failure kinds, masking), `ops` (calls into core), `model` (view rows), `activity` (progress panel), `settings` (theme and the menu bar setting in `gui.toml`; the editor and terminal commands live in core's `settings.toml`, which the app moves out of an older `gui.toml` the first time it starts) and `views/` (pages and dialogs). The setup views: `onboarding` (the six-step wizard and the approval panel; each step is a core call on the background executor, `detect`/`propose`/`apply`/`trust`), `hooks_editor` (the Setup tab; every save is `config_edit::apply` with the hash of the file it read), `workspace_detail` (the pane under the Workspaces table, from the receipt) and `widgets` (cards, banners and chips drawn from theme tokens only).

The developer-experience views sit on the same split. `redaction` masks every view model once, when a call's result enters the app (credentials in daemon errors, process refusals, service rows; `RefusalView` carries core's code, text and hint). `services` holds the container services' view models and the `ServiceBackend` trait over core's `Service` (a fake backs the headless tests), read from the cache unless the user asks to measure. `ops_services` and `ops_pitchfork` are the jobs behind the buttons: each calls one core function (`up`, `down`, `setup::service_snapshot`, `service_reset`, `reconcile`, `workspace::forget`, `pitchfork::run_install`) and reports through the activity log. Gates are core's: `views/processes` derives Start, Stop, Restart and **Review and start…** from `processes::Gate`, and one function serves the Daemons tab, the workspace detail and the palette. The views: `data` (service cards) with `service_view` and `service_dialogs`, `overview`, `pitchfork_panel` (install and proxy cards shared by the wizard and the Daemons tab), `doctor` and `palette` (entries built from the same state).

## Core modules (`crates/devflow-core/src`)

| Module | Responsibility |
| --- | --- |
| `config` | `devflow.toml` schema (`[services.<key>]` selected by `engine`: `postgres`, or the managed-only `valkey`, `redis` and `mysql` with `image`, `env` and `require_cow` (`mysql` also has `database`, and exports `MYSQL_HOST`, `MYSQL_PORT`, `MYSQL_USER`, `MYSQL_PASSWORD` and `MYSQL_DATABASE` beside its URL, which is `DATABASE_URL`, or `MYSQL_URL` beside a postgres service; at most one); the postgres service's validated `extra_databases` names and its clone settings (`on_busy_source` = `disconnect`, `fail` or `wait` with `busy_wait`; `wal_log_below`); the optional `[data]` section (`noninteractive_from`, `noninteractive_max_age`, `noninteractive_fallback`: seed snapshot for runs that cannot prompt, validated, part of no generation because a data source is immutable once chosen); services exporting one variable are an error naming both, `[hooks]` entries as strings or `{name, run, timeout}` tables, `[env]` recipes and presets with their validation), merge with `devflow.local.toml` (each file's shape is checked before the merge), raw-text editing with concurrent-edit detection, detection of 0.x files by shape, configuration generations (SHA-256 per service section and of the environment, `[env]` included) |
| `config_edit` | Typed, format-preserving edits of `devflow.toml` or `devflow.local.toml` (`toml_edit`): add, update, remove and move hooks, the `[hooks]` timeout, `[env]` recipes and presets. Every edit is validated by parsing the merged result before the write, refused when the file's content hash differs from the one the caller read, at the write itself too through `fsutil::replace_if_unchanged` (`ConfigChanged`, naming a kept `.devflow-conflict-*` file), reports an override by the local file instead of hiding it, refuses credentials in the committed file, and names key paths only. Its views are masked in core by variable name and by text (`masked_template`, `masked_value`); the real text is behind `reveal()`. Also the read-only views frontends render (`ConfigFiles::hooks`, `::env`, the `[env]` preview in a workspace). `config_edit::migrate` rewrites an earlier build's top-level `[postgres]` table as `[services.db]` (`plan` previews it as a diff, `apply` writes it); the key is `db` because the server, its databases and receipts are identified by the project id, never by the service key |
| `conn` | libpq-compatible parsing of connection URLs and conninfo strings; the `PG*` variables for a connection and the ones to clear |
| `error` | Typed errors frontends act on: `NotInitialized`, `Busy`, `Protected`, `PartialRemoval` (a removal that failed after its first effect: what was done, what remains, whether `--force` goes on), `ConfigChanged`, `ConfigShape` (a configuration shape devflow refuses: an earlier build's `[postgres]`, 0.x keys). A message says what is wrong and never contains a command |
| `remedy` | What a person can do about a problem, as data: the `Remedy` enum (`Retry`, `ForgetProject`, `LocateProject`, `MigrateConfig`, `Init`, `OpenFile`, `Reveal`, `OpenGuide`, `CleanUp`; more are added here, never in a frontend), each with a plain `label()` (the desktop app's button), a `command()` (the CLI line, for the CLI and JSON only), `hint()` and `destructive()`; the typed `Problem` error that carries remedies; `remedies_of(&anyhow::Error)`, which also knows the typed errors above. The CLI prints remedies as `hint:` lines and puts them in the JSON error envelope; the desktop app draws them as buttons that call the core function behind each one. Neither keeps a list of fixes of its own |
| `health` | Classifies a registry entry from the disk without side effects: ok, folder missing, not a Git checkout, not initialized, earlier-build `[postgres]` (auto-fixable), 0.x configuration, invalid configuration, or another project in the folder. A `ProjectProblem` carries its message and `Remedy` values |
| `project` | Project discovery: the main checkout, its configuration and the Git common directory |
| `registry` | Machine-local list of known projects for the GUI and `devflow list --all` (`projects.toml`); `remove`, `prune_missing` and `relocate` (the folder must hold that project's id) change only the list, never the project or its data |
| `worktree` | Create, list, protect and remove Git worktrees (`git2`); `merge_evidence` (advisory, shared with `wide`: merged into the default branch's upstream, looks squash-merged, not merged, unknown); `find` matches a branch, Git's worktree name, the name the workspace was created under (its receipt's, so a checkout moved to another branch is still found by its workspace) and a path, and returns the workspace under that name; `create_with` decides where a new branch starts before anything is created: `--base` (any commit-ish, resolved once; `origin/x` for `x` tracks it), else the HEAD of `--from`, else the one `refs/remotes/<remote>/<name>` (several: `checkout.defaultRemote`, else a typed ambiguity error with `Remedy::ChooseBase`; never fetches) with `branch.<name>.remote` and `.merge` set as `git worktree add` does (`.merge` is the remote's own name for the branch, found by reversing the remote's fetch refspec; when it cannot be derived no upstream is set, with a warning), else the default workspace's HEAD; it reports the choice as `BranchOrigin`, refuses what libgit2 cannot check out faithfully (`worktree::faithful`: Git LFS, partial clones; a sparse checkout is a warning) and turns libgit2's ref and directory conflicts into plain errors that name the other branch or workspace; `worktree::prune` lists the registrations whose directory is gone (`prune_candidates`) and forgets only the confirmed ones, rechecked under the workspace's locks: a registration that owns data, is busy, has an unreadable receipt or lost its folder too (a disconnected drive) is kept |
| `ports` | The app port (`DEVFLOW_PORT`): `ensure` gives a workspace one port, once, from `[worktree] port_range` (default 40000–49999) under a machine-wide lock in the data directory, skipping ports the ledger gives to other workspaces and ports something listens on, journaled in the receipt (`pending_app_port`) before the reservation and then kept (a kept port is never moved; a conflict is a warning); `CONDUCTOR_PORT` is used where Conductor made the workspace; `release` on removal. The lock is the innermost, taken inside the workspace's process and receipt locks. The env phase calls it, and a ready workspace without a port is repaired by an env phase that runs no hook (only where the recipes are approved) |
| `settings` | `settings.toml` in the config directory: the editor and terminal commands shared by `devflow open` and the app, `adopt` (fill what is missing from an older place, never replacing a value), and the command-line splitting (`{path}` substitution) |
| `wide` | `list --wide`: dirty state, distance from the default branch's upstream, advisory merge evidence (ancestor, same tree, looks squash-merged from patch ids), last activity, port, container state (Docker, one bounded call per container) and daemons (one pitchfork snapshot) |
| `cow` | Clone files and directories: APFS `clonefile` (which keeps the times of files and links, so only directories get theirs back, in a parallel walk), Linux `FICLONE`, copy fallback; payload staging, path validation and an atomic no-replace install (`renamex_np` with `RENAME_EXCL`, `renameat2` with `RENAME_NOREPLACE`, check-then-rename elsewhere); `measure` reports a path's apparent and allocated size (shared blocks counted in full, so an upper bound) |
| `receipt` | Per-worktree receipt (version 2): instance id, one binding per service with the generation it was applied under (a PostgreSQL binding also lists its scratch databases, `extras`: name to database, no credentials; a container binding names a catalog branch, its URL, container endpoint and clone report), the data source each container service pinned (`service_sources`), the pitchfork daemons devflow started and has not seen stop (`processes`, which tells a supervisor that is down from "nothing runs"), phase states with when each attempt began, how each payload path was written, when the workspace was last entered (`last_active_at`), in-place migration of version 1, receipt lock `Receipt::save` writes the workspace's record in the ledger (`ledger`) first, so the receipt is never ahead of it |
| `ledger` | The workspace ledger: one record per workspace instance in the repository's common Git directory (`<common git dir>/devflow/workspaces/<instance id>.json`, 0600, versioned, written atomically, no credentials, one lock per record) that Git cannot take away. It names the instance, the project, the checkout it was written for (main checkout and common directory), the workspace name at creation, the worktree and Git's administrative id for it (and the directory's identity, branch and commit), the owned resources by identity (database and container branches per service key, a pending one included with the engine it was begun on; the pitchfork namespace and the daemon ids devflow started and has not seen stop, with a flag when a forced removal could not show that nothing runs under the namespace, and the ids it found running added; branches the person kept with `--keep-data` are remembered as disowned so a resumed removal and a later receipt write do not take them back) and the app port (given back to the machine's port ledger by a removal, as `remove` does) and a removal journal. `Receipt::save` is the one writer: it writes the record first, under the receipt lock its callers hold, and fails before provisioning when the Git directory it would write into is gone or is not a worktree's administrative directory (it never recreates a removed one), and the record only grows while the receipt changes (daemons mirror `processes`, except while the namespace is in doubt: then they leave only through a listing that was read). It shrinks when a removal accounts for a resource: dropped, found to belong to another instance, or found not to exist. Lock order: process lock, receipt lock, then the record's own lock (a removal of a workspace with no receipt holds a removal lock instead). A `remove` journals each effect before it happens and keeps the record (`removing`) when it could not account for something; an identity replaced on purpose (`setup --new-instance`) forgets the old record |
| `gc` | `devflow gc`: `inventory` classifies every record and registered worktree (`active`, `moved`, `missing`, `removed elsewhere`, `unknown`; anything not positively identified is `unknown` and never removable: an unreadable record or receipt, a record written for a copy of the repository (a record moves to the checkout it is found at only when the old checkout is gone and the repository's directory identity, inode and birth time, is the one it was written for), a missing parent directory, a server or Docker daemon that cannot be asked about a branch it names), measures what it can (database size, container state and memory) and attaches advisory merge evidence (`worktree::merge_evidence`, a thin layer over `wide`'s: the same ancestry, same-tree and patch-id checks against the same base, for the branch while it exists and else the commit the record last saw). It writes only the records older workspaces lack. `remove` takes the instances named with the generation they were shown, reads each again, snapshots each branch first if asked (a branch recorded before its creation finished too, when the backend has it ready; what cannot be snapshotted stops the removal), asks pitchfork what runs under the recorded namespace (from an empty directory, a query: devflow never stops the daemons of a workspace with no checkout, because pitchfork would run their lifecycle hooks from a configuration nobody approved; the record stops listing them only after a listing shows none running, and a forced removal leaves them on the record), and drops branches with the backends' journaled operations, each looked for in the backend its record names (the inventory and the removal share `BranchRef::lookup_engine`) and checked again under the backend's lock for its owner and for the generation and volume that were shown, since a reset keeps the id and the owner. A `missing` workspace goes through the ordinary removal, told its directory was gone (`ExpectedWorkspace::missing`, looked at again live): the revalidation and the snapshots run as its `before_effects` step under the process and receipt locks, and a checkout that came back is not removed. `summary` is the files-only version `list` and `doctor` use |
| `setup` | The idempotent pipeline shared by `switch` and `setup`; status computation. `setup::activate` and `setup::create_and_activate` (module `setup/activate.rs`) are the one entry the command line and the app use to enter a workspace: setup or resume, repair, endpoint refresh, container services, `switch` hooks, autostart, with their report on `SetupOutcome` (`switch_hooks`, `services_state`, `repaired`, `drift`, `first_setup`) |
| `hooks` | Run `setup`/`switch`/`teardown` commands with `sh -c`, the workspace's `ChildEnv` (see `env_owner`), per-command timeouts, names, process groups and masked logs (known secrets included) |
| `redact` | Credential masking for output and logs: exact match for known secrets, patterns for the rest |
| `scope` | The trust scope (version 2): hooks with names and timeouts, `[env]` templates and presets, the pitchfork processes; its canonical-JSON digest and the review sections frontends render |
| `pitchfork_scope` | Reads `pitchfork.toml`, `.config/pitchfork.toml` and their `.local.toml` overlays read-only (parsed up to 1 MiB, hashed whole up to 256 MiB, every path component checked for links), keeps every daemon field, finds the autonomous triggers (`cron`, `watch`, `boot_start`, `auto`) |
| `trust` | Approvals of the scope per project checkout (`trust.toml`, each entry with its scope version; version 1 entries never apply), and `Approval`/`Verdict`: a one-time answer bound to the digest that was reviewed, compared with the scope of the workspace an operation acts on |
| `detect` | Read-only repository scan that reports facts (package managers, frameworks, migration tools, compose services, `.env*` variable names, dev processes, ignored directories, existing devflow, pitchfork and mise files). It makes no decisions, runs no project code and never returns a secret |
| `propose` | `plan` turns the facts and the configuration that exists into a `Proposal`: items with stable ids, confidence, evidence, risks, dependencies, conflicts and structured additive patches (`toml_edit`, so formatting and comments survive; a differing existing key is a conflict, never an overwrite). Commands it builds go through `devflow exec`. Compose services with a Valkey, Redis or MySQL 8.4 image become `service:<key>` items (`propose::containers`); the compose hooks start what devflow does not branch, and a proposed service that is declined: `Proposal::resolved` renders them from the accepted ids (`value.compose` holds what it needs), which `apply` and `preview` use, so branching or compose is decided at selection and never makes the plan stale. `apply` validates the accepted items, compares the inputs' SHA-256 (every mise configuration layer included, with a marker for their set) with the plan's, journals the intended before and after hashes (`<git common dir>/devflow/init-apply.json`, 0600) and writes atomically; a retry continues. It writes configuration only: nothing is installed, trusted or run |
| `githook` | Install and uninstall the `post-checkout` hook; a hook somebody else wrote is never edited, moved or wrapped (typed `ForeignHook` refusal; `HOOK_LINE`, the one line devflow's own hook is made of, is what the CLI prints and the app copies); `uninstall` removes only devflow's own hook (and renames back the original of a wrapper an unreleased build installed); `--if-new` detection; `spawn_background` starts the setup detached (own process group, Git's variables removed, output appended to `devflow/logs/git-hook.log`) for `[integrations] git_hook = "background"`; `relative_hooks_path` finds a relative `core.hooksPath` that a new worktree lacks (husky) |
| `diag` | Value-free diagnostics: configuration, receipt, `admin.json` and plan errors name the file, the key path and the rule broken and never quote a value (a deserializer's message is classified, not shown; key paths come from `serde_path_to_error`) |
| `env_file` | Write and read `.devflow/env` (with the versioned manifest of owned names: `# devflow-owns v1:` and `# devflow-formerly v1:`; a file without it needs to be written again); keeps `.devflow/` self-ignored; renders `[env]` recipes (`${NAME}`, one pass) and presets, classifying values built from credentials as secret. `env_file::mise` asks mise, bounded and naming keys only: `check_mise_delivery` runs `mise env --json` (what mise resolves on its own: shells, editors, daemons with `mise = true`), `check_command_env` runs `mise exec -- sh -c …` with exactly the environment a hook gets and reads back every owned name from the process (a set variable overridden or removed, an owned name without a value reintroduced); this is the one gate for hooks of every phase (`setup::mise_gate`) and for daemons started with `mise = true`, after `check_mise_trust` (`mise env`, which refuses an untrusted configuration and trusts nothing, unlike `mise exec`). `env_file::commands` reads a hook's command: where it runs mise, whether `devflow exec` runs inside it, and why a check at the worktree root cannot stand for it (`cd`, a mise task, `-C`). `setup` runs the checks before the first hook, `doctor` on demand |
| `env_owner` | Whose variables a child process gets, one function for hooks (every phase), `devflow exec` and the mise checks. Owned names are the target set (`declared_names`: identity, each service's connection variables, the `[env]` recipes and presets, bound or not, and the former names the receipt remembers; `.devflow/env` records them as `# devflow-owns v1:` and `# devflow-formerly v1:`, and a file without the manifest is refused, never guessed at) plus the source set (every name, and every former name, in the `.devflow/env` of the workspace the inherited `DEVFLOW_WORKSPACE_PATH` names, only when that file is reached without a symlink in any component of its path (checked from `/` down, then opened `O_NOFOLLOW`) and records the inherited `DEVFLOW_WORKSPACE_ID`; `previous_names` reads the file setup is about to replace the same way, to seed the receipt's history first). `lacks_manifest` (`env_file::lacks_manifest`, `Contents::lacks_manifest`) is the one predicate for a file that needs to be written again. A workspace the environment names and that cannot be resolved is `Stale`: nothing runs (remedy `clear_inherited`) unless `DEVFLOW_CLEAR_INHERITED` or `--clear-inherited` says to go on, which also clears `generatable_names`. `ChildEnv::apply` removes the owned names from the inherited environment, then sets the workspace's variables; `ChildEnv::absent` lists the owned names without a value, which the mise gate checks stay absent. Execution controls (`DEVFLOW_SETUP_ACTIVE`, `DEVFLOW_PHASE`, … every non-identity `DEVFLOW_*`) and process names (`PATH`, `HOME`, …) are never removed; `DEVFLOW_INHERIT` and `--inherit` keep named names. Also `leaks` (the `doctor` isolation comparison) and `dotenv_conflicts` (copied dotenv files that set an owned name to another value; names only) |
| `integrate` | Agent-host integrations (`devflow integrate`): one editor per host over the one file it reads (`t3.json`, `.claude/settings.json`, `.conductor/settings.toml`, `.cursor/worktrees.json`), additive and conflict-reporting (`Change`: the file before and after, `Conflict`s that name an entry and never quote it, the line to add by hand, typed `Note`s), read and written through `integrate::confined`: the checkout is opened once and every directory on the way from its parent (cap-std), each component `lstat`ed before and after the open, a link refused anywhere at plan and at apply, the new file installed in the verified directory (hard link or rename) only if the file is unchanged since planning. JSON goes through `integrate::json`, an order- and number-preserving tree (`serde_json::Value` sorts keys); TOML through `toml_edit`. `integrate::claude` is Claude Code's `WorktreeCreate`/`WorktreeRemove` contract: `claude_create` makes or re-enters workspace `worktree-NAME` non-interactively and fails unless it is ready, `claude_remove` removes without force and keeps the branch, `StdoutGuard` points descriptor 1 at standard error so the path is the only line on standard output. `detect` reads the markers (`t3.json`, `.conductor/`, `conductor.json`, `.cursor/`, `.claude/`) and how each host stands. Each host's contract is quoted next to the code that depends on it |
| `wait` | `devflow wait`, `setup --wait`, `exec --wait`: poll the workspace's setup lock with one non-blocking attempt per look (released at once, so a waiter never holds up the run it waits for), read the receipt when it is free, end at the deadline with `ready`, `needs_attention`, `still_running` or `not_set_up` (a grace of 3 s for a run that is about to start). A devflow started by a hook looks once |
| `worktreeinclude` | `.worktreeinclude` (gitignore syntax) from the source checkout, else the main one: what Git reports as ignored in the source checkout (`statuses` with ignored files, directories collapsed) and a pattern matches, an ignored directory looked inside only when a pattern names it, bounded; merged after `[worktree] copy` and cloned by `cow` |
| `exec` | `devflow exec`: walk up to the worktree root (the nearest `.git`), read its `.devflow/env`, take the names the workspace owns out of the inherited environment and set the file's values on top (`env_owner::ChildEnv`), and replace the process with the command (Unix `exec`); `--inherit` keeps named caller values; never starts the command without the file, with a file written by an earlier devflow (no manifest), or with an environment that names a workspace that cannot be resolved. No project scan, no registry, no server |
| `db::admin` | Admin connection, version check (>= 18), generated names, SQL quoting, session advisory lock |
| `db::meta` | `devflow` metadata database: bootstrap, schema migration (version 4: scratch databases, the reset journal, `clone_strategy`), projects, branches, snapshots, scratch databases, retired roles |
| `db::steps` | Single DDL steps on the lock session: owner and login roles, closed creation and cloning (`STRATEGY FILE_COPY` or `WAL_LOG`), ACL normalization, grants, opening, busy-source sessions (named by application, role, address and state, never query; `fail`, `disconnect`, `wait`), drop and the reset swap |
| `db::managed` | Managed server: `compose.yaml`, `docker compose` lifecycle, the host port allocated once and kept in `admin.json`, OrbStack container name, CoW probe |
| `db::ops` | Branch operations: create, clone, snapshot, reset, drop, credential rotation, `ensure_scratch`, `drop_orphans` |
| `db::scratch` | The scratch databases of a branch (`extra_databases`): provision, empty again on reset, drop with the branch, recover, report and drop orphans |
| `db::reconcile` | Crash recovery: completes or rolls back interrupted creates, deletes, resets and scratch builds |
| `services::catalog` | The container services' authority: a versioned, locked, atomically written JSON catalog per project (`services/<project id>.json`, 0600) bound to the Docker daemon id, with branches (owner instance, container id and name, volume, pinned image, port, source, capture time, clone method, source downtime, state; for MySQL the database, account and root password), snapshots (versions from a permanent per-name counter, allocated under the catalog lock) and the operation journal; the journal's step sequences (`Restoring` is the step where a stopped source is started again), `can_move`, the `recovery` table and `RollingBack`, the intent recorded before a rollback removes anything |
| `services::docker` | The `docker` CLI as the services use it: daemon id, image pinning, `ContainerSpec`, volumes, label corroboration, the copy helper (`--network none`, source mounted read-only) |
| `services::profile`, `services::resp` | The Valkey/Redis profile (AOF off, RDB on, `--requirepass`, health with `AUTH`+`PING`, capability-gated `BGSAVE` completion judged from `INFO persistence`) over a small RESP client |
| `services::mysql` | The MySQL 8.4 profile (preview): the generated `my.cnf` mounted read-only, the URL and typed fields, the SQL that gives a data directory its identity, the account audit, the clean-stop judgment (exit code 0 and InnoDB's shutdown report in the log since the start), the copy script (whole data directory; identity files dropped for a branch), the bootstrap (no network, no grant tables, local socket) and the health check (`SELECT 1` as the application account through `docker exec`, then the greeting on the published port) |
| `services::plan`, `services::exec` | Planning (journal first) and the coordinator (`devflow __clone`, its own process group, holds the source lock, handshake): quiesce (`BGSAVE`, or a verified clean stop for MySQL), reflink copy under a deadline, restoring a stopped source, start, staged reset and cutover. A source volume is checked (it exists, carries the catalog's identity labels) before it is mounted, and a missing dump is never empty data |
| `services::launch`, `services::locks`, `services::ops`, `services::recover` | Container start and the host port (allocated once from `hash(project, service, branch)`, journaled before Docker publishes it, kept); per-resource flock files; start, stop, drop, forget; reconcile of every unfinished journal entry |
| `services::probe`, `services::workspace` | Per-daemon CoW probe (cached); `--data-from` resolution per service, receipt bindings and orphan reports |
| `doctor` | Checks: project config, Git, worktree-directory CoW, Docker/compose, server reachability and version, `file_copy_method`, CoW capability (measured or declared), hook trust, Git hook state, pitchfork and mise, workspaces needing attention, a relative `core.hooksPath` that a new worktree lacks (`git-hook-path`), agent hosts in use that devflow does not set up (`integration-<host>`), and (`doctor::mise`) what mise does to the current workspace's variables: `mise-env` (the hooks' check, the hooks not routed through `devflow exec`, the offer for an untrusted configuration: text only) and `mise-wiring` (what shells and editors get); `doctor::isolation`: `isolation` (the process environment's owned values against `.devflow/env`, naming the workspace they came from or the stale workspace that cannot be resolved, and an `.devflow/env` without the manifest of owned names, and `SELECT current_database()` through the workspace URL against the receipt's database when the server is reachable) and `dotenv` (copied dotenv files that set an owned name to another value) |
| `pitchfork` | The `pitchfork` CLI as devflow uses it: detection (`--version` must exit 0, then the features `list --json` and `proxy status --json`, and `start`/`stop` by `namespace/name`, judged on pitchfork 2.0 or later; remembered for ten seconds for operations and gates), `list --json`, `proxy status --json`, `supervisor status --json`, and `start -q` / `stop` with full `namespace/name` ids (never `--local`, `--all` or `--global`) with a deadline, the install plan and the proxy commands it only prints. Queries run with the supervisor's auto-start off; a `Pitchfork` handle takes any executable, so tests use a fake |
| `subprocess` | The one bounded command runner for commands whose answer devflow reads (pitchfork, Docker): own process group, TERM then KILL and reaping on the deadline, output kept up to a budget (4 MiB per stream, `truncated` beyond it) as it arrives, one bounded wait for the pipes after exit, strays of a query ended with its group |
| `processes` | A workspace's daemons: the machine-local `pitchfork.local.toml` (namespace `df-<project8>-<instance8>`, `worktree_label`, excluded through `info/exclude`; conflicts and hand-written files reported, never touched), the static check that daemons are wired to mise (`env_wiring`; `.devflow/env` reaches daemons through mise only), `start`/`stop`/`status`/`restart` gated by readiness, the namespace devflow assigned (from the receipt, never from a file), the worktree's own approved scope, daemons that depend only on the workspace's own daemons and the absence of autonomous triggers, judged again immediately before the effect, the state read back after every call (an unreadable state is `state_unknown`, not "nothing runs"), `autostart`, and the stop that `setup::remove` runs first (also for a checkout that is gone) |
| `paths` | Config and data directories (`DEVFLOW_CONFIG_DIR`, `DEVFLOW_DATA_DIR` override) |

## Principles

- **Data lifetime is independent of code lifetime.** A database branch has its own identity; a worktree or VM attaches to it. Code origin (`--from`) and data origin (`--data-from`) are separate and immutable once chosen.
- **Never infer ownership from names.** Branches, snapshots and roles are recorded in a metadata database on the server. Worktrees carry a receipt with their instance id, and the ledger keeps a record per instance outside the worktree for when Git or an agent host deletes it. Generated database and role names are never derived from user input.
- **Resumable, not transactional.** Every multi-step operation records intent before its external effect and can be re-run to completion.
- **Report what actually happened.** CoW is `verified`, `copy` or `unknown`; it is never assumed.
- **Synchronous core.** Blocking API, no async runtime, no UI types.
- **No connection data on a command line.** `devflow db psql` parses the workspace URL like libpq does (`conn`), drops every connection variable inherited from the caller, and sets the workspace's `PG*` variables, password included, in psql's own environment (or the docker client's, forwarded into the container by name). argv is readable by every local user; a process's environment only by the same user and root, the audience of a 0600 file, and no temporary file has to be cleaned up. devflow then replaces itself with psql, so psql handles Ctrl-C and signals itself.

## The pipeline

`switch -c`, `setup` and `switch` to an existing workspace run the same five phases. The receipt is written as soon as the worktree exists; every later phase is recorded before and after its effect, and a re-run resumes at the first incomplete phase.

1. **materialize**: create the Git branch (or reuse an existing local branch of that name) and the worktree; write the receipt with a fresh instance id. A new branch starts at `--base`, else at the HEAD of `--from`, else at the one remote-tracking branch of that name (which it then tracks), else at the default workspace's HEAD; the outcome's `branch_start` and the phase detail say which, and what it tracks.
2. **payload**: clone each `worktree.copy` path from the source worktree. Paths stay inside both worktrees; entries are staged under a temporary name and renamed into place without replacing anything; existing destinations are left alone. The phase says `cloned` of entries that share blocks and `copied` of byte copies.
3. **services**: for each configured service (PostgreSQL, Valkey, Redis, MySQL), create or reconcile the data branch from `--data-from` (without it, a run that cannot prompt takes the service's `[data] noninteractive_from` snapshot; a service without it fails with a typed `Problem` (remedies `CreateSeedSnapshot`, `ChooseDataSource`) rather than clone a live source, unless `noninteractive_fallback = "empty"`; the default workspace is never seeded; `setup/seed.rs` decides, the service looks the snapshot up) and record its binding under `services.<key>`, saving the receipt after each service; a clone that had to stop its source (MySQL) adds a setup warning with the downtime. A container service's binding names a catalog branch (id, URL with its password, the OrbStack container endpoint, owned flag, applied generation, how the data was cloned); its resolved data source is pinned per service before the branch is journaled, as a label in `receipt.service_sources` and as the catalog identity (branch or snapshot id) in `receipt.service_source_ids`, which a retry clones without looking the label up again; a source it lacks fails that service. Its container is started (and health-checked) here and again by every `switch`. A service with no binding, or bound under another generation of its section, is (re)applied; for a branch the workspace owns, that includes provisioning the scratch databases (`extra_databases`) the configuration now names and updating the binding's `extras`.
4. **env**: write the worktree's `pitchfork.local.toml` when the project uses pitchfork (identity only, no approval needed), then write `.devflow/env`: the generated variables (`DATABASE_URL`, `PG*`, `<NAME>_DATABASE_URL` for each scratch database of the binding, `DEVFLOW_*`, `COMPOSE_PROJECT_NAME`) and, for an approved scope, the rendered `[env]` recipes and presets. Without approval only the generated ones are written and the phase is a required skip.
5. **hooks**: if the scope is trusted, run `setup` commands (named, each with its timeout); otherwise prompt (interactive) or skip and mark `needs_attention`.

Status is derived from the phases: `ready` when every phase is done or skipped on request (`--no-db`, `--no-hooks`), `needs_attention` (a required phase was skipped or failed) or `in_progress` (another process holds the receipt lock, or a crash left a phase started). `list`, `switch` to a ready workspace and `remove --keep-data` do not contact the PostgreSQL server, so they work while it is unreachable; `db status` reports it unreachable. `remove` checks all protections before any effect (the mise check of the teardown hooks, and every branch the receipt names: bindings, a branch recorded as about to be created, an earlier build's), runs `teardown`, drops the data branches this instance created (the plan drops nothing; each drop is the backend's journaled operation and decides again under its own lock), then removes the worktree. A bound branch it cannot account for stops it, forceably; a branch recorded as about to be created that it cannot resolve stops it for good (`force` does not lift it: the receipt dies with the worktree). A failure after the first effect is a `PartialRemoval` that says what was done and what remains.

**Activation.** Entering a workspace is `setup::activate` (an existing one) or `setup::create_and_activate` (a new one), for `switch`, `switch -c` and the app's New workspace and Set up alike: the five phases above (resumed if unfinished), then repair, the refresh of a moved database endpoint, the container services, the `switch` hooks (only for a `ready` workspace) and `[pitchfork] autostart`. Everything up to and including the switch hooks runs under both of the workspace's locks, taken in the documented order (process lock, then receipt lock; see `receipt.rs`). Before autostart the receipt lock is released (a start records its intent in the receipt under it) and the process lock is kept and handed to the start (`processes::autostart_locked`). Helpers that need a lock take the caller's as an argument (`refresh_endpoint` takes the receipt lock, `start_locked` the process lock) and never take or try it themselves: a run that holds a lock cannot be told "busy" by itself. A devflow that a hook started (`DEVFLOW_SETUP_ACTIVE=1`) tries both locks once and gets `Busy` at once; the post-checkout hook's guard on the same variable stays a successful no-op. The setup status stays separate from the rest: each container service is `running`, `started` or `failed` (with the reason), the switch hooks and autostart have reports of their own, and a ready workspace whose service failed to start is still `ready` and exits 0. `last_active_at` in the receipt is set by activation, not by `setup`. The first activation of the default workspace (no receipt yet) says, before it runs, that setup (hooks included) runs in the main checkout.

**Repair.** `.devflow/env` and devflow's own `pitchfork.local.toml` are derived from the receipt, and a `git clean -fdx` removes them. The receipt is read first the way every setup reads it (migrated, with what the configuration invalidates reopened); a workspace whose `env` phase is still finished but whose file is missing or unreadable gets that phase run again, by `setup`, by activation and by `setup --if-new` (the shortcut for a ready receipt does not apply to a workspace that needs a repair). It is the env phase's own writer with the bindings and credentials the receipt holds: the recipes only when the current scope is approved, services a `--no-db` skip left out stay out, a moved managed endpoint is followed first, nothing is provisioned, and the recorded credentials are neither rotated nor claimed to be valid. The `services` and `hooks` phases stay as they are, so "no hook runs again" holds for a lost file only; a real configuration change has already reopened the phases it concerns. A file an earlier devflow wrote without the owned-names manifest (`env_file::lacks_manifest`) counts as lost too, because hooks and `devflow exec` refuse it: `activate::env_problem` is the one place that decides, and the rebuild goes through the env phase's `WorkspaceEnv::write` (so the file gets the manifest) and `Receipt::record_exported` (so the exported-name history is kept). A `--no-db` workspace whose receipt still holds the generation an earlier devflow recorded for it (the `[env]` section alone, `Receipt::env_generation_is_legacy`) is rebuilt the same way even though its file has a manifest: that generation cannot see PostgreSQL come or a service export another variable, and it stays valid for `drift` only so that no hook is reopened by the upgrade; the rebuild stamps the current generation, which covers the declared names. The repair runs before the switch hooks, which is why their refusal of a manifest-less file only shows when no repair was possible. The outcome lists what was repaired, and `list` shows a workspace that has lost its file.

**Identity.** A workspace is its receipt, whose `workspace` is the name it was created under, not the branch the checkout holds now. After `git switch other` inside `feature/a`, `list` still shows `feature/a` (its branch column says `other`, with a note), `find` and `path` find it by either name, activation reports the drift ("now on branch other; its data still belongs to workspace feature/a") and keeps writing the variables of `feature/a`. `worktree::find` looks at every identity a name can have (branch, Git's worktree name, the receipt's name, a path), counts the matching checkouts, and refuses a name that means more than one with a typed problem that lists their paths (`Remedy::UsePath`): it never picks one by precedence. A path names a registered checkout whether or not its directory still exists (a deleted one is found, and removed, by the path it is registered under). What a workspace was created from is remembered the same way: the receipt keeps the source checkout's path and instance (`code_source_path`, `code_source_instance`), so payloads, `DEVFLOW_SOURCE_PATH` and the default data source follow that checkout, not a name that may mean two (a source recreated at the same path is another incarnation: it is gone, and the default workspace is the fallback). Drift is judged from what the receipt records: a workspace adopted while its HEAD was detached says so (`adopted_detached`), and any other workspace with a detached HEAD has moved. The desktop app names workspaces by their checkout everywhere (selection, the row that is clicked to remove, the "Code from" and "Data from" choices): a name is a label.

**Ledger and gc.** Receipts live in `.git/worktrees/<id>/devflow/`, which `git worktree remove` deletes, as do the agent hosts that delete worktrees themselves (T3 Code, Cursor, Codex, Claude Code) and none of them offers a reliable teardown hook. The data branches, containers and daemons a workspace owned would then stay with no record, so every receipt write also writes the workspace's record in the repository's common Git directory (`ledger`), and the record is what names the resources once the receipt is gone. `devflow gc` (core `gc`) is the clean-up: the inventory removes nothing, `--remove ID…` removes the instances named, revalidating the record's generation, the data that was shown and each branch's owner under the backends' locks. A removal that cannot account for a resource (a forced removal over an unreachable server, a daemon whose state pitchfork cannot confirm) leaves it on the record, `removing`, for a later `gc` or `remove`; data the person keeps (`--keep-data`) is released. `list` adds a line when workspaces gone from Git still own something and `doctor` reports them; both read the records only, never a server or Docker.

**Configuration generations.** Every binding records the generation of its service section (the SHA-256 of its canonical serialization; credentials in `admin_url` are masked first), and the receipt records the generation of the environment `.devflow/env` was written under. When the current configuration adds a service, changes a service's section or changes what the environment exports, the workspace reads as `needs_attention`: `services` (for the services concerned), `env` and `hooks` are reopened as required skips, in memory for `list` and on disk by the next `setup` or `switch`. Skips someone asked for (`--no-db`, `--no-hooks`) are kept, and removing a service from the configuration never deletes its binding or its data. `setup --if-new` and `switch` compare generations before treating a workspace as ready.

**Receipt versions.** Version 2 keeps one binding per service under `services.<key>` and renames the `database` phase to `services`. A version 1 receipt is migrated in place, under the receipt lock, by the next flow that holds the lock and the configuration; readers migrate in memory. Nothing is provisioned: every field is kept, `data` moves to the project's sole PostgreSQL service, or to `unmapped` when there is none (reported by `setup` and `doctor`, never exported or guessed).

Worktrees created by other tools are adopted through a `post-checkout` hook that runs `devflow setup --if-new --from-git-hook`: it skips a worktree whose receipt is `ready`, resumes any other, never prompts, and always exits 0.

**Processes.** `up`, `down`, `ps`, `[pitchfork] autostart` and `remove` go through `processes`, never straight to pitchfork. A start needs a pitchfork that runs with every feature devflow calls, a `ready` receipt (and no setup holding the lock), the scope of that worktree approved (`trust::state_at`, or the `Approval` of exactly that scope that the caller reviewed) and no daemon among those about to start that also starts on its own (`cron`, `watch`, `boot_start`, `auto`); naming a plain daemon starts it and what it depends on, which must be daemons of the same workspace. The namespace in the worktree's files must be the one in its receipt, or nothing is attributed, started or stopped. A stop needs the same approval because pitchfork runs lifecycle hooks from the current file. Both name the full `namespace/name` ids (never `--local`) and run pitchfork in the worktree with a deadline, after a last look at the files right before the effect, then read `list --json` and `proxy status --json` back: the report says what pitchfork reports, not what was asked. Process state never feeds back into the receipt or the exit code of `setup` and `switch`. `ps` judges a start as `up` does, the mise delivery check included (the shared gate of `setup::mise_gate` through `env_file::check_workspace_env`, then what mise resolves on its own; a file the gate cannot read is `workspace_env`, not a state of mise). `remove` stops the namespace's running daemons before teardown, as part of its protections (for a workspace whose checkout is gone it only asks what runs under the receipt's namespace, from an empty directory of devflow's own, and never stops it: a stop makes the supervisor run `on_stop` from the configuration at the daemon's recorded directory, whoever asks, and no pitchfork stop skips that; running daemons or an unreadable state are `state_unknown`, and a forced removal that went on lists the namespace and ids that may still run): it fails before any effect if they must run `on_stop` hooks from a configuration that no longer matches the approval, if their state cannot be read, or if the stop cannot be seen to work (pitchfork failed, or the state afterwards is unreadable or shows a daemon still active), unless forced; the files are read again right before the stop is carried out. devflow never writes an environment or a credential into a pitchfork file and never runs `pitchfork proxy setup`.

## Role model

One PostgreSQL server per project. Verified on PostgreSQL 18.6 with a non-superuser provisioner.

| Role | Attributes | Holds |
| --- | --- | --- |
| Admin (provisioner) | Superuser (managed) or `CREATEDB CREATEROLE` login (external) | Owns every devflow database and the metadata database. Never given to sandboxes. |
| Project owner `dfo_<project8>` | `NOLOGIN` | Owns every object in every branch and snapshot database of the project; `CREATE, TEMPORARY, CONNECT` on each branch and scratch database (not on snapshots) |
| Branch login `dfl_<id12>` | `LOGIN`, random password, member of the owner with `SET` but not `INHERIT`, default `role` set to the owner | `CONNECT` on its own databases only |

Because the objects of all branches share one owner, clones need no ownership translation, and the owner role is the supported identity for anything that must survive cloning (default privileges, RLS policies, grants). The login does not inherit the owner, so a session that does `SET ROLE NONE` has no right to create in the owner's schemas; login-owned objects only exist in branches made by an earlier build (where the login inherited), and cloning or snapshotting reassigns them to the owner. Privileges or policies that name the login are rejected rather than translated.

Sessions run as the owner, so functions that check `CONNECT` on the current database for the current user, such as `pg_database_size(current_database())` (pgAdmin, DBeaver and Prisma Studio call it), need the owner to hold it: it does, on the branch's own databases. Granting the shared owner `CONNECT` is safe only because no login inherits the owner: `CONNECT` is checked for the login at connection time, before `SET role`, so each login still reaches its own databases only. Each mutation (and `devflow db reconcile`) first makes every branch login of the project non-inheriting, then grants the owner `CONNECT` where a branch made by an earlier build lacks it. The one visible side effect: a session can read the size of a sibling's database, not connect to it.

**Scratch databases** (`[services.<pg>] extra_databases = ["test", "shadow"]`) keep this model: the login stays `NOCREATEDB`, so tools that want a test or shadow database are given one instead of creating it. Each branch has, per configured name, a recorded database in the `scratch_databases` table (own id, the branch's id, the configured label, the generated name `df_<project8>_<branch12>_<n>` with a per-branch counter that is never reused, a status and the branch generation it was last emptied for). It is created empty from `template0` by the same protocol as a branch's own database, owned by the admin, with the owner role holding `CREATE, TEMPORARY` and the branch's login alone holding `CONNECT`. Because the login is the branch's, credential rotation covers them. They are separate databases, so a clone or snapshot never contains them: a new branch, whatever its source, gets empty ones. A reset empties each again in its cleanup phase, after the new data is in place; the label is configuration, the identity is the row.

**Clone strategy and busy sources.** A clone is `CREATE DATABASE … TEMPLATE … STRATEGY s`. `s` is `FILE_COPY` when the capability that applies to the source is `verified` (measured on a managed server and cached in `admin.json` per postmaster start, or declared on an external one; a source outside the default tablespace is `unknown`), and, when it is `copy` or `unknown`, `WAL_LOG` for a source whose `pg_database_size` is under `wal_log_below` (default 256 MiB), because `FILE_COPY` forces checkpoints and, without shared blocks, a full file copy: 6.7 s against 0.47 s for a small database on ext4 (pytest-postgresql issue 1260). A size that cannot be read keeps `FILE_COPY`. `WAL_LOG` never stands in for `require_cow`: with it set, a non-`verified` source is refused before any strategy is chosen and the clone is `FILE_COPY`. The strategy is decided before the branch row is written and journaled in `branches.clone_strategy` (a reset journals the replacement's in `op_clone_strategy` with its intent, and the cutover moves it to `clone_strategy`), always before the `CREATE DATABASE` runs. Metadata schema 4 adds the columns; branch reads go through `to_jsonb(branches)`, so readers of an older schema see null instead of failing. The value is shown as `clone_strategy`. A source with sessions follows `on_busy_source`: `fail` names them, `disconnect` ends them (bounded retries; the warning in `BranchCredentials.warnings` names what was ended) and `wait` polls `pg_stat_activity` every 200 ms on the lock-owning session (re-checking the lock each time), under one deadline taken when the clone starts and shared by the polls and the retries after `object in use`, and then fails naming what is left. Sessions are described as application name (control characters dropped, 40 characters), role, process id, client address and state; a query is never read.

Every new database is created closed (`ALLOW_CONNECTIONS false`) and opened only after its ACLs are normalized. The `devflow` metadata database is closed the same way, so branch logins cannot reach it; managed mode also revokes `PUBLIC` `CONNECT` on `postgres` and `template1`. On an external server devflow changes only databases it created. Snapshots are not templates; only the admin can clone them.

## Recovery model

- Every branch operation holds a session-level advisory lock on the project id and records each step on the branch row before performing it. If the lock connection dies, the operation stops and leaves the row.
- The next mutation of the project, or `devflow db reconcile`, completes or rolls back rows in `creating` or `deleting` and resets with an `op`, by inspecting `pg_database` and `pg_roles`. A reset in `staging` drops its replacement; one in `cutover` whose rename did not commit reopens the original; one in `cleanup` drops the backup. Any other combination is left alone and reported.
- Scratch databases are journaled on their own rows (`creating` before the build, `deleting` before the drop) and follow their branch. A new branch is `ready` only with all the scratch databases configured when it was created, so an interrupted creation is rolled back whole. A reset empties them in its `cleanup` phase and records on each the branch generation it was emptied for, so a repeat after a crash empties only the ones not done (never what the user wrote after the reset). A `creating` row of a ready branch is built again when its name is still configured and dropped when it is not; a `deleting` row is dropped; a branch drop removes its rows (orphans included) before its own database and login. A name that leaves the configuration is an orphan: kept, not exported, untouched by resets, reported by `reconcile` and `doctor`, dropped only by `db reconcile --drop-orphans`. A name that joins it is provisioned for existing branches by the next `setup` or `switch` (`Server::ensure_scratch`).
- A crash between creating a branch and saving the receipt is repaired by the recorded branch id: the retry finds the branch and sets a new password, since the old one was never delivered, and a removal drops it (the receipt's `creating` is read like a binding, and the drop is judged again under the backend's lock). Roles that cannot be dropped are made `NOLOGIN` and recorded in `retired_roles`; `reconcile` retries them. Prepared transactions and replication slots that block `DROP DATABASE … WITH (FORCE)` are reported, not forced.
- Container services record every operation in the catalog's journal before its first effect (destination ids and names, the port candidates, the credentials, whether a full copy is allowed, the deadline) and every step before it is taken. A clone, snapshot or reset is run by one coordinator process that takes the source's and destination's locks itself and holds them to the end; the recorded sequences are clone `planned → quiescing → quiesced → copying → copied → starting → done`, snapshot the same without `starting`, and reset `… → copied → staging → cutover → cleanup → done`. If the coordinator dies, its flocks vanish while a copy helper may live on in the Docker VM, so the next operation on either resource, or `devflow service reconcile`, finds an unfinished entry with free locks and recovers it: before a copy is proven complete (`copied`), and for a reset before its cutover is committed (the catalog moves to the new pair in the same write that enters `cleanup`), it kills the recorded helper, confirms it is gone, removes what the entry created by recorded identity (labels must agree) and marks the destination `aborted`, never promoted, restarting the original container if a cutover had stopped it (a stop whose return was never seen is fenced: the container is stopped, removed by its recorded id and recreated on the same volume, name and port, so a late `docker stop` names a container that is gone), and sweeping the list of helper attempts that outlives every operation; from `copied` a clone is finished by starting it again, and removals (`drop`, snapshot delete, a reset's cleanup) are always finished. An entry with no coordinator yet is given two minutes before it counts as abandoned. A copy past its deadline is the same abort, done by the coordinator.
- Worktree setup is resumable from the receipt. Hooks run at least once: a crash after a command succeeds but before the receipt update reruns it, so hook commands must be idempotent.
- A VM fork copies the receipt. `devflow setup --new-instance` gives it a fresh identity and a new branch. Only the instance that created a branch may reset or drop it; `--database-url` attachments are detach-only. For container services the fork's new branches are cloned from the branches the copy knew (or `--data-from`).

## Checkouts devflow does not make

devflow makes worktrees through libgit2, so it refuses, before creating a branch, a directory or a registration, what libgit2 cannot check out faithfully:

- **Git LFS**, decided by attributes alone, since pointer files appear only where an attribute names `filter=lfs`: any attributes source containing `filter=lfs` (an `[attr]` macro definition included) makes the repository an LFS repository. The sources are every `.gitattributes` of the commit that will be checked out (its whole tree is scanned, each distinct subtree once: about 0.1 s for 200,000 entries, 0.5 s for a million), `info/attributes`, the effective `core.attributesFile` (or Git's default location for it) and the system attributes file. A `filter.lfs` section in a configuration file, repository or global, changes nothing on its own and is not a signal. The commit judged is the one actually checked out: `--base`, the HEAD of `--from`, the remote branch, the default HEAD, or the tip of a reused local branch (judged again if the branch moves before the checkout). Absence has to be established: a tree of more than five million entries, an attributes file that exists but cannot be read, or a configuration file or include condition that cannot be read or evaluated is refused as "cannot tell". libgit2 does not run the smudge filter, so the worktree would hold pointer files.
- **Where `core.attributesFile` points**, and the partial-clone keys below, are read from libgit2's effective configuration and from the configuration files themselves (`worktree::rawconfig`): libgit2 skips `includeIf "hasconfig:remote.*.url:…"`, so the include graph is walked in Git's order (system, XDG, `~/.gitconfig`, the repository's `config`, `config.worktree`; each include expanded in place and resolved from the directory of the file that holds it). `core.attributesFile` is one setting, so the last one read is the effective one and only it is judged (a global file's rules are not applied when the repository points it at `/dev/null`; an empty value means no file, not the default; with none set, `$XDG_CONFIG_HOME/git/attributes` or `~/.config/git/attributes`). The reader follows Git's own syntax rules (a leading UTF-8 byte order mark is skipped) and refuses what Git refuses, naming the file and line. Conditions (`gitdir`, `gitdir/i`, `onbranch`, `hasconfig:remote.*.url`) are evaluated with Git's `wildmatch` with `WM_PATHNAME`: `*`, `?` and bracket expressions (ranges, `[!…]`, `[^…]`, `[[:alpha:]]`-style classes, escapes) stop at `/`, `**/` is zero or more directories, in time linear in pattern times text. Another `hasconfig` form, a relative or `~user` `core.attributesFile` that is the effective one, or a file that exists but cannot be read is "cannot tell". The tests use the `git` on `PATH` as the oracle (`config --list -z`, `check-attr`, `includeIf`).
- **Partial clones**: `extensions.partialClone`, or `remote.<name>.promisor` true in Git's sense (`true`, `yes`, `on` or a non-zero integer), in the repository's own configuration; a value Git cannot read as a boolean is refused. libgit2 cannot fetch the objects a partial clone leaves out.

Make the worktree with Git itself (`git worktree add`); the Git hook (`devflow hook install`) then sets it up. A configured sparse checkout is only a warning: the new worktree is a full checkout.
