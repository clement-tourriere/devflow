# SQLite

[Data services](data-services.md) has the rules every service shares (`--data-from`, snapshots, seed data); [copy-on-write, measured](copy-on-write.md) has the numbers for reflinks.

A `sqlite` service gives each workspace its own copy of a database **file**. Nothing runs and Docker is not needed:

```toml
[services.app]
engine = "sqlite"
path = "db/development.sqlite3"   # relative to the worktree; the same path in every workspace
# env = "DATABASE_URL"            # the variable the sqlite: URL is exported as; default DATABASE_URL, or SQLITE_URL when another service claims it (a postgres service, or mysql without an `env`)
# path_env = "SQLITE_PATH"        # the variable the absolute path is exported as
# busy_wait = "30s"               # how long a clone waits for a writer to release the source
# require_cow = false             # true: refuse a clone unless the file system shares blocks
```

- **Variables.** `.devflow/env` gets the workspace's own file twice: `SQLITE_PATH=/work/shop.worktrees/feature-a/db/development.sqlite3` and `DATABASE_URL=sqlite:///work/shop.worktrees/feature-a/db/development.sqlite3` (the RFC 3986 form: `sqlite://` and the absolute path). Frameworks disagree on how a URL spells an absolute path, so build theirs from the path in an `[env]` recipe under a name of your own: `SQLALCHEMY_DATABASE_URI = "sqlite:///${SQLITE_PATH}"` (four slashes in all, since the path starts with one; SQLAlchemy and dj-database-url read three as relative) or `PRISMA_DATABASE_URL = "file:${SQLITE_PATH}"` for a Prisma schema that reads `env("PRISMA_DATABASE_URL")`. Both names are owned like every other (a `--no-db` workspace clears the caller's). The path follows the worktree if it moves.
- **Where the data comes from.** The default workspace uses the file already in the main checkout: it is yours, and setup, reset and drop never touch it. Any other workspace starts as a copy of its source's file: the code source's, `--data-from WS`, `--data-from snapshot:NAME[@vN]` or `--data-from empty` (no file; the application creates one). A source with no file yet starts the workspace without one and says so. `[data] noninteractive_from` seeds runs that cannot prompt, as for the other services. A file that is already in the workspace (cloned by `[worktree] copy`, or tracked by Git) is left alone and not owned: take it out of `copy` to have devflow clone it consistently.
- **A copy is never torn.** Copying a SQLite file while somebody writes to it can produce a database that never existed, so the copy is made under SQLite's own locks, by one of two ways. If the file system shares blocks and the write lock can be had, devflow takes it (`BEGIN EXCLUSIVE`; in WAL mode it first folds the log into the file and only trusts the lock once the log is seen empty while it is held), clones the file with a reflink and lets go, so a gigabyte database costs one metadata operation and shares blocks (`reflink`). Otherwise SQLite's online backup API reads one consistent state and writes a new file (`copy`: every page is written again). A writer that holds the source is waited for up to `busy_wait` (a rollback-journal database cannot be read while one is mid-commit) and the source is refused after that, copying nothing; in WAL mode a transaction in flight is not waited for beyond a short while: the copy is the last committed state. With `require_cow`, only the reflink is accepted.
- **Crashes.** The creation is journaled in the receipt before the first byte, the new file is staged beside its destination as `.NAME.devflow-<id>.partial` and installed with an atomic no-replace rename, so an interrupted run leaves a partial file under a name that setup removes by that identity, never a half-written database under the real one. The source is chosen once and pinned.
- **Snapshots and reset.** `devflow service NAME snapshot create SEED [--from WS]` keeps a consistent, read-only copy under `<data dir>/sqlite/<project id>/` (a catalog that records every change before it is made; versions are never reused); `service NAME reset [WS] [--to SRC]` replaces a workspace's file with a fresh copy of its source and refuses while another process has it open (SQLite's exclusive lock, within `busy_wait`); the old file's `-wal`, `-shm` and `-journal` go with it, since beside a new file they would be replayed into it. `service NAME drop ID` removes the file and the binding (the next `setup` clones it again). `up` and `down` have nothing to do. Removing a workspace removes its file with the worktree; snapshots stay until deleted (`service NAME forget` removes those of a service the configuration no longer has).
- **Not supported.** Branches (a SQLite database has none: take data from a workspace or a snapshot), a database on a network file system (SQLite's locks are not reliable there, so a copy made under them is not either) and a file other tools write without SQLite (they bypass the locks the copy relies on). devflow links SQLite itself (`rusqlite` with the bundled library, 3.5x); `devflow doctor` and `service NAME status` print its version, and no `sqlite3` program is needed.
