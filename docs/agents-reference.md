## Output contract

| Flag | Effect |
| --- | --- |
| `--json` | Print exactly one JSON document on stdout. Progress and hook output go to stderr; warnings are added to the document's `warnings` array. Never prompts. |
| `--non-interactive` (or `DEVFLOW_NON_INTERACTIVE=1`; also `0`, `true`, `false`, `yes`, `no`, `on`, `off`) | Never prompt. Untrusted hooks are skipped instead of asked about. |
| `-C DIR` | Run as if devflow was started in `DIR`. |

Every document has `"version"` (currently `1`) and `"command"`. With `--json` anywhere in the arguments before a `--`, every failure prints `{"version": 1, "command": …, "error": "…"}` and exits 1: a missing argument, a bad `-C` directory, a configuration problem and a refused operation alike. `command` is the subcommand that was asked for (`devflow` when none could be identified). When devflow knows the next step, the document also has `"hint"` (for example `run `devflow init` …` when there is no `devflow.toml`, or `devflow remove NAME --force` when only `--force` can override a protection). `--help` and `--version` still print their text.

### Errors and remedies

When devflow knows how to get past a failure, the error document also has `"remedies"`: an array, most useful first, of things that can be done about it. A remedy is data, not a sentence to parse:

```json
{"version": 1, "command": "list",
 "error": "no devflow.toml in /work/shop",
 "hint": "run `devflow init` in /work/shop (`devflow init --plan` shows the proposed setup first)",
 "remedies": [{"kind": "init", "root": "/work/shop", "label": "Set up devflow…", "command": "devflow init", "destructive": false}]}
```

`kind` is one of `retry`, `forget_project` (`root`), `locate_project` (`id`, `root`), `migrate_config` (`root`), `init` (`root`), `clean_up` (`root`), `rebind_record` (`root`, `instance`; a record written for another repository directory, which only the person's word makes this repository's: destructive, so confirmed first; its `command` is `devflow gc --rebind ID`), `open_file` (`path`), `reveal` (`path`), `open_guide` (`url`), `setup` (`workspace`), `trust` (`workspace`), `use_default_recipes` (`workspace`; a workspace whose own `devflow.toml` is missing or unusable has no hooks, `[env]` or copy list: the `command` is `devflow setup --use-default-recipes`, run in the workspace, which records the choice, see "Each workspace runs its own branch's recipes"), `start_database` (`root`), `start_service` (`root`, `key`, `branch`, `workspace`), `measure_services` (`root`, `key`), `reconcile_service` (`root`, `key`), `forget_service` (`root`, `key`), `drop_service_branch` (`root`, `key`, `branch`; an orphan no workspace owns), `drop_lost_branch` (`root`, `key`, `branch`, `volume`; a branch a workspace owns whose volume is gone: core takes the branch's lock, reads the record again under it and drops the branch only while it still names `volume` and that volume is missing, so a branch a concurrent reset gave a new volume is kept; its `command` is `devflow service KEY drop ID --lost`, which does the same), `reconcile_databases` (`root`), `drop_orphan_databases` (`root`), `install_git_hook` (`root`), `copy_hook_line` (`path`; the `post-checkout` hook another tool wrote, which devflow never edits: the app copies core's one-line snippet, the CLI prints it as the hint; no `command`), `install_pitchfork`, `prune_worktrees` (`root`), `remove_workspace` (`root`, `name`), `switch_to` (`root`, `name`), `add_env_preset` (`root`, `preset`), `clear_inherited` (no target, no `command`: the process's environment carries the variables of a workspace that cannot be resolved; open a new shell, or set `DEVFLOW_CLEAR_INHERITED=1`, `devflow exec` also takes `--clear-inherited`), `use_path` (`name`, `candidates`: a name that means several workspaces, a checkout that moved to another branch and one that took its old branch, is refused and listed by path; the `command` depends on the command you ran, so there is none: give the path instead of the name), `choose_base` (`root`, `name`, `candidates`: several remotes have a branch of that name and devflow never picks one; the `command` is `devflow switch -c NAME --base CANDIDATE` for the first), `choose_data_source` (`root`: a creation that cannot prompt was told no data source; pass `--data-from`; no `command`), `create_seed_snapshot` (`root`, `key`, `snapshot`, `engine`: the seed snapshot `[data] noninteractive_from` names does not exist for that service; the `command` is `devflow db snapshot create NAME` for PostgreSQL and `devflow service KEY snapshot create NAME` for the others), `integrate_host` (`root`, `host`: `devflow integrate HOST`), `choose_workspace` (`root`: a command that needs a workspace was given none and cannot ask; the `command` is `devflow list`) and `shell_integration` (`shell` when known: the wrapper `devflow switch` needs to change the shell's directory; the `command` is `eval "$(devflow shell-init SHELL)"`); new kinds appear over time, so ignore the ones you do not know. A remedy always names its target (the workspace's path, the project's root, the service key); it never means "the current directory's" or "the selection". `label` is the button text the desktop app shows. `command` is the equivalent CLI line when there is one (`devflow setup`, `devflow db up`, `devflow service KEY reconcile`, … run in the workspace or project the remedy names; `start_service` has a `command` only when `workspace` (the one checkout whose receipt binds that branch) is known: `devflow -C WORKSPACE service KEY up`; `prune_worktrees` is `devflow prune`, which is `destructive` and asks first).

The remedies of a refused `up` or `down` name the workspace the command resolved (`devflow --json up feature` from the main checkout names `feature`'s directory), never the directory it was started in.

Messages say what is wrong in plain words and never carry a command line: the fix travels as a remedy. This holds for the errors above, for `doctor` checks, for the `reason` of a phase a configuration change reopened, and for `warnings`. A failed setup phase keeps its cause's remedies (`start_database`, `drop_lost_branch`, …) ahead of the `setup` retry. A setup outcome (`setup`, `switch`, `create`) has `remedies` too when the workspace is not ready (`trust` first when the hooks or `[env]` wait for approval, then `setup`). An older receipt on disk may still hold a reason written with a command in it.

`devflow --json list --all` gives each registered project a `problem` (`kind`, `message`, `root`, `remedies`) instead of `workspaces` when it cannot be opened: `folder_missing`, `not_git_checkout`, `not_initialized`, `pre_release_config`, `legacy_config`, `invalid_config`, `wrong_project` or `unreadable`.

```sh
devflow --json list --all                                  # which projects have a problem
devflow --json project forget PATH_OR_ID                   # remove an entry; nothing on disk changes
devflow --json project forget --missing                    # every entry whose folder is gone
devflow --json project relocate PATH_OR_ID NEW_PATH        # the folder moved (it must be that project)
devflow --json config migrate --dry-run                    # show how an earlier build's [postgres] becomes [services.db]
devflow --json config migrate                              # write it (never prompts under --json)
devflow config schema [--local]                            # the JSON Schema of devflow.toml (devflow.local.toml): the schema itself on stdout, with or without --json
```

`config migrate` rewrites only the top-level `[postgres]` table of `devflow.toml` (or `.devflow.toml`) and `devflow.local.toml` into `[services.db]` with `engine = "postgres"`, keeping comments and the table's place. The server, its branches and the workspaces' receipts are identified by the project id, not by the service key, so they keep working. It refuses (nothing is written) when a file has both `[postgres]` and a PostgreSQL service, when `services.db` is something else, and for 0.x configuration, which is never rewritten. The document has `migrated`, `dry_run`, `service_key`, `files` (`file`, `path`, `added`, `removed`, `diff`) and `notes`.

| Exit code | Meaning |
| --- | --- |
| 0 | Done; for `switch` and `setup`, the workspace is `ready` |
| 1 | Error: usage, configuration, an unreachable server, a failed protection check. The message is in `error`. This includes a phase that fails after the worktree was created (for example an unreachable server during `switch -c`): the worktree is kept and named in the message; re-run `switch -c NAME` or `devflow setup` there. `doctor` also exits 1 when a check fails, but prints its normal document with `"ok": false` and no `error`. |
| 2 | The workspace is not ready. The worktree exists, but `status` is `needs_attention` (a required phase was skipped or failed) or `in_progress` (another process holds the receipt lock, or a crash left a phase started). The reason is in the document and in the receipt. When `switch` or `setup` finds the lock held, the document has `"status": "in_progress"` and a `detail` message instead of an `error`; wait and run the command again. A devflow that a hook started (`DEVFLOW_SETUP_ACTIVE=1`) and that asks for either lock of the workspace being set up or entered tries it once and gets this at once, instead of waiting for the run that is waiting for it (the post-checkout hook's own guard is unchanged: it does nothing and succeeds). |

`switch` and `setup` documents carry `project`, `created`, `skipped`, `status` (`ready`, `needs_attention` or `in_progress`), `path`, `workspace` (`name`, `branch`, `path`, …), the `receipt` (phases `materialize`, `payload`, `services`, `env` and `hooks`, each with its state and detail, and the bindings of the project's services under `receipt.services.<key>`), `payload`, `hooks` and `warnings`. With `[pitchfork] autostart = true` the document also has `processes` once the workspace is `ready`: `{report}` (what `devflow up` would print, see Processes) or `{skipped, refusal}` when the daemons were not started and why. It never changes `status` or the exit code. `hooks` is the setup run's. Entering a workspace (`switch NAME`, `switch -c NAME`, and the desktop app's New workspace and Set up) is one activation in core, whoever asks: setup or resume, repair, refresh of a moved database endpoint, container services, the project's `switch` hooks once the workspace is `ready`, then autostart. Setup, repair, the endpoint refresh and the switch hooks run under both of the workspace's locks (the process lock first, then the receipt lock), so nothing else sets the workspace up or starts its daemons meanwhile; the receipt lock is released before autostart, which runs under the process lock the entry kept. A switch hook that runs `devflow up` or `devflow switch` is refused as busy, and `[pitchfork] autostart` is how daemons start on entry. The document adds `switch_hooks` (the hook run; a failing or skipped switch hook is a warning, and the status stays `ready`), `services_state` (`[{key, engine, state: running|started|failed, reason}]`, one per container service of a workspace that has them; `started` is a container the entry brought up, in its setup or afterwards, and `running` one that was already up; a service that could not start is also a warning with a `start_service` remedy, and changes neither `status` nor the exit code), `repaired` (`env_file`, `pitchfork_namespace`, `app_port`: a file derived from the receipt that was missing or unreadable and was written again by the env phase from the receipt's own bindings, identity and the recipes the current approval covers, with no new data, nothing rotated and no hook run again; the recorded credentials are written as they are and are not checked against the server, and a service a `--no-db` skip left out stays out. A managed server's moved endpoint is followed before the file is written. Only a lost file is repaired without hooks: a real configuration change has reopened the phases it concerns, hooks included, and they run. `devflow setup` repairs too, and so does `setup --if-new`: a ready workspace with a missing file is not skipped. A file written by an earlier devflow without the owned-names manifest counts as lost too, and is rebuilt before the switch hooks run. `list` shows `env_file` (`missing`, `unreadable`, `no_manifest` or `old_generation`: a `--no-db` workspace whose receipt still holds the generation an earlier devflow recorded, which could not see a service come or export another variable, so the file is rebuilt even though it has a manifest, with no hook run) on a workspace that is set up and has lost it, with the `setup` remedy and the status unchanged), `drift` (`{workspace, branch, head}` when the checkout holds another branch than the workspace was created for: the data and variables still belong to `workspace`, which `list` shows as the name, and `switch`, `path` and the other commands find by that name as well as by the branch, by Git's worktree name and by the path; a name that matches two checkouts (A moved to `other`, B then took A's old branch) is refused with the paths of both and the `use_path` remedy, never resolved by an order of precedence; a path always names one checkout, even a registered one whose directory was deleted. `--from PATH` and `--data-from PATH` name a source that way, and a workspace remembers the checkout it was made from, not only its name; `workspace:NAME` labels in receipts are the resolved workspace's name), `recipes` (where the workspace's configuration came from: `source` is `main`, `workspace` (its own `devflow.toml`), `default_chosen` or `unavailable`, with the `file` it was read from, `because` (`kind` `missing`, `not_committed`, `legacy`, `invalid` or `other_project`, the `file` and a message that names keys and never values) when its own recipes are not used, the `shared` file the project's services and the rest are read from, `local` and `ignored_local`, `differing` (the shared sections its own file has with another content, named with their file, never valued: they are not applied, and each is also a warning) and `choice`: `recorded`, `cleared` or `migrated` when this run changed the choice of the default workspace's recipes), `first_setup` (`true` when the main checkout had never been set up: a notice on stderr, before anything runs, says that setup, hooks included, runs there) and `receipt.last_active_at` (when the workspace was last entered). The `warnings` of an outcome include what the data layer reports: sessions ended on the source and operations recovered, and a container source that was stopped for the copy (MySQL), with how long. `setup --if-new` on a `ready` workspace returns only `{project, skipped: true, workspace, path}`, with no `status` or `receipt`; the skip is judged again in full under the receipt lock (readiness, the identity `DEVFLOW_INSTANCE_ID` asks for, the derived files that need repair, the receipt still being there), and anything that changed since the first look is a real setup. Before it answers, still under that lock, it writes the workspace's record if it has none and reconciles it with the receipt, so a `remove --keep-data` that failed part-way (the workspace is still in use) is over and the data it had disowned is owned again. Passwords are replaced by `***` in every document and message except where handing out the credential is the command's purpose: `devflow db url`, `devflow db branch create` (also when `--instance-id` rotates an existing branch's password), `devflow service [NAME] url` and `devflow env list --show-values` (the real recipe templates and resolved values). Without `--json`, `db url` and `service url` print the URL alone. The same secrets are in files written 0600 (`.devflow/env`, receipts, `admin.json`, the managed `compose.yaml`), and the desktop app reveals a connection only on request. `db psql`, `shell-init`, `completions` and `gui` do not accept `--json`.

## Set up a project

Do not write `devflow.toml`, `pitchfork.toml` or `mise.toml` from guesses: ask devflow to propose them, read the proposal, and apply the items you agree with. `init` is two steps with a document between them, and neither step installs a tool, approves a hook or runs a command.

```sh
devflow --json init --plan > plan.json     # writes nothing
jq '.items[] | {id, confidence, title, risks, conflicts, depends_on}' plan.json
devflow --json init --apply plan.json --accept hook:setup:compose-up --reject daemon:worker
```

`init --plan` takes `--name NAME` and `--postgres managed|external|none`, which change the proposal. Without `--plan`, `--apply` or `--yes`, `init` needs a terminal and fails under `--json`, `--non-interactive` and in a pipe.

The plan is the whole stdout document: the envelope (`version`, `command`) plus `proposal_version`, `schema_version`, `input_hashes` (the SHA-256 of every configuration file the plan read or could write, `null` when absent, and of the detection facts under `detection`), `items`, `already_configured` (ids the files already have) and `warnings`. Each item has:

| Field | Meaning |
| --- | --- |
| `id` | Stable and deterministic: `project:init`, `copy:node_modules`, `service:db`, `service:cache`, `service:mysql`, `hook:setup:install`, `hook:setup:codegen`, `hook:setup:migrate`, `hook:setup:compose-up`, `env:preset:prisma`, `daemon:web`, `pitchfork:autostart`, `mise:env-file`, … |
| `kind` | `project`, `copy`, `service`, `hook`, `env`, `daemon` or `mise` |
| `title`, `value` | One sentence, and the proposed content as structured data (never a secret; `.env` values are never read) |
| `confidence` | `high` (applied by default), `medium` (likely, depends on something detection cannot see: compose hooks, extra daemons, a new `mise.toml`) or `low` |
| `evidence`, `risks` | Files and keys that support it (`compose.yaml:services.db.image`); what can go wrong (an older compose Postgres major, init scripts, `container_name`, fixed ports, named volumes, a copied `.env` that keeps the original `DATABASE_URL`) |
| `depends_on`, `conflicts` | Ids that must be applied with it; ids it excludes, or descriptions of existing configuration in the way |
| `patch` | `{file, ops}`: the additive edit (`table`, `set`, `append`). No `ops` means there is nothing devflow can write: a Procfile process to copy by hand, or a conflict |

A `conflicts` entry that is not an item id describes existing configuration in the way (a `mise.toml` with another `_.file`, an `[env]` recipe that already sets `DIRECT_URL`, a hook named `migrate` that runs something else). Such an item has no `ops`, is never applied by default and is refused if you `--accept` it: resolve it in the file, then plan again. Nothing is ever overwritten. `mise:env-file` is judged on mise's layered configuration (`.tool-versions`, `.config/mise/conf.d`, the base files, `mise.<env>.toml`, `mise.local.toml`, `.mise.local.toml`, … in mise's precedence order, every `_.file`/`_.source` entry in order, repeats included): it is blocked, naming the file (`mise.local.toml ([env] _.file)`, never a path or a value), when an entry comes after `.devflow/env`, whether in the same list, in a file mise reads later, or in any file above the one the wiring would go to. A `mise.<env>.toml` applies only when its `MISE_ENV` is selected, which a scan cannot tell; it is a warning. A hook or daemon depends on `mise:env-file` only when it runs repository code through mise without `devflow exec` having the last word: a mise task (`mise run migrate`, `mise watch`) or a bare `mise exec -- CMD`, since mise applies its own `[env]` over whatever devflow set (installs and code generation count as well as migrations, since `postinstall` scripts can reach the database). Wrapped commands do not depend on it and need no wiring change: `mise exec -- devflow exec -- CMD` in a hook and `run = "devflow exec -- CMD"` (with `mise = true`) in a daemon get `.devflow/env` from `devflow exec`, which sets it after mise has run. This is an early warning: `devflow setup` asks mise what it really resolves (see "Start a task", item 7).

`--apply` takes the plan's `high` items that can be applied, plus every `--accept ID`, minus every `--reject ID`. A default item whose dependency is not selected is left out and listed in `dropped` with the reason; an explicit `--accept` whose dependency is missing is an error that names it. `--no-defaults` applies only what `--accept` names. Dependencies and conflicts are validated before the first write, then the current hashes are compared with `input_hashes`: if any file changed since the plan (or the repository's detected facts did), nothing is written and the error lists what changed, so plan again. A save that lands between that check and the write is not overwritten either: each file is replaced by exchanging a staged copy with it and comparing what was displaced with what the plan read. A mismatch is put back and the apply stops with "edited since the plan was made"; if it cannot be put back, or the file changed twice, the displaced content is kept next to the file as `NAME.devflow-conflict-<timestamp>` and the error names both paths.

**Container services.** A compose service with a `valkey/valkey`, `redis` (or `docker.io/library/…`, Bitnami's, or a `valkey`/`redis` tag) or `mysql:8.4*` image becomes `service:<key>` (the key is the compose name; `service:mysql` for MySQL), whose `value` is `{key, engine, image, env, compose_service}` (`preview: true` for MySQL) and whose patch writes `[services.<key>]`. The compose image is kept when devflow's profile can run it (Redis 7+, Valkey 7.2+, the official MySQL 8.4 image); otherwise the item sets devflow's default image and the first `risks` entry says why. Valkey and Redis are `high` (applied by default; `medium` for an image from a repository devflow does not know); **MySQL is a preview, `medium`, never applied unless you `--accept service:mysql`**. `env` is what the application reads (`REDIS_URL`, `VALKEY_URL`, `CACHE_URL`; MySQL `DATABASE_URL`, or `MYSQL_URL` beside a PostgreSQL service) and a second cache gets `<KEY>_URL`; it is written to the file only when it is not the default. `risks` name what devflow knows: AOF and other persistence settings do not carry over, compose volumes are not carried over, init scripts do not run, MySQL is InnoDB only and at most one, and a cloned `.env` that defines the variable keeps the original value. The compose container can stay for other uses, but the application must use the URL devflow exports. **Branch or compose is decided at selection.** The compose hook items (`hook:setup:compose-up`, `hook:switch:compose-up`, `hook:teardown:compose-down`) list what devflow never branches; their `value.compose.members` also lists every compose service devflow proposes to branch, with `branched_by` (the `service:<key>` item). `apply` and `preview` render the hooks from the final accepted ids (`Proposal::resolved`): a service whose item is not accepted (unticked, `--reject service:cache`, MySQL without `--accept service:mysql`) is started by the hooks you accepted, in compose order; an accepted hook with nothing left to start is not written and appears neither in `applied` nor in `manual`. A project whose only datastore is a proposed cache or MySQL lists the three hooks as `medium` alternatives to the service. The plan itself and its digest do not change, so a saved `plan.json` stays valid for any choice. Nothing is proposed (and no item duplicates) when the configuration already has that service. What is not proposed is in `warnings`, in two kinds: `not proposed automatically` (modules in the image, an unpinned MySQL tag, a second MySQL service, a compose profile: configure it by hand, see the guide pages it names: [Valkey and Redis](guide/valkey-redis.md), [MySQL](guide/mysql.md)) and `unsupported` (MySQL other than 8.4, Percona, a Redis cluster); both stay in the `hook:setup:compose-up` hook when compose can start them.

The apply document has `project`, `config`, `postgres`, `services` (`[{key, engine}]` of the configuration now), `accepted`, `dropped`, `applied` (items now in the files), `manual` (accepted items that ask for work by hand), `files` (`{file, status: created|modified|already_applied, before, after}`), `resumed`, `already_applied`, `journal` and `next_steps`. The journal (`.git/devflow/init-apply.json`, 0600) records each file's intended hashes: if a run is interrupted, repeat the same command with the same `--accept`/`--reject` and it continues; once finished, repeating it changes nothing.

Then a person reviews and commits the files and runs `devflow trust` (hooks, `[env]` and pitchfork daemons stay unapproved until then), and `devflow switch -c NAME` creates a workspace.

### LLM setup recipe

The whole path, from an unconfigured repository to a workspace that runs its own hooks, using only commands that print one JSON document and never prompt. Each step names the next.

```sh
# 1. Read the proposal. Writes nothing.
devflow --json init --plan > plan.json
jq '.items[] | {id, confidence, title, risks, conflicts}' plan.json
# 2. Apply the items you agree with (high-confidence ones are applied by default).
devflow --json init --apply plan.json --accept hook:setup:compose-up --reject daemon:worker
# 3. Adjust hooks and [env] with typed edits instead of editing TOML. Read what init
#    already set first, and edit only what is missing.
devflow --json hooks list
devflow --json env list
devflow --json hooks add setup 'bunx prisma migrate deploy' --name migrate --timeout 5m --after install
#    A variable has one owner. Pick ONE of these for DIRECT_URL; core refuses both,
#    because the prisma preset sets DIRECT_URL itself:
devflow --json env preset add prisma                  # typed: the preset owns DIRECT_URL
# devflow --json env set DIRECT_URL '${DATABASE_URL}' # or a recipe of your own, without the preset
# 4. A person reviews and approves what now runs; you do not.
devflow --json trust            # shows everything one approval covers; approves nothing
#    (a person runs: devflow trust)
# 5. Create the workspace.
devflow --json --non-interactive switch -c agent/TASK
# 6. Commands that need the workspace's database go through `devflow exec`: it applies
#    .devflow/env last (over mise, a profile, anything), from any subdirectory, and
#    refuses to start the command without it.
(cd "$path" && devflow exec -- bun test)
```

Never write `devflow.toml` by hand when `init` or `hooks`/`env` can do it: those edits keep comments and order, are validated before they are written, and refuse to overwrite a file that changed meanwhile. Never approve for the person: `trust` is the one step that is not yours.

#### `devflow hooks` and `devflow env`

Both print one document with `--json` and exit 1 with `{"error", "hint"?}` when an edit is refused; a refused edit writes nothing. An edit is judged as the project before it is written: the main checkout's configuration with the overlay, and for a workspace's own file also that workspace's recipes next to the main checkout's services, so a `--local` recipe for a variable a service of the main checkout exports is refused from any workspace, whatever its branch has.

| Command | Effect |
| --- | --- |
| `devflow --json hooks list` | `phases.{setup,switch,teardown}`: `source` (`project` or `local`), `hooks[]` of `{position (from 1), name, run, timeout, effective_timeout}` and `shadowed[]` (committed hooks a local list hides); `timeout`, `path` (the workspace the hooks are of), `files.{project,local}` with `name`, `path`, `exists` and `sha256`, `files.recipes` (where this workspace takes its hooks and `[env]` from: `source` `main`, `workspace`, `default_chosen`, and the `file`) and `trust` |
| `devflow hooks add PHASE COMMAND [--name N] [--timeout T] [--before REF \| --after REF] [--local]` | Adds a command (`PHASE` is `setup`, `switch` or `teardown`). A plain command is written as a string, one with a name or timeout as a table. `REF` is a hook name or a position from 1 |
| `devflow hooks update PHASE REF [--run C] [--name N \| --clear-name] [--timeout T \| --clear-timeout] [--local]` | Changes what is given and keeps the rest |
| `devflow hooks remove PHASE REF [--local]`, `devflow hooks move PHASE REF POSITION [--local]` | `POSITION` is a number from 1, `first` or `last` |
| `devflow --json env list [--workspace NAME] [--show-values]` | `recipes[]` of `{key, template, masked, source}`, `presets[]` with their variables and description, `available_presets`, `references` (the `${NAME}` you may use), `preview` (what the recipes resolve to in a workspace, as `variables[]` of `{key, origin, value, masked}`; `null` before the workspace is set up), `revealed`, `trust` and `warnings` (valid configuration that is probably not what was meant: `[env] preset = "prisma"`, or `presets_`, `Presets` and other near misses of `presets`, is a variable named `preset`, and the warning says `did you mean `presets = ["prisma"]`?`; `devflow --json doctor` has the same warning as an `env-presets` check). A credential is shown as `***` (`masked: true`): a recipe whose name says it holds one (`PASSWORD`, `PASS`, `SECRET`, `TOKEN`, `KEY`, `CREDENTIAL`, `DSN`, in any spelling) and has literal text, and any text with a password in a URL or a `password=` assignment. A template made only of `${NAME}` references is shown as written. **`--show-values` prints the real templates and resolved values, secrets included** (`revealed: true`, `masked: false`): use it only when you must read one, and never log or paste its output |
| `devflow env set KEY VALUE [--local]`, `devflow env unset KEY [--local]` | A recipe: `VALUE` may reference `${DATABASE_URL}`, `${PGHOST}`, `${DEVFLOW_WORKSPACE}` and the other generated variables, once. The response lists `recipes[]` as `{key, source}` only: an edit never echoes a value (read it with `env list`) |
| `devflow env preset add\|remove NAME [--local]` | `prisma`, `laravel`, `spring`, `sqlalchemy`, `db_parts` |

**Recipes are per workspace.** `hooks` and `env` act on the workspace they are about: `--workspace NAME`, else the workspace the current directory is in, else the main checkout. They read and edit the file that workspace takes the section from: its own `devflow.toml` (a worktree carries the one its branch has, so the edit is a change to that branch, committed with it), or the main checkout's for the main checkout and for a workspace that chose the default workspace's recipes. A workspace with no usable file has nothing to edit: the error carries the `use_default_recipes` remedy. `--local` is always the main checkout's `devflow.local.toml`, which overlays every workspace. Every edit document and every `list` names the file (`path`, `files.recipes.file`) and the `workspace`.

Every edit command takes `--if-unchanged SHA256` (the `files.*.sha256` of a `list` you read, or `none` for a file that does not exist yet): the edit is refused when the file is different now, so an agent never overwrites a person's edit. Without it, the file is compared with what the command itself just read.

Every edit document has `file`, `path`, `workspace`, `recipes` (where the recipes come from), `target` (`project` or `local`), `changed` (an edit whose effect is already there changes nothing), the resulting list, `notes` and `trust`:

- `--local` writes `devflow.local.toml` (not committed, merged on top). A list there replaces the committed list whole, so the first local edit of a phase copies the committed hooks (or presets) into it first and says so in `notes`. Removing the last entry of a local list leaves an empty list (`setup = []`, `presets = []`) rather than dropping the key, since a local file without the key inherits the committed list again; `env unset --local` of a recipe the committed file also sets brings the committed value back, and says so. Editing the committed file while a local list overrides it is allowed and reported, because it changes nothing on this machine. A credential in a recipe or a command is refused in the committed file and accepted with `--local`.
- `trust.needs_review` is `true` when the edit changed what an approval covers (hooks, `[env]`) and the project is not trusted now; `trust.review` is then `devflow trust`. Until a person approves it, the new hooks and recipes are skipped and a workspace set up meanwhile is `needs_attention`. An edit that returns to the approved content leaves the project `trusted`.
- Errors name the key (`hooks.setup[1]`, `env.DIRECT_URL`) and never repeat the command, name or value they complain about.

## Start a task

```sh
devflow --json --non-interactive switch -c agent/TASK > switch.json
status=$?                                   # 0 ready, 2 needs_attention, 1 error
path=$(jq -r '.workspace.path' switch.json)       # same value as .path
jq -r '.status' switch.json                       # ready | needs_attention | in_progress
```

1. Read `workspace.path` from the output and run every later command with that directory as the working directory. The worktree is outside the main checkout, under `worktree.dir` from `devflow.toml` (by default `../<repo>.worktrees/`), in a directory named after the sanitized workspace (`agent/a` becomes `agent-a`); `workspace.path` is authoritative, so do not build the path yourself.
2. The environment is in `<path>/.devflow/env`: `DATABASE_URL`, the `PG*` variables, `DEVFLOW_*` identifiers, `COMPOSE_PROJECT_NAME` (`df-<project8>-<instance8>`, unique to the workspace), `DEVFLOW_PORT` (the workspace's own port for its dev server: chosen once from `[worktree] port_range`, default 40000–49999, skipping ports other workspaces hold or something listens on, and kept for the workspace's life; `CONDUCTOR_PORT` is used where Conductor made the workspace (only when `CONDUCTOR_WORKSPACE_PATH` names it: an inherited `CONDUCTOR_PORT` alone is ignored); a new identity of a checkout gets a new port; an owned name, so recipes may use `${DEVFLOW_PORT}` and cannot set it; a workspace set up before ports existed gets one on its next `switch` or `setup`, as a repair of the env phase that runs no hook again; `ps` and `list --wide` show it as `app_port`) and the project's `[env]` recipes and presets (for example `DIRECT_URL`, `DB_*`, `SPRING_DATASOURCE_*`, `SQLALCHEMY_DATABASE_URI`). `DATABASE_URL` and `PG*` are absent when the project has no postgres service (`[services.<key>]` with `engine = "postgres"`) or the workspace was created with `--no-db`, and so are the presets and the recipes that reference them (a warning says which). When the service sets `extra_databases = ["test", "shadow"]`, the file also has `TEST_DATABASE_URL` and `SHADOW_DATABASE_URL` (generally `<NAME>_DATABASE_URL`): separate, empty databases for tests and migration shadow schemas, reached with the same login and password as `DATABASE_URL`. Point test runners and `prisma migrate dev` at them instead of trying to create a database (branch logins cannot). A reset empties them again; they are never cloned from another workspace or snapshot. A `valkey` or `redis` service (`[services.cache]`) adds one more variable, `REDIS_URL` by default or the service's `env`: `redis://:<password>@127.0.0.1:<port>/0` for the workspace's own cache branch, cloned from the data source, with a port and a password of its own. It is a secret like `DATABASE_URL`. Point test runners and queues at it; do not share one `REDIS_URL` between workspaces. A `mysql` service (`[services.sql]`, **preview**) adds its URL, `mysql://app:<password>@127.0.0.1:<port>/<database>`, as `DATABASE_URL` (the service's `env` if set, or `MYSQL_URL` when the project also has a postgres service, which owns `DATABASE_URL`; a collision is a configuration error naming both services) and the typed fields `MYSQL_HOST`, `MYSQL_PORT`, `MYSQL_USER`, `MYSQL_PASSWORD` and `MYSQL_DATABASE`, which `[env]` recipes may read (`${MYSQL_HOST}`) and cannot set. A project has at most one `mysql` service for now. The account is `app`, the database is the service's `database` (default: the project name as an identifier), the password is the branch's own and a secret. Creating a MySQL branch from a running source stops that source for a few seconds (below), so a `switch -c` that clones a MySQL source briefly interrupts the source workspace's connections: a client must reconnect. The container starts on `setup` and `switch`; if `switch` warns that it could not start (the port is taken), the service is `failed` in `services_state` with the reason: free the port and run `devflow --json service up` (the warning carries the `start_service` remedy). The `[env]` variables appear only once the scope is trusted (see below); until then the env phase is a required skip. Run commands that need it through `devflow exec -- CMD` (item 7), which applies it last, or load it yourself in a plain shell (`set -a; . .devflow/env; set +a`). The directory ignores itself; never commit it.
3. Choose where code and data come from with `--from WS` (code; needs `-c`) and `--data-from WS|snapshot:NAME[@vN]|branch:ID|empty` (data). Both are fixed once chosen. `--base REF` (needs `-c`) chooses where a new branch starts: any branch, tag or commit, resolved once and reported in `branch_start` (`commit`, `start`, `tracks`); `--base origin/x` for `x` makes `x` track `origin/x`. Without `--base` a branch that exists only as `refs/remotes/<remote>/NAME` is created there and tracks it (several remotes: `checkout.defaultRemote`, else a typed error with the `choose_base` remedy; devflow never fetches), and `--from WS` starts it at that workspace's HEAD. A repository that uses Git LFS or is a partial clone is refused before anything is created (libgit2 cannot check it out faithfully; the remedies are `install_git_hook` and `open_guide`) unless the person chose the native checkout (`[worktree] checkout = "git"`, accepted in `devflow.local.toml` only, and only when that is a regular file Git does not track, not a link: a shipped or linked one that sets it is a configuration error naming the file; Git itself then checks the files out and runs its own filters and hooks, which `devflow trust` does not cover; an environment that names a workspace that cannot be resolved is refused before anything is created, with the `clear_inherited` remedy). The result's `checkout` says who ran the checkout (`{"backend": "libgit2"}` or `{"backend": "git", "git": "git version …"}`); a native checkout that fails is not retried with libgit2 and the error names what survives (the `setup` and `reveal` remedies point at the worktree). A branch `ID` anywhere (`--data-from branch:ID`, `db branch delete ID`, `service NAME drop ID`) is a UUID or a unique prefix of at least 8 hex characters, with or without dashes: the short ids the listings show work; an unknown or ambiguous prefix is an error naming the candidates. `--data-from` defaults to the code source's database, or `empty` for the default workspace. A `sqlite` service (a database file at the same relative `path` in every workspace) has no server and no branches: `--data-from` takes `WS`, `snapshot:NAME[@vN]` or `empty` (`branch:ID` is refused), the default workspace's file is the project's own and is never replaced, and the workspace's file is exported as `SQLITE_PATH` (the absolute path) and `DATABASE_URL` (`sqlite://` and the absolute path; `SQLITE_URL` when a postgres service or a mysql one without an `env` claims `DATABASE_URL`). `receipt.services.<key>` is `{engine: "sqlite", database: <relative path>, source, owned, cloned: {method: reflink|copy}}`; a copy is made under SQLite's own locks and a writer that holds the source past `busy_wait` is a typed error with the `retry` remedy, never a torn copy. If a local branch NAME already exists, `switch -c` checks it out and `--from` only sets the payload and data source.
4. `--no-db` and `--no-hooks` skip those phases, and the skip is recorded permanently: a later `devflow setup` leaves them skipped and the workspace stays `ready`. Only `setup --new-instance` runs the services, env and hooks phases again.
5. If the exit code is 2, read the reason from the document, fix it (usually trust, see below, or the mise checks, see item 8) and run `devflow --json --non-interactive setup` inside the worktree. It resumes at the first incomplete phase.
6. A workspace stays `ready` only while the configuration it was set up under is current. When the main checkout's `devflow.toml` (with `devflow.local.toml`) adds a service or changes a service's section, or the workspace's own recipes change what `.devflow/env` holds, every affected workspace reports `needs_attention` with the `services` (for that service), `env` and `hooks` phases reopened, until `devflow setup` or the next `devflow switch` there completes them; `setup --if-new` does not skip such a workspace. The bindings and the configuration generation they were applied under are in `receipt.services.<key>` (`applied`). The same happens to a ready workspace whose bound container branch the catalog no longer has (for example a lost branch that was dropped): `services`, `env` and `hooks` are reopened, so setting the workspace up again provisions a new branch instead of keeping the obsolete connection (setup reopens them under the receipt lock; a missing or unreadable catalog proves nothing and reopens nothing; a workspace whose services were skipped with `--no-db` reopens nothing either, because its `.devflow/env` is written without services and the binding it kept is only a record of its data, so it stays `ready`). `--no-db` and `--no-hooks` skips are kept. A receipt written by an earlier 1.0 build is migrated in place by the next `setup`; a database binding the configuration cannot place is kept as `receipt.unmapped` and reported in `warnings` and by `doctor`, never exported.
7. **Commands that need the workspace's database go through `devflow exec`.** `devflow exec [--workspace NAME] -- CMD [ARGS…]` finds the workspace containing the current directory (any subdirectory; the nearest directory with a `.git` is the worktree root) or the named one, reads its `.devflow/env`, takes every name the workspace owns out of the inherited environment (what its configuration declares, set here or not, and every name in the `.devflow/env` of the workspace the environment came from), sets each variable over what is left (overriding whatever mise, a profile or the shell set) and replaces itself with `CMD`: signals, standard streams and the exit status pass through (a program that cannot start exits 127 when it is not found and 126 otherwise, like `env(1)`, with a message that never holds an argument). It never starts `CMD` against an unknown database: outside a workspace, in a checkout without `.devflow/env`, or with a symlinked `.devflow` or `.devflow/env` it exits 1 with a message that holds no value (`--json` is refused). It prints nothing of its own. A `--no-db` workspace therefore never gets the caller's `DATABASE_URL`, and hooks get the same treatment; execution controls such as `DEVFLOW_SETUP_ACTIVE` are never touched, and `--inherit NAME` (repeatable) or `DEVFLOW_INHERIT=NAME,NAME` keeps the caller's value of a name the workspace sets none for. A `.devflow/env` written by an earlier devflow (no `# devflow-owns v1:` manifest) is refused with the `setup` remedy, and so is an environment that carries `DEVFLOW_WORKSPACE_PATH`/`DEVFLOW_WORKSPACE_ID` of a workspace that cannot be resolved (the `clear_inherited` remedy): a hook or agent in that state opens a new shell or sets `DEVFLOW_CLEAR_INHERITED=1`. Use it for tests, migrations, a REPL, anything that connects: `cd "$path" && devflow exec -- bun test`; inside mise, `mise exec -- devflow exec -- bun test`, so mise sets its environment first and devflow's values win. Loading the file by hand (`set -a; . .devflow/env; set +a`) works in a plain shell and loses to anything that runs after it, mise included.
8. **mise checks, for hooks written by hand.** A command that goes through mise (`mise exec`, `mise run`, a shim) has mise's `[env]` applied over the variables devflow gives it: a later `_.file`, `mise.local.toml`, a plain `[env]` key or `DATABASE_URL = false`, a `mise.toml` in a subdirectory, an environment-specific file selected by `MISE_ENV`, a task's own `env`, `conf.d` or the global configuration can hand a hook the main checkout's database. Hooks that `devflow init` generates avoid it by construction (`mise exec -- devflow exec -- CMD`). Before the first setup hook the `hooks` phase reads the hooks' commands (a hook "runs mise" when `mise` is a command word of its string, also inside `sh -c '…'` and after `devflow exec --`; a command hidden behind `xargs` or a variable, or one that reaches mise through a shim, is not seen): a hook that runs `devflow exec` inside mise needs no check of the variables; for any other hook that runs mise devflow runs `mise exec -- sh -c …` in the worktree with exactly the environment the hook gets (the workspace's variables injected, `MISE_ENV` included; killed after 20 seconds; no tool is installed) and compares each variable of `.devflow/env` with what the process sees. Only variable names are ever shown, never values. If a variable is overridden or removed the phase is a required skip (`status` `needs_attention`, exit 2) and **no hook runs**; `receipt.phases.hooks.detail` reads "setup hook #2 would not get the workspace's variables as devflow sets them: mise resolves DATABASE_URL from another source than .devflow/env; …" and suggests `devflow exec`. The same happens when mise does not trust the configuration (asked with `mise env` for every hook that runs mise, because `mise exec` would trust it itself without a terminal; the detail gives `mise trust PATH`; devflow never trusts anything itself, and `devflow doctor` prints the choices), when the check cannot be made, and when mise is not installed while a setup hook runs it. A hook the check cannot stand for (a `cd` ahead of mise, `mise run`/`mise r`/`mise tasks run`, `mise -C`/`-E`, a `MISE_*` assigned in the command) is not blocked: `warnings` names it (`the setup hook 'NAME'` or `setup hook #N`, never its command) and recommends `devflow exec`. The setup hooks are checked once, when the `hooks` phase runs. The `switch` hooks get the same check before each switch that runs them: when it fails they are not run, `warnings` says why (`switch hooks were not run: switch hook #1 would not get the workspace's variables as devflow sets them: …`) and `remedies` has `open_file` for `devflow.toml`, while the switch itself succeeds. Those reasons say what is wrong and hold no command line (the way on is the `open_file` remedy), and the check does not depend on `.devflow/env` being there: the environment the hooks get is built from the receipt, so a removal after generated files were cleaned is checked all the same. The `teardown` hooks get it on `remove`, before any effect: a failing check refuses the removal (a forceable protection with the same `open_file` remedy), and `--force` removes the workspace without running them, with a warning. Fix mise's configuration, route the command through `devflow exec`, and run `devflow setup`, or run the hooks anyway with `devflow setup --skip-mise-check` (also on `switch`, which says so in `warnings`; `remove` has no such option): `receipt.mise_check_skipped_at` records when, `devflow list` shows `ready (mise check skipped)` and the setup summary says so. `devflow --json doctor` runs the same check for the current workspace as `mise-env` (a failure when a hook that would be refused is overridden, naming the variables; the setup hooks not routed through `devflow exec` are listed) and `mise-wiring` (what shells and editors get through mise: a warning that "shells in the worktree won't see the branch's variables through mise; commands devflow runs are unaffected"). `devflow_core::env_file::check_mise_delivery` (`mise env --json`) remains for a caller that starts daemons with `mise = true`.

Work inside the worktree as usual: commit with Git, run tests, start daemons with pitchfork. Do not edit `.devflow/` or the receipt in the worktree's Git directory.

## Finish a task

`devflow prune [NAME…] [--yes]` forgets the Git registration of worktrees whose directory is gone, as far as core allows. Without `--yes` (and always with `--json`) it only lists them: `{project, candidates[], confirmed, pruned[], refused[], changed[]}`, each candidate `{name, id, path, why, has_receipt, data[], refusal?, remedies?}`. A registration whose receipt still records data (service bindings, a branch being created, daemons devflow started), whose receipt cannot be read, that another devflow operation holds, or whose directory's folder is missing too (an unplugged drive) is kept with a `refusal` (`owns_data`, `receipt_unreadable`, `busy`, `parent_missing`); `owns_data` carries the `remove_workspace` remedy, the normal removal that drops the data. Each confirmed registration is looked at again under its locks; branches are never deleted. Exit 1 when something named was refused; the document then also has the usual top-level `error` (what was kept and why), `hint` and `remedies` (the refused ones' remedies, without repeats), next to the partial results.

Remove from the **main checkout**, not from inside the worktree: devflow refuses to remove the default workspace and the workspace that contains the caller's directory, and `--force` does not override either.

```sh
cd "$MAIN_CHECKOUT"
devflow --json --non-interactive remove agent/TASK --force
```

`--force` accepts a dirty or locked worktree and a failing `teardown` hook, and it skips untrusted `teardown` hooks, and ones the mise check refuses (see "mise checks", item 8), with a warning, so a cleanup script that passes `--force` does not run them. Without it, a protection (dirty, locked, untrusted teardown hooks, teardown hooks mise would not hand the workspace's variables, data that cannot be accounted for) stops the removal before anything changes; a failing `teardown` hook can only be detected after it ran, and it then stops the removal before the database branch or the worktree is touched. `--keep-data` leaves the database branch and the Valkey/Redis/MySQL branches in place (they show as orphans in `service list --orphans`), and records that in the workspace's record before the first effect, so a removal that stops half-way and is run again without the flag (the receipt it left still names the data as owned) does not drop them; without it their containers and volumes are removed by recorded identity. A removal accounts for every branch the receipt names before it changes anything: the bindings the workspace owns, the branch recorded as about to be created (a crash between its creation and its binding leaves that, and the removal drops it when this instance created it, judged again under the backend's lock), and a database an earlier build bound. Planning drops nothing; each drop then uses the backend's own journaled operation and decides on the branch again under the lock it holds for the deletion. A bound branch that cannot be inspected (the server or Docker cannot be asked, the project no longer configures the postgres service) is a forceable protection that says which and why; `--force` leaves it and says so in `warnings`. A branch recorded as about to be created that cannot be resolved (its server or Docker cannot be asked) is a forceable protection too, since the workspace's record in the ledger (see "Worktrees removed outside devflow") keeps naming it after the receipt goes: the error has the remedies `setup` (resume it, which recovers the branch by its recorded identity) and `reconcile_databases` or `reconcile_service`, and a forced removal reports it in `still_recorded` and `warnings`. The backend is recorded with the intent (`receipt.creating.engine`), because the configuration can change before the removal (a PostgreSQL `db` becomes a Valkey service): that backend is the one looked in, even when its service has left the configuration. A record from before that field is looked for in every backend (the PostgreSQL server by id, the container catalog by the key), and one that either has is decided there; absence from the configured backend alone proves nothing. Setup and activation honour the recorded intent before any service is touched: the receipt holds one such intent, the only evidence that a branch was made, and no binding, attachment or provisioning step of another service may clear or replace it. While a pending creation names another engine than its service is configured with now (a PostgreSQL creation that was interrupted, then `services.db` changed to Valkey), or names a service that is no longer configured while others are, the whole services phase fails up front with a problem that names the branch and offers the remedies reconcile (`reconcile_databases` or `reconcile_service`), `remove_workspace` and `open_file` (to restore the configuration), and nothing is bound (an earlier-sorting service is not attached either). When its service is configured with the engine it was begun on, that service is processed first, so the intent is resolved before another service can reach it. A binding clears the intent only when it names that service, on the same engine, and the branch it records is the one the creation was begun for; an attachment resolves nothing. A branch another instance created is left alone with a warning; `--delete-branch` also deletes the Git branch, and without `--force` it requires that branch to be merged into the default workspace's HEAD (the hint that offers `--force` repeats `--delete-branch` and `--keep-data` when you passed them, and a forced removal that could not delete the branch says so in `warnings`). Merge or push what you want to keep first.

"Before any effect" means the preflight: every refusal above comes before the first daemon is stopped, teardown hook run or branch dropped. A failure after that point (a teardown hook that fails, a drop that fails, the worktree that cannot be deleted) is a partial removal, an error that says what was done and what remains (`Already done: …. Still there: the worktree …; the workspace's receipt; …`), with the remedy `remove_workspace` to run it again; it converges, and a failing teardown hook or drop is forceable like the protections. A forced removal that went on without being able to tell what pitchfork runs (or without a pitchfork to ask, or over daemons of a gone checkout that it will not stop) lists in its result `may_still_run: {namespace, ids}`, the namespace devflow assigned and the daemon ids that may still be running (the namespace stays even when no id is known, until a listing that was read shows nothing running), since the receipt that could name them is gone. Whatever a removal could not account for (a branch it left, daemons it could not confirm stopped, an unread namespace) stays on the workspace's record, which keeps the namespace and the ids: the result lists it in `still_recorded[]` and `devflow gc` finishes it once a listing that was read shows nothing running. `--keep-data` releases the data (a later clean-up never offers it). A stop that ended half-way (some daemons stopped, others not, or the state unreadable afterwards) is a partial removal too, saying which daemons stopped (only a state that says no process runs counts: `stopped`, `errored`, `failed`, `available`), which still run, and which are not known (unlisted, in a state devflow does not recognise, or an entry that could not be read as pitchfork's, such as a pid that is not a number: whatever its status string says, a malformed record is never counted as stopped, in the report or in the forced removal's result; `daemons[].unreadable` says why).

## Each workspace runs its own branch's recipes

A project's configuration has two kinds of parts. The **shared** ones are read from the main checkout's working copy and never from a branch: `[project]`, `[services.*]` (engines, images, modes, ports, admin settings), `[data]`, `[integrations]`, `[pitchfork] autostart`, and `[worktree]` `dir` and `port_range`. A branch never reconfigures a shared server and never acquires a resource by renaming a service. The **recipes** are read from the target worktree's own `devflow.toml` (or `.devflow.toml`), which is versioned with the code: `[hooks]`, `[env]` recipes and presets and `[worktree] copy`; the pitchfork files already came from the worktree. The main checkout's `devflow.local.toml` overlays both, as it always did (it is checkout-wide), each part with its own fields: its shared fields (a `[services.db]` override, say) go to the main checkout's shared sections, its recipe fields to the workspace's recipes, so an override of a service an older branch lacks neither breaks that branch nor hides its recipes. What a recipe may reference and may not set (`${NAME}`, a name a service exports) depends on the services, which are the main checkout's, so it is checked on the recipes next to the main checkout's services, not on the branch's file next to its own; one inside a linked worktree is ignored (`doctor` says so). The main checkout is both sources at once.

- A branch file must parse as a whole with the same strict parser (unknown keys stay errors) and carry the same `[project] id`. Its shared sections are never applied: when they differ from the main checkout's, setup and switch add a warning (`recipes.differing` in the outcome) and `doctor` a `shared-sections` check, each naming the file and the section and never a value.
- Each operation resolves one effective configuration and keeps it for its whole run: a setup hook that rewrites `devflow.toml` changes nothing for that run (its remaining hooks, the switch hooks and the env phase work from what was read when the run began).
- **A branch without recipes** (its `devflow.toml` is missing, invalid, a 0.x shape, or another project's) is an explicit condition, not a fallback. The workspace is `needs_attention` (exit 2) with `recipes.source` `unavailable` and a typed problem; payload, `[env]` and hooks are required skips, so nothing of the main checkout's recipes runs, is copied or is exported. devflow still binds services and writes `.devflow/env` with its generated variables. The remedies are `use_default_recipes` (a button in the app, `devflow setup --use-default-recipes` or `switch --use-default-recipes` for scripts), then `setup`. The choice is recorded in the receipt (`default_recipes`, an optional field; receipts stay version 2) and holds only while the workspace has no valid file: once it has one, its own recipes apply, the choice is cleared and the outcome says so (`recipes.choice` `cleared`). devflow never borrows the main checkout's hooks silently. A first run in a repository whose `devflow.toml` is not committed yet therefore finds the condition in a new worktree, and says exactly that: `because.kind` is `not_committed`, the message names the workspace's start point (its commit) as having no `devflow.toml` and the main checkout's file as not committed (untracked, staged or ignored), and the remedies come in this order: `use_default_recipes`, then `open_file` for the main checkout's file (there is no `setup` remedy: the start point cannot have the file whatever setup does). `init`'s next steps already say to commit it.
- **A workspace set up by an earlier devflow.** Every workspace once ran the main checkout's recipes, so a receipt written then (it lacks `workspace_recipes`, which every receipt written since carries) whose branch has no valid recipes keeps them: it is not turned into `needs_attention`, its status and approval stand, and the first run that holds its receipt lock records the choice (`default_recipes`) and reports it once (`recipes.choice` `migrated`, a warning: the workspace keeps the default workspace's recipes, as before, until its branch has its own). A pre-change workspace whose branch has valid recipes that differ runs its own from then on, which reopens its env and hooks once; one whose branch file equals the default's reopens nothing. The generation of the hooks is adopted only for hooks that did run: the baseline of such a receipt is the default workspace's setup hooks, so a branch with other setup hooks (even with the same environment and services) has not run them, and its `hooks` phase reopens, alone, to run them once at the next setup, approved like any hooks (`list` and `--if-new` see it too).
- **Generations follow the effective configuration.** Services and their bindings follow the main checkout's shared part; hooks, env and `.devflow/env` follow the workspace's own recipes (the main checkout's for a workspace that chose the default recipes). A change to a branch's own `[env]` or setup hooks reopens that workspace only (a change to the setup hooks alone reopens the `hooks` phase alone, recorded as `hooks_generation` in the receipt; `switch` and `teardown` commands are not part of it), and a change to the main checkout's hooks reopens no workspace that has its own file. A receipt from before it was recorded adopts the generation it finds, so an unchanged recipe reopens nothing.

## Trust in automation

`[hooks]` commands are arbitrary shell, and `[env]` and pitchfork's `pitchfork.toml` decide what runs in the worktree's processes, so devflow acts only on content a person has approved. Approval is the SHA-256 of a versioned **scope** (version 2): every hook command with its name and effective timeout, the `[env]` presets and recipe templates (never generated values or passwords), and the workspace's pitchfork configuration (`pitchfork.toml`, `.config/pitchfork.toml` and their `.local.toml` overlays, every daemon field). The recipes are the workspace's own (see above), so a worktree whose recipes and pitchfork files equal the main checkout's has the digest it always had. `trust.toml` keeps **several** approved digests per project (project id and main-checkout path), each with its scope version and date: any workspace whose scope digest is in the set is trusted, so approving one workspace never revokes another's. `devflow trust` adds the digest of the workspace it is run in (identical content is approved once), `devflow trust --revoke` removes that digest only and `devflow trust --revoke-all` every one of the project; beyond 20 approvals the oldest are dropped, never the one being made. An entry written by an earlier devflow is the first of the set and applies as before; an approval made by version 1 (hooks only) authorizes nothing (`trust.format_changed`). `devflow --json trust` inside a worktree reports its directory as `path`, `recipes` (where its hooks and `[env]` come from), `approvals` (every digest on record, with version and date) and the scope. The approval does not cover scripts the commands invoke. A project with no hook, no `[env]` and no pitchfork configuration has nothing to approve.

| Situation | What happens |
| --- | --- |
| Scope trusted | `setup` commands run in order in the worktree with the env applied, and the `[env]` recipes and presets are written to `.devflow/env` |
| Setup hooks or `[env]` untrusted, and no prompt is possible (`--non-interactive`, `--json`, or stdin or stderr is not a terminal) | Hooks are skipped and `.devflow/env` holds only what devflow generates; the workspace is `needs_attention` and the worktree is kept |
| `switch` hooks untrusted, workspace `ready` | Not run; a warning is added and the switch succeeds |
| `teardown` hooks untrusted | `remove` is refused; `--force` skips them with a warning |
| `teardown` hooks that mise would not hand the workspace's variables | `remove` is refused before any effect; `--force` skips them with a warning |
| `switch` hooks that mise would not hand the workspace's variables | Not run; a warning and an `open_file` remedy are added and the switch succeeds |
| `DEVFLOW_TRUST_HOOKS=1` | Trusts the whole scope (hooks, `[env]`, pitchfork processes) for that one run. Use it in CI, or for repositories whose configuration you have read. Do not set it for code you did not review. |

The usual setup is a one-time `devflow trust` by a person, which then covers every agent task in that project until the scope changes. `devflow --json trust` shows everything one approval covers and the trust state without approving anything. `scope` has `version` (2), `hooks` (`setup`, `switch` and `teardown` lists of `{name, run, timeout}`, and the default `timeout`), `env` (`presets` and `vars`: the templates; a variable whose name says it holds a credential, such as `DB_PASS`, `SESSION_KEY` or `MY_CREDENTIAL`, shows `***` when its template has literal text, exactly as in `env list`, and a template of `${NAME}` references only is shown as written; the same holds for the `env` tables of pitchfork files and for the text review; the `digest` is the real scope's), `processes` (`layers`: one per pitchfork file with content, lowest precedence first, each with its `daemons` and `shared` content, or a `problem` and `sha256` for a file that could not be read; and `autonomous`: every `{file, daemon, trigger}` where pitchfork starts a daemon on its own with `cron`, `watch`, `boot_start` or `auto`) and the `digest`. `trust.state` is `nothing_to_approve`, `trusted` or `untrusted` (with `previously_trusted` and `format_changed`). `devflow trust -y` (`--yes`) approves exactly that scope without asking and prints it, so run it only after reading it, autonomous triggers included. `devflow trust --revoke` withdraws the approval of the scope in hand and `--revoke-all` every approval of the project (`revoked`, and `revoked_count` for `--revoke-all`). An approval handed to a single operation (the terminal's "Run once" or "Trust and run", the GUI's dialog) is bound to the digest that was shown: core compares it with the scope of the workspace the operation acts on after the payload exists and before any hook, recipe or process runs, and refuses the run (`needs_attention`, "differs from what you reviewed") if that workspace holds something else, for example an existing branch with other hooks. `doctor` judges the worktree it runs in and says which directory (its `recipes` check says which file the hooks and `[env]` come from, `shared-sections` names the shared sections a branch's file has that are not applied, and `local-config` a `devflow.local.toml` inside a worktree that is ignored).

## Processes

devflow does not supervise anything: pitchfork does, and mise delivers the environment. devflow decides whether it may *ask* pitchfork to start or stop a workspace's daemons, and reports what pitchfork says afterwards.

```sh
devflow --json pitchfork status        # installed? version, `unsupported` (a typed problem when the release is older than 2.20.0 or unreadable), supervisor, proxy, conflicts, install plan
devflow --json up [WS] [--daemon NAME]… [--timeout SECONDS] [--services]   # pitchfork start -q NAMESPACE/NAME…, then list --json
devflow --json ps [WS | --all]         # daemons of the workspace(s): state, pid, ports, url, and the workspace's app_port
devflow --json down [WS | --all] [--force] [--services]   # pitchfork stop NAMESPACE/NAME… (the workspace's running daemons)
```

devflow never uses `--local`, `--all` or `--global` with pitchfork: `--local` selects the daemons of every configuration from the working directory up to the root, so a worktree inside another project would start and stop that project's daemons too. It starts and stops exactly the fully qualified ids `<namespace>/<name>` of the workspace's own daemons.

- **Namespace.** For a project with a `pitchfork.toml`, the env phase writes a machine-local `pitchfork.local.toml` in each worktree: a marker comment, `namespace = "df-<project8>-<instance8>"` (the receipt's `COMPOSE_PROJECT_NAME`) and `worktree_label`, nothing else, and adds it once to the repository's `info/exclude`. A file that is not exactly that is never touched. If a committed pitchfork file declares its own `namespace`, pitchfork would refuse the siblings that disagree, so devflow writes nothing and says so in `warnings` and `doctor` (`pitchfork-namespace`), and such a workspace is refused for `up` and `down` (`foreign_namespace`, below). Daemons of a workspace are the ones of its assigned namespace in `pitchfork list --json`; proxy URLs come from `pitchfork proxy status --json`, matched by the worktree directory.
- **Environment.** `.devflow/env` reaches daemons through `devflow exec`: `run = "devflow exec -- CMD"` on each daemon, with `mise = true` for the toolchain (devflow exec runs inside mise and applies the file after it), which is what `devflow init` proposes for every daemon it gives `mise = true` (the repository uses mise), whatever the project exports, because `.devflow/env` always exists and `up` refuses an unwrapped daemon with `mise = true` unless mise loads it; for a project with a managed service (PostgreSQL, Valkey, Redis or MySQL, configured or proposed) or `[env]` content it wraps the commands of repositories without mise too, and the same condition proposes `mise:env-file`; a project with neither and without mise keeps its daemon commands as they are. A mise task (`mise run dev`) cannot be wrapped: it gets `mise = true` only together with the wiring. Only a `run` that is wholly one simple `devflow exec -- CMD` counts (optionally behind `NAME=value` and `exec`, redirections allowed): `devflow exec -- true; npm run dev` starts the app outside the wrapper, and `devflow exec -- mise exec -- npm run dev` hands it mise's values, applied after devflow's, so neither is treated as delivered, and a daemon with `mise = true` is checked like any other that relies on mise. The test after `devflow exec --` is conservative: any occurrence of `mise` as a word counts, in a string for `sh -c`/`bash -c`/`zsh -c`/`eval` (`devflow exec -- sh -c 'env -u X mise exec -- bun run dev'`), behind a wrapper with options (`env -u X`, `sudo -E`, `timeout 5`, `nice -n`, `nohup`, `xargs`, `command`, `exec`, `time`) or in a path ending in `/mise`; a command word that is a shell expansion (`devflow exec -- $TOOL run`) is not followed; anything the scanner does not understand is not wrapped. The hook gate applies the same rule to `through_devflow_exec`, so a `mise exec -- devflow exec -- sh -c '… mise …'` is an unprotected use, and so is a `mise` in the same string that the scanner did not classify next to a protected use (`mise exec -- devflow exec -- true; echo "mise exec -- bun run migrate" | sh`: every occurrence of `mise` as a word must be a protected use, or the command is unprotected), and a hook that runs `devflow exec -- sh -c 'env -u X mise …'` is checked like any other that runs mise. A daemon can still get it from mise alone (`mise = true` and `[env] _.file = ".devflow/env"` in `mise.toml`), which loses to anything mise applies later. devflow never writes environment or credentials into a pitchfork file (pitchfork keeps daemon environments in its state file). `doctor` (`pitchfork-env`) warns about daemons without the mise wiring.
- **Namespace ownership.** A workspace acts only through the namespace devflow assigned to it, the receipt's `df-<project8>-<instance8>`, never through whatever its pitchfork files declare. Before a daemon is attributed to a workspace (`ps`), started or stopped, the namespace the files give must equal it, or the command is refused with `foreign_namespace` ("the pitchfork namespace does not belong to this workspace"). `--force` does not override it. A start first rewrites devflow's own `pitchfork.local.toml` when it is missing or stale (that is how a file edited to name another workspace's namespace is repaired); a hand-written file or a committed `namespace` is never touched, so those workspaces stay refused. `ps` shows no daemon for a workspace whose files name another namespace. The digest leaves out only the `namespace` and `worktree_label` equal to the values devflow generated for that workspace; any other value of either key, in any file, is part of the scope, so pointing a file at another namespace also drops the approval.
- **Start** is refused, with a typed reason, unless pitchfork runs and is a release devflow supports (`--version` exits 0 and names 2.20.0 or later, the release of `supervisor status --json`; `list --json` and `proxy status --json` are older, and `start` and `stop` take `namespace/name` ids since 2.0.0; `pitchfork status` has `unsupported`: `{tool, reason: too_old|unreadable, found, minimum}`), the workspace is `ready`, the namespace is the assigned one, that worktree's own scope (hooks, `[env]` and pitchfork files) is approved, and no daemon about to start also starts on its own (`cron`, `watch`, `boot_start`, `auto`). What a started daemon `depends` on must be a daemon of the workspace's own files (a plain name, or its own namespace): pitchfork starts dependencies by itself, so one that points anywhere else is refused with `external_dependency`. Only a daemon's highest-priority definition counts (pitchfork replaces a daemon defined in several files whole), and `ps` judges each daemon on its own closure: starting everything is refused, but a daemon that depends on nothing outside the workspace stays `startable` and `up --daemon NAME` starts it. Plain daemons can still be started by name (`--daemon NAME`) once approved. A start that is already satisfied is not repeated. pitchfork is run with a timeout (default 60 s); afterwards the real state is read back, so a timeout or a failure is reported with the state at that moment and exits 1.
- **The last look.** The slow parts of a start (the mise check, asking pitchfork what runs) come first. Immediately before `pitchfork start`, `stop` or a removal's stop, devflow reads the files again, `devflow.toml` included (the project in hand is a snapshot: readiness against the configuration's generations, the scope and the approval are judged on the configuration as it is then), and checks readiness, namespace, approval and (for a start) that the content is the one it first checked; any change refuses the operation (`not_ready`, `not_approved`, `foreign_namespace`, …), and a `devflow.toml` that cannot be read then is `unreadable` (a stop answers it with `--force`). The instant between that look and pitchfork reading its own files remains (see SECURITY.md).
- **Stop** runs only while the worktree's scope still matches the approval, because pitchfork runs lifecycle hooks (`on_stop`, …) from the current file. Otherwise it is refused; `--force` stops anyway and the report carries a warning. A state devflow cannot read (the listing fails, its output is over the 4 MiB devflow keeps, or pitchfork lacks a feature) is never read as "nothing runs": it is refused with `state_unknown`, and `--force` asks pitchfork to stop the daemons the workspace declares without being able to tell which ran. So is a listing that cannot show the workspace's daemons stopped: for a stop or a removal only `stopped`, `errored`, `failed` and `available` count as not running (`running`, `waiting` and `stopping` as running; a status counts by its leading word, so `running (ready)` is running and `failed: exit 3` is failed, and one classifier, `pitchfork::DaemonStatus`, is shared by the listing, `ps`, the reports and the app's counts and pills), a daemon of the workspace in any other state (`unknown`, one a later pitchfork adds), a malformed required field (an `id` that is not `namespace/name` or that contradicts the `namespace` field, a status that is missing or not text, a pid that is not a number) and an entry that cannot be read at all are `state_unknown` (forceable), and a stop whose listing afterwards shows one of them is not ok. **A supervisor that is down is not "nothing runs"** (pitchfork's daemons survive their supervisor: SIGKILL of the supervisor leaves them running, and a restarted one takes them back): devflow records in the receipt, before it asks pitchfork to start daemons (`up`, autostart, the app's start, `restart`), `processes: {started_at, ids}` (the qualified ids), and clears it after a stop whose result it read back with the supervisor up and nothing of the namespace active. With the supervisor down and a recorded start, `down` and `remove` are refused with `state_unknown` (the message says the supervisor is down and the daemons devflow started may still run; the hint is `pitchfork supervisor start`, then `devflow down`, or `--force`); `down --force` cannot stop anything and returns a report that is not ok, and a forced removal goes on with a warning and stops nothing. With the supervisor down and no recorded start, `down` and `remove` proceed with the warning "pitchfork's supervisor is down; devflow started no daemons here, but processes started outside devflow can't be checked". The result of a start or stop is verified against the namespace it acted in (the receipt's, captured when it decided to act) in the raw `list --json`, not through the workspace's files as they are afterwards: a daemon of that namespace that still runs makes a stop not ok, and an attribution that changed while the operation ran (the files now name another namespace) is a not-ok report with `state_error`. `restart` returns the stop's report, and starts nothing, unless the stop left none of the workspace's daemons active and its state could be read. **One operation at a time.** `up`, `down`, `restart`, `remove` and `setup --new-instance` each hold the workspace's process lock (`devflow/process.lock` in its Git directory, always taken before the receipt lock) from the record of intent through the effect to the read-back, so a stop cannot read "nothing runs" between a start's record and its effect and erase the record; a second operation waits two seconds and then fails with `Busy` ("another devflow operation is starting, stopping or replacing the daemons of '…'"; exit 1, or `in_progress` from `setup`). `remove` stops the workspace's running daemons first (before teardown) and lists them in `stopped_daemons`; it needs a stop whose result it saw (pitchfork succeeded, the state could be read and verified back, nothing of the workspace is active) and otherwise it is a forceable protection (`--force` goes on with a warning); with a namespace it cannot attribute, or a pitchfork that is on `PATH` but cannot be asked (it does not run, as a mise shim without a version, or lacks a feature: `state_unknown`), a forced removal leaves the daemons running and says so. **A workspace whose checkout is gone** (the directory was deleted, or sits on a drive that is not connected) is planned from its receipt alone, which lives in the Git directory: the namespace devflow assigned and the ids it recorded starting name its daemons, and pitchfork is asked what runs under that namespace from an empty directory of devflow's own. They are never stopped: a stop makes the supervisor run `on_stop` and `on_exit` itself, from the configuration at the directory the daemon was started from, whoever asks and from wherever (pitchfork 2.29.0 and 2.30.1 have no stop that skips them; the ids establish whose daemons these are, not an approval to run anyone's hooks), so devflow has no stop path it can verify to be safe. Daemons found running, a state that cannot be read, and a pitchfork that is not on `PATH` while the receipt records a start are `state_unknown` (forceable, the receipt stays); only a listing that was read and shows nothing of the namespace running lets the removal go on without a word. `prune` keeps such a registration while the receipt records a start. A workspace with no pitchfork file and one devflow never set up proceed without asking, and so does a machine with no pitchfork on `PATH` at all, with a warning in the removal result ("pitchfork isn't on PATH, so devflow couldn't check this workspace's daemons") when the workspace has devflow's namespace file or a recorded start.
- **Approval** is asked at a terminal as for hooks (`up` shows the worktree's scope); `--json` and `--non-interactive` never ask, run `devflow trust` first.
- **Install and proxy are offers.** `pitchfork install` runs `mise use -g pitchfork@latest` only with `--yes` or after a terminal confirmation (the JSON form without `--yes` returns `needs_confirmation: true` and runs nothing), and prints brew and cargo instructions when mise is missing. `pitchfork proxy` and `doctor` print the proxy commands (`pitchfork settings set proxy.enable true --global`, a supervisor restart, `pitchfork proxy setup`, which uses sudo); devflow never runs them.
- **Documents.** `up` and `down`: `{project, ok, workspace, path, namespace, action, ran, timed_out, error, daemons[], state_error, warnings}` (`state_error` is also how a result that could not be verified is said, for example an attribution that changed during the operation; `daemons[]` then includes the raw daemons of the namespace devflow acted in). `ps`: `{project, workspaces[]}` of `{workspace, path, namespace, installed, version, configured, supervisor_up, daemons[], observation, proxy, error, can_start, can_stop, autostart, autostart_blocked}`, where `observation` is `{complete, reasons[]}`: `complete: false` says `daemons[]` (its `not started` fallbacks and "nothing runs") was not observed, because pitchfork could not be used or its listing failed, an entry could not be read or a daemon is in a state devflow does not know (the judgement a stop makes), the files could not be read or name another namespace, the workspace's receipt cannot be read (no namespace is assigned, so every listed daemon would be filtered out), devflow's `pitchfork.local.toml` is missing while the receipt records a start or pitchfork lists daemons under the assigned namespace (the same filtering; a start writes the file again), or the supervisor is down while the receipt records a start devflow has not seen stop (pitchfork's daemons survive a supervisor that crashed); a stop in that state is the forceable `state_unknown`; and `can_start` and `can_stop` are `{allowed, reason, refusal{kind, …}}` (`kind`: `not_installed` (also a pitchfork that runs but lacks a feature: its `detail` names it), `nothing_configured`, `unreadable`, `not_ready`, `foreign_namespace` (`expected`, `found`, `file`), `not_approved`, `autonomous_triggers`, `unknown_daemon`, `external_dependency` (`daemon`, `dependency`), `state_unknown` (`detail`, and a `hint` when the generic advice would mislead, as for a supervisor that is down; the only one besides `not_approved` that `--force` answers), and `mise_delivery` and `workspace_env`, which `ps` reports exactly as `up` would answer them: daemons that pitchfork runs through mise (`mise = true` on the daemon, else `[settings.general] mise = true` resolved over every pitchfork file in pitchfork's own order, `pitchfork.local.toml` first and the daemon's own value winning) and are not wholly `devflow exec -- CMD` start only when two questions agree with `.devflow/env`: the shared gate the hooks are checked by (`env_file::check_workspace_env`, from the file alone: every value as devflow wrote it and every owned name without a value absent, so `overridden`, `removed` or `reintroduced`, the check `doctor` shows as `mise-env`), then what mise resolves on its own (`mise env`: such a daemon gets `.devflow/env` from mise alone, `not_loaded` when it does not). `workspace_env` (`daemons`, `detail`, `remedies`) is a `.devflow/env` written by an earlier devflow, without the list of owned names (the remedy is `setup`), or an environment that names a workspace that cannot be resolved (`clear_inherited`); neither is a state of mise. The check runs only when everything else allows a start and a daemon relies on mise, once for all of them, and each daemon's `startable` is judged on its own closure) and a daemon is `{name, id, state, pid, ports, url, error, triggers, configured, startable}`. A refused `up` or `down` is the usual error document with `hint`.

## Worktrees created by other tools

Four things make a worktree that another tool created ready, from most to least dependable: the host's own setup script (`devflow integrate HOST`), a wait in the script or agent that uses the workspace (`devflow wait`, `setup --wait`, `exec --wait`), the Git hook, and `devflow setup` run by hand.

### Waiting

- `devflow wait [PATH|NAME] [--timeout D]` (D: `90s`, `10m`, `1h30m`, or seconds; default `15m`; `0` looks once). It looks at the workspace's setup lock without holding it (each look is one non-blocking attempt, released at once) until no run holds it, then reads the receipt. Exit 0: ready. Exit 2: `needs_attention`, still running at the timeout, or never set up (nothing held the lock and no receipt appeared within a 3 s grace). Exit 1: an error (no workspace, an unreadable receipt). A devflow started by a hook (`DEVFLOW_SETUP_ACTIVE=1`) looks once, because it would only wait for its own parent.
- JSON (`wait`, and `setup --wait` when it had to wait): `{project, workspace, path, status, settled, waited_ms, timeout_ms, problems[], detail, remedies[]}`; `settled` is `ready`, `needs_attention`, `still_running` or `not_set_up`; `problems[]` are the failed or required-skipped phases `{phase, state, detail}`.
- `devflow setup --wait [--timeout D]` runs the setup; if another run holds the workspace it waits for that run and reports how it ended (it does not run the setup a second time). `devflow exec --wait [--timeout D] -- CMD` waits the same way and starts the command only when the workspace is ready; otherwise the command is not started and the exit status is 2 (needs attention, still running at the timeout, never set up), with the usual explanation and hint on standard error. Once the command starts its own status is the result (the command's own 2 is indistinguishable from the workspace's, as for any wrapper).

### Agent hosts: `devflow integrate`

`devflow integrate [HOST] [--remove] [--print] [-y]`, `HOST` one of `t3`, `claude`, `conductor`, `cursor`. The file is the main checkout's (commit it so every clone gets the setup); an interactive run asks before writing unless `-y`, a non-interactive one writes. Without a host it lists them: `{project, hosts[]}` of `{host, label, file, detected, found[], state}` (`state`: `configured`, `not_configured`, `conflict`). With one: `{project, host, file, removing, written, would_write, printed_only, already_done, conflicts[], add_by_hand[], notes[], diff[], remedies[]}` (and `error` when something was left alone; the exit status is then 1). Writes are additive: JSON keeps key order and every other setting, TOML keeps comments and layout, a file that is not valid JSON/TOML (comments in `.json` included) is an error naming the file and line and is never rewritten, the file is read and written through directory descriptors opened from the checkout one component at a time, each looked at with `lstat` and confirmed after the open, so a link anywhere on the way (the file itself included) is refused at plan and again at apply, even when it appears while a confirmation prompt is open; the write installs a staged file in the verified directory and refuses a file that changed since the plan. Removing an entry from a file that is not there writes nothing. The shown diff masks values under secret-looking keys and what `redact` recognises (under `--print` too); the written content is the file's own. A script that is not devflow's (`conflicts[]`: `{item, reason}`, naming the script or key, never its contents) is left alone and the rest of the change is still made, except for Claude Code whose two hooks go together. `add_by_hand[]` is the line to add to the script that is in the way.

- **T3 Code**: `t3.json`, script `devflow setup` = `devflow setup --wait` with `runOnWorktreeCreate: true` and `async: false` (schema: `packages/contracts/src/t3ProjectFile.ts` in pingdotgg/t3code). The script runs in the new worktree; T3 Code uses the first script with `runOnWorktreeCreate`, so one of someone else's with the flag is a conflict. The file's scripts are imported in the project's settings. No teardown: `devflow gc` reconciles worktrees T3 Code deleted.
- **Claude Code**: `.claude/settings.json` hooks `WorktreeCreate` → `devflow integrate claude-create` and `WorktreeRemove` → `devflow integrate claude-remove`. `claude-create` reads `{"name": …, "cwd": …}` on stdin, creates (or enters again, when the name is reused: never the main checkout, even when it is on that branch, and only a workspace whose receipt says it was created as that one) workspace and branch `worktree-NAME`, non-interactively (hooks approved by `devflow trust` run; otherwise the workspace is not ready), and prints **only** the worktree's absolute path as the last line of standard output: descriptor 1 is pointed at standard error for the whole run, so nothing a child writes can be read as part of the path. A workspace that is not ready, or any error, exits non-zero (Claude Code fails the creation; the worktree stays and a second creation resumes it). `claude-remove` reads `{"worktree_path": …}` and refuses a path that goes through a symbolic link (nothing is resolved, so a stored path that became a link to another workspace removes nothing), takes the workspace Git registered at exactly that path (its Git directory must be the registered one), removes it without `--force` (a dirty worktree, a failing teardown hook or an unknown daemon state refuses, exits 1, and Claude Code keeps the directory), keeps the Git branch, and exits 0 without doing anything only for a path that is positively not a devflow workspace's (in no repository, or in one without a `devflow.toml`); a project it cannot read (an invalid `devflow.toml`) is an error, because Claude Code reads exit 0 as removed. When the directory is already gone, the session's `cwd` finds the project: a worktree Git still has registered is removed too (its data dropped, the registration forgotten), but daemons recorded for a gone checkout are never stopped by devflow, so they refuse the removal (non-zero exit, listed in the message; Claude Code counts the worktree as removed because its directory is gone). Without `cwd`, or with nothing registered, it is a no-op. A removal that stopped half-way (`PartialRemoval`) exits non-zero and says what was done and what remains. Neither has `--json`.
- **Conductor**: `.conductor/settings.toml` `[scripts] setup = "devflow setup --wait"` and `archive = "devflow -C \"$CONDUCTOR_ROOT_PATH\" remove \"$CONDUCTOR_WORKSPACE_PATH\""`. The archive script never forces: a dirty workspace, a failing or unapproved teardown hook, or daemons whose state is unknown make it exit non-zero and say why, and it is unverified whether Conductor then still archives or stops (its documentation does not say). `CONDUCTOR_PORT` is the first of ten ports Conductor allocates; devflow uses it as the workspace's app port when present at creation.
- **Cursor**: `.cursor/worktrees.json`, `devflow setup --wait` first in `setup-worktree` (and in `setup-worktree-unix` when it exists); a key that points at a script file is a conflict. Cursor deletes worktrees past `cursor.worktreeMaxCount` (25), even ones created with `git worktree add`; `devflow gc` covers them.
- **Codex**: no file is written (its local-environment file format is not documented). Its detached-HEAD worktrees are adopted under their directory name.
- `devflow init --plan` lists the hosts the repository shows signs of (`t3.json`, `.conductor/`, `conductor.json`, `.cursor/`, `.claude/`); `init` offers them at a terminal and, unattended, sets up only the hosts named with `--integrate HOST`. `doctor` reports a used host that is not set up (`integration-<host>`, remedy `integrate_host`) and a relative `core.hooksPath` that a new worktree lacks (`git-hook-path`).

### `.worktreeinclude`

Gitignore syntax at the repository root (read from the source checkout, else the main one; a symbolic link or a file over 256 KiB is not read). A path is carried over when a pattern matches it **and** Git ignores it, so tracked files are never duplicated. They are merged after `[worktree] copy`, cloned the same way and listed in the setup outcome's `payload[]` and in the payload phase's detail (`N selected by .worktreeinclude`). An ignored directory that a pattern matches is one entry; it is looked inside only when a pattern names it (a path under it, or `**/` followed by its name), within 20,000 entries and 12 levels, and the outcome says when the bound was reached. The `dotenv` diagnostics cover included `.env` files.

### The Git hook

Install the Git hook once per repository: `devflow hook install`. It adds a `post-checkout` hook (respecting `core.hooksPath`) that runs `devflow setup --if-new` when a new branch is checked out into an empty worktree. That covers `git worktree add` and tools such as T3 Code and Claude Code that use the git CLI. Git does not copy `.git/hooks` on clone, so a fresh clone gets the hook only through `core.hooksPath` or a template directory. A relative `core.hooksPath` is resolved inside each worktree: a directory that is not part of the checkout (husky's generated and ignored `.husky/_`) does not exist in a new one, so the hook never fires there; use the host integration.

- `[integrations] git_hook = "synchronous"` (default) makes `git worktree add` wait for the whole setup (4.3 s for a 4 s hook). `"background"` starts `devflow setup --if-new --from-git-hook --detached` in its own process group, with Git's own variables removed, no standard input and its output appended to `devflow/logs/git-hook.log` in the worktree's Git directory, and returns at once; nothing is started for a worktree that is ready. Wait with `devflow wait`. The section is part of no approval and no generation.
- It does nothing when the worktree's receipt is `ready`, and resumes any other receipt.
- It does nothing unless `devflow` is on the `PATH` of the process that runs Git, which matters for GUI tools started outside your shell.
- `hook install` never edits, moves or wraps a `post-checkout` hook devflow did not write: it refuses with a typed error (plain words naming the file, never its contents) and the remedies `copy_hook_line` (`path`; no `command`) and `open_file`. The hint, and the app's "Copy the line" button, is the line devflow's own hook is made of (core's `githook::HOOK_LINE`), to add by hand at the END of that hook (a line after an `exit` never runs; an earlier `exit` is not changed): `devflow_status=$?; if [ -n "${1:-}" ] && [ "${1#*[!0]}" = "$1" ] && [ "${3:-}" = 1 ] && [ -z "${DEVFLOW_SETUP_ACTIVE:-}" ] && command -v devflow >/dev/null 2>&1; then devflow setup --if-new --from-git-hook || echo "devflow: setup failed; run \`devflow setup\` in $(pwd) to retry" >&2; fi; (exit "$devflow_status")`. It runs setup only for a branch checkout (flag 1) from the all-zero previous HEAD (nothing for a file checkout), defaults every variable (works under `set -u`), keeps the status the hook had before it, and a failing setup only prints a hint. The line is shell: from a hook in another language, run `devflow setup --if-new --from-git-hook` under the same conditions. `doctor` reports a hook that contains the line as configured and otherwise offers the same two remedies. `hook uninstall` removes a hook devflow wrote (`{"removed": BOOL}`) and never one it did not write. One exception for dev builds: an unreleased devflow wrapped a foreign hook (it moved it to `post-checkout.devflow-original` and installed a wrapper); `hook install` leaves such a wrapper as it is, `doctor` says it is a wrapper from an older devflow, and `hook uninstall` renames the original back.
- It always exits 0 so Git does not report the worktree as failed, and it stays silent when another devflow process is already setting the worktree up. Check `devflow --json list` for `needs_attention`, or read the setup logs under the worktree's Git directory (`devflow/logs/`).
- `git worktree add --orphan`, `--no-checkout` and libgit2-based tools skip the hook. Run `devflow setup` in those worktrees.
- Adopted worktrees take the default workspace as code and data source.
- `DEVFLOW_SETUP_ACTIVE=1` prevents re-entry from inside hooks.

## Worktrees removed outside devflow

Agent hosts (T3 Code, Cursor, Codex, Claude Code) and `git worktree remove` delete a worktree without asking devflow, and Git deletes the workspace's receipt with it. devflow keeps a record of what each workspace owns in the repository's common Git directory (`devflow/workspaces/<instance id>.json`, 0600, no credentials; written by every receipt write, so a workspace set up before records existed gets one the next time it is set up or entered (`setup --if-new` on a ready workspace writes it before it answers `skipped`, provisioning nothing), or when `gc` looks), and `devflow gc` works from it. The record is written first: a save whose Git directory is gone (a removed worktree must not be resurrected) or is not a worktree's administrative directory fails before anything is provisioned, rather than going on without a record. A record is acted on only by the repository directory it was written for, and the path never proves it (a repository copied to another machine at the same absolute path, or restored from a backup, keeps every path and gets other directories): the record holds the repository's directory identity (inode and birth time), and it moves to a new path only when the identity is the same and the old checkout is gone. A copy, a record that does not say which directory it was written for, a file system that gives no identity (also when neither side has one: the same path is what a copy has too), and a receipt write in a copy are all `unknown` and never refresh the record (`cause: other_checkout`; `common_dir` is where it says it was written). Only the person's word binds it (below); where the file system gives no identity the confirmation is also remembered on this machine, for that path and record, outside the repository (`<data dir>/record-bindings/`), so that a copy of the repository does not carry it. The receipt, its locks, its hook logs and the hook runner's log directory are written only into a Git directory that is still there (at most one level is created, below a parent that exists): one Git removed is never brought back, the write or the run fails.

- `devflow --json gc [--all]` lists and changes nothing: `{project, inventory: {project, base?, entries[], notes[]}}`. Each entry is `{instance?, workspace, class, cause?, reason?, path, recorded_path?, branch?, has_record, removing, created_at, last_active_at, branches[], namespace?, daemons[], merge?, generation?, removable, not_removable?, remedies?}`. `class` is `active` (registered, directory present, receipt matching the record), `moved` (registered elsewhere, same instance), `missing` (registered, directory gone: what `prune` sees), `removed_elsewhere` (no registration and no directory) or `unknown` (an unreadable record or receipt, a server or Docker daemon that cannot be asked about a branch it names, a missing parent directory such as a disconnected drive, a record written for another copy of the repository, a directory Git does not know, a locked registration (Git's mark for a worktree on a portable device), an instance that is live in another worktree); `cause` says which unknown (`other_checkout`, `uninspectable` and `checkout_not_openable` among them). Only "not found" is absence: a permission or I/O error when looking at a path, or a registered directory Git cannot open as a checkout, is `unknown`, never `removed_elsewhere` or `missing`. Anything not positively identified is `unknown` and never removable. Each `branches[]` is `{service?, engine?, id, pending, state, size_bytes?, container?, memory_bytes?, ready?, generation?, volume?}` (`ready`: the backend has it ready, not being made or failed; `generation` and `volume`: what the backend had when it was shown, which a removal checks again) where `state` is `owned`, `foreign` (another instance's, left alone), `absent`, `unreachable` (`reason`) or `not_checked`. `merge` is the advisory evidence `list --wide` shows (one implementation), against the default branch's upstream (the local default without one), for the workspace's branch while it exists, else the commit it was last on: `{base, state}` with `state` `merged` (`how`: `ancestor`, `same_tree`, `no_changes` or `looks_squashed`, a hint from patch ids and never a reason to delete), `not_merged` (`ahead`) or `unknown`. `app_port` is the workspace's app port, which the record carries and a removal gives back to the machine's port ledger as `remove` does; `daemons_unverified` is set when a forced removal could not show that nothing runs under the recorded namespace (the namespace and the ids stay on the record until a listing that was read shows nothing running).
- `devflow --json gc --remove ID… [--yes] [--snapshot] [--force]` removes the named instances (`ID`: a UUID or at least 8 hex characters of the id the listing shows). Without `--yes` (and always with `--json`) it only reports `confirmed: false`; `--yes` skips the prompt and never widens the selection. Each instance is read again first: it must still be `missing` or `removed_elsewhere` with the `generation` it was shown, and its branches must be the data that was shown (a reset keeps a branch's id and owner but bumps its generation and replaces its volume, so the request carries both and a branch that was reset since is refused, with the snapshot and the drop checking it again under the backend's lock). Every branch is looked for in the backend its record names and dropped by its recorded identity under that lock after checking that this instance owns it. A `missing` entry is revalidated under its process lock and receipt lock right before the snapshot and again before the first effect, and the removal is told its directory was gone: a checkout that came back meanwhile is an active workspace, `--force` or not, and is left alone; a `removed_elsewhere` entry, which has no lock to take, is read again after its snapshot. `--snapshot` takes a snapshot of each branch first (`gc-<workspace>-<date>`, kept), including a branch recorded before its creation finished when the backend has it ready and as this instance's; a branch it cannot snapshot (not ready, not answering) stops the removal before anything is dropped, and `skipped[].done` lists the snapshots taken. Daemons are asked about and never stopped (a stop makes pitchfork run the daemon's lifecycle hooks from a configuration nobody can approve now that the checkout is gone): a listing that was read and shows nothing of the namespace running lets the record stop naming them; daemons found running, or pitchfork that cannot be asked, are `state_unknown` (an entry in `skipped[]` with `forceable: true`), which `--force` goes on past, leaving them running, on the record (`still_recorded`, the ids it found running added to the ones it listed) and in `may_still_run`. A namespace the record marks in doubt is cleared only by a listing that was read and shows nothing of it running: no recorded id, no pitchfork on `PATH` and a supervisor that is down are not that, and the removal asks about such a namespace whether or not the project uses pitchfork. Teardown hooks are not run (there is no checkout). An instance another operation holds is skipped with `busy: true` and read not at all: a setup holds the instance lock (`devflow/workspaces/<instance id>.op.lock` in the common Git directory, which Git does not delete with the worktree) from its first write to its end, so a clean-up cannot settle a branch it is still creating; a removal and a rebind hold it too, and it is only tried, never waited for. Result: `{project, inventory, confirmed, removed[], skipped[], not_removable[]}` (`not_removable[]` carries the entry's `remedies`); `removed[]` is `{instance, workspace, dropped[], snapshots[], still_recorded[], may_still_run?, warnings[]}`. Exit 1 when something named was kept (the document then has the usual top-level `error`).
- `devflow --json gc --rebind ID… [--yes]` binds the records of the named instances to this repository, for records `unknown` with `cause: other_checkout` (`rebindable` in spirit: the entry offers the `rebind_record` remedy). Without `--yes` (and always with `--json`) it only reports `confirmed: false`. It is the one way out of an unproven checkout: each record is read again and must still have the generation shown, nothing else may hold the instance (`skipped[].busy`), the binding is journaled in the record (`effect: rebind`, `from`) and nothing is removed or released; afterwards the entry is judged like any other. Result `{project, inventory, confirmed, rebound[], skipped[], not_bindable[]}`, `rebound[]` of `{instance, workspace, from, class}`. Exclusive with `--remove`. The desktop app's Clean up page shows the same as a button on the entry, with a confirmation.
- Never removed by `gc`: an `active` workspace (use `remove`), attachments (`setup --database-url` bindings are not owned, so never recorded), shared servers, snapshots, branches another instance owns, anything `unknown`. A `missing` entry is removed through the ordinary removal, which also forgets its Git registration.
- `devflow --json list` has a `cleanup: {removed_elsewhere[], missing[], message, remedies}` object when workspaces gone from Git still own something (the human output adds one line), `doctor` has a `workspaces-gone` check, and `remove NAME` of such a name fails with the `clean_up` remedy. All of it reads the records only: no server, no Docker.

## Sandboxes and forks

For VM sandboxes and forks, keep the admin credentials on the trusted side and give the sandbox only a branch URL: `devflow setup --database-url URL` attaches it, and `devflow setup --new-instance` (or an orchestrator-set `DEVFLOW_INSTANCE_ID`, honoured only by an explicit `devflow setup`) gives a forked worktree a fresh identity. The identity is the pitchfork namespace the workspace's daemons run under, so a new one is refused, before anything changes, while this machine's pitchfork lists a daemon of the old namespace as active (`daemons_running`: run `devflow down` first) and while devflow cannot show that none is (`state_unknown`: pitchfork cannot be asked, its listing cannot be read or has a state devflow does not know, or its supervisor is down while the receipt records a start devflow has not seen stop; `pitchfork supervisor start` then `devflow down` answers it). There is no `--force`: stopping daemons is `devflow down`'s job. **A copy from another machine is told from a second instance on this one by how the new identity is chosen:** with `DEVFLOW_INSTANCE_ID` naming another instance the orchestrator declares the receipt a copy, so its record of started daemons, and a pitchfork that cannot answer, describe another machine and do not block (a daemon this machine's own pitchfork lists as active in the old namespace still does); `--new-instance` alone declares nothing, so a copy made with it needs a supervisor that is up and shows nothing active, or `DEVFLOW_INSTANCE_ID`. Setup, the secrets a sandbox must not receive, and cleanup are in [Remote data hosts](guide/remote-data-hosts.md).

| Variable | Use |

| `COMPLETE=<shell>` | Shell completion requests (`devflow completions SHELL` prints the registration). Workspace names are read from local Git and receipts, never a server or Docker |
| `DEVFLOW_INSTANCE_ID` | Orchestrator override: the instance identity a forked worktree takes. Must be a UUID (anything else is ignored) and is refused if another worktree of the project already records it. Honoured only by an explicit `devflow setup` |
| `DEVFLOW_PG_ADMIN_URL` | Admin URL for external mode (trusted machines only) |
| `DEVFLOW_CONFIG_DIR`, `DEVFLOW_DATA_DIR` | Redirect the registry, trust and managed-server directories (useful for isolated tests) |
| `DEVFLOW_SETUP_ACTIVE` | Set to `1` by devflow inside hook commands; the `post-checkout` hook does nothing when it is `1`, so Git commands in a hook cannot start another setup |

Hook commands run with `sh -c` in the worktree with stdin closed. Each entry of `setup`, `switch` and `teardown` is a string or a table `{ name = "migrate", run = "…", timeout = "5m" }` (`name` and `timeout` optional; `timeout` overrides `[hooks] timeout`); a name is shown in output and logs as `[migrate] $ …`, and hook runs in the JSON documents carry it as `name`. Hooks also receive the `[env]` recipes and presets, and `DEVFLOW_PROJECT`, `DEVFLOW_PROJECT_ROOT`, `DEVFLOW_WORKSPACE`, `DEVFLOW_WORKSPACE_PATH`, `DEVFLOW_SOURCE_PATH` (absent for the default workspace), `DEVFLOW_WORKSPACE_ID` (the workspace's instance id; informational, also in `.devflow/env`), `COMPOSE_PROJECT_NAME`, `DEVFLOW_PORT` (once the workspace has its port) and `DEVFLOW_PHASE` (`setup`, `switch` or `teardown`). Git's hook context (`GIT_DIR`, `GIT_WORK_TREE`, …) is removed, and when the workspace has a database so are inherited libpq variables such as `PGHOST`, so `psql` in a hook reaches the workspace's own database. Hooks run at least once, so write them to be idempotent. There is no command templating (`[env]` values reference generated variables as `${NAME}`, and nothing else).

[`examples/agent-task.sh`](../examples/agent-task.sh) implements this flow: it stays the parent of the command, so the workspace is removed after a success and after a failure (`KEEP=1` keeps it), the command's exit status is the script's, and INT and TERM are forwarded to the command's whole process group. The workspace is removed only once that group has exited: processes the command left behind (a dev server, a test runner's workers) are stopped when it ends, TERM first and KILL after `AGENT_TASK_GRACE` seconds (default 10), with a message on stderr; a process that started its own session is not stopped. A command that ignores INT or TERM is not waited for forever: the grace starts at the first signal, and when it is over with the command still running the group is killed and the command's real exit status is the script's. `AGENT_TASK_GRACE` is a whole number of seconds from 0 to 3600 (anything else is refused before the workspace is created). If the group is still there after KILL, the workspace is kept, stderr names it and the remaining PIDs, and the exit status is 70.
