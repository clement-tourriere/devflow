# Findings by area


## Proxy core (TLS, routing, forwarding, discovery)  (`proxy-core`)

The proxy core is cleanly factored (discovery is pure and well-tested, router is a simple RwLock map, SNI cert minting is lazy with a cache) and the label conventions (devproxy.*, VIRTUAL_HOST/VIRTUAL_PORT nginx-proxy compat, compose/devflow label fallbacks) are sensible. The biggest structural risks are lifecycle robustness and forwarding fidelity: every long-lived loop (Docker event stream, TCP accept loops) exits permanently on the first error with no retry, so the proxy silently degrades into a stale state after a Docker Desktop restart or a transient accept failure — which matches the reported "small recurring issues, restart fixes it" pattern. Forwarding is store-and-forward (full request and response bodies are buffered), which silently breaks SSE/streaming and chunked responses. Discovery has a genuinely nondeterministic port picker for multi-port containers because bollard drains a HashMap, and route removal depends on a post-`die` inspect that races container auto-removal. Finally, minted leaf certificates lack the EKU serverAuth extension that Apple's trust evaluator requires, undermining the whole "trusted CA in the macOS keychain" story for Safari/Security.framework clients.


### 🟠 HIGH · CONFIRMED — Port selection is random for multi-port containers (bollard drains a HashMap for ExposedPorts)

**Where**: `crates/devflow-proxy/src/discovery.rs:289`

extract_port falls back to "the first" exposed port: `for port_str in exposed { if let Some(port_num) = port_str.split('/').next() { if let Ok(port) = port_num.parse::<u16>() { return port; } } }`. But bollard-stubs deserializes `ExposedPorts` (a JSON object) into `Option<Vec<String>>` via `deserialize_hashmap_string_hashmap_empty`, which does `for (key, _) in hsh.drain()` on a std HashMap (bollard-stubs-1.52.1 models.rs:110-124) — iteration order is randomized per process and per deserialization. So for any image exposing more than one port (nginx: 80+443 -> may route plaintext HTTP to the TLS port; ClickHouse: 8123+9000+9009 -> picks the HTTP port only 1 in 3 times; Mongo+metrics sidecars, etc.) the chosen upstream port is a dice roll that re-rolls on every container start event and every proxy restart. This is a textbook source of "it worked yesterday, today the same container 502s" daily flakiness.

**Fix**: Make the choice deterministic and HTTP-biased: parse all exposed ports, sort numerically, and prefer well-known HTTP ports in priority order (80, 8080, 3000, 8000, 5173, 8123...) before falling back to the lowest port; log a warning listing all exposed ports when more than one candidate exists so users know to set devproxy.port/VIRTUAL_PORT.

## Proxy platform integration (trust, mDNS, API, lifecycle)  (`proxy-platform`)

The proxy platform layer is thoughtfully designed: trust installation has per-distro Linux paths plus a Firefox enterprise-policy fallback, the macOS mDNS responder correctly funnels all dns_sd calls through a dedicated worker thread owning the non-Send connection, and the JSON API gives the CLI a clean way to observe a daemonized proxy. The biggest structural risk is that there are three independent notions of "the proxy is running" — the CLI pidfile, the GUI's in-process ProxyHandle, and the API port — and they are never reconciled, so CLI and GUI routinely disagree and can silently double-start. The second structural risk is that run_proxy() binds all three listeners inside spawned tasks and unconditionally returns Ok, so every caller (CLI foreground, CLI daemon, GUI button, GUI auto-start, tray toggle) reports success even when nothing is listening. Trust verification is presence-based rather than identity-based, which produces a confident-but-wrong "Trusted" state after CA regeneration. Fixing run_proxy to bind eagerly and making the API port the single source of truth for liveness would resolve most of the reported "small issues".

## Hook engine (executor, templates, triggers, approval)  (`hooks-engine`)

The hook engine is well-architected on paper: a clean phase model (blocking vs background), three hook entry kinds (simple/extended/action), built-in safe conditions, an approval store with file locking, and solid unit-test coverage of the happy paths. However, the runtime behavior diverges sharply from what the config promises, and the failure modes are exactly what you report. The three root causes of "hooks don't always work" are: (1) the approval system keys on the fully *rendered* command and on a per-directory project key, so any templated hook can never be pre-approved for a new workspace — and in `--json --non-interactive` (the exact command your agent skills emit) it hard-fails the blocking post-create phase; (2) hooks on non-blocking phases (post-switch, post-merge, post-rewrite, all custom phases) are fire-and-forget `tokio::spawn` tasks that nothing awaits, so they race process exit and nondeterministically never run from the CLI (while working fine in the long-lived Tauri GUI); (3) the switch path passes the *sanitized* workspace name into the hook context while the create path passes the raw branch name, so `{{ workspace }}` templates and `workspace_matches:` conditions silently behave differently depending on entry point. Worktree working-dir resolution is mostly correct (post-create does run inside the new worktree when detection succeeds), but it short-circuits to the *current* worktree whenever devflow is invoked from inside any worktree, clobbering the wrong directory. There are also several dead config options (`triggers:` remapping, `environment:` on action hooks, `working_dir:` on background hooks) and an approval bypass on the git-generated pre-commit path.

## Workspace lifecycle (create/switch/delete/merge)  (`workspace-lifecycle`)

The workspace lifecycle module is well-factored: create/switch/delete live in devflow-core and are shared by CLI, TUI, and GUI, with clean result structs and best-effort hook summaries. The recommended shell-init wrapper also captures all stdout while a command runs, making every interactive prompt (and the TUI) invisible. ## CoW Postgres backend (general correctness)  (`cow-postgres`)

The local CoW Postgres backend is well-structured: provider logic (mod.rs), Docker runtime (docker.rs), SQLite state (state.rs), reconcile loop, and pluggable storage drivers (APFS/reflink/copy/ZFS) are cleanly separated, and the reconcile-before-act pattern is a good idea. However, the core branching primitive — clone a paused container's PGDATA via per-file `cp -c` on a Docker Desktop bind mount — is not guaranteed crash-consistent on macOS (your primary platform), which validates your suspicion about the CoW solution. Identity is fragile at three layers (project name from cwd, store workspace name, sanitized/truncated container name), allowing distinct workspaces/projects to silently share or destroy each other's containers. Readiness detection via unix-socket `pg_isready` returns "ready" during the image's initdb temp-server phase, which directly explains intermittent post-create hook failures. Several config options (image, postgres_password, port_range_start, docker settings) are silently pinned at first creation and never re-applied, and seed/reset error paths swallow real failures. ZFS reset is 100% broken due to an origin-snapshot name collision and destroys the workspace dataset before failing.


### 🟠 HIGH · UNVERIFIED — CoW clone of a paused (not checkpointed/stopped) Postgres is not crash-consistent on Docker Desktop/macOS

**Where**: `crates/devflow-core/src/services/postgres/local/mod.rs:264`

create_workspace/reset_workspace clone PGDATA while the parent container is merely paused: `if parent_running { self.runtime.pause_branch(...).await?; }` then `self.storage.clone_branch_from_parent(...)` which runs `cp -cR source/. target` on the host (local_driver.rs:136-141). No CHECKPOINT or sync is issued anywhere (grep confirms zero CHECKPOINT in services/). `docker pause` only freezes the processes inside the Linux VM; on Docker Desktop the bind-mounted PGDATA crosses the VM boundary via virtiofs, so (a) dirty pages still cached in the guest kernel are not visible to the host-side `cp`, and (b) virtiofsd can keep flushing queued writes WHILE the host walks the tree, producing torn copies where data files are newer than the copied WAL. On native Linux the frozen view is at least crash-consistent (shared page cache), but on macOS the clone can fail to start or silently lose recently committed rows. The ZFS path has the same missing-checkpoint issue but at least snapshots atomically.

**Fix**: Before cloning, exec `psql -U <user> -c CHECKPOINT` followed by `sync` inside the parent container (forces all data through fsync/virtiofs to the host), THEN pause and clone. Safer still: stop the parent container (clean shutdown = checkpoint + fsync of everything) for the duration of the clone and restart it after — the code already tolerates a parent stop/start cycle. Document that pause-based cloning is best-effort.


### 🟠 HIGH · UNVERIFIED — wait_ready false-positives during initdb: pg_isready over unix socket succeeds while the entrypoint's temp server runs, so hooks fire before TCP is up

**Where**: `crates/devflow-core/src/services/postgres/local/docker.rs:390`

Readiness is `self.exec_check(container_name, &["pg_isready", "-U", pg_user, "-d", pg_db])`. Without `-h`, pg_isready uses the unix socket. The official postgres entrypoint, on first boot of an empty PGDATA, starts a temporary server with `listen_addresses=''` (unix socket only), runs init, stops it, then starts the real server. pg_isready answers OK against that temp server (PQping succeeds even before the target DB exists), so wait_ready returns, create_workspace marks the branch Running (mod.rs:319-330), and post-create hooks (migrations, `.env` writers that immediately connect) hit connection-refused on the mapped TCP port — exactly your "hooks don't always work" symptom for the first/empty workspace of a project (created by init.rs:120 `create_workspace("main", None)`).

**Fix**: Probe over TCP: either `pg_isready -h 127.0.0.1 -p 5432` inside the container (the temp server has no TCP listener so it can't false-positive), or better, connect from the host to 127.0.0.1:<mapped port> and run `SELECT 1` — that also validates the port mapping itself. Optionally require two consecutive successes to ride out the temp-server restart window.

## CoW data-integrity deep dive (APFS/ZFS cloning a live database)  (`cow-integrity`)

The CoW storage layer is well-organized: a clean StorageCoordinator dispatch over four drivers (ZFS, APFS clone, reflink, copy), a sensible doctor/probe system, and SQLite state with reconciliation against actual Docker container status. The ZFS clone path (atomic snapshot of a paused container, same-kernel) is conceptually sound, and ClickHouse/MySQL correctly stop the parent before copying. The two biggest structural risks are: (1) the PostgreSQL clone path is the only one that does NOT quiesce the source — it merely `docker pause`s the parent and then does a host-side per-file `cp -cR` of a live PGDATA, which on macOS (your primary platform, with Docker Desktop's VM/virtiofs boundary in between) is at best crash-consistent and not guaranteed even that; the reconciler can even unpause the parent mid-copy from a concurrent process. (2) The ZFS workspace lifecycle has deterministic-name and error-swallowing bugs that make reset permanently fail and leak datasets. There are also several robustness gaps where a failed step leaves orphaned clone data or silently degrades (empty workspace instead of clone, full copy instead of clone, copy driver instead of ZFS). Your instinct that the Postgres CoW solution "may not be correct" is justified for the APFS path specifically; the fix is cheap (stop or CHECKPOINT the parent like the other providers already do).


### 🟠 HIGH · UNVERIFIED — Postgres PGDATA cloned from a paused (not stopped/checkpointed) container via non-atomic per-file copy

**Where**: `crates/devflow-core/src/services/postgres/local/mod.rs:264`

The clone sequence in create_workspace (and reset_workspace) is: pause parent → host-side copy → unpause:

```rust
if parent_running {
    self.runtime.pause_branch(&parent_workspace.container_name).await?;
}
let result = self.storage.clone_branch_from_parent(&project, parent_workspace, &branch_id, &data_dir).await;
```

There is no `CHECKPOINT`, no `pg_backup_start`, and no clean shutdown (grep for "checkpoint" across the crate: zero hits). `docker pause` only freezes the cgroup — PostgreSQL's shared_buffers and the container kernel's dirty page cache are NOT flushed. The copy itself is `cp -cR` (local_driver.rs:136-141), which clonefile()s file-by-file — it is not an atomic snapshot across files, unlike `zfs snapshot`. On Linux this is borderline OK (frozen writer + same page cache = point-in-time view, recovered by WAL replay). But on macOS — the primary platform and the only place the ApfsClone driver activates — the container runs in the Docker Desktop VM and PGDATA is shared via virtiofs: the host `cp` can observe heap/WAL files mid-writeback from the guest, producing torn 8K pages and inter-file skew. The clone then boots as a crashed cluster and relies on WAL replay + full_page_writes to repair it; torn hint-bit-only writes and any virtiofs ordering violation produce a silently corrupt clone. Note the inconsistency: clickhouse/local.rs:384-397 and mysql/local.rs:380-393 STOP the parent container before `clone_data_dir`, only Postgres pauses. The cloned dir also carries `postmaster.pid` (nothing removes it — only saved because postgres is PID 1 in the new container so it self-detects the stale lock).

**Fix**: For the ApfsClone/Reflink/Copy drivers, stop the parent container (`stop_workspace`, clean shutdown = checkpoint + flush, no recovery needed in the clone) before copying and restart it after — exactly what the ClickHouse/MySQL providers already do. If the pause-based flow must stay for speed, at minimum exec `psql -c CHECKPOINT` followed by `sync` inside the container before pausing, and delete `postmaster.pid` from the clone before first start. Keep pause-only for the ZFS driver, where the snapshot is genuinely atomic.

## Other container backends (ClickHouse, MySQL, generic, plugin, factory, orphans)  (`containers-other`)

The container-backend layer (ClickHouse/MySQL/generic/plugin providers, factory orchestration, orphan GC, docker helpers) is well-factored: providers share consistent helpers (local_docker.rs), the factory tolerates partial failures, the plugin protocol handles timeouts/exit codes/stderr correctly, and discovery has real tests. The biggest structural risk is identity: project identity is a bare name derived from `config.name` or the current working directory's basename, and three different stores (Docker labels, local-state YAML keyed by path, SQLite keyed by name+path) are cross-referenced by fragile basename matching. Orphan detection/cleanup builds on this and can destroy containers and data directories of live projects after a directory rename, a second checkout, or simply a `name:` that differs from the folder name. The second systemic gap is that ClickHouse/MySQL/generic providers inherit trait defaults that silently no-op (`reset`) or delete data in the wrong order (`cleanup` with `created_at: None`), so several CLI commands report success while doing nothing or the wrong thing. ClickHouse/MySQL themselves are reasonable copies of a sane pattern (stop-parent → CoW clone → restart), but error paths leave the parent stopped and the readiness probe for password-protected ClickHouse depends on undocumented env-var fallback in clickhouse-client.

### 🟡 MEDIUM · UNVERIFIED — ClickHouse/MySQL workspace cloning leaves the parent container stopped when the copy fails, and the 10s stop timeout can SIGKILL the DB before snapshotting

**Where**: `crates/devflow-core/src/services/clickhouse/local.rs:399`

## Cloud branching providers (Neon, Xata, DBLab)  (`cloud-providers`)

The cloud branching subsystem (Neon, Xata, DBLab) is well-architected on paper: a clean ServiceProvider trait, per-service orchestration with partial-failure tolerance, feature-gated compilation, and ${ENV_VAR} credential resolution. In practice, all three providers are vestigial: I verified each against the providers' current OpenAPI specs and every single API call uses wrong paths, wrong request bodies, or response shapes that cannot deserialize — Neon and Xata appear to have been corrupted by a mechanical 'branch'->'workspace' rename that rewrote API URL segments and JSON keys, and DBLab was written against an imagined API (plural /clones, cloneName/snapshotID fields that do not exist). There are zero tests for these files, which is why this has gone unnoticed. Worse, no CLI/TUI/GUI surface can even produce a usable cloud config (they all hardcode neon/dblab/xata: None), and because provider construction is all-or-nothing in factory.rs, adding one cloud service silently breaks orchestration and hook env propagation for every working local service too. My recommendation: either delete these providers until you can test them against real accounts (they currently only add a footgun), or rewrite them against the verified API shapes below and add wiremock-based contract tests, plus an ownership filter on cleanup before any of them can delete remote branches.


### 🟠 HIGH · UNVERIFIED — Neon provider calls nonexistent API endpoints — every operation 404s (branch->workspace rename corrupted API strings)

**Where**: `crates/devflow-core/src/services/postgres/neon.rs:140`

All Neon API paths and JSON keys use 'workspaces' where Neon's API uses 'branches'. Line 140: `let path = format!("projects/{}/workspaces", self.project_id);` (same at lines 161-164 and 173). I verified against Neon's current OpenAPI spec (neon.com/api_spec/release/v2.json): the path is `/projects/{project_id}/branches`, the list response key is `branches` (code expects `struct ListBranchesResponse { workspaces: Vec<NeonBranch> }`, lines 33-35), and the create request must be wrapped as `{"branch": {"name", "parent_id"}, "endpoints": [{"type": "read_write"}]}` — the code sends `{name, parent_id}` at top level (lines 135-138). Three additional latent bugs even after fixing the paths: (1) line 137 `parent_id: from_workspace.map(|s| s.to_string())` passes a branch NAME where Neon requires a branch ID (`br-...`); (2) no `endpoints` array is sent, so created branches have no compute endpoint and can never be connected to; (3) the response wrapper key `workspace` (line 39) should be `branch`. Scenario: any `devflow workspace switch` or `service create` with a Neon service fails with 'Neon API request failed with status 404'. This looks like a global s/branch/workspace/ rename applied to API wire strings during the pgbranch->devflow renaming (the trait doc at services/mod.rs:71 confirms the rename).

**Fix**: Restore Neon wire names independent of devflow's internal vocabulary: path `projects/{id}/branches`, deserialize `{"branches": [...]}` / `{"branch": {...}}`, serialize create as `{"branch": {"name": ..., "parent_id": <resolved br-id>}, "endpoints": [{"type": "read_write"}]}` (resolve parent name to ID via list, as delete_workspace already does). Add a wiremock contract test pinned to the real response shapes.


### 🟠 HIGH · UNVERIFIED — Xata provider hits /workspaces instead of /branches and omits the required 'mode' discriminator — all calls fail

**Where**: `crates/devflow-core/src/services/postgres/xata.rs:72`

Lines 72-77: `format!("{}/organizations/{}/projects/{}/workspaces", ...)`. I verified against the live spec at api.xata.tech/openapi.json: the only branch paths are `/organizations/{organizationID}/projects/{projectID}/branches[/{branchID}[/credentials]]` — `/workspaces` does not exist, so list/create/delete/credentials all 404. Additionally: (1) the list response struct expects `workspaces` (line 34: `workspaces: Vec<XataBranch>`) but the spec's required top-level key is `branches`; (2) `CreateBranchRequest { name, parentID }` (lines 37-43, sent at lines 199-206) is invalid — `BranchCreationDetails` is a oneOf discriminated on a required `mode` field, and branching from a parent requires `{"mode": "inherit", "parentID": ...}` (both required together); the no-parent case also needs a mode. ### 🟠 HIGH · UNVERIFIED — DBLab provider uses invented endpoints and request/response shapes — list, create, and delete all fail

**Where**: `crates/devflow-core/src/services/postgres/dblab.rs:180`

Verified against DBLab Engine's official swagger (engine/api/swagger-spec/dblab_server_swagger.yaml): the engine exposes `POST /clone`, `GET/DELETE /clone/{id}`, `GET /snapshots`, `GET /status` — there is no `/clones` collection endpoint. The code POSTs to `"/api/clones"` (line 180), GETs `"/api/clones"` to list (lines 196, 213-215, 251) and DELETEs `"/api/clones/{}"` (line 204) — all 404 (clone listing must come from `GET /status` -> `cloning.clones`). ### 🟠 HIGH · UNVERIFIED — One misconfigured service poisons all services: provider construction is all-or-nothing, breaking workspace switch and hook env for working local services

**Where**: `crates/devflow-core/src/services/factory.rs:294`

`create_all_providers` (line 294: `let provider = create_provider_from_named_config(config, named).await?;`) and `create_auto_branch_providers` (line 326, same `?`) abort on the FIRST service whose provider cannot be constructed. ### 🟠 HIGH · UNVERIFIED — cleanup_old_workspaces on cloud providers would mass-delete remote branches it does not own, including teammates' work

**Where**: `crates/devflow-core/src/services/mod.rs:120`

The default trait impl used by Neon/Xata/DBLab lists ALL branches in the remote project, exempts only the literal names 'main' and 'master', sorts by created_at and deletes everything beyond max_count: lines 120-134: `let workspaces = self.list_workspaces().await?; ... .filter(|b| b.name != "main" && b.name != "master") ... for workspace in sorted_branches.into_iter().skip(max_count) { match self.delete_workspace(&workspace.name)...`. ### 🟡 MEDIUM · UNVERIFIED — Xata get_connection_info fabricates host localhost:5432 — would point hooks/.env at the wrong database even after the path fix

**Where**: `crates/devflow-core/src/services/postgres/xata.rs:266`

### 🟡 MEDIUM · UNVERIFIED — Cloud HTTP clients have no timeout — a stalled Neon/Xata/DBLab connection hangs workspace switch (and git checkout) forever

## AI agent integration (agent start/context/skills)  (`agent-harness`)

The agent subsystem is mostly a thin layer over the workspace `switch -x` machinery plus a skills installer; the skills install/uninstall/lock logic is well-tested and internally consistent. The biggest structural problem is that there is no real "agent start" flow at all — the command advertised in help does not exist, and the actual launch path (`switch -x <agent>`) only changes the child's working directory while passing through the parent process's entire environment, so the agent runs against the launching repo's mise/direnv state and never receives the new workspace's service URLs. A second cross-cutting issue is workspace-name normalization: services are stored under the sanitized name, but `agent context` and the agent-facing `connection` calls the bundled skills prescribe use the raw branch name, so service info silently disappears for any branch with a slash or capital. There is also an unsanitized path-join in the marketplace skill installer that allows directory traversal from untrusted SKILL.md frontmatter. Context generation and skill generation/installation themselves are otherwise correct.


### 🟠 HIGH · UNVERIFIED — Agent launched via `switch -x` inherits the launching shell's environment and only changes cwd — no service URLs, no mise/direnv activation

**Where**: `src/cli/workspace.rs:2319`

The foreground exec path runs the agent with `tokio::process::Command::new("sh").args(["-c", &full_cmd]).current_dir(&work_dir)` (and the sandbox branch likewise only sets `.current_dir(&work_dir)`). It never calls `.env(...)`/`.envs(...)`, so the child `claude`/`codex` process inherits the *entire* environment of the devflow process, which was launched from the original repo where mise/direnv had injected the ORIGINAL workspace's PATH shims and env vars (e.g. a stale `DATABASE_URL`). Setting `current_dir` to the worktree does NOT re-trigger mise/direnv (those are shell hooks, not subprocess-automatic), and devflow never injects the new workspace's resolved service connection strings into the child env. Net effect for `devflow switch -c --sandboxed agent/x -x claude`: the agent runs in the right directory but with the wrong environment — pointing at the previous workspace's services and tooling. This directly matches the author's report that after worktree creation it 'does not run mise trust/activate'. Additionally, `work_dir` is resolved with a silent fallback: `vcs::detect_vcs_provider(".").ok().and_then(|repo| repo.worktree_path(workspace_name).ok().flatten()).unwrap_or_else(|| std::env::current_dir().unwrap_or_default())` (workspace.rs:2153) — if worktree resolution ever returns None/Err, the supposedly-sandboxed agent runs in the ORIGINAL repo with no warning.

**Fix**: Build a hook context for the target workspace (reuse `build_hook_context`) and inject each service's connection env (e.g. `DATABASE_URL`, `<NAME>_URL`) plus run the command through `mise exec`/`direnv exec <dir>` when those tools and a `.mise.toml`/`.envrc` are present in the worktree. At minimum, set the resolved service env vars via `.envs(...)`. Also make the `work_dir` resolution fail loudly (bail) instead of silently falling back to the original repo when a worktree was expected.


### 🟠 HIGH · UNVERIFIED — `agent context` and the bundled skills query service connections with the raw (un-normalized) workspace name, so services silently vanish

**Where**: `src/cli/agent.rs:66`

`AgentCommands::Context` derives `workspace_name` from `--workspace` or `vcs_repo.current_workspace()` (the raw git branch, e.g. `agent/task-id` or `feature/Auth`) and passes it un-normalized to `generate_agent_context` → `build_hook_context` → `get_all_connection_info(config, workspace_name)` (hooks/mod.rs:469). But services are created/stored under the SANITIZED name: `switch_workspace` calls `orchestrate_switch(config, &normalized_name, ...)` (switch.rs:164), and the local Postgres backend looks workspaces up by exact name (`get_workspace_by_name` does `WHERE name = ?2`). For any branch that normalizes differently (anything with `/` or uppercase), the lookup misses; `get_all_connection_info` swallows the error at `log::debug` (factory.rs:545) and returns nothing. Result: `devflow agent context` reports zero services with no error, even though the workspace has running databases. Hooks work (they pass `normalized_name`) but `agent context` does not — a real CLI divergence. Worse, the bundled skills this subsystem generates instruct agents to run `devflow --json connection agent/<task-id>` / `devflow --json connection $ARGUMENTS` (agent.rs:287,334) with the raw name; `service connection` also passes the raw name straight to `provider.get_connection_info` (service.rs:934), so that command hard-errors with "Workspace 'agent/task-id' not found" for slashed names — the skill's own prescribed workflow is broken.

**Fix**: Normalize the workspace name with `config.get_normalized_workspace_name(...)` before calling `generate_agent_context`/`get_all_connection_info`, and likewise normalize in the `service connection` handler (service.rs:934). Alternatively normalize once at the provider boundary. Also stop silently dropping connection-info errors when a workspace is expected to exist.


### 🟠 HIGH · UNVERIFIED — Marketplace skill install joins an untrusted SKILL.md `name` into a path and `remove_dir_all`s it (directory traversal / arbitrary deletion)

**Where**: `crates/devflow-core/src/skills/installer.rs:35`

`install_skill` computes `let skill_dir = project_dir.join(CLAUDE_SKILLS_DIR).join(&skill.name); remove_link_or_dir(&skill_dir)?; std::fs::create_dir_all(&skill_dir)?; std::fs::write(skill_dir.join("SKILL.md"), ...)`. `skill.name` for a marketplace install comes from attacker-controlled GitHub frontmatter: `marketplace::try_fetch_skill_at_path` sets `name: frontmatter.name` (marketplace.rs:73) with no validation. ## ROOT CAUSE: agent-created worktree does not switch/activate mise  (`agent-mise-bug`)

The workspace-creation/hook subsystem is well layered (CLI -> devflow-core workspace::create/switch -> HookEngine) and the lifecycle ordering, worktree-aware working_dir resolution, and recipe system are thoughtfully designed. However, the exact agent repro ("worktree created, but session never switches into it and mise is never trusted/activated") is fully explained by a chain of confirmed defects: in the agent-documented flow (`devflow --json --non-interactive switch -c --sandboxed`, per the bundled skill) any unapproved shell post-create hook aborts the whole command AFTER the worktree exists, and the abort suppresses the JSON output that carries `worktree_path`, so the agent never learns where to cd. Independently, the mise-trust recipe only matches the legacy `.mise.toml` filename, approvals are keyed on the per-workspace *rendered* command so they can never be pre-approved once-and-for-all, post-switch hooks are fire-and-forget tokio tasks that race with process exit, and every spawned command uses bare `sh -c` so `mise activate` never takes effect even when hooks do run. Finally, the feature that was supposed to solve all of this — `devflow agent start` (exec the agent inside the worktree) — is advertised in the help text and CLAUDE.md but simply not implemented. The biggest structural risk is the approval system's interaction with non-interactive/agent execution: it currently converts "hook not yet approved" into either a hard failure mid-lifecycle or a silent skip, both of which present as "hooks don't always work".


### 🟠 HIGH · UNVERIFIED — Agent flow: unapproved post-create hook aborts `switch -c` after worktree creation and suppresses the JSON containing worktree_path

**Where**: `crates/devflow-core/src/workspace/switch.rs:199`

The bundled agent skill (skills/devflow-workspace-create/SKILL.md:12) tells agents to run `devflow --json --non-interactive switch -c --sandboxed ...` and then read `worktree_path` from the JSON. But with `--json`/`--non-interactive`, src/cli/workspace.rs:1939 selects `HookApprovalMode::NonInteractive`, and in the executor an unapproved shell hook hard-fails: executor.rs:507 `anyhow::bail!("Hook '{}' requires approval in non-interactive mode: {}", ...)`. PostCreate is a blocking phase (hooks/mod.rs:86-98) so `continue_on_error` defaults to `false` (executor.rs:151-157) and the error propagates through switch.rs:199-206 `let post_create = run_lifecycle_hooks_with_result(...).await?;`. The caller at src/cli/workspace.rs:1968-1974 does `let result = ...switch_workspace(...).await?;` BEFORE printing anything, so on failure no JSON is ever emitted. Net effect, exactly as reported: the branch, worktree and services are already created (steps 2-4 of switch_workspace), but the command exits non-zero with no `worktree_path`, the agent stays in the original repo, and the `mise trust`/`direnv allow` hooks never ran. The test `switch_workspace_fails_when_post_create_hook_requires_approval` (switch.rs:352) codifies this behavior as intended, which it clearly is not for the agent flow.

**Fix**: Treat project-config hooks as implicitly trusted when explicitly invoked by the user/agent (the GUI already uses NoApproval for exactly this reason, workspace/hooks.rs:17-18), or at minimum: (a) in non-interactive mode record unapproved hooks as skipped instead of bailing, and (b) in handle_switch_command, emit the JSON result (including worktree_path and per-hook errors) even when hook phases fail, returning a non-zero exit code separately. Also consider an `--approve-hooks` flag or auto-approval of hooks committed in .devflow.yml.


### 🟠 HIGH · UNVERIFIED — mise-trust recipe condition only matches legacy `.mise.toml`, not the modern default `mise.toml`

**Where**: `crates/devflow-core/src/hooks/recipes.rs:284`

The local-dev-setup recipe installs: `command: "mise trust"` with `condition: Some("file_exists:.mise.toml".to_string())` (recipes.rs:280-288). `file_exists:` is resolved against the hook working dir (executor.rs:534-537), which is correctly the new worktree — but mise's current default config file name is `mise.toml` (also common: `mise.local.toml`, `.config/mise/config.toml`, `.tool-versions`). For any project using `mise.toml`, the condition evaluates false and the hook is silently counted as skipped, so the new worktree is never trusted. This is one of the two direct causes of "mise is not trusted in agent-created worktrees" (the other being the approval bail above). Additionally the recipe only runs `mise trust` — it never runs `mise install`, so even on `.mise.toml` projects the toolchain isn't provisioned in the worktree.

**Fix**: Broaden the condition to cover all mise config names, e.g. use a shell condition `test -f mise.toml -o -f .mise.toml -o -f mise.local.toml -o -f .tool-versions` or add a built-in `any_file_exists:mise.toml,.mise.toml,...` condition, and change the command to `mise trust && mise install`. Alternatively make the hook unconditional with `continue_on_error: true` since `mise trust` is a no-op without a config file... actually it errors, so keep the condition but complete it.


### 🟠 HIGH · UNVERIFIED — Post-switch (and all non-blocking phase) hooks are fire-and-forget tokio tasks that race with CLI process exit

**Where**: `crates/devflow-core/src/hooks/executor.rs:285`

executor.rs:257: `let run_background = extended.map(|e| e.background).unwrap_or(false) || !phase_blocking;` forces EVERY hook in a non-blocking phase (PostSwitch, PostMerge, PostServiceSwitch, etc. — see hooks/mod.rs:86-98 where only Pre* phases and PostCreate are blocking) into `tokio::spawn(async move { ... run_shell_command(...) })` (executor.rs:285-297). The JoinHandle is dropped, no caller ever awaits background tasks (verified: no JoinHandle/join_all anywhere in hooks/ or cli/), and the CLI is `#[tokio::main]` (src/main.rs:143), so when main returns the runtime is dropped and any spawned task that has not yet been polled is destroyed without ever running. `devflow switch` prints its summary and returns almost immediately after run_phase, so post-switch hooks like the documented `update-env: echo DATABASE_URL=... > .env.local` intermittently never execute. This is a direct cause of "hooks don't always work" and explains the nondeterminism. It also makes the `background: false` setting on hooks in these phases a silent no-op.

**Fix**: Collect the JoinHandles in HookEngine (e.g. a `Vec<JoinHandle>` or TaskTracker) and expose a `wait_for_background(timeout)` that lifecycle callers await before the CLI exits; or honor `background: false` literally and run non-background hooks of non-blocking phases synchronously (best-effort, continue_on_error=true) instead of spawning.


### 🟠 HIGH · UNVERIFIED — Hook approvals are keyed on the fully rendered command, so per-workspace templates can never be durably approved

**Where**: `crates/devflow-core/src/hooks/executor.rs:247`

run_shell_hook renders first, then approves the rendered string: executor.rs:247 `let rendered_command = self.template_engine.render(command_template, context)?;` followed by `self.check_approval(name, &rendered_command)` (executor.rs:251), and ApprovalStore::is_approved compares the exact command text (approval.rs:79-86). Any hook template containing `{{ workspace }}` or `{{ service[...].url }}` (the canonical examples in CLAUDE.md, e.g. `echo DATABASE_URL={{ service['app-db'].url }} > .env.local`) renders to a different string for every workspace — host port and workspace name differ — so "Approve (always for this command)" only covers the one workspace it was approved in. Interactively the user is re-prompted for every new workspace; in non-interactive/agent mode it is impossible to pre-approve future workspaces at all (`devflow hook approvals approve <command>` would need the exact future rendered string), guaranteeing the bail described in finding 1 on every agent-created workspace.

**Fix**: Key approvals on the command *template* (plus hook name/phase), not the rendered output: check approval before rendering, or store the template alongside and match on it. Optionally show both template and rendered preview at the prompt for transparency.


### 🟠 HIGH · UNVERIFIED — Without a TTY, interactive approval prompt errors are treated as Deny — hooks silently skipped

**Where**: `crates/devflow-core/src/hooks/executor.rs:661`

If an agent (or any piped/CI environment) runs `devflow switch -c <ws>` WITHOUT `--json`/`--non-interactive`, approval mode is Interactive (src/cli/workspace.rs:1939-1943). ### 🟠 HIGH · UNVERIFIED — `devflow agent start` is documented everywhere but does not exist; agent.command/workspace_prefix config options are dead

**Where**: `src/cli/mod.rs:704`

The help text advertises the feature that would actually fix the repro: src/main.rs:72 `agent start         Start an AI agent in a new isolated workspace`, and src/cli/mod.rs:359 long_about shows `devflow agent start fix-login -- 'Fix the login timeout bug'`. ### 🟠 HIGH · UNVERIFIED — All spawned commands use bare `sh -c`: mise activate/direnv env never applies to hooks or workspace execution

**Where**: `crates/devflow-core/src/hooks/actions/shell.rs:79`

Hooks run via `let mut cmd = Command::new("sh"); cmd.args(["-c", command]);` (actions/shell.rs:79-81) and `-x`/`--execute` workspace commands run via `tokio::process::Command::new("sh").args(["-c", &full_cmd]).current_dir(&work_dir)` (src/cli/workspace.rs:2319-2324). `mise activate` is a shell-profile hook and `direnv` exports happen via a prompt hook, so neither ever runs in these non-login, non-interactive `sh -c` children; PATH and tool versions are inherited unchanged from whatever environment launched devflow. ### 🟡 MEDIUM · UNVERIFIED — Background hooks ignore the configured working_dir, running in the engine root instead

In the background branch of run_shell_hook, the working directory is taken verbatim from the engine: `let wd = self.working_dir.clone();` (executor.rs:278) and passed to run_shell_command (executor.rs:286-293) — `ext.working_dir` is never consulted. Because every hook in a non-blocking phase is forced into the background path (executor.rs:257), the documented `working_dir:` option is silently dead for all post-switch/post-merge/post-* hooks and for any hook marked `background: true` — e.g. a post-switch hook with `working_dir: backend` writes its .env into the worktree root instead.

### 🟡 MEDIUM · UNVERIFIED — Hook context workspace name diverges between create and switch paths (raw vs aggressively normalized)

**Where**: `crates/devflow-core/src/workspace/switch.rs:65`

switch_workspace passes the normalized name to every hook phase (`run_lifecycle_hooks(config, project_dir, &normalized_name, ...)`, switch.rs:62-69 and 199-226), while create_workspace passes the raw branch name (`run_lifecycle_hooks_best_effort(config, project_dir, workspace_name, ...)`, create.rs:105-181). Normalization is aggressive: lowercase plus every non-[a-z0-9_$] char replaced with `_` (config/mod.rs:767-776), so branch `feature/Auth` yields `{{ workspace }}` = "feature_auth" via `devflow switch -c` but "feature/Auth" via `devflow create`. **Fix**: Standardize on the raw VCS branch name for `context.workspace` in both paths (it is what users write conditions against), and expose the normalized form as a separate variable (e.g. `{{ workspace_slug }}`) for use in DB names/paths.

## GUI backend (Tauri commands, state)  (`gui-backend`)

The Tauri backend is a thin, mostly well-structured IPC layer over devflow-core: commands are async, errors are mapped to strings via a decent anyhow-chain formatter, and the terminal/PTY plumbing (devflow-terminal + terminal.rs) is cleaner than average. The biggest structural risk is environment inheritance: the GUI never bootstraps a login-shell PATH, so every hook, condition, and docker-exec spawned from GUI-triggered workspace operations runs with launchd's minimal PATH — this is almost certainly the root cause of "hooks don't always work" (mise/npm not found when the app is started from the Dock, while the same hooks work from the CLI). The second systemic problem is success-reporting on swallowed failures: add_service ignores workspace-create/seed errors, and start_proxy reports "running" even when the listeners never bound, so the GUI's status frequently lies. Finally, app settings (the project registry) are managed as a whole-object read-modify-write blob with no merge or atomicity, which makes the registry vulnerable to both concurrent-writer clobbering and silent reset on a corrupt file. Destructive paths (destroy_project) bypass git's dirty-worktree safety and reach beyond devflow-managed resources.


### 🟠 HIGH · UNVERIFIED — GUI-spawned hooks inherit launchd's minimal PATH — mise/npm/docker not found when app launched from Dock

**Where**: `src-tauri/src/main.rs:59`

Nothing in `fn main()` (src-tauri/src/main.rs:59) or anywhere in src-tauri fixes the process PATH (no fix-path-env, no login-shell probe). A macOS app launched from Finder/Dock gets PATH=/usr/bin:/bin:/usr/sbin:/sbin. All lifecycle hooks triggered from GUI commands (create_workspace/switch_workspace via `gui_lifecycle_options()`, run_hook) ultimately execute through `Command::new("sh"); cmd.args(["-c", command])` (crates/devflow-core/src/hooks/actions/shell.rs:79) and `Command::new("docker")` (crates/devflow-core/src/hooks/actions/docker_exec.rs:22), inheriting that PATH. So `mise trust`, `npm run migrate`, `bun install`, etc. fail with exit 127 only when run from the GUI — exactly matching the reported "hooks don't always work / does not run mise trust". Condition evaluation (`hooks/executor.rs:600`, also `sh -c`) is affected too, silently skipping hooks whose conditions shell out. The embedded terminal escapes this only because it spawns `-l` login shells.

**Fix**: At startup (before building AppState), resolve the user's real PATH and set it on the process: use the fix-path-env crate, or run `$SHELL -lc 'echo $PATH'` once and `std::env::set_var("PATH", ...)`. Alternatively have the hook executor accept an explicit PATH and have the GUI pass a shell-resolved one.


### 🟠 HIGH · UNVERIFIED — start_proxy and auto-start report "running" even when the proxy failed to bind its ports

**Where**: `src-tauri/src/commands/proxy.rs:36`

`let handle = devflow_proxy::run_proxy(config.clone()).await.map_err(...)?` then `running: true` is returned and `settings.proxy_auto_start = true` persisted. But `run_proxy` spawns the HTTPS/HTTP/API listeners with `tokio::spawn(async move { if let Err(e) = server::run_https_server(...) { log::error!(...) } })` (crates/devflow-proxy/src/lib.rs:243-252) and returns `Ok(ProxyHandle)` unconditionally — bind errors are only logged. Concrete scenario: the CLI `devflow proxy start` (or nginx/another app) already holds 443/80; the user clicks Start Proxy in the GUI — the command succeeds, the tray shows "Proxy: Running (443)", `proxy-status-changed {running:true}` is emitted, auto-start is persisted, yet nothing is listening for this instance. `get_proxy_status` only checks `state.proxy.is_some()` so the lie persists forever. **Fix**: In run_proxy, bind all three listeners (TcpListener::bind) BEFORE spawning the accept loops and return Err on bind failure. In the GUI, treat that error as not-running, do not persist proxy_auto_start, and surface the error string. Log the error in the tray toggle path.

`for wt in worktrees.iter().filter(|wt| !wt.is_main) { if repo.remove_worktree(&wt.path).is_ok() || (wt.path.exists() && std::fs::remove_dir_all(&wt.path).is_ok()) { ... } }`. ### 🟡 MEDIUM · UNVERIFIED — Terminal child processes are never killed — ChildKiller stored but unused; exit-poll task can spin forever

**Where**: `crates/devflow-terminal/src/lib.rs:264`

`close_session` only drops the PTY master: the comment claims `// Dropping master + writer closes the PTY and kills the child`, but the stored `_killer: Box<dyn ChildKiller + Send + Sync>` (lib.rs:53) is never invoked anywhere. **Fix**: In close_session, call `killer.kill()` (and ideally signal the process group) before dropping the master; have the exit-poll task also listen to the cancel signal so it terminates when the session is closed.

## GUI frontend correctness (React)  (`gui-frontend`)

The React GUI is well-organized (typed invoke wrappers, types/index.ts mirrors the Rust DTOs closely — I found almost no field-name drift) and most pages handle their happy paths cleanly. The structural problem is error and result surfacing: roughly 26 error paths funnel into window.alert() and one into window.confirm(), which are silent no-ops in wry/WKWebView on macOS (your primary platform), and the rich result objects returned by create/switch/delete workspace (per-service success flags, hook failed/error counts) are discarded entirely. Combined, this means service-provision and hook failures in the GUI are completely invisible, which directly feeds the "hooks don't always work" perception. There are also a few destructive divergences between what the GUI displays and what the backend does (merge-train cleanup override is ignored; hook editing silently rewrites and strips extended-hook fields), a dead onboarding route (projects/*/setup never matches in React Router v6), and terminal content that is destroyed by panel minimize or font-size changes because there is no scrollback replay. Fixing the alert/confirm no-ops and rendering OrchestrationResult/HookRunResult failures would resolve the bulk of the GUI's perceived flakiness.

## Config + state persistence (cross-cutting)  (`config-state`)

The config layer (crates/devflow-core/src/config/mod.rs) is cleanly structured: the env > local > committed > global precedence is genuinely implemented in EffectiveConfig::get_merged_config, all seven core env toggles (DEVFLOW_DISABLED, DEVFLOW_SKIP_HOOKS, DEVFLOW_AUTO_CREATE, DEVFLOW_AUTO_SWITCH, DEVFLOW_BRANCH_FILTER_REGEX, DEVFLOW_DISABLED_BRANCHES, DEVFLOW_CURRENT_BRANCH_DISABLED) are read, and the state writer uses lock + tmp + atomic rename, so outright file corruption is unlikely. The two biggest structural risks are identity and ownership: (1) the local-state project key is the canonical directory of whichever .devflow.yml was found by walking up from cwd, so every worktree gets its own state silo — workspace registry, services and merge trains fragment as soon as commands (including git hooks and agents) run inside a worktree, which lines up with your "hooks don't work in agent-created worktrees" report; (2) services live in two competing stores — CLI `service add` writes only to local state, the GUI writes only to .devflow.yml, and the CLI/TUI then wholesale replace committed services with state services, so the three frontends can see three different service lists. Secondary risks: read-modify-write on the state file happens outside the lock (lost updates on concurrent checkouts), unknown YAML keys are silently dropped (typos = mystery misbehavior), and the documented `agent:` section / DEVFLOW_AGENT_COMMAND are dead. Note: only .devflow.yml/.devflow.yaml are supported — there is no devflow.toml support anywhere in the code.

### 🟡 MEDIUM · UNVERIFIED — State read-modify-write happens outside the file lock — concurrent checkouts lose registrations

**Where**: `crates/devflow-core/src/state/local_state.rs:298`

Every mutator does `self.refresh_state()?` (re-read file), mutates in memory, then calls save_state(), and the lock is only acquired inside save_state: `let lock_path = lock_file_path(&self.state_file_path); let _lock = acquire_file_lock(&lock_path)?;` (lines 596-598). The read is not under the lock, so the classic lost-update race exists: two parallel `devflow switch -c` / git checkouts (exactly the parallel-agent workflow) both refresh, both register their workspace in their in-memory copy, then write sequentially — the second write erases the first registration. The atomic tmp+rename only prevents torn files, not lost updates. The caller only logs a warning on failure (src/cli/workspace.rs:1676-1678 `log::warn!("Failed to register workspace in devflow state")`), so the loss is silent.

**Fix**: Acquire the lock at the start of each mutator, reload the state under the lock, apply the mutation, write, then release (e.g. a `with_locked_state(|state| ...)` helper). Better: replace the create_new lockfile with an OS advisory lock on the state file itself (fd-lock/fs2), which also survives kill -9 without staleness heuristics.

### 🟡 MEDIUM · UNVERIFIED — Stale-lock recovery race can hand the lock to two processes, and a crashed holder blocks saves which then fail silently

**Where**: `crates/devflow-core/src/state/local_state.rs:90`

TOCTOU: waiters A and B both observe the stale lock; A removes it and creates its own fresh lock; B then removes A's fresh lock (its decision was based on the old file's metadata) and creates its own — both now believe they hold the lock and write concurrently, and B's Drop deletes A's lock again. Separately, after a kill -9 the dead process's lock survives 30s while MAX_ATTEMPTS×SLEEP_MS = 200×25ms = 5s, so every save in that 25-second window bails with 'Timed out waiting for lock file' — and callers like register_workspace only `log::warn!`, so the workspace registration is dropped. Also `elapsed().unwrap_or_default()` maps clock-skew errors to 0s, making such a lock never stale.

**Fix**: Use an OS advisory lock on the state file itself (fd-lock / fs2 flock), which is atomically released on process death — eliminating both the staleness heuristic and the removal race. If keeping lockfiles, remove staleness by opening-and-flocking the lockfile rather than create_new+remove.

## TUI + merge train + sandbox + terminal crate + LLM/commit  (`tui-misc`)

The TUI is well-structured: a clean main/background-task split, a panic hook that restores the terminal (mod.rs:38-44), and components driven by an Action enum. The merge-train and sandbox modules have good unit-test coverage and clear types. The biggest structural risks are behavioral divergence between the CLI and the TUI/merge-train: the TUI create-workspace path bypasses worktree creation entirely and runs lifecycle hooks in the wrong directory, and the merge train re-implements merge without the CLI's hooks and full cleanup. There are also two real data-integrity gaps (force-checkout in merge can discard uncommitted work; rebase rebases the wrong branch when the target lives in a worktree) and a sandbox FS-isolation bypass on the --detach/--open path that is exactly the agent execution mode. Finally a latent panic in the LLM diff truncation will crash `commit --ai` on large UTF-8 diffs. None of the merge-train state machine itself is broken, but its side effects on the user's primary working directory are surprising and unsafe.


### 🟠 HIGH · UNVERIFIED — TUI 'create workspace' ignores worktree config: checks out branch in main repo and runs hooks in the wrong directory

`create_and_checkout_workspace` does only `self.vcs.create_workspace(name, from)?; self.vcs.checkout_workspace(name)?;` — it switches the TUI's own/main working copy onto the new branch and never creates a worktree, even when `worktree.enabled: true`. ### 🟠 HIGH · UNVERIFIED — Merge train and TUI merge skip pre/post-merge hooks and perform incomplete cleanup (orphaned worktrees, containers, state)

**Where**: `crates/devflow-core/src/merge/train.rs:295`

`process_next` performs the merge directly and, on success with cleanup enabled, only does `repo.delete_workspace(&workspace)` (train.rs:297) which deletes the git branch and nothing else. No PreMerge/PostMerge lifecycle hooks are ever fired. The CLI merge (src/cli/workspace.rs:2694-2783) runs PreMerge and PostMerge hooks and its cleanup is documented to 'delete source workspace, worktree, and service workspaces' (workspace.rs:2689). The config docstring for `effective_cleanup` and the merge plan message both promise worktree + service-workspace teardown, but the train deletes only the branch — leaving the worktree directory, Docker service containers, and local state entries orphaned. The TUI `MergeWorkspace` action (src/tui/app.rs:1160-1206) has the same gap: it calls `merge_vcs.merge_branch(&source)` with no pre/post-merge hooks and no cleanup at all. **Fix**: Have the merge train and TUI merge call the same merge orchestration the CLI uses (run PreMerge/PostMerge hooks; on cleanup call `factory::orchestrate_delete`, remove the worktree, and unregister local state) instead of a bare `repo.delete_workspace`.


### 🟠 HIGH · UNVERIFIED — Merge train rebase strategy rebases the wrong branch when the target has a worktree

**Where**: `crates/devflow-core/src/merge/train.rs:240`

In rebase strategy, `process_next` only checks out the source when `merge_dir == self.project_dir` (train.rs:241-250). When the target lives in its own worktree (`merge_dir != self.project_dir`), the source is never checked out, yet it still calls `repo.rebase(target)` where `repo` is the provider at `self.project_dir`. `GitRepository::rebase` (crates/devflow-core/src/vcs/git.rs:1093-1098) takes no source argument — it rebases `self.repo.head()` (whatever branch the user currently has checked out in the project dir) onto target and `rebase.finish()` (git.rs:1158) updates that branch. So in the worktree case it silently rebases the user's currently-checked-out branch onto target instead of the train entry's source workspace, corrupting an unrelated branch. The same latent bug exists in the CLI merge (workspace.rs:2718-2722) and is only masked there by the `merge_dir == initial_dir` guard. Quote (train.rs:240-251).

**Fix**: Make `rebase` take the source branch explicitly (rebase source onto target regardless of which dir HEAD points at), or always check out the source workspace in a dedicated location before rebasing. Never rely on the project dir's ambient HEAD for which branch gets rebased.


### 🟠 HIGH · UNVERIFIED — Sandbox filesystem isolation silently bypassed on the --detach/--open (multiplexer) execution path

**Where**: `src/cli/workspace.rs:2277`

For sandboxed workspaces, foreground execution wraps the command with the Seatbelt/Landlock policy via `policy.wrap_command_string` (workspace.rs:2311-2312). The `--detach`/`--open` path does NOT: it builds a tmux/zellij template and runs `sh -c '<full_cmd>'` (workspace.rs:2277-2281) with no `sandbox-exec` wrapping, so the filesystem sandbox is never applied — only the command guard's `validate_command` (workspace.rs:2172) runs. Yet the code prints `Sandbox: enabled (platform: ...)` (workspace.rs:2175-2183) and reports `"sandboxed": is_sandboxed` in JSON (workspace.rs:2298). Interactive/agent sessions are exactly the case launched via the multiplexer, so an agent running in a 'sandboxed' workspace gets full filesystem write access outside the workspace while the UI claims isolation is on. Quote (workspace.rs:2259): `format!("sh -c '{}'", escaped)` followed by `Command::new("sh").args(["-c", &expanded])`.

**Fix**: Apply the sandbox wrapping in the detach path too: substitute `policy.wrap_command_string` (sandbox-exec on macOS) into the `{cmd}` expansion, or for interactive shells launch the shell under `sandbox-exec -f <profile>` (the GUI already does this in src-tauri/src/commands/terminal.rs:333). If FS sandboxing cannot be applied, do not print 'Sandbox: enabled'.


### 🟡 MEDIUM · UNVERIFIED — LLM diff truncation panics on a non-char-boundary slice — crashes `commit --ai` on large UTF-8 diffs

**Where**: `crates/devflow-core/src/llm.rs:280`

`truncate_diff` does `let mut truncated = diff[..MAX_DIFF_SIZE].to_string();` with `MAX_DIFF_SIZE = 32_000`. Slicing a `&str` by byte index panics with 'byte index is not a char boundary' if byte 32000 falls in the middle of a multi-byte UTF-8 sequence. Git diffs routinely contain non-ASCII (accented filenames/content, emoji in docs/tests). Any staged diff larger than 32 KB whose 32000th byte is mid-codepoint will panic the whole `devflow commit --ai` process. Quote (llm.rs:277-282).

**Fix**: Truncate on a char boundary, e.g. find the largest `i <= MAX_DIFF_SIZE` with `diff.is_char_boundary(i)` (or use `diff.char_indices()` / `floor_char_boundary`) before slicing.


### 🟡 MEDIUM · UNVERIFIED — Merge train `dequeue` ignores the target — cannot remove entries from non-main trains

**Where**: `crates/devflow-core/src/merge/train.rs:118`

`dequeue` hardcodes `let target = self.config.git.main_workspace.clone();` and loads only that train, while `enqueue`, `reorder`, `status`, `run`, `pause`, and `resume` all take an explicit `target`. The CLI `TrainAction::Remove` (src/cli/train.rs:59-61) and the Tauri `remove_from_train` (src-tauri/src/commands/train.rs:275) both call `dequeue(&workspace)` with no target. So if a user runs `devflow train add --target release/v2 feature/x`, they can never remove it: `dequeue` looks only at the main train and bails 'not found in merge train'. Quote (train.rs:117-124).

**Fix**: Give `dequeue` a `target: &str` parameter (mirroring `enqueue`/`reorder`) and thread the target through the CLI and Tauri callers; or search all trains for the workspace when no target is given.


### 🟡 MEDIUM · UNVERIFIED — Merge train / TUI merge mutate the user's primary working directory and can discard uncommitted work via force checkout

**Where**: `crates/devflow-core/src/vcs/git.rs:949`

When the target has no dedicated worktree, both the merge train (train.rs:280-288) and the TUI merge (app.rs:1186-1189) run `checkout_workspace(target)` then `merge_branch(source)` in the user's main working copy — silently switching the user off their current branch and leaving them on `target` with no restore. `merge_branch`'s fast-forward path then does `self.repo.checkout_head(Some(CheckoutBuilder::new().force()))` (git.rs:950), a force checkout that discards uncommitted changes in the working tree. Running `devflow train run` (or a TUI merge) from the repo root while having local edits can therefore lose uncommitted work and leaves the working copy on an unexpected branch. Quote (git.rs:949-951): `self.repo.checkout_head(Some(git2::build::CheckoutBuilder::new().force()))`.

**Fix**: Refuse to merge in-place when the working tree is dirty (check `has_staged_changes`/status first), prefer operating in a dedicated target worktree, and restore the user's original branch after the train/TUI merge completes. Avoid `.force()` checkout on the user's live working directory.


### 🟡 MEDIUM · UNVERIFIED — CommandGuard rm pattern misses `rm -fr` (only blocks r-before-f ordering)

**Where**: `crates/devflow-core/src/sandbox/command_guard.rs:22`

The destructive-rm pattern is `r"\brm\s+(-[a-zA-Z]*r[a-zA-Z]*f|--recursive)\s+(/|~)"`. The first alternative requires the `r` flag to appear before the `f` flag, so `rm -rf /` is blocked but the equally common `rm -fr /` is NOT (the regex cannot match `-fr`). On platforms without an active filesystem sandbox (Linux without the `sandbox-landlock` feature, or any path inside a writable area on macOS), the command guard is the only protection, so this is a real bypass of an advertised block. The test suite only covers `rm -rf` (command_guard.rs:156-160), hiding the gap. Quote (command_guard.rs:22).

**Fix**: Match the flags order-independently, e.g. block any `rm` whose option cluster contains both `r` and `f` (or `--recursive` with `--force`) targeting `/` or `~` — for instance `\brm\s+(-[a-zA-Z]*\b.*)?` parsing, or two lookahead-style checks for `r` and `f`. Add a `rm -fr` test.


### ⚪ LOW · UNVERIFIED — Sandbox `allow` overrides do fragile substring matching against the regex source

**Where**: `crates/devflow-core/src/sandbox/command_guard.rs:55`

`from_config` removes default block patterns via `patterns.retain(|p| !allow.iter().any(|a| p.contains(a.as_str())))` — it matches the allow string as a substring of the raw regex source, not against command semantics. So `allow: ["git"]` removes both `\bgit\s+push\b` and `\bjj\s+git\s+push\b`, and a short allow like `"s"` would strip nearly every default pattern (all contain `\s`). This makes the allowlist easy to over-broaden by accident and silently disables protections. Quote (command_guard.rs:54-61).

**Fix**: Match allow entries against a stable identifier for each default rule (e.g. give each default pattern a name/key and let `allow` reference those keys) rather than substring-matching the regex source.


### ⚪ LOW · UNVERIFIED — Seatbelt profile interpolates paths unescaped — a path containing a quote can break or weaken the policy

**Where**: `crates/devflow-core/src/sandbox/seatbelt.rs:45`

`generate_seatbelt_profile` builds the `.sb` policy with raw `format!("(allow file-write* (subpath \"{}\"))\n", workspace)` for the workspace dir, $TMPDIR, and each `extra_write` path (seatbelt.rs:45-62), with no escaping of `"`, `)` or newlines. A workspace or configured extra path containing a double-quote (legal on macOS/APFS) would terminate the subpath string early and either make `sandbox-exec` reject the profile or alter which paths are writable. Worktree path templates and user-supplied `filesystem.extra_write` entries are plausible sources. Quote (seatbelt.rs:45-48).

**Fix**: Escape path strings before embedding them in the SBPL profile (at minimum reject/replace `"`, `\`, and newlines), or canonicalize and validate paths and fail closed if a path cannot be safely represented.


### ⚪ LOW · UNVERIFIED — AI commit prompt injects diff inside a markdown code fence; configured CLI command is echoed to stderr

**Where**: `crates/devflow-core/src/llm.rs:299`

`build_user_prompt` wraps the diff in triple-backtick fences: `format!("...Here is the full diff:\n\n```\n{}\n```\n\n...")` (llm.rs:300-303). Diffs that themselves contain ``` (very common for docs/markdown/test fixtures) break out of the fence, letting diff content be interpreted as instructions to the model — a prompt-injection vector that can yield bogus or attacker-influenced commit messages. Separately, `src/cli/commit.rs:103` unconditionally `eprintln!("Generating commit message via: {}...", cmd)` prints the full configured commit command, which may embed a secret if the user put an API key inline in `DEVFLOW_COMMIT_COMMAND` / `commit.generation.command`. (The CLI path itself is safe from shell injection since the prompt is piped to stdin, not interpolated.) Quotes: llm.rs:300-303 and commit.rs:103.

**Fix**: Delimit the diff with a clear non-markdown sentinel or XML-style tags and instruct the model to treat the content as untrusted data, not instructions. Avoid printing the raw command string (or redact it) when announcing CLI generation.

# Vision gap analysis — "single global container + auto-provisioning"


## Current state
devflow today is a per-invocation CLI (plus TUI/Tauri GUI and a separate proxy daemon) that implements PHYSICAL isolation: every (project, service, workspace) triple gets its own Docker container. Postgres: LocalProvider (crates/devflow-core/src/services/postgres/local/mod.rs) keeps a global SQLite registry (~/.local/share/devflow/state.db, state.rs), gives each workspace its own pgdata dir under projects/<id>/workspaces/<branch_id>/pgdata, clones it from a parent via StorageCoordinator (storage/local_driver.rs APFS `cp -cR` / zfs_driver.rs ZFS snapshots) while pausing the parent container (mod.rs:256-281), and allocates a fresh host port per workspace (state.rs:160 `next_port` = MAX(port)+1, default base 55432). ClickHouse/MySQL/generic providers (services/clickhouse/local.rs, mysql/local.rs, generic/mod.rs) also create one container per workspace, named `devflow-{project}-{service}-{workspace}` (generic/mod.rs:82), with state derived purely from Docker labels (devflow.managed/project/service/workspace via services/local_docker.rs:74). ClickHouse/MySQL reuse the same CoW directory clone (services/mod.rs:200 clone_data_dir). Orchestration is provider-agnostic through the ServiceProvider trait (services/mod.rs:74) and factory (services/factory.rs:87-557), driven from workspace/create.rs (hook ordering PreServiceCreate -> services -> PostServiceCreate -> PostCreate -> PostSwitch) and git hooks (src/cli/git_hook.rs). Config is YAML-ONLY: Config::find_config_file (config/mod.rs:741-760) matches only `.devflow.yml`/`.devflow.yaml`, plus `.devflow.local.yml` (line 988) and global ~/.config/devflow/config.yml (line 611); no `toml` crate is a direct dependency of any workspace crate (only transitive in Cargo.lock), so devflow.toml is entirely unsupported. There is NO controller daemon: the only long-running processes are the reverse proxy (`devflow proxy start --daemon` spawns a detached process with a pidfile, src/cli/proxy.rs:65-160; core loop in crates/devflow-proxy/src/lib.rs run_proxy with DockerMonitor event stream) and the Tauri GUI. There is zero MinIO support and zero logical provisioning — grep finds no CREATE DATABASE/CREATE SCHEMA anywhere in devflow-core; the only S3 code is the rust-s3 client used to seed postgres from s3:// dumps (postgres/local/seed.rs:388). Notable half-built shared-instance gesture: GenericDockerConfig.port_mapping is documented as "Static port mapping ... Used when auto_workspace is false" (config/mod.rs:267, generic/mod.rs:39) but the host side is never honored — container_port() (generic/mod.rs:171) extracts only the container port and create_workspace always calls pick_port_for_branch() (line 395).


## Reusable as-is

- **ServiceProvider trait + factory dispatch + orchestration (crates/devflow-core/src/services/mod.rs:74-193, services/factory.rs:87-186 and orchestrate_create/switch/delete at 350-525)** — The trait is already abstract over what a 'workspace' is (create/delete/list/exists/switch/get_connection_info). A new SharedPostgresProvider whose create_workspace runs CREATE DATABASE and whose get_connection_info returns the fixed global port + per-project database slots in with zero changes to orchestration, git-hook plumbing, hook context, CLI, TUI, or GUI — they all go through this trait. Partial-failure tolerance in orchestrate_* carries over unchanged.
- **GenericDockerProvider container lifecycle (services/generic/mod.rs: ensure_image:100, create_and_start_container:181, wait_healthy:268, exec_check:304) + shared helpers (services/local_docker.rs: sanitize_name_component, inspect_container_status, pick_available_port, collect_container_logs)** — This is ~90% of an 'ensure one global container per engine' implementation: image pull, labeled container creation, healthcheck wait, in-container exec. Extract these into a reusable ensure_global_container() that uses a FIXED name (devflow-global-postgres) and identity port mapping instead of the per-workspace container_name()/pick_port_for_branch().
- **In-container exec plumbing: GenericDockerProvider::exec_check (generic/mod.rs:304-338) and the docker-exec hook action (hooks/actions/docker_exec.rs)** — Exactly the mechanism needed for logical provisioning: run `psql -c "CREATE DATABASE ..."`, `clickhouse-client -q "CREATE DATABASE ..."`, `mc mb` inside the global container. The hook action version is templated (MiniJinja with sanitize_db filter, hooks/template.rs:20/88) so the whole target UX can be PROTOTYPED today in YAML with no Rust changes: a manually-run global postgres + a post-create docker-exec hook doing CREATE DATABASE {{ workspace | sanitize_db }}.
- **Hook engine: phases (hooks/mod.rs:24-56 incl. PostServiceCreate/PostCreate), executor with working_dir + sandbox (hooks/executor.rs), actions (shell/docker-exec/write-env/http/notify), recipes (hooks/recipes.rs), context with per-service vars (build_hook_context, ServiceContext at hooks/mod.rs:398)** — The 'background hook running CREATE DATABASE if missing' from the vision maps 1:1 onto existing phases. write-env action already writes DATABASE_URL into .env.local from {{ service[x].url }} — when the provider becomes logical, templates keep working because ConnectionInfo still feeds the same context. Ship a 'shared-db' recipe via the existing recipe installer.
- **SQLite Store (services/postgres/local/state.rs, opened from a global data_root ~/.local/share/devflow/state.db) and LocalStateManager (state/local_state.rs)** — Already a machine-global registry spanning all projects (projects table has project_path for orphan detection). Add tables for global engines and logical resources (engine, database/bucket, owning project+workspace) to get refcounting and GC. SQLite gives cross-process serialization (BEGIN IMMEDIATE) for the create-if-missing race.
- **Docker discovery (docker/discovery.rs: discover_containers:50, detect_service_type_from_image:245, extract_credentials:266, build_connection_url:402) and compose parsing (docker/compose.rs)** — Lets the controller ADOPT an existing user-run postgres/redis/minio container as the global instance instead of creating its own — same flow `devflow service add --discover` already uses, including credential extraction from container env.
- **devflow-proxy crate: DockerMonitor event stream (monitor.rs:32), label-based routing (discovery.rs reads devflow.* labels at :73-99), api.rs JSON server on 127.0.0.1:2019, daemon spawn + pidfile lifecycle (src/cli/proxy.rs:65-160), mDNS .local advertising (mdns.rs)** — The proxy IS the embryo of the target 'local agent': long-running, watches Docker events, reconciles state, exposes a local JSON API, has start/stop/status/pidfile UX. A devflow controller can either extend this process or copy its skeleton. Global containers labeled devflow.managed=true get stable names (postgres.local) advertised automatically — DB endpoints over mDNS already exist on macOS.
- **Git trigger plumbing: src/cli/git_hook.rs (post-checkout) -> workspace/create.rs / switch.rs -> orchestrate_*** — 'Automatically provisions on the fly' entry points already exist and fire on git checkout. In the target model the same call sites simply hit a cheap idempotent ensure-database provider instead of booting a container — no new trigger machinery needed.
- **Seed engine (postgres/local/seed.rs: parse_source supports postgresql://, local .sql/.dump, s3://; rust-s3 client at :388-410)** — Seeding a logical database in the shared instance reuses parse_source and the docker-exec-based restore path with the database name parameterized; the s3 crate already in the tree also covers MinIO bucket API calls (create_bucket) for the MinIO provider.
- **PluginProvider JSON-over-stdio protocol (services/plugin.rs)** — Allows prototyping the logical-isolation provider OUT of tree (a 50-line script doing psql CREATE DATABASE) wired in via `type: plugin`, validating the model before committing to the Rust implementation.

## Conflicts with the vision

- **The entire CoW-per-container storage stack: StorageCoordinator + local/zfs drivers (services/postgres/local/storage/*), clone_branch_from_parent with parent container pause/unpause (postgres/local/mod.rs:256-281), clone_data_dir APFS/reflink copy (services/mod.rs:200-272), per-workspace pgdata dirs** — In a single global container there is no per-workspace PGDATA to clone — filesystem-level CoW cannot isolate databases inside one running postgres instance. Branch-from-parent semantics must be re-expressed as `CREATE DATABASE x TEMPLATE parent` (which requires no active connections to the template — a completely different constraint than pausing a container) or pg_dump|restore. The BranchState model (Provisioning/Running/Stopped per workspace, model.rs) also stops making sense: a logical database has no independent run state. This stack stays valid ONLY for the coexisting physical provider; none of it transfers.
- **Per-workspace host port allocation: Store::next_port = MAX(port)+1 from SQLite (postgres/local/state.rs:160-167), pick_available_port/pick_available_port_pair (services/local_docker.rs:151,189), port column in the workspaces table schema (state.rs:59), and ConnectionInfo carrying a distinct port per workspace** — The global model has exactly ONE fixed, well-known port per engine (5432/6379/9000/9001). Every consumer of per-workspace ports — hook template {{ service[x].port }}, .env.local writers, the GUI services view — silently changes meaning: isolation moves from the port axis to the database-name axis. Mixed setups (one CoW service + one shared service in the same project) must keep both schemes coherent in the same hook context.
- **Container identity == (project, service, workspace): container_name() naming (generic/mod.rs:82-94, postgres docker.rs:104-116 reserve_branch), workspace_exists implemented as container-exists (generic/mod.rs:447-453), per-workspace start/stop/reset/logs, delete_workspace force-removing the container (generic/mod.rs:410-431)** — Every lifecycle verb is currently scoped to a workspace-owned container. In the global model, stop_workspace must NOT stop the engine (it serves other projects), delete_workspace must mean DROP DATABASE (force-removing the shared container would destroy every project's data — a data-loss trap if the generic provider were naively pointed at a shared container), and logs are engine-level not workspace-level. supports_lifecycle semantics need an explicit scope (engine vs workspace) in the trait or capabilities.
- **destroy_project semantics (postgres/local/mod.rs:761-788 removes all containers + project storage; generic/mod.rs:569-589 force-removes all matching containers; orphan cleanup in services/orphan.rs)** — Destroy/GC currently assumes everything matching a label prefix belongs exclusively to this project. With shared engines, destroy must drop only this project's databases/buckets and remove the engine only when the global registry shows zero remaining references — reference counting that does not exist anywhere today.
- **Short-lived per-project process model: LocalProvider::new captures project from cwd (postgres/local/mod.rs:106-113), Mutex<Store> is per-process only, container creation is not idempotent across processes** — A 'single global container for ALL repos' requires cross-repo coordination. Two concurrent `git checkout`s in different repos would race to create devflow-global-postgres (Docker returns 409 on duplicate name; current code paths treat that as a hard error rather than 'already exists, proceed'). Needs SQLite BEGIN IMMEDIATE or flock plus 409-tolerant ensure logic — a structural change to how providers acquire resources.
- **GenericDockerConfig.port_mapping host-side is dead config (config/mod.rs:267-269 promises static mapping when auto_workspace is false; generic/mod.rs:171-179 extracts only the container port and create_workspace:395 always picks a dynamic host port)** — This half-designed 'static/shared instance' escape hatch conflicts with the target design: rather than fixing it inside the per-workspace generic provider, it should be deprecated in favor of an explicit shared/global provider type, or it will become a second, subtly different way to express the same thing.

## Missing entirely

- **devflow.toml (TOML config) support** (small) — Config::find_config_file (crates/devflow-core/src/config/mod.rs:741-760) matches only .devflow.yml/.devflow.yaml; from_file (:721) and load_from_project_dir (:987) hard-code serde_yaml_ng; no workspace crate depends on the toml crate (verified: zero hits in Cargo.toml manifests, only transitive entries in Cargo.lock). Add `toml` to devflow-core, branch on file extension in from_file/find_config_file, add devflow.toml/.devflow.toml to the search list, and define the 'lightweight' subset (services + hooks) the vision calls for. Serde structs are format-agnostic already, so this is mostly plumbing + tests.
- **A controller/daemon ('local agent')** (large) — No long-running devflow process exists besides the proxy and the GUI. Need `devflow daemon start/stop/status`: reconcile loop ensuring the 4 global containers (postgres/redis/minio/clickhouse) exist and are healthy, Docker event subscription (reuse devflow-proxy/src/monitor.rs DockerMonitor), local JSON API (clone devflow-proxy/src/api.rs pattern on 127.0.0.1), pidfile lifecycle (clone src/cli/proxy.rs:65-160), and a registered-projects list (src-tauri/src/state.rs ProjectEntry registry already persists one for the GUI — promote it to core). Decide whether this merges into the proxy process (one daemon) or stands alone. CLI/git-hook paths must degrade gracefully to direct in-process provisioning when the daemon is not running.
- **Logical-isolation providers (CREATE DATABASE / Redis DB-index / ClickHouse DATABASE)** (medium) — Zero CREATE DATABASE/CREATE SCHEMA logic exists in devflow-core (verified by grep). Need services/postgres/shared.rs implementing ServiceProvider: ensure global container (reuse generic/mod.rs:100-301 machinery), create_workspace -> `CREATE DATABASE "<project>_<workspace>"` (optionally TEMPLATE parent for branch semantics), delete_workspace -> DROP DATABASE, workspace_exists -> catalog query, get_connection_info -> fixed port + db name; plus a DB-name sanitizer mirroring the existing sanitize_db template filter (hooks/template.rs:88) with the 63-byte identifier limit. Analogous shared providers for Redis (SELECT index allocation or ACL key-prefix) and ClickHouse (CREATE DATABASE via the exec plumbing already in clickhouse/local.rs). Register new provider_type in factory.rs and config/mod.rs NamedServiceConfig.
- **MinIO support (engine + bucket provisioning)** (medium) — MinIO appears nowhere in the codebase. Need a global minio/minio container definition (two ports, 9000/9001 — pick_available_port_pair in local_docker.rs:189 is reusable if ports must shift), bucket-per-project provisioning via the `s3` crate already used in postgres/local/seed.rs:388 (Bucket::create against the local endpoint) or `mc` via docker exec, credential handout into the hook context (ServiceContext), and bucket deletion on workspace removal.
- **Global resource registry with reference counting** (medium) — state.db schema (postgres/local/state.rs:50-70) only models project->workspace containers. Need tables: global_engines (engine, container_name, port, image, status) and logical_resources (engine, resource name, project, workspace, created_at) so that destroy/GC (services/orphan.rs, cli/gc.rs) can drop only owned databases/buckets and remove an engine only at refcount zero.
- **Cross-process idempotency and locking for ensure-if-missing** (small) — Concurrent provisioning from two repos must not double-create the global container or race CREATE DATABASE. Use SQLite BEGIN IMMEDIATE transactions on state.db plus tolerate Docker 409 name-conflict as success-already-exists, and use IF NOT EXISTS / catalog checks on the SQL side. No such tolerance exists today (create_container errors are fatal in generic/mod.rs:251-254).
- **Scope-aware ServiceProvider semantics** (medium) — The trait (services/mod.rs:74) needs either a capabilities extension (e.g. scope: engine|workspace so the CLI/TUI/GUI stop offering per-workspace stop/reset/logs for shared services) or documented no-op behavior; otherwise `devflow service stop feature-x` on a shared service either lies or stops the engine for everyone. Also surface engine-level status in src/tui/components/services_tab.rs, src-tauri/src/commands/services.rs, and ui/src/pages.

# GUI UX critique & redesign


## Assessment
The GUI is a functional but undesigned developer tool: a GitHub-dark clone built from one 831-line styles.css (~30 classes) plus ~400 inline style={{}} objects scattered across pages (ProjectDetail alone has 128, HookManager 87, HookEditModal 73). There is no component library, no icon set (SVGs are copy-pasted inline, the same trash icon 4+ times), no toast system, no light/dark theming (dark hard-coded in :root; tauri.conf.json sets no window theme, so on macOS in light mode the native title bar is light over a dark app). Error UX is 27 native alert()/confirm() calls across 8 files mixed inconsistently with a custom ConfirmDialog. The information architecture is service-centric while the user's mental model is workspace-centric: the most common task ("what workspaces do I have, what services run in each, switch to one") takes 1 click to reach a project but then requires expanding N collapsed service accordions (state resets on every reload) to see per-workspace service status, and the workspaces table itself shows zero service information. Project sub-areas are split incoherently: Overview/Skills are hash-synced tabs inside the 1923-line ProjectDetail god-page, while Hooks/Config/Setup are separate top-level routes with "Back to project" links that lose sidebar highlight and project context. The HookManager is unusable for the author's actual pain ("hooks don't always work"): running a hook returns a one-line summary with no stdout/stderr and no execution history, and the workspace input that controls runs is hidden in a different panel's Preview tab. The ProxyDashboard fetches once on mount with no refresh button, no event subscription, and no polling, so the container table silently goes stale. Loading states are bare "Loading..." divs, and both Home and ProjectList flash a false "No projects registered yet" empty state while data loads. Verdict: the bones (routes, data fetching, Tauri IPC) are fine; the visual layer and IA need a systematic rebuild, not spot fixes.

## Redesign direction
Direction: keep the GitHub-dark personality but rebuild on a real component layer and re-center the IA on "project → workspace" instead of "page → table".

Stack: Tailwind CSS v4 + shadcn/ui (Radix primitives) + lucide-react icons + sonner toasts. This is the de-facto standard for Tauri 2 + React + Vite, ships accessible Dialog/Tabs/DropdownMenu/Tooltip/AlertDialog out of the box, and its default zinc dark theme is two tokens away from the current palette (map --bg-primary #0d1117 → background, --accent #58a6ff → primary, keep success/warning/danger). Port the existing 13 CSS variables into Tailwind theme tokens, define exactly: 3 text sizes (12/13/15) + page title, 2 button sizes (sm 28px, default 32px), 4px spacing grid, one Card, one Table, one EmptyState, one Skeleton. Delete all inline style={{}} as components migrate. Set "theme": "dark" and macOS overlay title bar in tauri.conf.json.

Layout sketch: a slim left rail (icons + labels): Dashboard, Projects (expandable list of all projects, not capped at 5), Proxy, Skills, Settings; bottom: proxy status dot + terminal toggle. Selecting a project opens /projects/:id with a persistent project header (name, branch-mode badge, current workspace, Doctor health dot) and a horizontal tab strip: Workspaces · Services · Hooks · Config · Doctor · Skills — Hooks/Config/Doctor stop being orphaned top-level routes. The Workspaces tab is the default and the heart of the app: a single table where each row = workspace, columns = name+worktree path, service status dots (joined from serviceWorkspaces, not a separate accordion), agent/exec status, and a trailing action group (Switch for branch mode / Open Terminal · Reveal · Copy path for worktrees, overflow menu for connection info, logs, reset, delete). Clicking a row opens a right-side drawer with full service details, connection strings (copy buttons), recent hook executions for that workspace, and proxy domains — replacing four of today's modals. Create Workspace becomes a slide-over with the same form but a visible summary line ("worktree at ../repo.feature-x, copies .env, runs 3 post-create hooks") so users finally see what hooks will fire. Hooks tab: two panes — left lists only phases with hooks (empty phases under a collapsed "all phases" group), right shows the hook list with an execution log drawer (full stdout/stderr, history) replacing the one-line runResult; the MiniJinja playground moves to a "Test" sub-tab. Proxy page: live-updating via existing Tauri events, refresh button, copy-domain buttons, and HTTP-vs-TCP aware rows. Dashboard: one card per project listing its top 3 workspaces with status dots inline so the most common answer ("what's running?") is zero clicks after launch.
