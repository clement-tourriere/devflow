# devflow 1.0: worktrees, copy-on-write data, setup hooks

Status: implemented on this branch, not released yet (the crates are still at version 0.8.0). Design revised after review rounds 1–3 (GPT-6-Astra; round 3 found no blocking issues) and PostgreSQL 18 experiments. Supersedes the 0.x architecture.

## Why

The jdx tools now cover what devflow used to build itself:

- pitchfork 2.30 supervises daemons with ready checks, retries, cron, per-worktree namespaces, and an HTTPS proxy with `<daemon>.<worktree>.<project>.localhost` names.
- mise installs toolchains and dependencies (`mise install`, `mise deps`) and runs tasks.
- Mr. Boxington (mbx) shares and reflinks Rust build outputs across checkouts.

None of them creates worktrees, prepares a new worktree, or branches database data. devflow 1.0 keeps only that:

1. **Worktrees** — create, list and remove Git worktrees with deletion protections.
2. **Copy-on-write payloads** — clone explicitly listed ignored paths (`node_modules`, `.env`, …) from the source worktree using APFS `clonefile` / Linux `FICLONE`, falling back to a copy.
3. **Postgres branches** — one PostgreSQL ≥ 18 server per project; each workspace gets a database cloned with `CREATE DATABASE … TEMPLATE … STRATEGY FILE_COPY` and `file_copy_method = clone`. On a reflink filesystem (btrfs, XFS, ZFS 2.2+, OrbStack volumes) the clone shares blocks with its source. Benchmark on OrbStack: a 392 MB database cloned in 0.93 s with +0.2 MB on disk; `WAL_LOG` used +370 MB. `FILE_COPY` forces checkpoints, so latency depends on server activity. A macOS bind mount (virtiofs) gets full copies.
4. **Setup hooks** — trusted shell commands that run when a worktree is created (or adopted), with the database URL in the environment.
5. **GPUI desktop app** — built on `gpui-kit`, replacing Tauri + React.

Everything else is removed: jj, the TUI, the proxy crate, the terminal crate, the native process supervisor, the controller daemon, execution records, the general operation journal and retention framework, the ownership registry and orphan scan, cloud and plugin providers, MySQL/ClickHouse/Redis/RustFS/generic services, the ZFS driver, MiniJinja templating, hook recipes and actions, and the agent-guide generator. Processes and the proxy are pitchfork's job; toolchains and dependency installation are mise's.

## Principles

- **Data lifetime is independent of code lifetime.** A database branch has its own identity; a worktree (or a VM) attaches to it. Code origin (`--from`) and data origin (`--data-from`) are separate and immutable once chosen.
- **Never infer ownership from names.** Database branches, snapshots and roles are recorded in a metadata database on the server; worktrees carry a receipt with their instance ID.
- **Resumable, not transactional.** Every multi-step operation records intent before its external effect and can be re-run to completion. Creating the worktree itself is the one exception: its receipt is written after the worktree exists (see Workspace lifecycle).
- **Report what actually happened.** CoW is reported as `verified`, `copy` or `unknown`, never assumed.
- **Synchronous core.** `devflow-core` has a blocking API: no async and no GPUI types in its public API (the `postgres` crate runs its own hidden runtime inside). The CLI calls it directly; the GUI calls it from GPUI background tasks.

## Configuration (TOML only)

`devflow.toml` (or `.devflow.toml`) at the repository root, committed. `devflow.local.toml` beside it is machine-local and git-ignored; it is merged on top (tables merge recursively, other values are replaced). Unknown keys are errors in every section.

```toml
[project]
name = "shop"
id = "0b3c9d2e-…"            # written by `devflow init`; stable across machines

[worktree]
dir = "../{repo}.worktrees"      # parent directory for new worktrees; {repo} and {project} expand, "~/" is accepted
copy = [".env", "node_modules"]  # cloned from the source worktree when present; empty by default (`devflow init` writes [".env"])

[postgres]                       # omit the section to disable database branching
mode = "managed"                 # "managed" (devflow runs a container) or "external"
image = "postgres:18"            # managed only; must be PostgreSQL ≥ 18
# admin_url = "postgres://provisioner@db.internal:5432/postgres"   # external only (or DEVFLOW_PG_ADMIN_URL)
# app_host = "db.internal"       # host written into workspace URLs if different from the admin endpoint
# app_port = 5432                # port written into workspace URLs if different from the admin endpoint
database = "shop"                # display name of the default workspace's database branch (default: the project name)
# bind = "127.0.0.1"             # managed only: IP address the container port is published on
# port = 0                       # managed only: fixed host port (0 = ephemeral)
# on_busy_source = "disconnect"  # "disconnect" or "fail"; default "disconnect" for a managed server bound to loopback, "fail" otherwise
# cow = "verified"               # external only: "verified", "copy" or "unknown" (default), declared by the operator; normally in devflow.local.toml
require_cow = false              # true: refuse to create or reset a branch when CoW is not verified

[hooks]
setup = ["mise install", "bun install", "bun run db:migrate"]
switch = []                      # every `devflow switch` into the workspace (optional)
teardown = []                    # before removal; failure blocks removal unless --force
timeout = "15m"                  # per command
```

`{repo}` is the main checkout's directory name and `{project}` the sanitized project name; a relative `dir` is relative to the main checkout, and `~/` starts at the home directory. `bind` must be an IP address.

A 0.x configuration produces an actionable error that links the migration guide; it is never silently ignored. With no project file (`devflow.toml` or `.devflow.toml`), a `.devflow.yml`, `.devflow.yaml`, `.devflow.local.yml` or `.devflow.local.yaml` is that error; if a project file exists, those 0.x files are ignored. A TOML project file counts as 0.x when it has a top-level `services`, `processes`, `agent`, `default_workspace`, `git`, `commit` or `proxy` key, or a hyphenated key under `[hooks]`.

## Local state

| What | Where |
| --- | --- |
| Project registry (GUI, `list --all`) | `<config dir>/projects.toml`: main-checkout path, project id, name. Updated by `init`, `switch` and `setup`. |
| Hook trust | `<config dir>/trust.toml`: one `[[approval]]` per `{project_id, root}` (the main checkout) with `digest` and `approved_at`; `digest` is the SHA-256 of the JSON serialization of the merged `[hooks]` section |
| GUI settings | `<config dir>/gui.toml`: editor command, terminal command, theme |
| Workspace receipt | `<per-worktree git dir>/devflow/receipt.json` (`git rev-parse --git-dir`, `0600`): `version`, instance id, project id, workspace name, code source, data source as requested and `data_source_id` (the server identity it resolved to, pinned so a retry clones the same source), data binding (branch id, db, role, URL, `source` label, `owned`), a record per phase (state, `detail`, `required_skip`, `updated_at`), `hooks_digest` (written after a setup hook run, never read), timestamps. Removed with the worktree. |
| Receipt lock | `<per-worktree git dir>/devflow/setup.lock`: held while setup, switch, remove or a data reset runs in that worktree; a concurrent run gets a `Busy` error |
| Setup logs | `<per-worktree git dir>/devflow/logs/<timestamp>-<phase>.log` (`0600`) |
| Creation lock | `<common git dir>/devflow/create.lock`: serializes worktree creation per repository so a failed creation never cleans up a peer's directory |
| Generated env | `<worktree>/.devflow/env` (the directory contains a `.gitignore` with `*`): `DATABASE_URL`, `PG*`, `DEVFLOW_*` |
| Managed server | `<data dir>/postgres/<project id>/`: `compose.yaml` (`0600`; embeds the superuser password as `POSTGRES_PASSWORD`), `admin.json` (`0600`: the superuser password, the cached CoW probe result, and the names of probe databases in flight) |

`<config dir>` is `dirs::config_dir()/devflow` (Linux: `$XDG_CONFIG_HOME/devflow` or `~/.config/devflow`; macOS: `~/Library/Application Support/devflow`). `<data dir>` is `dirs::data_dir()/devflow` (Linux: `$XDG_DATA_HOME/devflow` or `~/.local/share/devflow`; macOS: `~/Library/Application Support/devflow`). `DEVFLOW_CONFIG_DIR` and `DEVFLOW_DATA_DIR` override them.

The receipt lives in the worktree's own Git directory (absolute `--git-dir`; `.git/devflow` for the main checkout), so linked worktrees each have their own and it is removed with the worktree. It belongs to the worktree, not to whichever branch is checked out later; devflow never silently rebinds its database. A receipt whose `project_id` differs from the project is refused, never adopted: `setup`, `switch`, `db reset` and `db snapshot create` fail with an error that names the file to remove to start over; `list`, `db url` and `db psql` treat the workspace as not set up; `remove` warns and leaves its data alone.

A VM fork copies the receipt. `devflow setup --new-instance` (or `DEVFLOW_INSTANCE_ID`, an orchestrator override honoured only by an explicit `devflow setup`, never by `switch` or other commands, and refused when another worktree already records that id) gives the fork a fresh identity, marks the database, env and hooks phases pending, and provisions a new branch (from `--data-from`, else a clone of the previous binding's branch, else the recorded data source). The copied binding loses its authority: only the instance recorded as a branch's creator may reset or drop it, and `--database-url` attachments are detach-only.

## Workspace lifecycle

`devflow switch -c NAME [--from WS] [--data-from WS|snapshot:NAME[@vN]|branch:ID|empty]` and `devflow setup` (in an existing worktree) both run the same idempotent pipeline. After the worktree exists, each phase is recorded in the receipt as `started` before its effect and `done`, `skipped` or `failed` after it; re-running resumes at the first incomplete phase. A plain `switch NAME` runs the pipeline too: it resumes an unfinished setup, adopts a checkout devflow has not set up, and, when a managed server on an ephemeral port came back on another port, rewrites the receipt URL and `.devflow/env`.

1. **materialize** — add the worktree at `<worktree.dir>/<sanitized NAME>` on branch `NAME`. The branch is created from `--from` (default: the default workspace's HEAD) unless a local branch of that name already exists; that branch is reused, and `--from` then only chooses where payloads are copied from. The receipt, with a fresh instance id, is written after the worktree exists, so this phase is not recorded before its effect: a crash in between leaves a worktree without a receipt, and `switch -c NAME` then says to run `devflow setup` inside it.
2. **payload** — clone each `worktree.copy` path from the source worktree. Paths must be relative and stay inside both worktrees (no `..`, no symlink escapes); each entry is staged under a temporary name and renamed into place; entries missing in the source are skipped and existing destination entries are left alone.
3. **database** — when `[postgres]` is configured: create (or reconcile) the data branch from `--data-from` and record the binding. The default source is the source workspace's branch, and `empty` for the default workspace. The source is resolved to a server identity and pinned in the receipt before the branch is created, so a retry clones exactly the same data. If the source is the default workspace and it has no branch yet, setup first gives it an empty root branch and warns. A branch is named after its workspace; the default workspace's branch after `postgres.database`, else the project name. `switch --no-db` skips the phase.
4. **env** — write `.devflow/env`.
5. **hooks** — with no `setup` commands the phase is done without a trust check. Otherwise, if the `[hooks]` content is trusted, run the `setup` commands in order in the worktree with the env applied (`sh -c`, timeout, logs teed to the log file and stderr). If untrusted: prompt when interactive (Trust and run, Run once or Skip); otherwise skip and mark the workspace `needs_attention`. `switch --no-hooks` skips the phase on purpose.

The status is derived from the phase records, not stored, and there is no sixth phase. `ready`: every phase is `done`, or `skipped` without `required_skip` (so `switch --no-db`, `switch --no-hooks` and a missing `[postgres]` leave the workspace ready). `needs_attention`: a phase `failed` or was skipped with `required_skip` (untrusted hooks); the error is in the phase's `detail`. `in_progress`: any other state, that is a phase left pending or `started` by a crash, or a setup that another process is running right now (`busy`). A worktree without a receipt has no status (`null` in JSON, "not set up" in `list`). A skip that is not required counts as complete, so a later `devflow setup` does not redo it; `--new-instance` resets the database, env and hooks phases.

A phase that raises an error (for example an unreachable database server) is recorded as `failed`, the worktree is kept, and the command exits 1; re-running resumes it. A failing hook command ends the hooks phase as `failed` and the command exits 2. Exit codes of `switch` and `setup`: 0 `ready`, 2 `needs_attention` or `in_progress` (a setup already running elsewhere is reported as `in_progress`, not as an error), 1 any other error.

`switch` hooks run on every `devflow switch` into the workspace and, in the CLI, on first entry after `switch -c`, but only when the workspace is ready and the hooks are trusted; otherwise a warning says they did not run. A failing one is a warning too.

`devflow remove NAME` checks every protection before any effect. Never overridable: the default workspace, the workspace containing the caller's directory, a workspace that contains another workspace, and, for a caller that passes what it showed the user (the GUI: path, receipt instance and directory identity), a workspace that no longer matches it. Overridable with `--force`: locked and dirty worktrees, untrusted `teardown` hooks (skipped with a warning), failing `teardown` hooks, `--delete-branch` on a branch with commits that are not in the default workspace, and a failed drop of the data branch (the branch stays, with a warning). For a workspace that owns a data branch, an unreachable database server stops the removal before any effect unless `--keep-data` is given (`--force` does not skip this). On a terminal, a refusal that `--force` would override prompts to override it. `remove` then runs `teardown` hooks, drops the data branch if this instance created it (unless `--keep-data`), removes the worktree, and deletes the Git branch only with `--delete-branch`. New worktree paths that already exist (e.g. `feature/a` and `feature-a` both map to `feature-a`) are refused, never reused.

### Worktrees created by other tools

`devflow hook install` adds a `post-checkout` Git hook (respecting `core.hooksPath`) that runs `devflow setup --if-new --from-git-hook` when Git reports a branch checkout (flag `1`) whose previous HEAD is the all-zero OID (any hash length). That covers `git worktree add` and also fresh clones. The hook does nothing when `devflow` is not on `PATH`. An existing foreign hook is never replaced: installing over it is an error (exit 1) that prints the line to add to it instead. `--if-new` does nothing when the worktree's receipt is `ready`; any other receipt is resumed. `DEVFLOW_SETUP_ACTIVE=1` prevents re-entry. The hidden `--from-git-hook` flag makes setup safe for Git: it never prompts, trusts hooks only through `DEVFLOW_TRUST_HOOKS`, does not accept `--json`, prints a one-line note when setup fails or needs attention, and always exits 0 so Git does not report a created worktree as failed; failures are also recorded in the receipt. This catches `git worktree add`, T3 Code, Claude Code and other tools that use the git CLI; `git worktree add --orphan`, `--no-checkout` and libgit2-based tools skip the hook and need an explicit `devflow setup`. Adopted worktrees use the default workspace as code and data source (it gets an empty branch first if it has none). Hooks run at least once: a crash after a command succeeds but before the receipt update reruns it.

## Postgres branching

### Server

- **managed** — devflow writes `compose.yaml` under the managed-server directory and runs `docker compose -p devflow-<name>-<id8>` (honouring `DOCKER_HOST`/`DOCKER_CONTEXT`). The service `pg` uses the configured image, `restart: unless-stopped`, a healthcheck, the named volume `pgdata` mounted at `/var/lib/postgresql`, `-c file_copy_method=clone`, a generated superuser password, labels `dev.devflow.project=<id>` and `dev.devflow.version`, and publishes 5432 on `bind` (an IP address, default `127.0.0.1`) at `port` (default ephemeral, read back with `docker compose port`). A remote engine needs a reachable `bind` address and a fixed `port`, plus `app_host`. `db up`/`db down` start and stop it; `db down` is `docker compose stop`, never `down -v`, so it stops every branch of the project and keeps the volume.
- **external** — any PostgreSQL ≥ 18 server reachable at `admin_url` that should run with `file_copy_method = clone`. The admin role needs `CREATEDB` and `CREATEROLE` (or superuser). `db up` starts nothing: it connects and makes sure the metadata database and the project's owner role exist; `db down` does nothing.

devflow refuses servers older than 18. If `file_copy_method` is not `clone`, branches are created with full copies and reported as `copy`.

### CoW capability

Managed mode measures the real clone path once per server start: it creates and flushes a 64 MB probe database, samples free space in `$PGDATA` twice (`df` inside the container, one second apart; free space that drifts by more than 5% of the probe size means interference and records `unknown`), clones it with `STRATEGY FILE_COPY`, checkpoints and syncs, and measures again. Less than 10% growth records `verified`, more records `copy`; a probe error records `unknown`. The result describes `$PGDATA`'s filesystem only: a branch whose source uses another tablespace records `unknown`. The result is cached in `admin.json` with the image and the postmaster start time, so a restart measures again. External servers report `unknown` unless the operator declares `cow = "verified"` in `devflow.local.toml`. `devflow doctor`, the GUI and `db status --json` (`server.cow_source`: `measured` or `declared`) show whether the value was measured or declared; human `db status` prints only the value. `require_cow = true` refuses to create or reset a branch unless the capability is `verified`; it is not applied to snapshots.

### Metadata

A `devflow` database on the server, owned by the admin role, holds:

- `meta(key, value)` — `schema_version`. devflow migrates forward under an advisory lock and refuses to write to a newer schema.
- `projects(id uuid pk, name, owner_role unique, created_at)`.
- `branches(id uuid pk, project_id, name, db_name unique, role_name unique, source_kind ('empty'|'branch'|'snapshot'), source_id, instance_id /* creating instance: the only one allowed to reset or drop it by default */, status ('creating'|'ready'|'deleting'|'failed'), cow, error, generation int, op ('reset'|null), op_phase ('staging'|'cutover'|'cleanup'|null), replacement_db, backup_db, op_source_kind, op_source_id, created_at, updated_at)`. Creation provenance (`source_*`) is immutable; resets only bump `generation`.
- `snapshot_names(project_id, name, last_version, pk(project_id, name))` — versions are monotonic and never reused after deletion.
- `snapshots(id uuid pk, project_id, name, version int, db_name unique, source_branch_id, status, created_at, unique(project_id, name, version))`.
- `retired_roles(role_name pk, project_id, reason, created_at)` — roles that could not be dropped yet (tombstones; retried by `reconcile`).

The metadata database is bootstrapped under an advisory lock on the `postgres` database: devflow creates a closed staging database `devflow_bootstrap_<id12>`, marks it (`COMMENT ON DATABASE … IS 'devflow metadata v1'`), then renames it to `devflow`. An existing `devflow` database without the marker is refused untouched, never adopted; an unmarked staging database left by a crash is reported, never dropped; a marked one is renamed into place on retry. It is created closed like branch databases, with `CONNECT` and `TEMPORARY` revoked from `PUBLIC`, so branch logins cannot connect to it (advisory locks are per database). In managed mode devflow also revokes `PUBLIC` `CONNECT` on `postgres` and `template1`. On external servers devflow only changes databases it created; exclusive access to other databases is the operator's responsibility (`pg_hba.conf`).

Database and role names are generated (`df_<project8>_<id12>`, roles `dfl_<id12>` for logins and `dfo_<project8>` for the project owner), never derived from user input. The same `df_` form names the replacement and backup databases of a reset; the metadata bootstrap uses `devflow_bootstrap_<id12>` and the CoW probe `devflow_probe_<id12>` (recorded in `admin.json` before creation, so the next probe drops what a crash left). Empty databases are created from `template0`, so a customized `template1` never leaks into branches. Every mutation of a project's branches holds a **session-level** advisory lock keyed on the project id, and every cluster-level statement of the operation (`CREATE`/`DROP DATABASE`, role DDL, `ALTER DATABASE`, database grants, backend termination, the reset rename transaction) runs on that same session. Metadata rows are written on that session too, with conditional updates (expected status, phase and generation), so a stale process can neither finish DDL nor rewrite a successor's journal after losing the lock. A process waiting for the lock gives up after 300 s. Per-database normalization uses a second connection to the new database; `reconcile` drops half-made databases `WITH (FORCE)`, which ends such connections.

When the server is unreachable, commands that only read local receipts still work: `list`, `switch` to a ready workspace and `remove --keep-data` do not contact it. Database mutations fail with a clear error. `db status` reports `reachable: false` plus a `problem`, and the GUI shows an unreachable badge.

### Roles and isolation

Verified on PostgreSQL 18.6 with a non-superuser provisioner.

- **Admin (provisioner)** — the superuser in managed mode; a `CREATEDB CREATEROLE` login in external mode. It owns every devflow database and the metadata database. Provisioning sessions run `SET createrole_self_grant = 'inherit,set'` so the admin can act for the roles it creates. Sandboxes never receive it.
- **Project owner** `dfo_<project8>` — `NOLOGIN`. Owns every object inside every branch and snapshot database of the project, including the `public` schema, and holds `CREATE, TEMPORARY` on each project database. It never holds `CONNECT`.
- **Branch login** `dfl_<id12>` — `LOGIN` with a random password, member of the project owner (`INHERIT TRUE, SET TRUE`), with `ALTER ROLE … SET role = dfo_<project8>` so sessions act as the owner and new objects belong to it. It holds `CONNECT` on its own database only.

Because all branches and snapshots of a project share one owner role, clones need no ownership or privilege translation: default privileges, RLS policies and grants that name the owner stay valid. The owner role is the supported identity for anything that must survive cloning. Objects created after `SET ROLE NONE` belong to a branch login; when that branch is cloned or snapshotted, `REASSIGN OWNED BY <source login> TO <project owner>` runs inside the new database. That is local to the new database because logins own no databases or other shared objects. `REASSIGN OWNED` does not move default privileges, grants to the login, or RLS policies naming it; devflow detects those in the new database and fails the operation before granting access, rather than translating them. `DROP OWNED` is never used.

Role invariants: logins and owners have no elevated attributes (`NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS`), no `ADMIN OPTION` on any membership, and no grant options; owners never own databases or tablespaces and never log in. PostgreSQL checks backend signalling against the target's authenticated login, so a session acting as the owner cannot cancel or terminate a sibling branch's sessions. Replication machinery (subscriptions, background workers) is outside the cloning contract.

New databases are never reachable by other roles: every `CREATE DATABASE` uses `ALLOW_CONNECTIONS false`, then `CONNECT, TEMPORARY` are revoked from `PUBLIC` and `CREATE, TEMPORARY` granted to the project owner, then connections are allowed (only the admin can connect), normalization runs, and `CONNECT` is granted to the branch login last.

| Operation | Steps (under the project lock; every step recorded on the row first) |
| --- | --- |
| create empty | insert `creating` row → create login → `CREATE DATABASE … TEMPLATE template0` closed → ACLs → `ALTER SCHEMA public OWNER TO owner` → grant `CONNECT` → `ready` |
| clone from branch B | insert row → if B has sessions: `fail`, or terminate them and retry `CREATE DATABASE … TEMPLATE B STRATEGY FILE_COPY ALLOW_CONNECTIONS false` (bounded; report that open transactions were aborted) → create login → ACLs → reassign B's login stragglers → grant `CONNECT` → `ready` |
| snapshot of branch B as NAME (1–100 characters, no `@`, whitespace or control characters) | bump `snapshot_names.last_version` → insert snapshot row → clone B (same busy policy) → reassign stragglers → `ALLOW_CONNECTIONS false` → `ready`. Snapshots are not templates, so only the admin can clone them. |
| clone from snapshot S | as clone from a branch; S never has sessions |
| reset branch to source | row `op=reset, op_phase=staging, replacement_db, backup_db` → clone the source into the replacement (closed) and normalize → `op_phase=cutover`: close both databases to new connections and terminate sessions → in one transaction on the lock session: rename original → backup, replacement → original, set `op_phase=cleanup`, bump `generation`, record the reset's CoW capability (`require_cow` is checked before staging) → allow connections, grant `CONNECT` → drop the backup → clear `op`. The login and URL are unchanged. |
| drop branch | mark `deleting` → `DROP DATABASE … WITH (FORCE)` → `DROP ROLE` login; if dependencies remain, set it `NOLOGIN PASSWORD NULL`, record it in `retired_roles`, and retry in `reconcile` → delete row |

Recovery: the next mutation of the project (or `devflow db reconcile`) finishes or rolls back rows in `creating`/`deleting` or with an `op`, by inspecting `pg_database` and `pg_roles`. Resets: `staging` → drop the replacement; `cutover` not committed (names unchanged) → reopen the original and drop the replacement; `cleanup` → drop the backup. The rename transaction makes any other combination impossible; if one is found, devflow leaves it alone and reports a diagnostic. Prepared transactions or replication slots that block `DROP DATABASE … FORCE` are reported, not forced. `devflow db reconcile` prints the actions it took, then the problems that need an operator (JSON: `actions` and `problems`); other mutations report both as warnings.

Credentials: a branch's plaintext password is stored in the worktree receipt and `.devflow/env` (both `0600`). It is also shown by `devflow db url` and `db branch create` (human and JSON output) and is in the environment of hook commands (`DATABASE_URL`, `PGPASSWORD`) and of the `psql` that `db psql` starts. The superuser password is in `admin.json` and `compose.yaml` (both `0600`). Everything else devflow prints is redacted. If a setup crashes after creating a branch but before saving the receipt, the retry finds the branch by its instance id (`branch_for_instance`) and sets a new password; the old one was never delivered. `db branch create --instance-id ID` makes launcher retries reuse a branch the same way, which invalidates any URL handed out earlier.

Trusted extensions need database `CREATE` (held by the owner). For an untrusted extension, no devflow command opens an admin session: an operator connects with the admin credentials (`admin.json` for a managed server, the configured `admin_url` for an external one), installs it in a seed branch, and others clone that.

### Remote data hosts

The data host is a machine that stays up and runs PostgreSQL 18 on a reflink-capable filesystem (a managed container on a Linux host with btrfs/XFS, or any external server). Code runs elsewhere: laptops, local VM forks such as Cove, cloud sandboxes.

- A trusted machine (laptop or launcher) holds the admin URL and provisions: `devflow db branch create --data-from snapshot:seed --json` returns the branch id and its application URL.
- A sandbox receives only the branch URL (`devflow setup --database-url URL` records it without provisioning) or, if trusted, the admin URL itself. URL-only attachments are never dropped by `remove`; only the creating instance drops a branch.
- Management and application endpoints are separate settings (`admin_url`, `app_host`); Docker-over-SSH only reaches the Docker API, so the PostgreSQL port must be reachable on a private network (e.g. Tailscale) with TLS where it crosses machines.
- A provisioning API (`devflow serve`) is deferred until untrusted sandboxes must create branches themselves.

## Hooks and trust

Hooks are plain shell commands run with `sh -c` in the worktree, in order, each in its own process group (on timeout it gets SIGTERM, then SIGKILL after 5 s). They inherit the caller's environment minus Git's hook context (`GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_PREFIX`, `GIT_COMMON_DIR`, `GIT_OBJECT_DIRECTORY`), plus the variables of `.devflow/env`: `DATABASE_URL`, `PG*`, `DEVFLOW_PROJECT`, `DEVFLOW_PROJECT_ROOT`, `DEVFLOW_WORKSPACE`, `DEVFLOW_WORKSPACE_PATH`, `DEVFLOW_SOURCE_PATH` (absent for the default workspace) and `DEVFLOW_WORKSPACE_ID` (the receipt's instance id, informational). Hook processes also get `DEVFLOW_PHASE` (`setup`, `switch` or `teardown`) and `DEVFLOW_SETUP_ACTIVE=1`; these two are not written to `.devflow/env`. Output goes to the log file (`0600`) and to stderr with known credentials masked. There is no templating; use the environment. Connection URLs are parsed the way libpq parses them (`conn.rs`): the generated `PG*` variables express exactly the `DATABASE_URL` connection, inherited connection variables are cleared, and options libpq cannot express in the environment or that would redirect the connection (`sslpassword`, multiple hosts, `replication`, `ssl`/`requiressl`, `service=`) are rejected. `devflow db psql` passes every connection parameter, including the password, through the child's environment only, never argv.

Trust is the SHA-256 of the JSON serialization of the merged `[hooks]` section (after merging the local file; all three phases and `timeout`), stored per project and main checkout in `trust.toml`. `devflow trust` shows every command and asks for approval on a terminal; `--yes` approves without asking, and a non-interactive run without `--yes` shows the commands and approves nothing. `--revoke` withdraws the approval. A changed section needs re-approval. When an operation needs untrusted hooks, a person at a terminal chooses Trust and run, Run once or Skip; everyone else skips them and gets `needs_attention`. `DEVFLOW_TRUST_HOOKS=1` (or `true`) trusts for one run (CI, agents). Trust does not cover scripts the commands invoke.

## Processes and proxy

devflow does not supervise processes. Projects declare daemons in `pitchfork.toml`; pitchfork discovers worktrees and namespaces them. Daemons read the database URL from `.devflow/env` (via mise `[env] _.file = ".devflow/env"` or the app's own dotenv loading). The GUI lists the pitchfork daemons of the selected workspace (`pitchfork list --project --json`, run in the workspace directory; it keeps daemons whose reported directory is inside the workspace and those that report none) and can start/stop them.

## CLI

Global options: `--json`, `--non-interactive` (env `DEVFLOW_NON_INTERACTIVE`; accepts 1/0, true/false, yes/no, on/off) and `-C DIR` (run as if started in `DIR`). A command is interactive when neither `--json` nor `--non-interactive` is given and both stdin and stderr are terminals; only then does devflow prompt (hook trust, forced removal).

All inspection and mutation commands accept `--json` and print one versioned document on stdout: `{"version": 1, "command": "…", …}`, plus `warnings` when there are any. `db psql`, `shell-init`, `completions` and `gui` do not support it and fail if it is given. Under `--json` a failure is one document `{"version", "command", "error", "hint"?}` on stdout, with the human message on stderr. Exit codes: 0 success or `ready`; 2 `needs_attention` or `in_progress` from `switch` and `setup`; 1 every other failure, including usage errors and a failed `doctor` check.

Passwords are redacted everywhere except `devflow db url`, `devflow db branch create` and the generated env file. Redaction guards against accidental disclosure and is not a secret scanner (see SECURITY.md): every credential devflow knows (generated branch and admin passwords, the password of an attached `--database-url`) is masked by exact match in hook output and logs, and other credentials are masked by pattern on a best-effort basis.

```
devflow init [--name NAME] [--postgres managed|external] [--hook]
devflow switch [-c] NAME [--from WS] [--data-from SRC] [--no-db] [--no-hooks]
devflow list [--all]
devflow path NAME
devflow setup [--if-new] [--new-instance] [--database-url URL | --data-from SRC]
devflow remove NAME [--force] [--keep-data] [--delete-branch]
devflow trust [--revoke | -y|--yes]
devflow hook install|uninstall
devflow db status|up|down|url [WS]|psql [WS]|reset [WS] [--to SRC]|reconcile
devflow db snapshot create NAME [--from WS] | list | delete NAME@vN
devflow db branch list | create [--name NAME] [--data-from SRC] [--instance-id UUID] | delete ID
devflow doctor
devflow shell-init [zsh|bash|fish]
devflow completions SHELL
devflow gui
```

`SRC` is a workspace name, `snapshot:NAME[@vN]`, `branch:ID` or `empty` (`--data-from` and `db reset --to` accept all of them). `switch --from` needs `-c`, and `setup --database-url` cannot be combined with `--data-from`. `list --all` lists every registered project. `shell-init` detects the shell from `$SHELL` when none is given. `switch` prints the workspace path on stdout, or, behind the `shell-init` wrapper (`DEVFLOW_CD_FILE`), asks the wrapper to change the shell's directory.

## Desktop app (`devflow-gui`)

GPUI with `gpui-kit = "=0.7.1"` (pinned; lockfile committed). macOS 15+ first; Linux needs Wayland/X11 with Vulkan and is validated before it is advertised.

Layers: `devflow-core` (operations) → `state` (GPUI entities holding project/workspace models, request ids, in-flight tasks) → small views. Blocking core calls run with `cx.background_spawn`; results are applied only if their request id still matches the selected project, so a stale response never updates another project.

Screens:

- **Sidebar** — registered projects, add project (folder picker), settings.
- **Header** — project name and path, a Refresh button, and badges: server (`running`, `stopped`, `unreachable`, `not configured`), CoW capability with how it was established, and `hooks not trusted`.
- **Workspaces** — table: name, branch, status, database, path; actions: open in editor, open in terminal, copy path, rerun setup, remove. Create dialog: name, code from, and, only when `[postgres]` is configured, data from (workspace / snapshot / empty). Remove asks for confirmation (keep the database branch, also delete the Git branch) and applies the CLI's protections; when core refuses with a protection that `--force` would override, the failure notice offers a forced removal. An activity panel shows the phases and hook output of the running or last operation.
- **Trust dialog** — before an operation that would run untrusted hooks, lists every command of every phase and offers Skip, Run once or Trust and run.
- **Initialize** — a project without `devflow.toml` shows an "Initialize…" button; its dialog (optionally enabling the managed PostgreSQL section) creates the file as `devflow init` does.
- **Database** — server status and CoW capability, start/stop, branches (marking those "unattached locally" when no local worktree is bound), snapshots (create from workspace, delete after a confirmation), reset a workspace.
- **Daemons** — pitchfork daemons of the selected workspace with start/stop, when pitchfork is installed.
- **Config** — `devflow.toml` in a TOML editor with validation and concurrent-edit detection.
- **Logs** — the selected workspace's setup logs, read-only.
- **Settings** — editor command, terminal command (the workspace path is appended unless the command contains `{path}`) and theme (light, dark, system), saved in `gui.toml`.

No embedded terminal or tray in 1.0.

## Migration from 0.x

Clean break. devflow 1.0 detects 0.x configuration and stops with instructions; it never adopts or deletes 0.x containers, volumes or data directories. The migration guide covers exporting a 0.x database (`pg_dump`), importing it into a 1.0 branch, creating a snapshot, and removing 0.x resources with devflow 0.8. v1 resources use new names (`devflow-<name>-<id8>` compose projects, `df_` databases, `dfl_`/`dfo_` roles).

## Release gates

The database gates are Docker tests (`db_postgres.rs`, ignored by default; commands in `CLAUDE.md`). CI runs them on ext4, where CoW is `copy`.

- CoW (manual, per environment): `verified` on OrbStack and Linux btrfs/XFS; `copy` on ext4 and Docker Desktop. The Docker tests assert `verified` only when `DEVFLOW_EXPECT_COW=verified` is set, which CI never does. `require_cow` refusal is an automated Docker test.
- Concurrent clone tests (two clients, same project) and busy-source behavior for both policies.
- Branch isolation: a branch role cannot connect to sibling branches or snapshots of the same or other projects, including during creation, snapshotting and reset; an unrelated `CREATEDB` role cannot clone a snapshot.
- Privilege matrix with a non-superuser provisioner: create, clone, snapshot, reset, drop; payload with default privileges, RLS policies, sequences, a trusted extension and post-`RESET ROLE` objects.
- Crash recovery: interrupting each phase (including credential delivery, snapshot sealing, reset renames and role cleanup) and re-running `setup` / `db reconcile` converges without touching unrelated resources.
- Fork and attach: copied receipt with `--new-instance` and URL-only attachment are tested; `remove --keep-data` with the server unreachable is a manual check, no test covers it.
- Remove protections (default, current, dirty, locked) and teardown blocking.
- GUI (headless `gpui-kit` tests on macOS): creating a workspace and removing one (refused, then forced) run end to end against a scratch repository without `[postgres]`. The reset and snapshot dialogs only render, and deleting a snapshot is tested only as far as asking first. No GUI test touches a database server, so the database actions are checked by hand on macOS; Linux rendering is checked before Linux is advertised.
