# devflow 1.0, developer-experience round

Status: design, final after three review rounds (open disagreement recorded at the end). Builds on the 1.0 design in [2026-10-10-devflow-1.0.md](2026-10-10-devflow-1.0.md); 1.0 is not released, so the schema and receipts may still change (with a migration for existing receipts).

## Why

Feedback on the first 1.0 build: correct but "too simple". Hooks are hard to set up (especially in the GUI), pitchfork is not proposed or installed, databases are only reachable through an ephemeral port, only PostgreSQL branches copy-on-write, and the GUI is plain (dark/light needs a trip to Settings).

Goal, in the user's words: the best dev tool to create and manage worktrees that spawn fast, take no space on disk, and whose hooks handle everything; almost transparent once set up; easy to set up by a human or an LLM; clear.

The coherent first result (review round 1): a workspace that starts predictably, connects to its own data, explains failures and resumes safely. Engine breadth follows that contract.

## Research summary (2026-10-10, measured on this machine unless stated)

- **Reflink clones of Docker volumes work on OrbStack** (btrfs in the VM): a 259 MB MySQL datadir cloned in 15 ms for +192 kB; `filefrag` shows shared extents. Clones must run inside the VM (helper container with `/var/lib/docker/volumes` mounted, GNU `cp -a --reflink=always`); `--reflink=auto` silently copies on ext4 and must not be used. btrfs and XFS (`reflink=1`) work on Linux; ext4 does not; Docker Desktop untested (expected ext4: full copies).
- **Quiescing a running source**: `docker pause` → clone → unpause blocks the source 50–150 ms and gives a crash-consistent image for InnoDB (MySQL), WiredTiger (journaled writes), ClickHouse and Redis with AOF. Redis/Valkey with RDB: completed `BGSAVE`, then clone `dump.rdb` (no pause; pausing an RDB-only Redis gave an empty clone).
- **Identity after clone**: MySQL keeps the source's accounts, passwords and `server_uuid` (delete `auto.cnf`; rotate with `ALTER USER`/`--init-file`); Redis `--requirepass` is per container.
- **Memory per idle branch container**: Redis/Valkey ~7–50 MiB; MySQL 115–210 MiB (tuned).
- **No database proxy to reuse**: pitchfork proxies HTTP only; Postgres can be routed by SNI only with TLS, MySQL not by hostname at all, Redis only with TLS. OrbStack names (`dev.orbstack.domains`, wildcards) work container-to-container; **host → container traffic fails here while NordVPN (full tunnel) is connected**, published 127.0.0.1 ports keep working.
- **pitchfork 2.30.1** (local 2.29.0): `pitchfork.toml` daemons; `port = { expect = [N], bump = true }` injects `PORT`; proxy disabled by default (enable: supervisor restart, `proxy setup` with sudo) → `<daemon>.<worktree>.<project>.localhost`; `proxy status --json` lists URLs per worktree dir; `config add FILE --dir --namespace --label` attaches a generated config; `start --local`/`stop --local` act on one worktree. The default namespace (worktree directory name) collides across repos (verified); `start` can hang. Today's adapter has a false positive (mise shim without a version) and a dead `dir` filter.
- **Detection**: lockfile → idempotent install (`npm ci` deletes cloned `node_modules`; venvs are not relocatable); migrations per framework; compose services; dev processes and their `PORT` convention. Pitfalls: a copied `.env` keeps pointing at the main database unless `.devflow/env` is loaded into the process; `NOCREATEDB` breaks test-database creation; frameworks read different variables.
- **GUI** (gpui-component 0.7.1): `TitleBar`, nested `Sidebar` menus, `Command` palette, `Stepper`, `DescriptionList`, `Clipboard`, `Notification` with actions, `Empty`, `Theme::change` + system appearance, 1,830 Lucide icons (add the needed ones with `icon_assets!`).

## Decisions

### D1. One service schema, distinct backends

```toml
[services.db]
engine = "postgres"          # postgres | valkey | redis | mysql   (first release)
# postgres keeps today's keys (mode, image, admin_url, port, require_cow, …)

[services.cache]
engine = "valkey"            # default image per engine; pinned per branch by digest
```

- Unified now, while unreleased. At most one `postgres` service; it keeps the shared-server backend (roles, metadata database, snapshots, reset, external mode). `devflow db …` addresses the sole Postgres service whatever its key.
- Container engines (`valkey`, `redis`, `mysql`; MariaDB after its own gates; MongoDB, ClickHouse and SQLite CoW deferred) are managed only, single-controller (one machine controls a Docker daemon).
- Schema detection: 0.x files are recognized by shape (`[[services]]` arrays, `processes`, `agent`, …), not by key names that 1.0 now uses; mixed or ambiguous shapes are rejected; unknown fields stay errors. Fixtures cover old, new and malformed shapes.
- Receipts move to version 2, migrated in place under the receipt lock with no provisioning effect, preserving every field: identities, pinned sources, ownership and attachment flags, phase states with their details, failures and deliberate skips (`database` phase → `services`). `data` maps to the sole Postgres service's key; if the configuration has no single Postgres service, the binding is kept as `unmapped` and reported, never guessed.
- The receipt records the applied configuration generation of each service and of the env recipes. A service added or changed after a workspace was set up reopens `services` (that service), `env` and `hooks` (at-least-once, as always), and the workspace is `needs_attention` until `devflow setup` or the next `switch` completes them; deliberate skips (`--no-db`, `--no-hooks`) are kept.
- Each service exports typed connection fields; default variables per engine: Postgres `DATABASE_URL` + `PG*`, MySQL `DATABASE_URL` (or `MYSQL_URL` when a Postgres service exists), Valkey/Redis `REDIS_URL`. Collisions are a config error naming both services.
- Receipt: `services: { key → binding }`; the `database` phase becomes `services`, each service recorded separately so retries resume. Per-service source pinning: a missing source fails that service (never substitutes an empty one).
- Removing or renaming a service in TOML never deletes its data: `devflow service list --orphans` and `reconcile` report it; `devflow service forget NAME` drops it explicitly.
- Multi-service snapshots are per service and independently consistent (stated in output); no cross-service atomicity.

### D2. Container engines, safely

Authority: a versioned, atomically written catalog per project in the data dir (`services/<project id>.json`, lock file), bound to the Docker daemon identity (`docker info` ID), service key and engine, branch/instance identity, image digest and volume identity. Labels corroborate records; ownership comes from the catalog.

Engine profiles: devflow generates each container's configuration, so it controls persistence. A profile = engine, version range, storage configuration, quiesce method, identity fixups, health check, consistency statement. Unsupported configurations are refused.

- **Valkey/Redis** (first): AOF off, RDB on, `requirepass` per container (ACL files refused). Quiesce = `BGSAVE` without pausing; completion is a capability-gated check of `INFO persistence` (`rdb_bgsave_in_progress:0`, `rdb_last_bgsave_status:ok`, save counter `rdb_saves` advanced, unchanged `run_id`), not `LASTSAVE`. The completed `dump.rdb` is reflinked (it is replaced by rename, so a clone always sees a whole file). Consistency: point-in-time at the `BGSAVE` fork, which is the reported capture time.
- **MySQL 8.4, standalone InnoDB** (second, behind its own release gate): devflow-generated `my.cnf`, no replication, single data dir. Quiesce = clean shutdown of the source (`stop` → clone → `start`; the source is unavailable for a few seconds, reported). `docker pause` is a process suspension, not a storage barrier, so a pause profile ships only after recovery and invariant tests under concurrent writes and DDL. Other versions only with the same gates.

Clone protocol, run by one operation-scoped **coordinator** (`devflow __clone`, its own process group) that the CLI or GUI starts and waits for:

1. The caller journals the operation (ids, destination names, port, credentials to set, the copy fallback decision) **before** anything exists, then starts the coordinator and waits for its handshake; the coordinator takes the source lock itself and holds it until the end, so no other clone or reset can start while it runs, even if the caller dies.
2. The coordinator records the source's identity and prior state (`running`/`stopped`); a source not in a state it can restore is refused.
3. It journals `quiescing`, quiesces (Valkey: `BGSAVE`; MySQL: clean stop), journals `quiesced`.
4. It clones inside the VM: `cp -a --reflink=always` in a warm helper container under a deadline. On timeout it kills the copier, confirms it has exited, marks the destination `aborted` (never promoted), and restores the source. `--reflink=auto` is never used; whether a full copy is allowed was decided in step 1.
5. It restores the source to its prior state (always, also on error) and journals `restored`.
6. If the coordinator itself dies, its host lock is released while a copier may survive in the VM. So every later operation on that source or destination (clone, reset, start, stop, remove) first reconciles unfinished journal entries under the same lock: it kills the recorded helper container, confirms it is gone, aborts the destination and restores the source, before treating the source as available. MySQL's clean stop is verified positively (exit code 0 and InnoDB's shutdown-complete message); a `docker stop` that ended in `SIGKILL` aborts the clone.
7. Bootstrap, isolated: the clone starts with `--network none`; administration goes through the container's local socket; identity fixups happen before it ever listens on a network (MySQL: `auto.cnf` removed before first start, new passwords for root and the app account, inherited extra accounts refused; Valkey: new `requirepass`). It is stopped gracefully and recreated with its final endpoint (per D3), then an authenticated health check runs on that endpoint. Each step is journaled; credentials are journaled before use.
8. The image digest is pinned from the source or snapshot record **before** the clone boots; the clone records its storage profile, clone method (`reflink`/`copy`), capture time and the guest `df` delta.

Snapshot = immutable cloned volume (no container). Reset = staged replacement volume, recovered and health-checked, then a journaled cutover; the original is kept until the replacement is validated. `reconcile` completes or rolls back every journaled step (unpause, half-created volumes, staged replacements).

As built for MySQL (milestone 6, a preview until its review closes), where the text above left a choice:

- **Schema.** `engine = "mysql"` with `image` (`mysql:8.4`), `database` (default: the project name as an identifier `^[a-z][a-z0-9_]{0,47}$`, never one of the server's own schemas), `env` and `require_cow`. The URL is `DATABASE_URL`, or `MYSQL_URL` beside a postgres service; `MYSQL_HOST`, `MYSQL_PORT`, `MYSQL_USER`, `MYSQL_PASSWORD` and `MYSQL_DATABASE` are exported next to it and join the names recipes may read and cannot set. **At most one mysql service**: the typed fields carry no prefix, and a prefix scheme (derived from the key) can lift the limit later without changing the one-service case.
- **Accounts.** `root@localhost` (no `root@%`: root is unreachable from the published port) and `app@%` with all privileges on the one database; both passwords are generated per branch and live in the 0600 catalog. The database and account names are part of the data, so a branch records them and clones inherit their source's; a reset keeps the branch's URL and therefore refuses data with another database.
- **Health is two checks**, because devflow has no MySQL client: an authenticated `SELECT 1` as `app` through `docker exec` on the container's own loopback (it proves the account and the listener), then the MySQL greeting read from the published `127.0.0.1` port (it proves the endpoint reaches a MySQL server). A native client would need `caching_sha2_password`'s RSA exchange or TLS for the first login; the in-container client avoids both.
- **Passwords on standard input.** `docker exec -i` carries them as SQL (`ALTER USER … IDENTIFIED BY`) or as the first input line of a `bash` wrapper that puts it in the `mysql` client's own `MYSQL_PWD`; none is on a command line, in `docker exec`'s environment or in `docker inspect` (SECURITY.md says what remains: the client's environment inside the container for the length of one query).
- **The stop is proven by the log.** The profile sets `log_error_verbosity=3` so that InnoDB's `Shutdown completed; log sequence number …` note is written; a stop is clean when the container exited with 0 and the log since its last start (`docker logs --since StartedAt`) has that note and the server's `Shutdown complete (mysqld …)`. A source already found stopped must pass the same check or the clone is refused; the instant of the data is the container's `FinishedAt`. The stop timeout is 5 minutes (`DEVFLOW_TEST_STOP_TIMEOUT_SECS` shortens it in tests, 0 included, and is journaled with the operation).
- **Journal.** `Restoring` (the stopped source is being started and checked) joins the sequences between `Copied` and `Starting`/`Done`; engines whose source keeps serving skip it. The source's downtime runs from just before `docker stop` to its first authenticated answer after the restart, and is recorded on the operation, the branch or snapshot and the receipt's clone report. Recovery never completes a MySQL clone or snapshot (their bootstrap is journaled but not resumable): any unfinished one is rolled back, which starts a source it had stopped (`source_running` is recorded before the stop), kills the helper, removes the bootstrap container and the destination. A rollback is journaled (`RollingBack`) before it removes anything and is resumable.
- **Identity.** The copy drops `auto.cnf` and the TLS and RSA key pairs of a data directory that becomes a branch (not of a snapshot, which is a plain copy). A bootstrap container (`--network none`, `--skip-networking`, `--skip-grant-tables`) runs the image's `mysqld` through `bash` and `gosu`, bypassing the entrypoint (which wants a root password option and would create `root@%`), initializes an empty volume with `--initialize-insecure` for a root, checks the version and audits `mysql.user`, sets both passwords and proves both logins through the socket, and is stopped cleanly and removed before the container with the published port is created.
- **Profile delivery.** The generated `my.cnf` is written once to `<data dir>/services/mysql-profile-v1.cnf` (no secret in it) and bind-mounted read-only with `--mount`, which fails on a missing source instead of creating a directory. A Docker daemon that cannot mount that path (a remote one) cannot run the engine.
- **What is not done.** No time zone tables, no `initdb.d`, no MariaDB, no pause profile, no more than one mysql service, and `init` does not propose a mysql service from a compose file yet.

### D3. Endpoints (the "database proxy" question)

- No generic TCP proxy: protocols cannot be routed by hostname without TLS (MySQL not at all), and a listener daemon adds lifecycle and failure modes. Limitation, stated: connecting cannot wake a stopped database; startup happens on workspace activation (`switch`, `setup`) or `devflow up`.
- **First release: loopback endpoints everywhere.** Each managed endpoint (the shared Postgres server: one port; each container-engine branch: one port) is published on 127.0.0.1 at a port allocated once from `hash(project, service, branch)`, persisted in the catalog, with Docker's bind deciding success; a retained port that became unavailable is reported, never silently changed. This works on every Docker host and with full-tunnel VPNs (measured here).
- On OrbStack, every container also gets identity-suffixed names (`<service>.<project>-<project8>.devflow.orb.local`, per branch `<branch8>.<service>.<project>-<project8>.devflow.orb.local`) used as the **container endpoint** (for apps running in containers on the same Docker networks; the docs say which network to attach). The GUI shows host and container endpoints.
- An OrbStack-only mode (no published ports, honoring the user's preference) comes later together with an explicit, resumable `devflow endpoints switch` operation: each binding records its applied endpoint generation; switching updates containers, receipts, env files and pitchfork configuration, states the shared-Postgres interruption and which processes must restart, and never happens automatically. Until then, the loopback publication is documented as the deliberate trade-off (unreachable from the network; robust under VPNs).

### D4. pitchfork, trusted

- Detect by running `pitchfork --version` and checking for the features used (`config add --label`, `proxy status --json`), not a version number alone. Install (`mise use -g pitchfork`), proxy enablement, supervisor restart and `pitchfork proxy setup` (sudo) are separate, explicit offers in onboarding, `doctor` and the GUI.
- `pitchfork.toml` (committed) defines daemons; `devflow init` generates it from detection.
- **Trust, versioned.** Approval scope v2 = `[hooks]` + `[env]` recipes + the effective pitchfork configuration of the worktree (every daemon's command, `dir`, `env`, hooks, `cron`, `watch`, `boot_start`, `auto`). A v1 approval (hooks only) never authorizes v2 content; the "nothing to approve" shortcut considers the whole v2 scope. Digests never include generated passwords.
- **No global registration, no secrets in pitchfork.** devflow writes a machine-local `pitchfork.local.toml` into each worktree (excluded through the repository's `info/exclude`) that sets only a unique `namespace` (`df-<project8>-<instance8>`) and `worktree_label`; a conflicting `namespace` in the committed `pitchfork.toml` is reported during onboarding (pitchfork errors on disagreeing sibling declarations). Daemons receive `.devflow/env` through `devflow exec` in their `run` (applied after mise, `mise = true` for the toolchain; or through mise's `[env] _.file` alone, which anything applied later wins over), never through pitchfork `[env]`, because pitchfork persists daemon environments in its state file without restricting permissions. Without mise, devflow does not inject the environment and says so.
- **Autostart only for plain daemons.** A pitchfork supervisor started in the repository discovers every linked worktree on its own, and its `cron`, `watch`, `boot_start` and `auto` triggers then run without devflow. So devflow autostarts daemons only when no daemon in the effective configuration uses an autonomous trigger; otherwise it offers manual control and explains why. Daemons start only for a `ready` workspace whose effective configuration matches the approved digest, on `setup`/`switch` when `[pitchfork] autostart` (chosen during onboarding, persisted in `devflow.toml`) is on, or on request.
- **Digest-gated stop.** pitchfork runs lifecycle hooks (`on_stop`, …) from the current configuration, so devflow calls `pitchfork stop` only when the configuration still matches the approval; otherwise it reports the change, marks processes `needs approval`, and `remove` refuses until the user stops the daemons or passes `--force`.
- Residual risk, documented: running pitchfork directly (its CLI, shell hook or a supervisor started in the repository) acts on whatever the worktree's configuration says; that is pitchfork's own behavior, outside devflow's approval guarantee.
- `start` runs with a devflow timeout; afterwards devflow reads the actual state (`list --json`) instead of assuming startup stopped. Process state is reported separately from workspace readiness. `remove` stops the namespace's daemons before deleting the worktree.

As built (milestone 3), where the text above left a choice:

- **Detection** is `pitchfork --version` exiting 0 (a mise shim without a configured version is executable and exits 1) plus a check that the `--help` of `list` and `proxy status` mentions `--json`, and that the version is 2.0 or later (the first with `namespace/name` daemon ids, which is how `start` and `stop` are called; their help text does not say so); the version and the missing features are reported. Operations and gates use this full detection, remembered in-process for ten seconds, not the version alone. `list --json` carries no directory, so a workspace's daemons are those of its namespace, and URLs come from `proxy status --json` matched by the worktree directory (`projects[].dir`, compared canonically). Queries run with `PITCHFORK_SUPERVISOR_AUTO_START=false`: asking never starts a supervisor; only a start does, as pitchfork itself does.
- **Offers.** `devflow pitchfork install` runs `mise use -g pitchfork@latest` only after a terminal confirmation or `--yes` and prints brew/cargo instructions without mise. `devflow pitchfork proxy` and `doctor` print `pitchfork settings set proxy.enable true --global`, a supervisor restart, `pitchfork proxy setup --dry-run`/`proxy setup` (sudo) and `proxy doctor`; devflow never runs them.
- **Namespace file.** Written by the env phase (not by `start`; a start repairs a workspace set up earlier), recognised as devflow's by its marker comment and exact content, so a hand-written `pitchfork.local.toml` or one a person edited is never touched. Only the `namespace` and `worktree_label` equal to the values devflow generated for that workspace (the receipt's `COMPOSE_PROJECT_NAME` and the directory name) are left out of the trust scope, so writing the file never changes the digest; any other value of either key, in any file, counts (see the pitchfork review below).
- **Gating.** `check_start` order: unreadable pitchfork file, nothing configured, workspace readiness (a receipt, not locked, `ready`), the namespace of the files equals the assigned one, approval of that worktree's scope, every `depends` of the daemons about to start is a daemon of the workspace's own files, autonomous triggers among the daemons about to start (named daemons and their `depends`, or all). `DEVFLOW_TRUST_HOOKS=1` approves, as for hooks. A `NothingToApprove` scope (no hook, `[env]` or pitchfork file) cannot reach a start because there is nothing configured. A start is skipped when every wanted daemon already runs. The mise delivery check slot is marked in `processes::pre_start_checks`.
- **Stop** names the ids of the workspace's running daemons (never `--local`, see the pitchfork review below). `remove` plans the stop among its protections (before any effect) and runs it before teardown; a failed stop, one that leaves daemons running, or one whose result cannot be read blocks removal unless `--force`.
- **Pitchfork review (implementation review of the process integration).** Decisions that replace what the bullets above first said:
  - *Explicit ids, never `--local`.* pitchfork's `--local` selects the non-global daemons of every configuration file from the working directory up to the root (`get_local_configured_daemons`, `ipc/batch.rs`), so from `child/` with configurations in `parent/` and `parent/child/` it started and stopped both (reproduced against 2.25.0 and 2.29.0 with an isolated supervisor). devflow starts and stops full `namespace/name` ids of the workspace's own daemons. Both versions, and the sources of 2.0.0, 2.14.0 and 2.30.1, accept a qualified id as given (an id with a `/` is parsed, not looked up), so the feature is "pitchfork 2.0 or later" (`namespace` in daemon ids is the 2.0.0 breaking change). A started daemon's `depends` are started by pitchfork, also across namespaces (reproduced): every dependency must be a daemon of the workspace's own files, a plain name or its own namespace, or the start is refused.
  - *The namespace comes from the receipt.* The expected namespace is `df-<project8>-<instance8>`. Before a daemon is attributed to a workspace, started or stopped, the namespace the files give must equal it, or the operation is refused (`foreign_namespace`, never overridden by `--force`; a forced removal leaves the daemons running). A start first restores devflow's own file when it is missing or stale. The trust scope leaves out only the generated `namespace` and `worktree_label`; any other value counts in the digest, so pointing a file at another namespace also drops the approval.
  - *The last look.* The slow queries come first; immediately before each effect the scope is read again and readiness, namespace and approval are judged on it (a start also compares the content digest with the first look). `remove` revalidates in `stop_for_removal`. Residual risk, stated in SECURITY.md: pitchfork reads its files itself, after the last look.
  - *Unknown is not nothing.* A listing that fails is `state_unknown` (forceable); removal needs a stop report with verified state; `restart` returns the stop's report when it is not ok.
  - *Settings across layers.* Whether a daemon runs through mise follows pitchfork's own resolution (verified in 2.29.0): a daemon defined in several files is replaced whole by the highest layer's definition, and `[settings.general] mise` is merged over all the project's files (`pitchfork.local.toml` first, then `pitchfork.toml`, `.config/pitchfork.local.toml`, `.config/pitchfork.toml`, after `PITCHFORK_MISE`), with the daemon's own value winning. Settings outside the project directory are not visible to devflow.
  - *One bounded runner.* Endpoint discovery for the managed PostgreSQL server (`docker compose port`) runs under what is left of the readiness deadline, through the same runner as pitchfork's queries (`subprocess::run`), which kills and reaps the command and what it started.
- **Pitchfork review, round 2.** Seven more decisions, none of which changes the model above:
  - *"Wrapped" means wholly one `devflow exec`.* A daemon's `run` counts as delivering `.devflow/env` itself only when it is one simple command, `devflow exec [opts] -- PROGRAM ARGS` (behind `NAME=value` and `exec`, redirections allowed), with no `;`, `&&`, `||`, `|`, `&`, newline, backtick, `$(` or parenthesis outside quotes, and PROGRAM reaches no mise (the scanner of `env_file::commands`, plus any word named `mise`). `devflow exec -- true; npm run dev` starts the app outside the wrapper, and `devflow exec -- mise exec -- npm run dev` gives it mise's values, applied after devflow's; both used to skip the delivery probe. The hook gate applies the same rule inside mise: a `mise exec -- devflow exec -- mise exec -- CMD` is an unprotected use of mise.
  - *The last look reloads devflow's own configuration.* The `Project` a caller holds is a snapshot; readiness (the receipt against the configuration's generations), the scope and the approval are judged on `devflow.toml` as it is at the last look of a start, a stop and a removal's stop. A configuration that cannot be read then is `unreadable` (forceable for a stop).
  - *A pitchfork on `PATH` that cannot be asked is unknown at removal.* A failed `--version` (a mise shim without a version) used to read as "nothing running". With pitchfork files and a namespace, it is now the forceable `state_unknown`; with no pitchfork on `PATH` at all, or no pitchfork file, or no receipt, removal proceeds. Recorded disagreement with the review's strict reading ("only a workspace with no pitchfork configuration may proceed silently"): a committed `pitchfork.toml` must not make everyone without pitchfork pass `--force`, which also overrides the dirty and unmerged protections.
  - *Results are verified against the namespace acted in.* A start or stop captures the receipt's namespace and verifies the raw `list --json` against it; daemons of that namespace are all in the report, so one still running makes a stop not ok, and an attribution that changed in between (`status_from` filters through the files as they are afterwards) is a not-ok report. Without this a file pointed at another namespace during `pitchfork stop` made the running daemon vanish from the view and authorized removal.
  - *Only the highest definition's dependencies count.* pitchfork replaces a daemon defined in several files whole (2.29.0), so the closure is computed from each daemon's highest-priority definition; every layer stays in the scope. Triggers are still collected from every layer (conservative: it can only refuse autostart).
  - *Dependencies are judged per daemon.* `ps` judges `external_dependency` like `autonomous_triggers`: starting everything stays refused, an independent daemon stays `startable`.
  - *The runner is bounded in output and in what outlives a command.* At most 4 MiB kept per stream (the excess is read and dropped, `truncated` is set, and pitchfork queries, `docker compose` lookups and `docker exec` fail instead of parsing a prefix), one bounded wait for both streams after the command exits, queries end what they left behind (process group, TERM then KILL), `start`, `stop` and `mise use` leave it alone (the supervisor `pitchfork start` launches stays in its process group: read in 2.14.0, `start_in_background`; so the deadline kill of a first `start` ends it too, an existing property worth knowing), readers are joined or detached deterministically.
- **Pitchfork review, final round.** Four decisions:
  - *"Wrapped" is conservative about where mise hides.* After `devflow exec --`, any occurrence of `mise` as a word counts as a use of mise: inside a string for `sh -c`/`bash -c`/`eval` (`devflow exec -- sh -c 'env -u UNUSED mise exec -- bun run dev'`), after a wrapper with options (`env -u X`, `sudo -E`, `timeout 5`, `nice -n`, `nohup`, `xargs`, `command`, `exec`, `time`), in a path ending in `/mise`, however the quotes are spelled; a command word that is a shell expansion is not followed. Anything the scanner does not understand is not wrapped and not protected. The daemon predicate and the hook gate's `through_devflow_exec` share the rule, and a hook that runs such a command after `devflow exec --` is a use of mise the gate checks. Left as a limit: a variable after a wrapper's options (`env -u X $TOOL`), mise started from a script file or from a program's own code.
  - *A supervisor that is down is not "verified nothing runs".* pitchfork's daemons survive their supervisor (reproduced against 2.29.0 with an isolated supervisor: SIGKILL of it leaves `sleep` running, `list --json` fails, a restarted supervisor takes the daemon back, `pitchfork stop` against a dead supervisor fails). The receipt records `processes: {started_at, ids}` under the receipt lock before every start (`start_with`: `up`, autostart, the app, `restart`), and a stop read back with the supervisor up clears it. Supervisor down with a recorded start: `state_unknown` for `down` and `remove` (hint: `pitchfork supervisor start`, then `devflow down`, or `--force`), and a forced removal warns; with no recorded start: a warning that processes started outside devflow cannot be checked. An ignored test kills an isolated real supervisor.
  - *Unknown statuses are not inactive.* For a stop or a removal only `stopped`, `errored`, `failed` and `available` say nothing runs; any other status of a daemon of the workspace, a malformed id, status or pid, and an unreadable entry are `state_unknown`, and a stop whose listing afterwards shows one is not ok.
  - *No pitchfork on `PATH` stays an accepted exception* (a committed `pitchfork.toml` must not force `--force` on everyone without pitchfork), but it is said: the removal result warns when the workspace has devflow's namespace file or a recorded start.
- **Approvals bound to the review (review round 4).** A single operation's approval is a `trust::Approval` (digest and version of what was shown), compared with the scope of the workspace it acts on after the payload exists and before any hook, recipe or process runs; a mismatch is `needs_attention` with its own message. The interactive CLI asks again with the new workspace's scope; the GUI reports it. One-time answers are never stored.
- **GUI.** The model keeps the selected workspace's `ProcessStatus` and the pitchfork detection (cached 30 s); the badge, review dialog, approval and staleness check take the workspace they are about. Buttons are enabled from core's gates (`can_start`, `can_stop`, per-daemon `startable`); an unapproved configuration turns Start into "Review and start…". Autostart also runs after the GUI's create and set up.

### D5. Init: plan, then apply

- Core `detect` (facts: package manager, frameworks, migration tools, compose services, `.env*` key names, dev processes, ignored expensive directories) → core `propose` (items with stable ids, `kind`, `value`, `confidence`, `evidence`, `risks`, `depends_on`, `conflicts`, intended file patch).
- CLI: `devflow init` (interactive: plan, review, apply); `devflow init --plan [--json]` writes nothing and returns proposal version, schema version, input hashes and patches; `devflow init --apply PLAN.json [--accept ID…]` validates the accepted items' dependencies and conflicts before the first write, records each file's intended before and after hashes in an apply journal, and writes. A retry recognizes files already at their "after" hash and continues; any other change refuses. Each file is replaced by staging the new content and atomically exchanging it with the file, then comparing what was displaced with the "before" hash (put back on a mismatch, or kept next to the file as `NAME.devflow-conflict-<timestamp>` when it cannot be), so a save that lands after the last check is never overwritten or lost *where the platform has an atomic exchange* (APFS, Linux filesystems with `RENAME_EXCHANGE`). Elsewhere a narrow window between the last check and the rename remains, and the hard-link backup of the displaced file is kept for the edits it can show. Input hashes cover every mise configuration layer detection discovers (`conf.d`, `config.local.toml`, environment-specific files) and a marker for the set of their paths, so a layer that appears while an apply is interrupted counts as a change; only the files the journaled apply writes are left out. Writing configuration, installing tools, trusting and running are separate steps.
- Existing files are preserved; conflicts are reported (e.g. an existing `mise.toml` without `_.file = ".devflow/env"` is a conflict to resolve, not silently left unwired). Proposals never contain `.env` values or other secrets.
- Detection never runs repository code.

### D6. Hooks and environment

- Hook entries: strings or `{ name, run, timeout }` tables; `sh -c`, trusted by digest, at-least-once, no command templating.
- `[env]` recipes: values may reference devflow-generated variables, one pass (`DIRECT_URL = "${DATABASE_URL}"`); missing references, recursion, invalid names and overriding generated variables are errors; values derived from secrets are classified secret (redacted, 0600). Presets render typed fields (`prisma`: `DIRECT_URL`, `SHADOW_DATABASE_URL`; `laravel`: `DB_*`; `spring`: `SPRING_DATASOURCE_*`; `sqlalchemy`: `postgresql+psycopg://…`). Recipes are part of the trust scope.
- `.devflow/env` exports `COMPOSE_PROJECT_NAME=df-<project8>-<instance8>`; `doctor`/`init` warn about compose `container_name`, named volumes, external resources and fixed ports, which a project name cannot isolate.
- **`devflow exec`: the workspace's variables win by construction** (as built, final review). A command that goes through mise has mise's `[env]` applied over the variables devflow gives it, and no check made at the root of the worktree can say what a command receives: `cd app && mise exec -- …` reads `app/mise.toml`; a task's `[tasks.NAME.env]` is applied after anything set before it; a generated `MISE_ENV` selects other files than the check saw; `conf.d` and `config.<env>.toml` are on no short list of names; `[env] DATABASE_URL = false` removes the variable `mise exec` was given while `mise env` shows nothing. So the variables are applied last. `devflow exec [--workspace NAME] -- CMD` (core `exec`) walks up to the worktree root (the nearest `.git`, never further: a worktree without its own file must not borrow the main checkout's), reads `.devflow/env`, sets it over the inherited environment (dropping inherited libpq selectors as hooks do) and replaces the process (Unix `exec`; env(1)'s 127 and 126 when the program cannot start). It starts nothing without the file, refuses symlinked `.devflow`/`.devflow/env`, prints no value, and reads two things (about 5 ms over starting the program directly, 1.3 ms of it devflow's own work, measured). Everything `init` builds goes through it: hooks `mise exec -- devflow exec -- CMD` (the `cd DIR &&` is safe because devflow applies last), daemons `run = "devflow exec -- CMD"` with `mise = true` for the toolchain. Those items no longer depend on `mise:env-file`; the wiring stays a proposal for shells and editors, on by default when unblocked, and carries a warning only ("shells in the worktree won't see the branch's variables through mise; commands devflow runs are unaffected") when blocked. The exception is a mise *task*, which `devflow exec` cannot wrap from outside (the nested `mise run` applies the task's own `env` again; verified): it keeps depending on the wiring. `mise trust` is not proposed: the worktree is stopped before the first hook, and devflow never trusts anything.
- **mise delivery, checked at run time, for hooks written by hand** (as built, final review; supersedes the `mise env --json` check of implementation review round 2 for hooks). The gate reads the hooks' commands (`env_file::commands`): a hook that runs `devflow exec` inside mise needs no check of the variables; any other hook that runs mise (a command word, also inside `sh -c` and after `devflow exec --`), whatever files exist, is checked with `env_file::check_command_env`: `mise exec -- sh -c …` in the worktree with exactly the environment the hook gets (devflow's variables injected, `MISE_ENV` among them; the inherited environment minus Git's and libpq's; `MISE_AUTO_INSTALL=0`, `--no-deps` and `--fresh-env` where known), reading back the variables the process sees: different is *overridden*, missing is *removed* (`MiseDelivery::Removed`, names only). A hook the check cannot stand for (`cd` ahead of mise, `mise run`/`r`/`tasks run`/`watch`, `-C`/`-E`, `MISE_*` in the command) gets a warning by name or index (never the command) recommending `devflow exec`, and is not blocked. `mise exec` and `mise run` trust a configuration themselves when they have no terminal (observed with mise 2026.10.7: the directory is recorded in `trusted-configs`), so whether mise trusts the worktree is asked first with `mise env`, which refuses and trusts nothing (`check_mise_trust`), for every hook that runs mise, `devflow exec` inside it or not; devflow never trusts anything. Outcomes: delivered runs; overridden, removed, untrusted (`mise trust PATH`), failed, or mise missing for a hook that runs it is a required skip (exit 2); `--skip-mise-check` is the recorded escape hatch. `doctor` runs the same check (`mise-env`, listing the hooks not routed through `devflow exec`; the workspace's mise configuration is found by the detection layer's complete discovery, equal to `mise config ls --json` for every location, checked by a test), says what shells get (`mise-wiring`) and, for an untrusted configuration, prints the choices as text only: `mise trust PATH`, or `mise settings add trusted_config_paths DIR` for the worktree directory with what that trusts. `check_mise_delivery` (`mise env --json`) remains for callers that start daemons with `mise = true`. Values are never returned or logged. `init` keeps the static reading of mise's layered order as an early warning for the wiring item (verified against `mise config ls`; a test compares every adjacent pair with the installed mise).
- GUI: one project-scoped hooks editor (effective commands, local overrides shown), move up/down, presets from detection, "Run in workspace…" (takes the workspace lock, revalidates trust, logs, does not rewrite provisioning phases), inline trust.

### D7. Test and shadow databases

Branch logins keep `NOCREATEDB`. `[services.db] extra_databases = ["test", "shadow"]` gives each branch **scratch databases**: created empty with the same closed-creation protocol and ownership, empty again in every clone, excluded from snapshots, dropped and recreated empty when the primary is reset (as recorded, resumable steps), using the branch's login (rotated with it), and dropped with the branch by recorded identity (kept with `--keep-data`). Removing an extra from the configuration leaves it as a recorded orphan. Exported as `TEST_DATABASE_URL`, `SHADOW_DATABASE_URL`; framework presets point Django `TEST` with `--keepdb`, Prisma `shadowDatabaseUrl` and the Rails test environment at them, so no framework command needs create or drop privileges.

As built (milestone 2b), where the text above left a choice:

- Rows live in a `scratch_databases` table (metadata schema 2), tied to the branch row by a foreign key; names are `df_<project8>_<branch12>_<n>` with `n` from a per-branch counter that is never reused, so an old URL never names another database. The configured label is a column, never part of a name.
- A reset records the ids of the scratch databases it selects (the configured, non-dropping ones) with its journal (`branches.op_scratch`, metadata schema 3), and its recovery empties exactly that set: a label removed from the configuration since is still emptied, and an orphan that was listed again since is left alone, because it was never part of the reset. A journal from before the column existed falls back to the configuration as it is.
- A new branch is `ready` only with its scratch databases (they are built inside the creation, so a failure rolls the branch back whole). A reset empties them in its `cleanup` phase after the swap; each row records the branch generation it was emptied for, which makes the step idempotent for `reconcile`. Orphans are untouched by resets.
- The URLs are devflow-generated variables (`<NAME>_DATABASE_URL`), written even before the scope is approved, like `DATABASE_URL`, and derived from the binding's URL rather than stored: the receipt lists names and databases only. The `prisma` preset therefore adds nothing for `SHADOW_DATABASE_URL`; it is there whenever `shadow` is configured.
- Orphans are reported by `db reconcile` (`orphans`) and `doctor`; the one way to drop them short of dropping the branch is `db reconcile --drop-orphans`. Workspaces attached to a URL get no scratch databases and a warning says so.

### D8. Spawn speed and disk, measured honestly

- The receipt records per-phase durations and, per payload path, the clone method and logical bytes; container services record the clone method and estimated allocation. Output and GUI say "payload 412 MB cloned (reflink) · services: db reflink, cache rdb" — never "zero disk".
- Benchmarks before release: cold and warm `switch -c` on a real repo, source interruption under concurrent writes per engine.
- Dependency reuse checks (lockfile changed since the source?) are reported, not enforced, in the first release.
